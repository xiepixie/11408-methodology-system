## 一、什么是拥塞

在计算机网络中，**链路容量（即带宽）、交换节点中的缓存和处理机**等都是网络的资源。教材把拥塞的条件写成一个不等式：∑对资源的需求>可用资源

在某段时间，若对网络中某一资源的需求超过了该资源所能提供的可用部分，网络的性能就要变坏。这种情况就叫作**拥塞**。

### 为什么加资源解决不了

这是本节最值得追问的一处。教材逐条否掉了三种"直觉解法"：

**扩大缓存？** 设想把某节点的缓存扩到非常大，凡到达的分组都能排队、不受限制。但**输出链路的容量和处理机的处理速度并未提高**，于是队列中绝大多数分组的排队等待时间大大增加，结果**上层软件只好把它们全部重传**（因为早就超时了）。**分组还在队列里排着，副本已经在路上了**——缓存越大，浪费越严重。

**提高处理机速率？** 可能缓解一些，但**往往又会将瓶颈转移到其他地方**。

教材给出的结论是：**问题的实质往往是整个系统的各个部分不匹配。只有所有的部分都平衡了，问题才会得到解决。**

### 拥塞会自我恶化

拥塞常常趋于恶化。如果一个路由器没有足够的缓存空间，它就会丢弃一些新到的分组。但当分组被丢弃时，发送这一分组的源点就会重传这一分组，甚至可能还要重传多次。这样会引起更多的分组流入网络和被网络中的路由器丢弃。可见**拥塞引起的重传并不会缓解网络的拥塞，反而会加剧网络的拥塞**。

**正反馈**这三个字是理解拥塞控制全部设计的钥匙：既然重传会加剧拥塞，那么拥塞控制的所有动作就必须朝"**主动减少注入**"的方向去，而不能只靠重传把数据补回来。

### 吞吐量随负载变化的三个阶段

横坐标是**提供的负载**（单位时间内输入给网络的分组数），纵坐标是**吞吐量**（单位时间内从网络输出的分组数）。

```
 吞吐量
   ▲
   │            理想拥塞控制：饱和后保持水平
   │        ┌──────────────────────────
   │      ╱ │
   │    ╱   │      实际：轻度拥塞（增速变缓）
   │  ╱     └╌╌╌╌╌╌╮
   │╱              ╰╌╌╌╌╌╮  拥塞（吞吐量反而下降）
   │                     ╰╌╌╌╌╌╌╌╌╌╌╮
   │                                ╰╌╌► 死锁（吞吐量降到 0）
   └────────────────────────────────────────► 提供的负载
      45° 斜线段：吞吐量 = 提供的负载
```

| 阶段 | 表现 | 教材原话 |
| --- | --- | --- |
| **未饱和** | 吞吐量 = 提供的负载，是一条 45° 斜线 | "具有理想拥塞控制的网络，在吞吐量饱和之前，网络吞吐量应等于提供的负载" |
| **轻度拥塞** | 吞吐量增长变缓，**已经有一部分输入分组被丢弃** | "当网络的吞吐量明显地小于理想的吞吐量时，网络就进入了轻度拥塞的状态" |
| **拥塞** | **吞吐量随负载增大反而下降** | "当提供的负载达到某一数值时，网络的吞吐量反而随提供的负载的增大而下降" |
| **死锁** | 吞吐量降到零，网络已无法工作 | "当提供的负载继续增大到某一数值时，网络的吞吐量就下降到零……这就是所谓的死锁" |

> [!WARNING]
>

一句被反复考的判断

教材点得非常明确：**"分组的丢失是网络发生拥塞的征兆而不是原因。"**

还有一句更值得警惕的："**在许多情况下，甚至正是拥塞控制机制本身成为引起网络性能恶化甚至发生死锁的原因。**"——拥塞控制过于频繁地采取行动会使系统产生不稳定的振荡，过于迟缓又不具有实用价值。

## 二、拥塞控制与流量控制

| 对比项 | 拥塞控制 | 流量控制 |
| --- | --- | --- |
| 防的是什么 | **过多的数据注入到网络中**，使路由器或链路过载 | 发送方发得太快，**接收方来不及接收** |
| 作用范围 | **全局性过程**，涉及所有主机、所有路由器以及与降低网络传输性能有关的所有因素 | **点对点通信量的控制，是个端到端的问题**（接收端控制发送端） |
| 控制变量 | 拥塞窗口 cwnd（发送方自己维护） | 接收窗口 rwnd（接收方通告） |
| 触发信号 | 丢包信号（超时 / 重复确认） | 接收方通告的窗口值变化 |
| 前提假设 | "网络能够承受现有的网络负荷" | — |

发送方的实际发送窗口取两者较小值：发送窗口=min(cwnd, rwnd)

两者的判据差别与教材那个"水龙头—水桶"的比喻，详见 [[04_计算机网络_CN/transport/tcp-flow-control.md|TCP 流量控制]]，本篇不重复。

> [!NOTE]
>

端系统的信息盲区

教材有一句话值得单独摘出来：**TCP 连接的端点只要迟迟不能收到对方的确认信息，就猜想在当前网络中的某处很可能发生了拥塞，但这时却无法知道拥塞到底发生在网络的何处，也无法知道发生拥塞的具体原因。**

"**猜想**"这两个字定下了 TCP 拥塞控制的全部基调：它是一套**在信息严重不足的条件下工作的启发式算法**，而不是精确控制。这也解释了为什么它的动作都很粗糙（翻倍、减半、置 1）——精细控制需要的信息它根本拿不到。

**网络层视角的拥塞控制**（开环控制与闭环控制、监测指标、AQM 与 RED），属大纲四（一）4，写在 [[04_计算机网络_CN/network/network-layer-functions.md|网络层功能]]，本篇不展开。

## 三、发送方凭什么判断"网络堵了"

发送方看不到路由器的队列，它手里只有一条线索：**确认有没有按时回来**。

教材的推理链是：

- 当网络发生拥塞时，路由器就要**把来不及处理而排不上队的分组丢弃**；
- 因此**只要发送方没有按时收到对方的确认报文，也就是说，只要出现了超时，就可以估计可能在网络某处出现了拥塞**；
- 这条推理成立的前提是：**现在通信线路的传输质量一般都很好，因传输出差错而丢弃分组的概率是很小的（远小于 1%）**。

**所以"超时 = 拥塞"是一个概率推断，不是逻辑必然。** 它的前提条件是"丢包主要由拥塞造成，而不是由链路误码造成"。

> [!WARNING]
>

这个判据在什么情况下失效

前提一旦不成立，判据就失效——最典型的就是**无线链路**：无线信道误码率高，丢包很可能是信号衰落造成的，网络根本不堵。此时 TCP 却照样把 cwnd 减半甚至降到 1，**在没有拥塞的网络上白白降速**。这是传统 TCP 拥塞控制在无线环境下的经典短板。

另一种失效场景教材也提到了：**路由器对某些分组的处理时间特别长**，导致发送方超时重传，"根据前面所讲的，重传会使 TCP 连接的发送端认为在网络中发生了拥塞。于是在 TCP 的发送端就采取了拥塞控制措施，**但实际上网络并没有发生拥塞**"。

## 四、慢开始

发送方维持一个叫作**拥塞窗口 cwnd** 的状态变量。**拥塞窗口的大小取决于网络的拥塞程度，并且是动态变化着的。** 控制原则很朴素：

只要网络没有出现拥塞，拥塞窗口就可以再增大一些，以便把更多的分组发送出去，这样就可以提高网络的利用率。但只要网络出现拥塞或有可能出现拥塞，就必须把拥塞窗口减小一些。

### 算法

**慢开始的思路**：当主机在已建立的 TCP 连接上开始发送数据时，**并不清楚网络当前的负荷情况**。如果立即把大量数据字节注入到网络，就有可能引起网络发生拥塞。较好的方法是**先探测一下，由小到大逐渐增大注入到网络中的数据字节**。

规则是：**在每收到一个对新的报文段的确认后，可以把拥塞窗口增加最多一个 SMSS 的数值**，即cwnd 每次的增加量=min(N, SMSS)

其中 N 是原先未被确认的、但现在被刚收到的确认报文段所确认的字节数。当 N<SMSS 时，拥塞窗口每次的增加量要小于 SMSS。

**由"每收到一个确认就加 1"推出"每 RTT 翻倍"**：设某轮开始时 cwnd = k（可发 k 个报文段），这 k 个都被确认，于是 cwnd 增加 k，下一轮变成 2k。所以按传输轮次看是 1→2→4→8→16→⋯ 的**指数增长**。

教材特意提醒：**发送方并不是要在所有的确认都收齐了之后才调整其拥塞窗口，而是收到一个确认就调整一下拥塞窗口，抓紧时间发送报文段。** 用"每 RTT 翻倍"来描述只是为了看清大致趋势。

### 初始 cwnd 到底是 1 还是 2~4

旧的规定是把初始 cwnd 设为 1 至 2 个 SMSS，**新的 RFC 5681 把初始拥塞窗口设置为不超过 2 至 4 个 SMSS**，具体规定按 SMSS 分档：

| SMSS 大小 | 初始 cwnd |
| --- | --- |
| SMSS > 2190 字节 | 2×SMSS 字节，且不超过 2 个报文段 |
| 1095 < SMSS ≤ 2190 字节 | 3×SMSS 字节，且不超过 3 个报文段 |
| SMSS ≤ 1095 字节 | 4×SMSS 字节，且不超过 4 个报文段 |

**这个规定本质上是在限制初始拥塞窗口的字节数**——SMSS 越小，允许的报文段个数越多，乘出来的字节数大致相当。

做题时如果题目没有特别说明，一律按 **cwnd 初值 = 1 MSS** 处理；上面这张表用于理解"为什么会有不同说法"，不用于套算。

### "慢"慢在哪

> [!TIP]
>

这是本节最常被误解的一处

教材原话：**"慢开始的'慢'并不是指 cwnd 的增长速率慢，而是指在 TCP 开始发送报文段时，只发送一个报文段，即设置 cwnd = 1，目的是试探一下网络的拥塞情况，然后视情况再逐渐增大 cwnd。"**

参照系是"一开始就把窗口开到最大、一下子把许多报文段迅速注入到网络"——**相对于那种做法，从 1 开始当然"慢得多"。** 所以"慢"说的是**起点低**，不是斜率小；慢开始阶段的斜率恰恰是全过程中最陡的。

### 退出条件

为了防止 cwnd 增长过大引起网络拥塞，设置一个**慢开始门限 ssthresh** 状态变量。教材给的三条用法：

- **cwnd < ssthresh** 时，使用慢开始算法；
- **cwnd > ssthresh** 时，停止使用慢开始算法而改用拥塞避免算法；
- **cwnd = ssthresh** 时，**既可使用慢开始算法，也可使用拥塞避免算法**。

第三条是教材明确留下的"两可"。做题的统一口径与相关取整问题，见 [[04_计算机网络_CN/transport/tcp-congestion-detail.md|detail 篇]]。

## 五、拥塞避免

**拥塞避免算法的目的是让拥塞窗口 cwnd 缓慢地增大。** 执行的结果大约是：**每经过一个往返时间 RTT，发送方的拥塞窗口 cwnd 的大小就加 1，而不是像慢开始阶段那样加倍增长。**

因此这个阶段称为"**加法增大**"AI（Additive Increase），拥塞窗口按线性规律缓慢增长。

> [!WARNING]
>

"拥塞避免"并非完全避免拥塞

教材原话：**"'拥塞避免'并非完全避免拥塞，而是让拥塞窗口增长得缓慢些，使网络不容易出现拥塞。"**

名字容易误导：它不是一个"能防住拥塞"的算法，只是把逼近容量上限的速度放慢，让越界这件事发生得晚一点、越界的幅度小一点。

### 为什么是"加法增"配"乘法减"

出现超时或 3 个重复确认时，就把门限值设置为当前拥塞窗口值的一半，并大大减小 cwnd，这称为**乘法减小** MD（Multiplicative Decrease）。二者合起来就是 **AIMD** 算法。

**为什么不能反过来（乘法增、加法减）？** 从两个方向想：

- **越界的代价远大于保守的代价。** 窗口开小了只是慢一点；开大了会丢包，而丢包引发重传、重传加剧拥塞（第一节的正反馈）。所以**逼近上限时必须谨慎（加法），撤离时必须果断（乘法）**。
- **加法增让多条连接趋于公平。** 若网络容量固定、有两条连接在竞争：乘法增会让本来窗口大的那条涨得更快（强者愈强）；而加法增使每条连接每轮都只加 1，**乘法减使窗口大的那条减得更多**——一增一减把两条连接的窗口不断推向相等。**AIMD 的公平性，正是"增用加法、减用乘法"这个不对称组合带来的。**

## 六、快重传

### 问题

有时**个别报文段会在网络中意外丢失，但实际上网络并未发生拥塞**。如果发送方迟迟收不到确认，就会产生超时，并**误认为网络发生了拥塞**。这就导致发送方错误地启动慢开始、把 cwnd 又设置为 1，**因而不必要地降低了传输效率**。

超时定时器（RTO）本身还留着 4 倍偏差的余量（见 [[04_计算机网络_CN/transport/tcp-reliable.md|TCP 可靠传输]]），等它超时要白白浪费很长时间。

### 算法

快重传要求**接收方**做一件事、**发送方**做一件事：

- **接收方**：不要等待自己发送数据时才捎带确认，而是**立即发送确认**；**即使收到了失序的报文段，也要立即发出对已收到的报文段的重复确认**。
- **发送方**：**只要一连收到 3 个重复确认，就可知道现在并未出现网络拥塞，而只是接收方少收到一个报文段，因而立即重传**，不必等待超时。

注意教材对计数的表述：接收方一共发出了 **4 个对 M2 的确认，其中后 3 个都是重复确认**。发送方数的是**重复确认的个数**（3 个），不是"总共收到 4 个相同的 ACK"这件事本身——两种数法结论相同，但表述要说清是"3 个重复"。

**效果**：教材给出的数字是 **使用快重传可以使整个网络的吞吐量提高约 20%。**

### 为什么是 3 个

这是一道典型的"边界为什么取在这里"的题，从两侧夹逼：

| 若取 | 会怎样 |
| --- | --- |
| **1~2 个** | **失序也会产生重复确认**。报文段走不同路由造成的乱序非常常见，只错一两个位置的乱序会立刻被误判成丢包，引发大量不必要的重传 |
| **3 个** | 连续 3 个失序位置的乱序已经很罕见，**误判概率显著下降**；同时只等 3 个确认，比等一个 RTO 快得多 |
| **4 个及以上** | 误判更少，但**要等更久**才能重传；等待的收益递减，而延迟的代价线性增加 |

**判据一句话：3 是"误判率已经足够低"与"等待时间还足够短"两条曲线的交点。** 它没有理论上的最优性，是工程上的经验取值——但知道它在权衡什么，就不需要死记这个数。

## 七、快恢复

### 关键推理

当发送方连续收到三个重复确认时，它知道的比"丢了个报文段"更多：

发送方知道现在只是丢失了个别的报文段。于是不启动慢开始，而是执行快恢复算法。

**凭什么能这么判断？** 因为重复确认本身就是证据：**接收方每收到一个失序报文段才会发一个重复确认**。收到 3 个重复确认，说明**在 M3 丢失之后，至少还有 3 个报文段成功穿过了网络到达接收方**。网络要是真堵死了，这 3 个也过不来。**所以"能收到重复确认"这件事本身，就证明了网络还通。**

### 算法

TCP Reno 的快恢复：

- ssthresh=cwnd/2；
- cwnd=ssthresh；
- **开始执行拥塞避免算法**（线性增长）。

**注意顺序：先更新 ssthresh，再设置 cwnd。** 顺序反了（先把 cwnd 改成一半再拿它算 ssthresh）结果会差一倍。

### 一个变体：为什么有的实现要再加 3 个 MSS

> [!NOTE]
>

教材点名的另一种实现

也有的快恢复实现是把快恢复开始时的拥塞窗口 cwnd 值再增大一些（增大 3 个报文段的长度），即等于新的 ssthresh+3×MSS。这样做的理由是：**既然发送方收到 3 个重复的确认，就表明有 3 个分组已经离开了网络。这 3 个分组不再消耗网络的资源而是停留在接收方的缓存中**（接收方发送出 3 个重复的确认就证明了这个事实）。**可见现在网络中并不是堆积了分组而是减少了 3 个分组**，因此可以适当把拥塞窗口扩大些。

这条推理很值得体会：它把"重复确认"当成了**网络中在途分组数的计量工具**——每收到一个重复确认，就意味着网络里少了一个分组。408 做题按 cwnd=ssthresh 即可，这个变体用于理解快恢复到底在恢复什么。

## 八、四个事件的规则表（本站唯一权威版本）

以下两张表是**本站关于拥塞控制动作的唯一权威口径**，detail 篇不重打、直接引用本节。

**正常传输时：**

| 当前阶段 | 判定条件 | 每经过一个 RTT，cwnd 如何变 |
| --- | --- | --- |
| 慢开始 | cwnd < ssthresh | **翻倍**（指数增长） |
| 拥塞避免 | cwnd ≥ ssthresh | **加 1**（线性增长） |

**发生事件时（TCP Reno）：**

| 事件 | ① ssthresh 更新为 | ② cwnd 更新为 | ③ 随后进入 |
| --- | --- | --- | --- |
| **超时** | cwnd / 2 | **1** | 慢开始 |
| **3 个重复确认** | cwnd / 2 | **ssthresh**（即 cwnd/2） | 拥塞避免（快恢复） |

**执行顺序恒为 ① → ② → ③**：先用事件发生时的 cwnd 算出新 ssthresh，再设置新 cwnd。

## 九、状态转换与 AIMD 锯齿

图里有两条容易被漏掉的边：**慢开始阶段同样可能发生超时或收到 3 个重复确认**。教材对此有专门说明——图 5-25 的那条曲线只是一个特例，"图 5-25 没有说明在慢开始阶段如果出现了超时或出现 3-ACK，发送方应采取什么措施，但从图 5-27 的流程图就可以很明确地知道"。

### 教材图 5-25 的五个关键拐点

教材用一条具体曲线演示了整个过程（初始 ssthresh = 16，cwnd 从 1 开始）。**这里只叙述五个拐点，不列逐轮数值表——完整的逐轮推演表在 [[04_计算机网络_CN/transport/tcp-congestion-detail.md|detail 篇]]。**

| 拐点 | 发生了什么 | 之后 |
| --- | --- | --- |
| **①** | cwnd 由 1 指数增长到 **16**，达到 ssthresh | 改执行拥塞避免，按线性规律增长 |
| **②** | cwnd 线性增长到 **24** 时出现**超时** | 第 1 次调整门限：ssthresh=24/2=12，同时 cwnd=1，执行慢开始 |
| **③** | cwnd 重新指数增长到 **12**（= 新 ssthresh） | 改执行拥塞避免，按线性规律增大 |
| **④** | cwnd 线性增长到 **16** 时，发送方一连收到 **3 个重复确认** | 判定只是丢了个别报文段，不启动慢开始 |
| **⑤** | 第 2 次调整门限：ssthresh=16/2=8，同时 cwnd=ssthresh=8 | 开始执行拥塞避免算法 |

**这条曲线的形状就是 AIMD 的招牌"锯齿"**：缓慢的线性爬升（AI）+ 陡直的腰斩（MD），反复不停。锯齿的物理含义是——**TCP 在持续试探网络容量的上界**：不撞到上界就永远不知道它在哪里，撞到了就退回来一半再慢慢爬。**"拥塞控制必然伴随周期性丢包"不是缺陷，而是这套探测机制的固有代价。**

## 十、TCP Tahoe 与 TCP Reno

| 对比项 | TCP Tahoe | TCP Reno |
| --- | --- | --- |
| 包含的算法 | 慢开始 + 拥塞避免 | 慢开始 + 拥塞避免 + **快重传 + 快恢复** |
| 超时的处理 | ssthresh = cwnd/2，cwnd = 1，慢开始 | **同 Tahoe** |
| **3 个重复确认的处理** | **同超时处理**（cwnd = 1，回慢开始） | ssthresh = cwnd/2，**cwnd = ssthresh**，拥塞避免 |
| 丢包后的恢复速度 | 每次丢包都回到 cwnd=1，恢复慢 | 区分两种信号，轻度拥塞恢复快 |
| 默认口径 | 少数题目会指明用 Tahoe | **默认按 Reno** |

**唯一的区别就在"3 个重复确认怎么处理"这一格。** Tahoe 把它当超时一样对待，Reno 认为网络还没堵死、只需减半。教材在图 5-25 上标注了"TCP Reno 版本"，正是为了与老的 Tahoe 版本区别。

## 十一、与流量控制合起来看

教材在讲完拥塞控制后，把两件事合并：

发送方的窗口的上限值应当取为接收方窗口 rwnd 和拥塞窗口 cwnd 这两个变量中较小的一个：发送方窗口的上限值=min[rwnd, cwnd]

当 rwnd < cwnd 时，是**接收方的接收能力**限制发送方窗口的最大值。 反之，当 cwnd < rwnd 时，则是**网络的拥塞程度**限制发送方窗口的最大值。

判断瓶颈的例题在 [[04_计算机网络_CN/transport/tcp-flow-control.md|TCP 流量控制]]，含 rwnd 限制的逐轮推演在 [[04_计算机网络_CN/transport/tcp-congestion-detail.md|detail 篇]]。

## 易混淆知识点

**1. 慢开始的"慢"是起点低，不是增长慢**

判据是**参照系**：相对于"一上来就把窗口开到最大"，从 cwnd=1 起步当然慢得多。慢开始阶段的斜率恰恰是全过程最陡的（指数增长）。

**2. "拥塞避免"并不能避免拥塞**

它只是让 cwnd 增长得缓慢些，使网络不容易出现拥塞。名字有误导性。

**3. 分组丢失是拥塞的征兆而不是原因**

教材明确表述。而且拥塞会自我恶化：丢包 → 重传 → 更多分组注入 → 更多丢弃，**重传不但不缓解拥塞，反而加剧拥塞**。

**4. 加缓存 / 提速率解决不了拥塞**

判据是**瓶颈会转移**：缓存扩大后排队时延暴涨，上层照样超时重传，缓存里的分组和它的副本同时占着资源；提高处理机速率则把瓶颈推到别处。实质是**系统各部分不匹配**，必须整体平衡。

**5. "超时 = 拥塞"是概率推断，有前提**

前提是**因传输差错而丢弃分组的概率远小于 1%**。在无线链路上这个前提不成立（误码丢包占主导），TCP 会在网络并不拥塞时白白降速。

**6. cwnd = ssthresh 时用哪个算法**

教材明确写"**既可使用慢开始算法，也可使用拥塞避免算法**"，这是标准留下的两可。做题统一口径见 [[04_计算机网络_CN/transport/tcp-congestion-detail.md|detail 篇]]，且**要先看题面有没有特别说明**。

**7. 快恢复的执行顺序：先算 ssthresh，再设 cwnd**

判据是"用哪个 cwnd 算"：ssthresh 用的是**事件发生时的**（旧的）cwnd。顺序反了结果差一倍。

**8. 为什么快恢复不把 cwnd 降到 1**

判据是**重复确认本身就是"网络还通"的证据**：接收方每收到一个失序报文段才发一个重复确认，收到 3 个说明丢包之后至少还有 3 个报文段成功穿过了网络。网络堵死时这 3 个也过不来。

**9. 为什么是 3 个重复确认**

两侧夹逼：1~2 个会把常见的**乱序**误判成丢包；4 个以上误判虽更少但等待时间线性增加、收益递减。3 是两条曲线的交点，是工程经验值而非理论最优。

**10. 发送窗口不等于 cwnd**

min(cwnd,rwnd)。题目只提拥塞控制时默认 rwnd 足够大，发送窗口 = cwnd；同时给出 rwnd 时必须取小。

**11. Tahoe 与 Reno 只差一格**

只差"3 个重复确认怎么处理"：Tahoe 当超时处理（cwnd=1，回慢开始），Reno 走快恢复（cwnd=ssthresh，进拥塞避免）。**超时的处理两者完全相同。**

**12. 拥塞控制本身也可能成为问题的来源**

教材点名：过于频繁地采取行动会使系统产生**不稳定的振荡**，过于迟缓又不具实用价值。选择正确的时间常数相当困难。

## 本节小结

- **拥塞的定义式是 ∑对资源的需求>可用资源**，资源指链路容量（带宽）、交换节点的缓存与处理机。**加资源解决不了拥塞**：缓存扩大会让排队时延暴涨、上层照样超时重传（分组还在排队、副本已在路上），提高处理机速率只把瓶颈转移到别处。**实质是系统各部分不匹配，只有所有部分都平衡了问题才解决。**
- **拥塞会自我恶化**：丢包 → 源点重传（可能多次）→ 更多分组流入并被丢弃。**拥塞引起的重传不会缓解拥塞，反而加剧拥塞**——这条正反馈决定了拥塞控制必须朝"主动减少注入"去，光靠重传补数据只会更糟。
- **吞吐量-负载曲线四阶段**：未饱和（45° 斜线，吞吐量 = 提供的负载）→ 轻度拥塞（增速变缓，已有分组被丢弃）→ 拥塞（**吞吐量随负载增大反而下降**）→ 死锁（吞吐量降到零）。**分组丢失是拥塞的征兆而不是原因**；且**拥塞控制机制本身也可能成为性能恶化甚至死锁的原因**（动作过频会振荡，过缓则无用）。
- **拥塞控制是全局性过程**（涉及所有主机、所有路由器及一切与降低网络传输性能有关的因素），**流量控制是点对点的端到端问题**（接收端控制发送端）。发送方窗口取 min(cwnd,rwnd)：rwnd 小则瓶颈在接收方，cwnd 小则瓶颈在网络。
- **端系统的判据只有一条：确认有没有按时回来。** 超时即"猜想"网络某处拥塞——但**无法知道拥塞发生在何处、原因是什么**。这条推断的前提是"因传输差错而丢弃分组的概率远小于 1%"，**无线链路上前提不成立，会导致无谓降速**。
- **慢开始**：cwnd 是发送方维护的状态变量，取决于网络拥塞程度且动态变化。规则是**每收到一个对新报文段的确认，cwnd 增加 min(N,SMSS)**，由此推出按轮次看是翻倍。**"慢"指起点低（cwnd 从 1 开始试探），不指增长速率慢**——这一段的斜率恰恰最陡。初值按 RFC 5681 分档为 2~4 个 SMSS，**做题无特别说明时按 1 MSS**。
- **门限 ssthresh 的三条用法**：cwnd < ssthresh 用慢开始；cwnd > ssthresh 用拥塞避免；**cwnd = ssthresh 时两者皆可**（标准留下的两可）。
- **拥塞避免 = 加法增大 AI**：每经过一个 RTT，cwnd 加 1，线性缓慢增长。**"拥塞避免"并非完全避免拥塞**，只是让越界发生得晚一点、幅度小一点。
- **AIMD 的不对称是刻意的**：越界的代价（丢包 → 重传 → 加剧拥塞）远大于保守的代价，所以**逼近上限用加法、撤离用乘法**；而且**加法增 + 乘法减会把竞争同一容量的多条连接推向窗口相等**，公平性正来自这个不对称组合。
- **快重传**：接收方**收到失序报文段也要立即发出重复确认**（不等捎带）；发送方**一连收到 3 个重复确认就立即重传，不等超时**。可使整个网络的吞吐量**提高约 20%**。**为什么是 3**——1~2 个会把常见乱序误判成丢包，4 个以上等待时间线性增加而收益递减，3 是两条曲线的交点。
- **快恢复**：3 个重复确认说明**只是丢了个别报文段**——因为每个重复确认对应一个成功到达的失序报文段，收到 3 个就证明网络还通。于是**不启动慢开始**：① ssthresh=cwnd/2；② cwnd=ssthresh；③ 进入拥塞避免。**顺序恒为先算 ssthresh 再设 cwnd。** 另有实现取 cwnd=ssthresh+3×MSS，理由是 3 个分组已经离开网络、停在接收方缓存里，网络中的分组数反而减少了 3 个。
- **AIMD 锯齿的含义**：TCP 在**持续试探网络容量的上界**——不撞上就不知道它在哪，撞上了就腰斩再慢慢爬。**周期性丢包是这套探测机制的固有代价，不是缺陷。**
- **Tahoe 与 Reno 只差一格**：3 个重复确认时，Tahoe 当超时处理（cwnd=1、回慢开始），Reno 走快恢复（cwnd=ssthresh、进拥塞避免）；**超时的处理两者完全相同**。默认按 Reno。

- 同书 **p241**（5.8.2 TCP 的拥塞控制方法）：cwnd 的定义与控制原则——"发送方维持一个叫作拥塞窗口 cwnd 的状态变量。**拥塞窗口的大小取决于网络的拥塞程度，并且是动态变化着的**"；判据与其前提——"**只要发送方没有按时收到对方的确认报文，也就是说，只要出现了超时，就可以估计可能在网络某处出现了拥塞**。现在通信线路的传输质量一般都很好，**因传输出差错而丢弃分组的概率是很小的（远小于 1%）**"；慢开始的思路"当主机在已建立的 TCP 连接上开始发送数据时，并不清楚网络当前的负荷情况……较好的方法是先探测一下，即由小到大逐渐增大注入到网络中的数据字节"；以及初始 cwnd 按 SMSS 分档的三条规定（RFC 5681）。
- 同书 **p242**：式 (5-8) "**拥塞窗口 cwnd 每次的增加量 = min(N, SMSS)**"及其中 N 的含义；"发送方并不是要在所有的确认都收齐了之后才调整其拥塞窗口，而是收到一个确认就调整一下拥塞窗口"；**"慢开始的'慢'并不是指 cwnd 的增长速率慢，而是指在 TCP 开始发送报文段时，只发送一个报文段，即设置 cwnd=1，目的是试探一下网络的拥塞情况"**。
- 同书 **p243**：ssthresh 的三条用法（cwnd < ssthresh 用慢开始、cwnd > ssthresh 用拥塞避免、**cwnd = ssthresh 时既可使用慢开始算法，也可使用拥塞避免算法**）；拥塞避免"**每经过一个往返时间 RTT，发送方的拥塞窗口 cwnd 的大小就加 1**……因此在拥塞避免阶段就称为'加法增大'AI"；**"'拥塞避免'并非完全避免拥塞，而是让拥塞窗口增长得缓慢些，使网络不容易出现拥塞"**；以及图 5-25 五个拐点的完整叙述（ssthresh 初值 16、cwnd=24 时超时、第 1 次调整 ssthresh=12、cwnd=16 时收到 3-ACK、第 2 次调整 ssthresh=8 且 cwnd=8）。
- 同书 **p244**：快重传算法的完整描述——"**接收方必须立即发送对 M2 的重复确认，以便让发送方及早知道接收方没有收到报文段 M3**……快重传算法规定，**发送方只要一连收到 3 个重复确认，就可知道现在并未出现网络拥塞，而只是接收方少收到一个报文段，因而立即进行重传 M3（即'快重传'）**。**使用快重传可以使整个网络的吞吐量提高约 20%**"；快恢复的三步与 AIMD 的定义"一旦出现超时或 3 个重复的确认，就要把门限值设置为当前拥塞窗口值的一半，并大大减小拥塞窗口的数值。这常称为'乘法减小'MD……二者合在一起就是所谓的 AIMD 算法"；以及 ssthresh+3×MSS 那个变体的完整理由——"**既然发送方收到 3 个重复的确认，就表明有 3 个分组已经离开了网络。这 3 个分组不再消耗网络的资源而是停留在接收方的缓存中……可见现在网络中并不是堆积了分组而是减少了 3 个分组**"。此页还说明图 5-25 只是特例，慢开始阶段出现超时或 3-ACK 的处理要看图 5-27 的流程图。
- 同书 **p245**：式 (5-9) 与判读——"**发送方窗口的上限值 = Min[rwnd, cwnd]**……当 rwnd < cwnd 时，是接收方的接收能力限制发送方窗口的最大值。反之，当 cwnd < rwnd 时，则是网络的拥塞程度限制发送方窗口的最大值"。
