## 知识框架

本节回答 7 个问题：

- 同样是"把分组送出去"，为什么要把**路由**和**转发**当成两件事？它们分别慢在哪、快在哪？
- IP 凭什么能把以太网、WiFi、PPP 这些完全不同的链路缝成一张网？它到底统一了什么、又没有统一什么？
- 互联网为什么把网络层做得这么"不负责任"（不保证不丢不乱不重）？这个决定还牵出了哪些别处的结论？数据报和虚电路差在哪一步，为什么"虚电路一定预留带宽"是错的？
- 一个目的地址同时匹配四条路由表项，路由器凭什么挑其中一条？**最长**指的是什么长？
- **拥塞是什么？为什么把路由器缓存加大反而解决不了拥塞、甚至会更糟？**
- 网络层的拥塞控制和传输层 TCP 的拥塞控制，是同一件事的两个说法，还是两件事？
- 路由器队列满了才丢包，听起来天经地义。**为什么这个"天经地义"的做法会让全网的 TCP 连接在同一时刻一起减速？主动提前丢包为什么反而更好？**

## 一、路由与转发：控制面与数据面

网络层要做的事只有一件——**把分组从源送到宿**。但这件事被拆成两个时间尺度完全不同的子问题。

|  | **路由（routing）** | **转发（forwarding）** |
| --- | --- | --- |
| 谁在做 | 路由协议（RIP / OSPF / BGP）在**多台**路由器之间协同 | **单台**路由器的转发引擎 |
| 做什么 | 综合拓扑与链路开销，**算出**去哪条路，写进路由表 | 对**已经到达**的分组，**查**表选下一跳、TTL 减 1、重新封装转出 |
| 涉及范围 | 全网（或全自治系统） | 只涉及这一台路由器 |
| 时间尺度 | 秒到数十秒（收敛时间） | 微秒（线速，Mpps 量级） |
| 实现方式 | 软件 | 可用专用硬件 |

**为什么必须拆开？** 因为两者的优化目标互相打架：路由表要**便于按拓扑变化重算**，所以用适合更新的软件数据结构；转发表要**便于按目的地址极快查找**，所以要拍进硬件。把这两个目标塞进同一张表，必然有一头被拖慢。谢希仁的说法是：转发表要包含"完成转发功能所必需的信息"（出端口、下一跳的 MAC 等），而路由表"一般仅包含从目的网络到下一跳的映射"。

**边界**：讨论路由选择**原理**时，两者常被笼统地都叫路由表——这不是错，是省略。但一旦题面把"路由表"和"转发表"并列写出来，就必须按上表严格区分。

## 二、异构网络互连：IP 到底统一了什么

不同链路层技术的帧格式不同、寻址方式不同、MTU 也不同（以太网 1500 B、PPP 可协商、无线又是另一套）。要把它们缝成一张网，有两条路：

- **翻译式**：在每两种网络的交界处做协议转换。n 种网络就要 n(n−1)/2 种转换器，规模一大就崩。
- **统一网络层式**：所有网络之上加一层**共同的、与底层无关的**协议。这就是 IP 的做法。

IP 统一了三件事：**统一的地址格式**（32 位 IP 地址）、**统一的分组格式**（IP 数据报首部）、**统一的尽力而为语义**（无连接、不保证不丢不乱不重）。

IP **没有**统一的是：链路怎么把这个分组真正搬过去。所以还需要三个配套机制：

| 差异 | 谁来抹平 |
| --- | --- |
| 各链路 MTU 不同 | **IP 分片**，见[[04_计算机网络_CN/network/ip-fragment.md|IP 分片]] |
| IP 地址 ≠ 链路层地址 | **ARP**，见[[04_计算机网络_CN/network/arp.md|ARP 地址解析协议]] |
| 链路类型不同、帧格式不同 | **路由器**在出接口重新封装 |

这就是**沙漏模型**：下面链路技术百花齐放，上面应用协议百花齐放，中间腰部**只有 IP 一根**。腰细，才换来两头都能自由演化。

**推一层**：为什么统一在**网络层**而不是链路层？因为链路层的帧只在一段物理链路内有意义，跨链路必须重新封装；而 IP 地址是**端到端不变**的，只有它能充当"全程通用的门牌号"。这也解释了为什么分组每过一跳都要换帧头、但 IP 首部里的源/目的地址始终不变。

关于 SDN 对"路由/转发"这条主线的改造——控制面被从每台设备里抽出来集中到控制器——见 [[04_计算机网络_CN/network/sdn.md|SDN 软件定义网络]]，本篇不重复展开。

## 三、数据报与虚电路：两种网络层服务模型

### 3.1 争论的实质：可靠交付该由谁负责

这两种服务模型的分歧，源头是一场长期争论——**在计算机通信中，可靠交付应当由谁来负责？是网络，还是端系统？**

**主张"由网络负责"的一方**借鉴电信网：传统电信网用面向连接的通信方式，让网络向用户提供可靠传输。放到分组交换里，就是先建立一条**虚电路 VC（Virtual Circuit）**再传数据。

图源：谢希仁《计算机网络》（第 7 版）图 4-1(a)，印刷版 p115

**互联网选了相反的思路**，理由在两种端系统的能力差别上：

|  | 电信网 | 计算机网络 |
| --- | --- | --- |
| 端系统是什么 | 电话机——**简单，没有智能，更没有差错处理能力** | 计算机——**有很强的差错处理能力** |
| 于是可靠性放在哪 | 只能由网络负责 | **可以交给端系统** |
| 网络中间节点 | 昂贵、复杂的程控交换机 | **比较简单、价格低廉**的路由器 |

所以互联网的设计思路是：**网络层要设计得尽量简单，向其上层只提供简单灵活的、无连接的、尽最大努力交付的数据报服务。**

图源：谢希仁《计算机网络》（第 7 版）图 4-1(b)，印刷版 p115

**这个选择的完整后果链**：

- 发送分组**不需要先建立连接**；
- 每一个分组**独立发送，与其前后的分组无关（不进行编号）**；
- 网络层**不提供服务质量的承诺**——所传送的分组**可能出错、丢失、重复和失序**，也不保证交付的时限；
- 于是路由器可以做得**比较简单、价格低廉**；
- 主机进程之间若需要可靠通信，**由主机中的运输层负责**（差错处理、流量控制等）。

**这条链解释了 408 里一连串看似孤立的结论**：为什么 TCP 需要序号（因为会失序、会重复）、为什么 TCP 需要确认与重传（因为会丢失）、为什么校验和只覆盖 IP 首部（因为 IP 本来就不打算保证数据正确）、为什么路由器丢包不是 bug。**它们全都是"可靠性下放给端系统"这一个决定的推论。**

**收益**：网络造价大大降低、运行方式灵活、能够适应多种应用——这正是互联网能发展到今日规模的原因之一。

### 3.2 两种模型的全面对照

区别的**根**只有一个：**转发决策是每个分组各做一次，还是在连接建立时一次做完。**

| 维度 | **数据报**（Datagram） | **虚电路**（Virtual Circuit, VC） |
| --- | --- | --- |
| 是否建立连接 | 不需要，随到随发 | **需要**：建立 → 数据传输 → 释放 三阶段 |
| 分组头带什么 | **完整的目的 IP 地址** | 只带一个**虚电路号 VCID**（短得多） |
| 路由决策时机 | **每个分组各查一次表** | **建立连接时定死**，之后照走 |
| 路径 | 同一对主机的分组可走不同路 | 同一条 VC 的分组**必走同一条路** |
| 中间节点是否有状态 | **无**（每包独立） | **有**，每条 VC 一行状态 |
| 是否会失序 | **可能失序** | 不会（同路径先进先出） |
| 节点故障影响 | 只丢经过该节点的少量分组，其余分组自动绕行 | **整条 VC 失效**，必须重建 |
| 差错与流量控制 | 交给端系统（传输层） | 可以由网络负责 |
| 代表 | **IP 网络** | X.25、帧中继、ATM |

**VCID 是局部标识，不是全局标识。** 路由器按「入接口 + 入 VCID」查表，输出时换成「出接口 + 出 VCID」。所以同一条虚电路在不同链路段上的 VCID 可以完全不同。这和 IP 地址端到端不变形成鲜明对照——**这也正是虚电路头部能比 IP 头部短得多的原因**：局部标识只要在一条链路上唯一即可，用十几位就够；全局地址必须全网唯一，就得 32 位。

**必须掰清的一个说法**："虚电路要为每条连接预分配带宽"——**这是电路交换的性质，不是虚电路的性质**。虚电路仍然是分组交换，链路带宽仍然是**统计复用**的；它只是把"路径"固定下来了，没有把"带宽"切出来。把两者混为一谈，就会得出"虚电路不会拥塞"这种错误推论。

**边界**：数据报"可能失序"不等于"经常失序"。实际 IP 网络中路由稳定时，同一 TCP 流的分组绝大多数按序到达。理论上允许失序，所以传输层必须准备好处理失序——这是 TCP 需要序号和重排缓存的根本原因。

## 四、路由表与分组转发

### 路由表的核心字段

| 字段 | 含义 |
| --- | --- |
| 目的网络 + 掩码 | 用 CIDR 记法写成 `192.168.1.0/24` |
| 下一跳 | 交给哪台路由器继续转发 |
| 出接口 | 从本机哪个接口送出去 |
| 度量值 metric | 路由协议算出来的开销 |

### 最长前缀匹配：为什么"最长"是掩码位数

一个目的 IP 常常同时匹配多条记录。规则是：**取掩码位数最多的那一条**。

道理不在"更精确"这句空话，而在**包含关系**：`/27` 描述的地址块是 `/24` 地址块的**子集**。既然某台管理员特意为这个子集写了一条更细的路由，说明他知道这个子集要走别的路。粗路由是兜底，细路由是特例，**特例优先于兜底**。默认路由 `0.0.0.0/0` 是掩码最短的那条，所以永远排在最后——它是"最大的兜底"。

#### 例题 1：三条路由同时命中，走哪条？

某路由器的路由表（自造数据）：

| 序号 | 目的网络 | 掩码 | 下一跳 |
| --- | --- | --- | --- |
| ① | `0.0.0.0/0` | `0.0.0.0` | R0 |
| ② | `202.114.0.0/16` | `255.255.0.0` | R1 |
| ③ | `202.114.32.0/20` | `255.255.240.0` | R2 |
| ④ | `202.114.40.0/21` | `255.255.248.0` | R3 |
| ⑤ | `202.114.44.0/24` | `255.255.255.0` | R4 |

分别求下面三个目的地址的下一跳：`202.114.44.130`、`202.114.46.7`、`202.114.20.9`。

**解**

统一做法：**把目的 IP 和每条记录的掩码做按位与，看结果是否等于该记录的目的网络**。前两个字节 `202.114` 在①②③④⑤中都一样，所以只需要盯**第三个字节**。

先把第三字节写成二进制，掩码的第三字节也写成二进制：

| 掩码 | 第三字节掩码 | 二进制 | 管住第三字节的前几位 |
| --- | --- | --- | --- |
| `/16` | `0` | `00000000` | 0 位（第三字节完全不管） |
| `/20` | `240` | `11110000` | 前 4 位 |
| `/21` | `248` | `11111000` | 前 5 位 |
| `/24` | `255` | `11111111` | 全 8 位 |

**（1）`202.114.44.130`，第三字节 44=001011002**

| 记录 | 与掩码相与后的第三字节 | 记录要求的值 | 命中？ |
| --- | --- | --- | --- |
| ② `/16` | 不比较 | — | ✅ |
| ③ `/20` | 00101100∧11110000=00100000=32 | 32 | ✅ |
| ④ `/21` | 00101100∧11111000=00101000=40 | 40 | ✅ |
| ⑤ `/24` | 44 | 44 | ✅ |

四条全中（加上默认路由是五条），取掩码最长的 ⑤ `/24` → **下一跳 R4**。

*这一步为什么这么做*：命中与否只看"相与后等不等于目的网络"，命中之后才比掩码长度。两步不能颠倒——先按长度排序再匹配，会把根本没命中的长掩码错当成答案。

**（2）`202.114.46.7`，第三字节 46=001011102**

- ⑤ `/24`：第三字节要求恰好等于 44，而它是 46 → ❌ **不命中**
- ④ `/21`：00101110∧11111000=00101000=40 ✅
- ③ `/20`：00101110∧11110000=00100000=32 ✅

最长命中是 ④ → **下一跳 R3**。

*这一步为什么这么做*：44 和 46 只差 2，但 `/24` 要求第三字节 8 位全等，一位不同就出局。这就是"细路由是特例"的具体含义——**特例的适用范围极窄**。

**（3）`202.114.20.9`，第三字节 20=000101002**

- ⑤ `/24`：20≠44 ❌
- ④ `/21`：00010100∧11111000=00010000=16≠40 ❌
- ③ `/20`：00010100∧11110000=00010000=16≠32 ❌
- ② `/16`：✅

只剩 ② → **下一跳 R1**。

**（4）附带一问**：如果目的是 `203.1.1.1`，连 ② 都不命中，就落到 ① 默认路由 → **下一跳 R0**。

**一句话收口**：最长前缀匹配 = 先做"与"筛出所有命中项，再在命中项里挑掩码位数最大的。默认路由只是"掩码位数 = 0"的普通一员，不是特殊分支。

### 路由聚合：什么时候能合、什么时候不能

把多条**下一跳与出接口相同**的细路由合并成一条粗路由，可以缩短路由表、加快查表。但合并有硬条件。

#### 例题 2：四条 `/24` 能不能合成一条？

**情形 A**：下面四条路由的下一跳都是 R2。

`192.168.8.0/24`、`192.168.9.0/24`、`192.168.10.0/24`、`192.168.11.0/24`

**解**

前两字节相同，只看第三字节的二进制：

| 网络 | 第三字节 | 二进制 |
| --- | --- | --- |
| `192.168.8.0/24` | 8 | `00001000` |
| `192.168.9.0/24` | 9 | `00001001` |
| `192.168.10.0/24` | 10 | `00001010` |
| `192.168.11.0/24` | 11 | `00001011` |

四行的**前 6 位全同**（`000010`），第 7、8 位取遍了 `00 / 01 / 10 / 11` 四种组合。

于是共同前缀长度 =16+6=22 位，聚合结果 **`192.168.8.0/22`**。

*这一步为什么这么做*：能不能聚合，等价于问"这几个地址块拼起来是不是恰好构成一个完整的、边界对齐的更大块"。前缀全同保证"是一块"，低位取遍所有组合保证"填满、不留洞"。两个条件缺一不可。

校验：`/22` 覆盖 `192.168.8.0` ~ `192.168.11.255`，正好是这四个 `/24` 的并集，**不多不少**。✅

**情形 B**：把第四条换成 `192.168.12.0/24`（下一跳仍是 R2），还能合吗？

| 网络 | 第三字节 | 二进制 | 前 5 位 | 第 6 位 |
| --- | --- | --- | --- | --- |
| `192.168.8.0/24` | 8 | `00001000` | `00001` | `0` |
| `192.168.9.0/24` | 9 | `00001001` | `00001` | `0` |
| `192.168.10.0/24` | 10 | `00001010` | `00001` | `0` |
| `192.168.12.0/24` | 12 | `00001100` | `00001` | **`1`** |

只有前 5 位全同（`00001`），第 6 位上 8/9/10 是 `0`、12 是 `1`。共同前缀只有 16+5=21 位。

若强行写成 `192.168.8.0/21`，它覆盖第三字节 8~15，比实际持有的多出 **`192.168.11.0/24`、`192.168.13.0/24`、`192.168.14.0/24`、`192.168.15.0/24`** 四块。

正确做法是拆成三条：**`192.168.8.0/23`**（含 8、9）+ **`192.168.10.0/24`** + **`192.168.12.0/24`**。

**边界（很多人会漏）**：聚合后**多覆盖一些地址块，本身不一定是错的**——如果这些多出来的块在本路由器上没有任何其他路由声明，那么用 `/21` 把它们一起吸收进来，只会让本来该走默认路由的分组走到 R2，最终被丢弃，**结果和不聚合时一样是不可达**。真正的问题出在：一旦 `192.168.13.0/24` 在别处另有一条下一跳不同的路由，`/21` 就会与它争夺流量——而 `/24` 比 `/21` 长，最长前缀匹配会让 `192.168.13.x` 仍然走对，**但你已经把路由表变成了一个靠优先级救场的脆弱结构**。工程与考试的口径都取严格版：**只有恰好填满一个对齐块时才聚合**。

### 默认路由

`0.0.0.0/0`，掩码 `0.0.0.0`。任何 IP 与 `0.0.0.0` 相与都等于 `0.0.0.0`，所以它**永远命中**；但它掩码位数为 0，所以**永远排在最后**。这两句话合起来就是"兜底"的准确含义。

## 五、拥塞控制（网络层视角）

这一节对应大纲 **四（一）4**。TCP 的四个具体算法在[[04_计算机网络_CN/transport/tcp-congestion.md|TCP 拥塞控制]]与[[04_计算机网络_CN/transport/tcp-congestion-detail.md|TCP 拥塞控制详解]]，本节只讲**拥塞这件事本身**：它是什么、为什么难、有哪几类办法。

### 5.1 拥塞的定义与判据

链路带宽、路由器缓存、处理机时间片，都是**网络资源**。谢希仁给出的定义式是：∑对资源的需求>可用资源

这个不等式一旦成立，网络性能就开始变坏——**这就是拥塞（congestion）**。

三个必须抓住的点：

- **拥塞是全局现象，不是某台设备的故障。** 它是"大家一起要得太多"，不是"谁坏了"。
- **拥塞的判据是性能，不是某个计数器。** 教材给的可观测指标有：因缓存不足而**被丢弃的分组百分数**、**平均队列长度**、**超时重传的分组数**、**平均分组时延**、**分组时延的标准差**。这些指标上升，都标志着拥塞可能性增加。
- **分组丢失是拥塞的征兆，不是原因。** 这句话是整节的枢纽——很多错误设计都源于把征兆当原因。

### 5.2 为什么加大缓存反而不解决拥塞

这是本节最值得追问的一层。直觉是："分组因为缓存放不下才被丢，那把缓存加到足够大不就行了？"

**推一遍就知道不行：**

设某路由器输出链路速率 C，到达速率 λ>C。

- 缓存**小**：队列很快满，超出的分组被丢弃。发送端因丢包而超时重传。
- 缓存**无限大**：分组不再被丢，全都排进队列。但输出链路速率还是 C，没变。队列长度以 (λ−C) 的速率**无限增长**，排队时延随之无限增长。
- 于是排在后面的分组，**在轮到它被发送之前，发送端的重传定时器早就超时了**。发送端判定"丢了"，重传一份。
- 这份重传的副本也进入同一条队列，进一步推高 λ。**原件最终还是被送出去了，但接收端已经从重传副本那里收到过，原件成了纯粹的浪费。**

结论：**加大缓存把"丢包"换成了"无限期延迟 + 重复传送"，网络资源浪费得更彻底。** 谢希仁的原话是"简单地扩大缓存的存储空间同样会造成网络资源的严重浪费，因而解决不了网络拥塞的问题"。

同样的推理可以套在别的资源上：

| 单点加资源 | 结果 |
| --- | --- |
| 加大缓存 | 排队时延无限增长 → 超时重传泛滥，浪费更彻底 |
| 提高处理机速率 | **瓶颈转移**到链路或缓存，总体没变好 |
| 换更高速的链路 | 瓶颈转移到处理机或对端 |

**本质**：拥塞是**系统各部分不匹配**的问题。只提升单一部件，瓶颈只会搬家。**只有所有部分都平衡了，问题才会得到解决**——这是教材的原话，也是这一节最该记住的一句。

### 5.3 拥塞会自我加剧

拥塞不是稳态，是**正反馈**：

**重传并不缓解拥塞，反而加剧拥塞。** 这条环路一旦转起来，如果没有任何机制去掐断它，网络就会一路滑向死锁。

### 5.4 吞吐量-负载曲线：四条线

图源：谢希仁《计算机网络》（第 7 版）图 5-23，印刷版 p240

两根坐标轴先定义清楚：

- **横轴 提供的负载（offered load）**：单位时间内**输入**给网络的分组数目，也叫输入负载、网络负载。
- **纵轴 吞吐量（throughput）**：单位时间内从网络**输出**的分组数目。

四条线逐条读：

| 曲线 | 形状 | 含义 |
| --- | --- | --- |
| **理想的拥塞控制** | 先是 45° 直线，到饱和后转为**水平** | 饱和前"输入多少就输出多少"（45° 即吞吐量 = 提供的负载，一个不丢）；饱和后受资源上限约束，吞吐量**保持在最大值不下降** |
| **实际的拥塞控制** | 增速逐渐放缓，最后趋于一个低于理想值的水平 | 吞吐量还没到饱和，就已经有一部分输入分组被丢弃了 |
| **无拥塞控制** | 先升，到峰值后**掉头向下** | 负载继续加大，吞吐量反而下降 |
| **死锁（deadlock）** | 曲线落到**零** | 负载大到某个值，吞吐量降为 0，网络完全无法工作 |

图上还标了两个区间：

- **轻度拥塞**：吞吐量已明显低于理想值，但还在随负载**增长**。
- **拥塞**：吞吐量随负载增大反而**下降**。这才是严格意义的拥塞区。

**读图的关键一问**：为什么"理想拥塞控制"饱和之后是**水平**而不是下降？因为理想控制会在入口处就把超额的负载挡住，网络内部始终工作在满载而不过载的状态。**水平线的高度 = 网络资源允许的最大吞吐量**——拥塞控制的全部目标，就是让实际曲线尽量贴近这条水平线，并且**绝不允许掉头向下**。

### 5.5 拥塞控制 vs 流量控制：本质区别

这两个概念常被弄混，因为**某些拥塞控制算法也是向发送端发控制报文、让它放慢**，动作看起来一样。但它们回答的是完全不同的问题。

|  | **拥塞控制** | **流量控制** |
| --- | --- | --- |
| 要解决什么 | 防止过多数据注入网络，使**路由器和链路**不至于过载 | 抑制发送端速率，使**接收端**来得及接收 |
| 涉及几方 | **全局**：所有主机、所有路由器、所有影响传输性能的因素 | **两方**：点对点，端到端（接收端控制发送端） |
| 谁"喊停" | 网络（间接地，通过丢包 / 显式标记） | 接收端（明确地，通过窗口通告） |
| 信息完整度 | 端点**只知道"某处堵了"，不知道堵在哪、为什么堵** | 接收端明确告诉发送端"我还能收多少" |
| 前提假设 | 网络能够承受现有的网络负荷 | 接收端缓存有限 |

**教材给的两个反例，比任何定义都管用：**

**反例一（只需要流量控制，不存在拥塞）**：某光纤网络链路速率 1000 Gbit/s，一台巨型计算机以 1 Gbit/s 向一台个人电脑传文件。网络带宽绰绰有余，**不可能拥塞**；但巨型机必须经常停下来等个人电脑处理，**流量控制是必需的**。

**反例二（只有拥塞，与接收端能力无关）**：另一网络链路速率 1 Mbit/s，接了 1000 台大型计算机，其中 500 台各以 100 kbit/s 向另外 500 台发文件。总需求 500×100 kbit/s=50 Mbit/s，是链路容量的 50 倍。这时问题**根本不是接收端来不及收**，而是整个网络的输入负载超过了网络所能承受的。

**一句话分辨**：问"如果把接收端换成一台无限快、缓存无限大的机器，问题还在不在？"——**还在，就是拥塞；消失了，就是流量控制**。

### 5.6 开环控制与闭环控制

从控制论视角，拥塞控制方法分两大类。

|  | **开环控制** | **闭环控制** |
| --- | --- | --- |
| 核心思想 | **设计时**就把发生拥塞的有关因素考虑周到，力求网络工作时不产生拥塞 | 基于**反馈环路**：出了拥塞再发现、再纠正 |
| 有没有反馈 | **没有**。系统一旦运行起来，就不再中途改正 | **有**。监测 → 传信息 → 调整，闭合成环 |
| 典型手段 | 容量规划、接入控制（拒绝新连接）、流量整形与预约、合理的缓存与调度设计 | 丢包检测、显式拥塞通告、抑制分组、窗口调节 |
| 优点 | 不需要运行时开销 | 能适应实际负载变化 |
| 缺点 | 无法应对预料之外的负载 | 有测量与通信开销，反应快慢难拿捏 |

**闭环控制的三个步骤**（教材原话）：

- **监测**网络系统，以便检测到拥塞在何时、何处发生；
- 把拥塞发生的**信息传送**到可采取行动的地方；
- **调整**网络系统的运行，以解决出现的问题。

第 2 步有三种做法，代价各不相同：

| 做法 | 机制 | 代价 |
| --- | --- | --- |
| 发抑制分组 | 监测到拥塞时，向产生分组的源站专门发一个通知分组 | **通知拥塞的分组本身会使网络更加拥塞** |
| 在转发的分组中捎带 | 路由器在正常转发的分组里保留一个比特或字段，用它表示有没有拥塞 | 几乎零额外开销（这就是显式拥塞通告 ECN 的思路） |
| 主机/路由器周期性发探测分组 | 主动去问"拥塞了吗" | 有固定开销，且探测有延迟 |

**第 3 步的时机极难拿捏**：动作太频繁，系统会产生**不稳定的振荡**；动作太迟缓，又没有任何实用价值。要采用折中，**但选择正确的时间常数是相当困难的**。

**一条容易被忽略的警告**：教材明确指出，"在许多情况下，甚至正是拥塞控制机制本身成为引起网络性能恶化甚至发生死锁的原因"。拥塞控制本身也要付出代价——需要获得网络内部流量分布的信息，需要在节点间交换信息和命令，还可能要把缓存、带宽这些资源分配给个别用户单独使用，**这样就使得网络资源不能更好地实现共享**。设计拥塞控制策略必须全面衡量得失。

### 5.7 和 TCP 拥塞控制是什么关系

**同一个目标，不同的层、不同的信息量。**

|  | 网络层能做的 | 传输层 TCP 做的 |
| --- | --- | --- |
| 位置 | 路由器上（网络内部） | 端主机上（网络边缘） |
| 掌握的信息 | 直接看得到自己的队列长度、丢弃率 | **只能靠"迟迟收不到确认"去猜**，不知道拥塞在哪、为什么 |
| 手段 | 丢弃分组、显式标记（ECN）、调度与整形、接入控制 | 调节**拥塞窗口 cwnd**，即调节自己往网络里注入多少数据 |
| 归属 | 大纲 四（一）4 | 大纲 五（三）5 |

因特网选择的路线是：**网络层保持简单（尽力而为、拥塞时直接丢包），把拥塞控制的主要责任交给端系统的 TCP。** 路由器丢包这个动作本身，就是网络层发给端系统的**隐式拥塞信号**——TCP 把"超时"或"三个重复确认"解读成"网络堵了"，然后减小 cwnd。

这条链路串起来就是：

**这是一个典型的闭环控制**：监测（TCP 检测超时/重复 ACK）→ 传信息（丢包本身就是信息）→ 调整（减小 cwnd）。

**要点**：所以"IP 不可靠"和"因特网有拥塞控制"并不矛盾。恰恰相反，**IP 的"丢了就丢了、不重传不通知"正是拥塞信号的载体**。如果网络层自己把丢的包补回来，端系统就永远收不到拥塞信号了。

具体的慢开始、拥塞避免、快重传、快恢复四个算法与 cwnd 的逐轮演变，见 [[04_计算机网络_CN/transport/tcp-congestion.md|TCP 拥塞控制]]。

### 5.8 主动队列管理 AQM：网络层怎样把拥塞信号发得更好

上一小节说"路由器丢包就是发给端系统的拥塞信号"。既然是信号，就有**发得好不好**的问题——**丢哪一个分组、什么时候丢**，全在路由器手里，这是**网络层的决定**，不是 TCP 能管的。这一小节讲的就是这个决定。

#### 尾部丢弃：最简单，也最糟

路由器的队列通常按**先进先出 FIFO** 处理到来的分组。队列长度总是有限的，于是最简单的做法是：**队列已满时，以后再到达的分组全部丢弃**。这叫**尾部丢弃策略（tail-drop policy）**。

它的问题不在"丢"，而在"**一丢就丢一串**"：

**这个现象叫全局同步（global synchronization）。** 推它的关键在中间那一步：路由器队列里排的分组来自**很多条不同的 TCP 连接**（它们复用在同一批 IP 数据报里传送），尾部丢弃是"不管你是谁，来了就丢"，所以**一次溢出同时打击几十上百条连接**。这些连接本来各自独立、加速减速的相位互不相干，被同一次尾部丢弃一"敲"，就全部对齐了。

**后果是吞吐量在高低之间大幅摆动**：全局同步使全网的通信量突然下降很多，网络恢复正常后又突然增大很多。链路平均利用率因此上不去——**丢包总量不见得多，浪费却很大**。

**接住 5.2 那条链**：5.2 说"加大缓存解决不了拥塞"。这里补上另一半——**队列管得不好，同样解决不了拥塞**。缓存大小和队列策略是两个独立的旋钮，把前一个拧到底不解决问题，真正有效的是后一个。

#### AQM：不等队列满就动手

**主动队列管理 AQM（Active Queue Management）** 的"主动"二字，就是针对尾部丢弃的"被动"来的：

不要等到路由器的队列长度**已经达到最大值**时才不得不丢弃后面到达的分组——那样太被动了。应当在队列长度**达到某个值得警惕的数值时**（即网络拥塞刚有征兆时），就**主动丢弃**到达的分组。

主动丢的收益不在"少丢"，而在**早丢**和**少量地丢**：早一点丢，就早一点提醒发送方放慢；只丢个别分组，被惊动的就只是个别连接，**拥塞控制只在个别 TCP 连接上进行，避免了全局性的拥塞控制**。

#### RED：AQM 的一种实现

**随机早期检测 RED（Random Early Detection）** 是流行多年的一种 AQM 实现。路由器维持两个参数：**队列长度最小门限**与**最大门限**。每来一个分组，先按规定算法算出**当前的平均队列长度**，然后三选一：

| 平均队列长度 | 动作 |
| --- | --- |
| 小于最小门限 | 放入队列**正常排队** |
| 超过最大门限 | **丢弃**新到达的分组 |
| 介于两个门限之间 | 按某一**丢弃概率 p** 把新到达的分组丢弃（随机性就体现在这里） |

三个必须抓住的设计要点：

- **判据是"平均"队列长度，不是瞬时长度。** 瞬时长度会因为突发流量剧烈抖动，拿它做判据会把正常的短暂排队误判成拥塞。取平均等于加了个低通滤波，只对**持续**的排队增长做反应。
- **中间区间必须是"随机"的。** 若这一区间改成"一律丢"，那就等于把尾部丢弃的门限提前了，全局同步照样发生。**随机地丢，才能让被惊动的连接分散开**——而且一条连接占的流量越大、分组越多，被随机选中的概率越高，惩罚天然按流量大小分摊。
- **丢弃概率 p 不是常数。** 它随平均队列长度在两个门限之间的位置而变，每来一个分组都要重算一次——**这正是 RED 最难处理的一点**。

**口径提醒（别把 RED 当"现行标准"）**：多年的实践证明 RED 的使用效果并不太理想。IETF 曾推荐在路由器中使用 RED（RFC 2309），但 RFC 7567 已经把 RFC 2309 列为"**陈旧的**"，并且**不再推荐使用 RED**。

但**对路由器进行主动队列管理 AQM 仍然是必要的**——AQM 实际上就是对路由器中的分组排队进行智能管理，而不是简单地把队列尾部丢弃。替代 RED 的算法已有几种，但都还在实验阶段，尚无一种成为 IETF 标准。**被否掉的是 RED 这个具体算法，不是 AQM 这个思路。**

#### 它为什么被放在网络层这一节

回到本节开头那条主线：拥塞控制的两个动作是"**发信号**"和"**收信号后调整**"。

| 动作 | 谁做 | 在哪一篇 |
| --- | --- | --- |
| **发信号**：什么时候丢、丢谁 | **路由器（网络层）** | 本节 |
| **收信号后调整**：cwnd 怎么变 | 端主机（传输层 TCP） | [[04_计算机网络_CN/transport/tcp-congestion.md|TCP 拥塞控制]] |

尾部丢弃与 AQM 的差别，全在**信号质量**上：尾部丢弃发出的是"又猛又集中"的信号，AQM 发出的是"又早又分散"的信号。**TCP 的四个算法一个字都没改，仅仅换一下路由器的丢弃策略，全网的表现就会明显不同**——这是"拥塞控制是全局问题、涉及所有路由器"这句话最具体的一个例证。

## 易混淆知识点

**1. 转发 ≠ 路由**

路由是"多台路由器协同算出路径、更新路由表"，在控制面、秒级；转发是"单台路由器对单个分组查表选下一跳"，在数据面、微秒级。一个是"怎么算出来的"，一个是"实际怎么走的"。

**2. IP 提供不可靠服务，但"不可靠"≠"经常丢"**

"不可靠"的准确含义是：**丢了不重传、也不通知**。拥塞时路由器主动丢 IP 分组是网络层的正常行为，不是故障——而且这个丢弃动作还兼任了"向端系统传递拥塞信号"的职能。

**3. 虚电路 ≠ 电路交换，虚电路不预留带宽**

虚电路固定的是**路径**，不是**带宽**。链路带宽仍然统计复用。凡是把"预分配带宽""独占信道"安到虚电路头上的说法都是错的——那是电路交换的性质。

**4. 最长前缀匹配的"最长"是掩码位数，不是匹配的字节数**

`/27` 比 `/24` 长，所以 `/27` 优先。别用"网络号占几个字节"去比。

**5. 默认路由不是"备用分支"，它就是普通的一条路由**

`0.0.0.0/0` 参与同一次最长前缀匹配，只是它的掩码位数为 0，所以只有在没有任何更长匹配时才会胜出。不存在"先查普通路由、查不到再查默认路由"这样的两趟流程。

**6. 拥塞控制 ≠ 流量控制**

拥塞控制是**全局**问题，涉及所有主机、所有路由器；流量控制是**两方**的端到端问题（接收端控制发送端）。判别法：把接收端换成无限快的机器，问题还在不在。

**7. 分组丢失是拥塞的征兆，不是原因**

按住这一句，就不会犯"加大缓存解决拥塞"的错。加大缓存只是把丢包换成了无限排队 + 重传泛滥。

**8. 开环控制不是"没有控制"**

开环指的是**没有运行时反馈**，控制在设计阶段就做完了（容量规划、接入控制、流量整形）。它有控制，只是不看运行结果。

**9. 拥塞控制机制本身也可能引发拥塞**

反应过于频繁会引起系统振荡，通知拥塞的分组本身也会加重拥塞。这是教材点名的一条警告，不是段子。

**10. 全局同步不是"很多连接碰巧一起变慢"，是被同一次尾部丢弃"敲"齐的**

路由器队列里排的分组来自很多条不同的 TCP 连接，尾部丢弃一次溢出就成片丢，于是这些本来相位互不相干的连接同时超时、同时进入慢开始。**根因是"成片地丢"，不是"丢得多"。**

**11. AQM 的"主动"指的是提前动手，不是丢得更多**

主动 = 在队列长度到达值得警惕的数值时就丢，而不是等队列满。收益在**早**和**散**：早提醒发送方，只惊动个别连接。

**12. RED 中间区间必须随机丢，判据必须用平均队列长度**

若中间区间"一律丢"，等于把尾部丢弃的门限提前，全局同步照旧；若用瞬时队列长度做判据，正常的突发排队会被误判成拥塞。

**13. RED 已不再被推荐，但 AQM 仍然必要**

RFC 7567 把推荐 RED 的 RFC 2309 列为"陈旧的"。被否的是 RED 这一个算法，**不是 AQM 这个思路**。

## 本节小结

**路由 vs 转发**：网络层把"送分组"拆成两个时间尺度——路由在控制面，多台路由器协同跑协议算路径，秒级；转发在数据面，单台路由器对每个分组查表转出，微秒级。拆开的理由是两者的数据结构优化目标相反：路由表要便于按拓扑重算，转发表要便于极速查找。

**异构网络互连**：IP 用"统一地址 + 统一分组格式 + 统一尽力而为语义"抹平底层差异，配合分片、ARP、路由器重新封装三个机制。统一在网络层而非链路层，是因为只有 IP 地址端到端不变。这就是沙漏模型的腰。

**数据报 vs 虚电路**：源头是一场"可靠交付该由谁负责"的争论。电信网的端系统是没有智能的电话机，只能由网络负责，于是走虚电路；互联网的端系统是有差错处理能力的计算机，于是把可靠性下放给端系统，网络层只提供**无连接、尽最大努力交付的数据报服务**。后果链是：不建连 → 每个分组独立发送不编号 → 不承诺服务质量（可能出错、丢失、重复、失序，也不保时限）→ 路由器简单廉价 → 可靠通信由主机运输层负责。**TCP 的序号、确认重传、IP 校验和只覆盖首部、路由器丢包不算 bug，全是这一个决定的推论。** 两种模型分歧的技术根是"转发决策每包做一次还是建连时做完"，由此派生出头部长度（完整 IP 地址 vs 局部 VCID）、中间节点有无状态、会不会失序、节点故障影响范围的全部差异。虚电路固定路径但**不预留带宽**。

**路由表查表**：最长前缀匹配分两步——先用"IP AND 掩码 = 目的网络"筛出所有命中项，再在命中项里取掩码位数最大的。默认路由是掩码位数为 0 的普通一员。路由聚合要求前缀全同且低位取遍所有组合（恰好填满一个对齐块），下一跳与出接口还必须相同。

**拥塞控制**：拥塞的定义式是"对资源的需求之和 > 可用资源"，是全局现象。核心洞见是**分组丢失是征兆不是原因**——所以加大缓存只会把丢包换成无限排队加重传泛滥，提高单个部件的性能只会让瓶颈搬家，只有各部分平衡才能真正解决。拥塞会通过"丢包 → 超时 → 重传 → 更多分组"自我加剧。吞吐量-负载曲线上，理想控制饱和后水平、实际控制提前偏离、无控制掉头向下直至死锁。拥塞控制与流量控制的分野是"全局 vs 两方"。方法分开环（设计时防，无反馈）与闭环（监测 → 传信息 → 调整），闭环的信息传递可以用抑制分组、捎带比特或探测分组，代价依次递减；调整的时间常数太快会振荡、太慢无用。

**与 TCP 的关系**：因特网把网络层做薄（尽力而为、拥塞就丢），把拥塞控制的主要责任交给端系统的 TCP。路由器丢包就是发给端系统的隐式拥塞信号，TCP 据此减小 cwnd，构成一个跨层的闭环。IP 的"不可靠"正是这个信号得以存在的前提。

**主动队列管理 AQM**：既然丢包是信号，那么"什么时候丢、丢谁"就是网络层能调的旋钮。最简单的**尾部丢弃**（FIFO 队列满了就丢后来的）会一次丢掉一串分组，而这串分组分属很多条 TCP 连接，于是它们同时超时、同时进入慢开始——这就是**全局同步**，表现为全网通信量骤降后又骤增，链路利用率上不去。**AQM 的"主动"是指不等队列满、在队列长度到达值得警惕的数值时就丢**，收益在"早"和"散"。其经典实现 **RED** 用**平均**队列长度对照最小/最大两个门限三分支：低于最小门限正常排队、高于最大门限丢弃、介于两者之间按概率 p 随机丢；用平均值是为了滤掉突发抖动，用随机是为了不把连接再敲齐。RED 实践效果不理想，RFC 7567 已把推荐它的 RFC 2309 列为"陈旧的"、不再推荐 RED，**但 AQM 这个思路仍然必要**。这一节的落点是：**TCP 四算法一个字不改，只换路由器的丢弃策略，全网表现就会明显不同**——拥塞确实是全局问题。
