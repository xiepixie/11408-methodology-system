## 知识框架

本节回答 5 个问题：

- ICMP 报文明明装在 IP 数据报里，跟 TCP/UDP 的位置一模一样，凭什么说它是**网络层**协议？
- ICMP 差错报告报文为什么要把**原数据报首部 + 数据部分的前 8 个字节**抄回去？为什么偏偏是 8 字节？
- 那四种"不发送 ICMP 差错报文"的情况，各自是为了防什么？
- ping 用回送请求/回答，traceroute 用超时报文 —— 为什么不能都用同一种？
- traceroute 探到终点时，收到的为什么是"终点不可达"而不是"超时"？

## 一、ICMP 的作用与定位

IP 提供的是**尽最大努力交付**：数据报可能因为 TTL 耗尽、路由器缓冲区溢出、找不到目的网络等原因被丢弃，而 IP 本身**不会通知任何人**。

ICMP（Internet Control Message Protocol，网际控制报文协议）就是补这一块的：它允许**路由器或目的主机**向**源点**报告差错情况，或提供有关异常情况的报告。

### 为什么它是网络层协议

ICMP 报文封装在 IP 数据报的数据部分，协议字段值为 **1**。位置上确实和 TCP 报文段、UDP 用户数据报一模一样，看起来像高层协议。

但判断一个协议属于哪一层，看的不是"它被谁封装"，而是"**它为谁服务、它的功能属于谁**"：

- TCP/UDP 是为**应用进程**服务的：提供端到端的进程间通信，有端口号的概念
- ICMP 是为 **IP 自己**服务的：它报告的是 IP 转发过程中出的事（TTL 耗尽、首部字段有误、找不到目的），它没有端口号，也不为任何应用进程提供通道

所以 ICMP 是**与 IP 配套使用的网络层协议**，与 [[04_计算机网络_CN/network/arp.md|ARP]]、IGMP 并列，是 IP 层的组成部分。同样的逻辑也适用于 IGMP（见 [[04_计算机网络_CN/network/multicast.md|IP 多播]]）。

```
+-------------------+
|  以太网帧首部      |  ← 数据链路层
+-------------------+
|  IP 首部           |  ← 网络层
|  (协议字段 = 1)     |
+-------------------+
|  ICMP 报文         |  ← 仍然是网络层
+-------------------+
```

### ICMP 报文的统一格式

所有 ICMP 报文的**前 4 个字节格式统一**：

| 字段 | 长度 | 说明 |
| --- | --- | --- |
| 类型 | 1 字节 | 报文的大类（如 3 = 终点不可达） |
| 代码 | 1 字节 | 在同一类型内进一步区分具体情况（如"端口不可达"） |
| 检验和 | 2 字节 | **检验整个 ICMP 报文** |

接下来 4 个字节的内容取决于类型；再往后是数据字段，长度也取决于类型。

**注意检验和这一栏。** IP 首部检验和**只检验首部、不检验数据部分**（见 [[04_计算机网络_CN/network/ip-datagram.md|IPv4 数据报格式]]），因此它保证不了作为"数据部分"被携带的 ICMP 报文没出错。ICMP 只能自己再算一遍，覆盖整个 ICMP 报文。**这是"IP 只保首部"这个设计必然要求的补偿。**

## 二、ICMP 报文的种类

ICMP 报文分两大类：**差错报告报文**与**询问报文**。

### 差错报告报文（四种）

| 类型 | 名称 | 什么时候发 |
| --- | --- | --- |
| **3** | 终点不可达 | 路由器或主机不能交付数据报（网络不可达、主机不可达、端口不可达等，由**代码**字段区分） |
| **11** | 时间超过 | ① 路由器收到 TTL 已减为 0 的数据报；② 终点在规定时间内收不齐一个数据报的全部分片 |
| **12** | 参数问题 | 收到的数据报首部中某字段的值不正确 |
| **5** | 改变路由（重定向） | 路由器告诉主机"下次发到这个目的地，走另一台路由器更好" |

⚠️ **只有这四种。** 有的旧资料还列"源点抑制（类型 4）"，它连同"信息请求与回答""地址掩码请求与回答""路由器请求与通告"一起，都**已经不再使用**了。

#### 改变路由报文在解决什么

这一条最容易被跳过，但它揭示了主机与路由器的分工：

**主机里也有转发表**，但主机数量远大于路由器数量，出于效率考虑，主机**不参加**路由协议、不与路由器定期交换路由信息。所以主机刚开机时，转发表里通常只配了一个默认路由器——不管发到哪，一律先交给它。

问题是默认路由器未必是最优的下一跳。假如本网络上还有另一台路由器 R，通往某个目的网络更近，默认路由器就会用**改变路由报文**告诉主机："发往这个目的地址应该经过 R"。主机于是在自己的转发表里加一条更具体的项目。

**所以改变路由报文是"路由器替不懂路由的主机做优化"的机制**，它是差错报告报文里唯一一个不报告差错、而是报告"有更好选择"的。

### 询问报文（两种）

| 类型 | 名称 | 用途 |
| --- | --- | --- |
| **8 / 0** | 回送（Echo）请求 / 回送回答 | 测试目的站是否可达、了解其状态 —— **ping** 的基础 |
| **13 / 14** | 时间戳请求 / 时间戳回答 | 报文中记录发送与接收时间，据此算出往返时延 |

记忆上注意方向：**8 是请求、0 是回答**，数值大的反而是请求。

## 三、差错报告报文的数据字段

所有 ICMP **差错报告报文**的数据字段格式相同：ICMP 差错报文=ICMP 前 8 字节⏟类型/代码/检验和/其余 4 字节+原数据报的 IP 首部⏟20∼60 字节+原数据报数据部分的前 8 字节⏟8 字节

### 为什么抄这两截，而且偏偏是 8 字节

**抄原 IP 首部**：源点收到差错报文时，手上可能有成百上千个正在传输的数据报。光说"有个数据报被丢了"毫无意义，必须能指出**是哪一个**。原首部里有源 IP、目的 IP、标识、协议字段，足以让源点认出来。

**抄数据部分的前 8 字节**：这 8 字节是精心挑的——它正好覆盖运输层报文的**关键头部信息**：

- 对 UDP：源端口（2 B）+ 目的端口（2 B）+ 长度（2 B）+ 检验和（2 B），恰好 **8 字节**，全都拿到了
- 对 TCP：源端口（2 B）+ 目的端口（2 B）+ 序号（4 B），也是 **8 字节**

所以这 8 字节让源点能知道：出问题的是**哪个进程**（端口号）的**哪一段数据**（TCP 序号）。有了这两条，IP 层才能把差错信息准确地通知给对应的高层协议实体，而不是笼统地报个错。

**为什么不多抄一点**：差错报文本身也要在网上传，而它是为"已经出错的网络"服务的——抄得越多，越可能自己也被丢。8 字节是"够用"与"够小"的平衡点。

### 例题：算 ICMP 差错报告报文的长度

**题目**（自造数据）：某路由器丢弃了一个 IP 数据报并向源点发回 ICMP 终点不可达报文。已知被丢弃的数据报首部长度字段值为 5。求：(1) 这个 ICMP 报文有多少字节？(2) 承载它的 IP 数据报总长度是多少？(3) 若被丢弃的数据报带了 8 字节可选项（首部长度字段值为 7），两个答案各变成多少？

**第 1 步：把被丢弃数据报的首部长度换算成字节。**

*为什么这么做*：首部长度字段的单位是 4 字节（见 [[04_计算机网络_CN/network/ip-datagram.md|IPv4 数据报格式]]），不能直接当字节数用。

首部长度字段 = 5 → 首部 = 5×4=20 字节。

**第 2 步：按公式拼出 ICMP 报文长度。**

*为什么这么做*：差错报告报文的三段结构是固定的，唯一会变的就是中间那段"原首部"的长度。8+20+8=36 字节

**第 3 步：加上承载它的新 IP 首部。**

*为什么这么做*：ICMP 报文自己不能上网，必须再封装成一个 IP 数据报发回源点。这个新数据报通常不带可选项，首部 20 字节。而"总长度"字段按定义**包含首部**。20+36=56 字节

**第 4 步：换成首部长度字段 = 7 的情形。**

*为什么这么做*：只有中间那一段变了，另外两段（ICMP 前 8 字节、原数据前 8 字节）是固定的。

原首部 = 7×4=28 字节 →ICMP 报文=8+28+8=44 字节,IP 总长度=20+44=64 字节

**第 5 步：一句话验算。** 两种情形的差值都是 28−20=8 字节，与"原首部多了 8 字节可选项"完全对应 ✓。

这里有两处容易失手：**一是把首部长度字段 5 直接当成 5 字节**；**二是漏掉最外层那 20 字节的新 IP 首部**——题目问"ICMP 报文多长"和问"这个 IP 数据报总长度多少"，答案差着一个首部。

## 四、不发送 ICMP 差错报文的四种情况

这四条不是硬记的清单，每一条都在防一件具体的事：

| 情况 | 防的是什么 |
| --- | --- |
| **对 ICMP 差错报告报文，不再发差错报告报文** | 防**无限循环**。若 A 的差错报文在路上又出错，B 回一个差错报文，这个差错报文又可能出错……两台机器能互相打到网络瘫痪 |
| **对第一个分片之后的所有后续分片，不发** | 防**报文风暴**，也是因为**没用**。一个数据报分成 10 片，若全部丢失都各回一个差错报文，源点会收到 10 个说的是同一件事的报文。而且只有第一个分片里才有运输层首部（端口号、序号），后续分片抄回来的"前 8 字节"是纯数据，源点根本认不出是哪个进程的 |
| **对具有多播地址的数据报，不发** | 防**响应爆炸**。多播数据报可能被成千上万台主机收到，若每台都因某种原因回一个差错报文，源点会被瞬间淹没。这就是"在 ping 后面键入多播地址永远收不到响应"的原因，见 [[04_计算机网络_CN/network/multicast.md|IP 多播]] |
| **对具有特殊地址（127.0.0.0 或 0.0.0.0）的数据报，不发** | 这两类地址**没有确定的回信对象**：127.x.x.x 是环回、根本不出主机；0.0.0.0 表示"本网络本主机"，是尚未配置地址的主机才用的源地址，回信无处可送 |

把四条串起来是一条统一的原则：**差错报文只在"能确定唯一收信人"且"不会引发级联"时才发。**

## 五、ping 的工作原理

ping（Packet InterNet Groper，分组网间探测）用来测试两台主机之间的连通性，基于 ICMP 的**回送请求与回送回答**。

三条要点：

- **ping 不使用 TCP 或 UDP。** 它是"**应用层程序直接使用网络层 ICMP**"的典型例子，中间跳过了整个运输层。
- **收不到回答不等于网络不通。** 有的主机为防止恶意攻击，故意不理睬外来的 ICMP 回送请求。所以 ping 不通只能说明"没收到回答"，不能直接推出"链路断了"。
- **ping 只报告丢失数，不报告丢失原因。** 它统计的是发送数、收到数、丢失数和 RTT 的最小/最大/平均值。

## 六、traceroute 的工作原理

traceroute（UNIX 命令；Windows 下叫 tracert）用来追踪数据报从源到目的经过的**每一台路由器**。它同时利用了 IP 首部的 **TTL 字段**和 ICMP 的**时间超过**报文。

### 逐跳探测的逻辑

核心思路是：**故意让数据报在第 k 跳上"死掉"，那么发回时间超过报文的那台路由器就是第 k 跳。**

假设路径是 `源主机 → R1 → R2 → R3 → 目的主机`：

| 第几轮 | TTL 初值 | 谁把 TTL 减到 0 | 源主机收到什么 | 因此得知 |
| --- | --- | --- | --- | --- |
| 1 | 1 | R1 | **时间超过**（类型 11），源地址 = R1 | 第 1 跳是 R1 |
| 2 | 2 | R2 | **时间超过**（类型 11），源地址 = R2 | 第 2 跳是 R2 |
| 3 | 3 | R3 | **时间超过**（类型 11），源地址 = R3 | 第 3 跳是 R3 |
| 4 | 4 | 没人 —— 数据报到达目的主机 | **终点不可达**（类型 3），源地址 = 目的主机 | 已到终点，探测结束 |

每一轮源主机通常发**三次**同样的数据报，所以输出里每一行有三个时间。

### 为什么终点回的是"终点不可达"而不是"时间超过"

关键在最后一跳发生了什么：数据报**到达目的主机**时 TTL 还是 1，而**主机不转发数据报，也不把 TTL 减 1**——所以永远不会触发时间超过。

那怎么知道"已经到了"？traceroute 的做法是：让 IP 数据报里封装一个**无法交付的 UDP 用户数据报**（目的端口取一个几乎不可能有进程在监听的值）。目的主机的运输层发现"没有进程在这个端口上"，于是向源点发回 **ICMP 终点不可达**报文（类型 3，代码为"端口不可达"）。

源主机据此判断：收到时间超过 → 还在路上；收到终点不可达 → **已经到终点了**，停止探测。

**两个报文类型的分工要分清**：中间路由器发回的是**时间超过（类型 11）**，最终目的主机发回的是**终点不可达（类型 3）**。这一对最容易记混。

另外注意：Windows 的 `tracert` 实现上常用 ICMP 回送请求代替 UDP，但**教材口径是"封装无法交付的 UDP 用户数据报、终点回终点不可达"**，以此为准。

### 一个反直觉的观察

从原则上讲，经过的路由器越多、花的时间应该越长。但 traceroute 的实测输出里**经常出现"跳数更多反而更快"**。原因是互联网的拥塞程度随时在变，某一跳恰好赶上拥塞，就会比更远的那一跳还慢。**逐跳时间不是单调递增的，这不是测量错误。**

## 易混淆知识点

**1. ICMP 是网络层协议，不是传输层**

判据不是"被谁封装"，而是"为谁服务"。ICMP 没有端口号、不为应用进程提供通道，它报告的是 IP 转发过程中的事。IP 首部协议字段 = 1 表示 ICMP。

**2. ping 不使用 TCP 或 UDP**

ping 是应用层程序直接调用网络层 ICMP 的例子，跳过整个运输层。而 **traceroute 用到了 UDP**（作为那个"无法交付"的载荷）——两者在这一点上相反，别互相套用。

**3. traceroute 中间收超时、终点收终点不可达**

中间路由器是 TTL 减到 0 触发**时间超过（11）**；目的主机不减 TTL，靠"端口无进程"触发**终点不可达（3）**。

**4. 差错报告报文只有四种**

终点不可达（3）、时间超过（11）、参数问题（12）、改变路由（5）。**源点抑制已弃用**，看到它出现在选项里要能识别。

**5. 差错报文抄回的是"首部 + 数据前 8 字节"**

不是"整个数据报"，也不是"只抄首部"。8 字节的意义是覆盖 UDP 完整首部 / TCP 的端口与序号。

**6. 算长度时别漏最外层的 IP 首部**

ICMP 报文长度 = 8 + 原首部 + 8；而承载它的 IP 数据报**总长度**还要再加 20 字节新首部。看清题目问的是哪个。

**7. ICMP 自己有检验和，且覆盖整个 ICMP 报文**

因为 IP 首部检验和不覆盖数据部分，保证不了 ICMP 报文的正确性。

**8. 时间超过报文有两个触发原因**

除了 TTL 减到 0，还有一个：**终点在规定时间内收不齐全部分片**，也发时间超过报文（见 [[04_计算机网络_CN/network/ip-fragment.md|IP 分片与重装]]）。只记住 TTL 那一个是不完整的。

**9. ping 不通不等于网络故障**

主机可能故意不理睬 ICMP 回送请求。

## 本节小结

本节可以串成"**IP 缺什么，ICMP 补什么，补的时候又必须防什么**"：

- **IP 尽最大努力交付、出了事不通知任何人**，ICMP 就是那条回程的通知通道。它是与 IP 配套的网络层协议——判据是"为 IP 自己服务、没有端口号"，而不是"被 IP 封装"（TCP/UDP 同样被 IP 封装）。
- **ICMP 必须自带检验和且覆盖整个报文**，因为 IP 首部检验和不管数据部分。这是"IP 只保首部"这一设计必然要求的补偿。
- **差错报告报文只有四种**：终点不可达（3）、时间超过（11）、参数问题（12）、改变路由（5）。其中改变路由是唯一不报差错的一个——它是路由器替"不参加路由协议的主机"做优化。
- **差错报文抄回"原首部 + 原数据前 8 字节"**：前者用来认出是哪个数据报，后者恰好覆盖 UDP 完整首部或 TCP 的端口与序号，让源点能定位到进程与数据段。算长度时是 8+原首部+8，再封装还要加 20 字节新首部。
- **四种不发差错报文的情况，统一原则是"只在能确定唯一收信人且不会引发级联时才发"**：防循环、防风暴、防响应爆炸、防无处可回。
- **ping = 回送请求（8）/ 回送回答（0）**，是应用层直接使用网络层的例子，不经运输层；收不到回答不等于不通。
- **traceroute = TTL 递增 + 时间超过**，靠"让数据报在第 k 跳死掉"逐跳定位；终点因为主机不减 TTL，改用"无法交付的 UDP 端口"触发终点不可达来宣告结束。**中间收 11、终点收 3**，是这套机制的直接结论。

## 教材出处

- 谢希仁《计算机网络》（第 7 版）：ICMP 的定位与报文格式，见印刷版 **p146**（4.4 网际控制报文协议 ICMP）——"ICMP 允许主机或路由器报告差错情况和提供有关异常情况的报告。ICMP 是互联网的标准协议。但 ICMP 不是高层协议（看起来好像是高层协议，因为 ICMP 报文装在 IP 数据报中，作为其中的数据部分），而是 IP 层的协议"；"ICMP 报文的前 4 字节是统一的格式，共有三个字段：类型、代码和检验和"，且"检验和字段用来检验整个 ICMP 报文。我们应当还记得，IP 数据报首部的检验和并不检验 IP 数据报的内容，因此不能保证经过传输的 ICMP 报文不产生差错"。同页表 4-6 给出四种差错报告报文（3 终点不可达、11 时间超过、12 参数问题、5 改变路由）与两种询问报文（8 或 0 回送、13 或 14 时间戳），并明确"已不再使用的 ICMP 报文有：'信息请求与回答报文''地址掩码请求与回答报文''路由器请求与通告报文'以及'源点抑制报文'"。
- 同书 **p147**：时间超过的两个触发原因——"当路由器收到生存时间为零的数据报时，除丢弃该数据报外，还要向源点发送时间超过报文。当终点在预先规定的时间内不能收到一个数据报的全部数据报片时，就把已收到的数据报片都丢弃，并向源点发送时间超过报文"；改变路由的机制："在互联网中主机的数量远大于路由器的数量，出于效率的考虑，这些主机不和连接在网络上的路由器定期交换路由信息。在主机刚开始工作时，一般都在转发表中设置一个默认路由器的 IP 地址……如果默认路由器发现主机发往某个目的地址的数据报的最佳路由应当经过网络上的另一个路由器 R，就用改变路由报文把这情况告诉主机"。
- 同书 **p147**：差错报告报文的数据字段——"把收到的需要进行差错报告的 IP 数据报的首部和数据字段的前 8 个字节提取出来，作为 ICMP 报文的数据字段。再加上相应的 ICMP 差错报告报文的前 8 个字节，就构成了 ICMP 差错报告报文。提取收到的数据报的数据字段前 8 个字节是为了得到运输层的端口号（对于 TCP 和 UDP）以及运输层报文的发送序号（对于 TCP）"。同页给出四条不发送差错报告报文的情况（对 ICMP 差错报告报文、对第一个分片的所有后续分片、对具有多播地址的数据报、对具有特殊地址如 127.0.0.0 或 0.0.0.0 的数据报）。
- 同书 **p148**（4.4.2 ICMP 的应用举例）：ping 的定位——"ICMP 的一个重要应用就是分组网间探测 PING……PING 使用了 ICMP 回送请求与回送回答报文。PING 是应用层直接使用网络层 ICMP 的一个例子。它没有通过运输层的 TCP 或 UDP"；并说明"有的主机为了防止恶意攻击就不理睬外界发送过来的这种报文"，统计结果"给出分组丢失的数目（但不给出分组丢失的原因），以及往返时间的最小值、最大值和平均值"。
- 同书 **p148–p149**：traceroute 的原理——"traceroute 从源主机向目的主机发送一连串的 IP 数据报，数据报中封装的是无法交付的 UDP 用户数据报"，逐轮 TTL 递增触发时间超过；到终点时"当最后一个数据报刚刚到达目的主机时，数据报的 TTL 是 1。主机不转发数据报，也不把 TTL 值减 1。但因 IP 数据报中封装的是无法交付的运输层的 UDP 用户数据报，因此目的主机要向源主机发送 ICMP 终点不可达差错报告报文"；"对应于每一个 TTL 值，源主机要发送三次同样的 IP 数据报"；以及那个反直觉的观察——"从原则上讲，IP 数据报经过的路由器越多，所花费的时间也会越长。但……有时正好相反。这是因为互联网的拥塞程度随时都在变化"。[[04_计算机网络_CN/network/arp.md|上一篇ARP 地址解析协议]][[04_计算机网络_CN/network/rip.md|下一篇RIP 路由协议]]
