## 知识框架

本节回答 6 个问题：

- HTTP "无状态"和"无连接"是两件事还是一件事？HTTP/1.1 有持久连接，还能叫无连接吗？
- 取一个文档为什么是 **2** 个 RTT 而不是 3 个？握手明明要三个报文。
- 持久连接省掉的是哪一个 RTT？流水线又省掉了哪一个？
- 并行连接和持久连接是不是一回事？各自的代价是什么？
- HTTP/2 的多路复用解决了什么 HTTP/1.1 流水线解决不了的问题？

第 2、3、4 个问题合起来是一个能算的整体：给定对象数与 RTT，四种方案的总时间都能写成"k 个 RTT + 传输时间"。这是本节唯一必须动笔算的地方。

## 一、HTTP 的基本特点

HTTP（HyperText Transfer Protocol，超文本传送协议）定义了浏览器怎样向万维网服务器请求文档、以及服务器怎样把文档传送给浏览器。它是**面向事务的**应用层协议——所谓事务，指一系列信息交换构成一个不可分割的整体：要么全部完成，要么一次交换都不进行。

HTTP 使用 **TCP 端口 80**（HTTPS 使用 443）。每个万维网网点都有一个服务器进程不断监听 TCP 端口 80。

### 无状态：是什么，为什么

**同一个客户第二次访问同一个服务器上的页面时，服务器的响应与第一次被访问时相同**（假定页面没更新），因为服务器并不记得曾经访问过这个客户，也不记得为该客户服务过多少次。

追问一层：**为什么要故意设计成无状态？** 教材给的理由只有一条，但很硬：**简化了服务器的设计，使服务器更容易支持大量并发的 HTTP 请求**。服务器如果要为每个客户记住状态，内存开销和状态清理逻辑都会随并发数线性增长；无状态让每个请求都能被独立处理，任何一台服务器都能接手任何一个请求——这也是后来负载均衡与水平扩容能成立的前提。

代价是很多场景需要状态信息，解决方案是 Cookie 和 Session（见第七节）。

### 无状态 ≠ 无连接，但 HTTP 本身确实"无连接"

这两个词在同一段里出现，最容易搅在一起。分开说：

| 说法 | 含义 | 对 HTTP 成立吗 |
| --- | --- | --- |
| **HTTP 是无状态的** | 服务器不记得之前的请求 | ✅ 各版本都成立 |
| **HTTP 本身是无连接的** | 通信双方**在交换 HTTP 报文之前不需要先建立 HTTP 连接**——HTTP 层没有自己的连接建立过程 | ✅ 成立 |
| **HTTP 不使用连接** | — | ❌ 错。HTTP 使用面向连接的 TCP，靠它保证可靠传输 |

所以准确的三句话是：**HTTP 使用了 TCP 连接；协议 HTTP 本身是无连接的；协议 HTTP 是无状态的。** "HTTP/1.1 有持久连接所以不是无连接协议"这个推理是错的——持久连接说的是**底下那条 TCP 连接**保持打开，不是 HTTP 层多出了一个连接建立阶段。

### 请求-响应模型

客户端发请求，服务器返响应；服务器不会主动向客户端推送数据（WebSocket 可以，但那不是标准 HTTP；HTTP/2 的服务器推送也是在客户端已发起的请求上下文里进行的）。

## 二、请求方法

| 方法 | 作用 | 是否有请求体 | 是否幂等 | 是否安全（不改变服务器状态） |
| --- | --- | --- | --- | --- |
| GET | 获取资源 | 无 | 是 | 是 |
| POST | 提交数据（如表单） | 有 | **否** | 否 |
| PUT | 上传/替换资源 | 有 | 是 | 否 |
| DELETE | 删除资源 | 无 | 是 | 否 |
| HEAD | 同 GET，但只返回首部、不返回实体 | 无 | 是 | 是 |

**幂等性怎么判**：执行一次和执行 n 次对服务器的**最终状态**影响相同，就是幂等。

- `PUT /user/3` 把用户 3 整个替换成给定内容——做 5 次和做 1 次，用户 3 的最终内容一样 → 幂等。
- `DELETE /user/3` 做 5 次，最终状态都是"用户 3 不存在" → 幂等（虽然后 4 次会返回 404，但**返回码不同不影响幂等性判断**，判据是服务器状态）。
- `POST /user` 每次都新建一条记录，做 5 次就多了 5 条 → 不幂等。

**GET 与 POST 的区别**：

| 对比项 | GET | POST |
| --- | --- | --- |
| 数据位置 | URL 的查询字符串中 | 请求体中 |
| 数据量限制 | 受 URL 长度限制（协议本身没规定上限，是实现的限制） | 理论上无限制 |
| 参数可见性 | 暴露在 URL 中，会进浏览器历史、服务器日志 | 不在 URL 中 |
| 幂等性 | 幂等 | 不幂等 |
| 可缓存性 | 可以被缓存 | 一般不缓存 |

> [!WARNING]
>

"POST 比 GET 安全"要限定说法

POST 只是**参数不出现在 URL 里**，因而不进历史记录、不进访问日志、不被 Referer 带走。报文本身在 HTTP 下同样是明文传输，抓包一样能看到。真正的传输安全靠 HTTPS（TLS），与选 GET 还是 POST 无关。

## 三、报文结构

HTTP 有两类报文：**请求报文**（客户 → 服务器）与**响应报文**（服务器 → 客户）。两者都由三部分组成，**区别只在开始行**：

| 部分 | 请求报文 | 响应报文 |
| --- | --- | --- |
| 开始行 | **请求行**：`方法 URL 版本` | **状态行**：`版本 状态码 短语` |
| 首部行 | 若干行 `字段名: 值`，可以没有 | 同左 |
| 空行 | CRLF，用来把首部与实体分开 | 同左 |
| 实体主体 | **一般不用**（GET 就没有） | 可能没有（如 304） |

由于 HTTP 是**面向文本**的，报文中每个字段都是 ASCII 码串，各字段长度都不确定——这与 TCP/IP 首部那种定长二进制字段是完全不同的设计。每行末尾的 `CR`（回车）与 `LF`（换行）就是靠这个来划边界的。

请求报文示例：

```
GET /index.html HTTP/1.1
Host: www.example.com
Connection: keep-alive
User-Agent: Mozilla/5.0
Accept: text/html
```

响应报文示例：

```
HTTP/1.1 200 OK
Content-Type: text/html
Content-Length: 1234

<html>...</html>
```

`Host` 首部在 HTTP/1.1 里是**必须**的：一个 IP 上可以放多个虚拟主机，服务器要靠 `Host` 才知道客户要的是哪个站点的页面。HTTP/1.0 没有这一强制要求，这也是 1.0 无法支持虚拟主机的原因。

## 四、状态码

状态码分五类，首位数字表示类别。

| 类别 | 含义 | 记忆抓手 |
| --- | --- | --- |
| 1xx | 信息性 | 请求收到了，继续 |
| 2xx | 成功 | 收到、理解、接受 |
| 3xx | 重定向 | 你要的东西不在这，或者你手上那份还能用 |
| 4xx | 客户端错误 | 你的请求有问题 |
| 5xx | 服务器错误 | 请求没问题，是我这边坏了 |

| 状态码 | 含义 | 要点 |
| --- | --- | --- |
| 100 Continue | 服务器收到请求的初始部分，客户端可继续发送 | 用于大请求体先探路 |
| **200 OK** | 请求成功 | — |
| 201 Created | 资源创建成功 | 通常是 POST/PUT 的结果 |
| **301 Moved Permanently** | 永久重定向 | 搜索引擎会更新索引，客户端可缓存这次跳转 |
| **302 Found** | 临时重定向 | 下次仍访问原地址 |
| **304 Not Modified** | 资源未修改，可用缓存 | **不带实体主体**，是优化不是错误 |
| **400 Bad Request** | 请求语法错误 | — |
| **403 Forbidden** | 服务器拒绝请求 | 服务器**懂**你的请求，但不给 |
| **404 Not Found** | 资源不存在 | — |
| **500 Internal Server Error** | 服务器内部错误 | — |
| 502 Bad Gateway | 网关/代理收到无效响应 | 出问题的是上游 |
| 503 Service Unavailable | 服务器暂时过载或维护 | 强调"暂时" |

需要牢记的是加粗那几个：200、301、302、304、400、403、404、500。

**401 与 403 的界线**：401 是"你还没证明你是谁"（缺鉴权），403 是"你是谁我知道了，但你没这个权限"（鉴权通过但授权不足）。

## 五、非持久连接与持久连接（本节重点）

### 为什么取一个文档是 2 个 RTT

这一步是整节的地基，也是最容易只记结论的地方。把时间轴拆开：

关键在第 ③ 步：**三报文握手的前两个报文完成后（即经过一个 RTT 后），客户就把 HTTP 请求报文作为握手第三个报文的数据发送出去**。所以第三个握手报文没有单独占用一个 RTT，它和 HTTP 请求合并了。

于是：T取一个文档=2×RTT⏟1 个建连 + 1 个请求/响应+T传输⏟与文档大小成正比

**如果不理解这一步，很容易把答案算成 3 个 RTT**（握手 1.5 RTT + 请求响应 1 RTT，再向上取整）。记住判据：**握手的第三个报文可以携带数据，所以它不额外计时**。

### 三种方式的机制差别

**HTTP/1.0：非持久连接。** 每请求一个对象就建一条 TCP 连接，收到响应立刻关闭。每个对象 2 个 RTT。

两项代价：

- 时间上，每个对象 2× RTT；
- 空间上，每次新建 TCP 连接都要**分配缓存和变量**，服务器同时服务大量客户时负担很重。

补救办法是**并行**：浏览器可以同时打开 5~10 条并行的 TCP 连接，每条处理一个请求。注意这是"用服务器资源换时间"，不是消除开销。

**HTTP/1.1：持久连接（persistent connection）。** 服务器发送响应后**仍在一段时间内保持这条连接**，同一客户与该服务器可以继续在这条连接上传后续请求与响应。而且不限于同一个页面上的对象——**只要这些文档都在同一个服务器上就行**。

持久连接又分两种工作方式：

- **非流水线（without pipelining）**：客户在收到前一个响应后才能发出下一个请求。TCP 连接建好后，**每访问一次对象要用去一个 RTT**。比非持久省掉了每次建连的那 1 个 RTT。缺点是服务器发完一个对象后 TCP 连接就空闲了，浪费服务器资源。
- **流水线（with pipelining）**：客户在收到响应之前就能接着发新的请求报文。请求一个接一个到达服务器，服务器就可以连续发回响应。因此**客户访问所有对象只需花费一个 RTT**。

### RTT 计数公式

设页面含 1 个 HTML 文件 + N 个引用对象，忽略传输时间：

| 方式 | TCP 连接数 | RTT 个数 | 说明 |
| --- | --- | --- | --- |
| 非持久 · 串行 | 1+N | 2(1+N) | 每个对象都要重新建连 |
| 非持久 · M 条并行 | 1+N | 2+2⌈N/M⌉ | 先花 2 个 RTT 拿 HTML，之后每"批"2 个 RTT |
| 持久 · 非流水线 | 1 | 2+N | 2 个拿 HTML，之后每对象 1 个 |
| 持久 · 流水线 | 1 | 2+1=3 | 2 个拿 HTML，所有对象共 1 个 |

**每一项的来历都要能自己说出来**：

- 那个恒定的 "2" 是取 HTML 本身的开销（建连 1 + 请求响应 1）——**四种方式都躲不掉**，因为不拿到 HTML 就不知道页面里引用了哪些对象。
- 非持久里第二个 "2×" 是因为每个对象都重走一遍"建连 + 请求响应"。
- 非流水线的 "N" 是每个对象一个请求-响应来回，建连那一个 RTT 被持久连接省掉了。
- 流水线的 "1" 是所有请求一次性发出、响应连续回来，只占一个来回。

### 例题：四种方案的总时间

**题目**（自造数据）：某网页含 1 个 HTML 文件和 8 个引用对象。客户到服务器的 RTT = 100 ms，链路速率 10 Mb/s，HTML 文件 10 kb，每个对象 100 kb。忽略 DNS 解析、忽略服务器处理时间。分别求四种方案的总时间：(1) 非持久串行；(2) 非持久 + 5 条并行连接；(3) 持久非流水线；(4) 持久流水线。

**第 1 步：先把传输时间单独算出来，它对四种方案是一样的。**T传输=10 kb10 Mb/s+8×100 kb10 Mb/s=1+8×10=81 ms

*这一步为什么这么做*：RTT 数与文件大小无关、传输时间与 RTT 无关，两者是可以分开算再相加的独立部分。先把不变量提出来，后面只比 RTT 个数，比较才干净。（注意 10 Mb/s = 10 000 kb/s。）

**第 2 步：非持久串行。** N=8：2(1+8)=18 个 RTT=1800 ms,T=1800+81=1881 ms

*这一步为什么这么做*：9 个对象（含 HTML），每个都要"建连 1 + 请求响应 1"，一个不落。

**第 3 步：非持久 + 5 条并行。** HTML 必须先单独取（不知道有哪些对象就没法并行），花 2 个 RTT；剩下 8 个对象分成 ⌈8/5⌉=2 批：2+2×2=6 个 RTT=600 ms,T=600+81=681 ms

*这一步为什么这么做*：向上取整是因为第二批只有 3 个对象，但仍要占满一整轮"建连 + 请求响应"。并行只压缩**轮数**，不改变每轮的 2 个 RTT。

**第 4 步：持久非流水线。**2+8=10 个 RTT=1000 ms,T=1000+81=1081 ms

*这一步为什么这么做*：连接只建一次，那 8 个"建连 RTT"全省了；但请求必须串行，8 个请求-响应来回一个不能少。

**第 5 步：持久流水线。**2+1=3 个 RTT=300 ms,T=300+81=381 ms

*这一步为什么这么做*：8 个请求连着发出去，服务器连着回，全部压进一个来回。

**第 6 步：汇总比较。**

| 方案 | TCP 连接数 | RTT 个数 | RTT 时间 | +传输 | 总时间 |
| --- | --- | --- | --- | --- | --- |
| 非持久 · 串行 | 9 | 18 | 1800 ms | 81 ms | **1881 ms** |
| 非持久 · 5 并行 | 9 | 6 | 600 ms | 81 ms | **681 ms** |
| 持久 · 非流水线 | 1 | 10 | 1000 ms | 81 ms | **1081 ms** |
| 持久 · 流水线 | 1 | 3 | 300 ms | 81 ms | **381 ms** |

**答**：依次为 1881 / 681 / 1081 / 381 ms。

**这张表里最值得注意的一行是第 2 行**：非持久 + 5 条并行（681 ms）竟然快过持久非流水线（1081 ms）。**"持久一定比非持久快"是错的**——持久连接省的是建连的 RTT，并行省的是**排队的轮数**，两者优化的维度不同。真正的组合拳是 HTTP/1.1 的持久 + 流水线（381 ms），或 HTTP/2 的单连接多路复用。

代价也要一并记住：并行连接的 9 条 TCP 连接要在服务器上分配 9 份缓存与变量，而持久流水线只占 1 条。**并行是拿服务器资源换时间。**

## 六、HTTP 版本演进

| 特性 | HTTP/1.0 | HTTP/1.1 | HTTP/2 | HTTP/3 |
| --- | --- | --- | --- | --- |
| 连接 | 非持久（默认） | **持久（默认）** | 持久 + 多路复用 | 基于 QUIC |
| 传输层 | TCP | TCP | TCP | **UDP** |
| 请求方式 | 串行 | 流水线（响应仍须排队） | 多路复用（响应可并行发回） | 多路复用 |
| 首部 | 面向文本，不压缩 | 面向文本，不压缩 | 二进制分帧 + HPACK 压缩 | QPACK 压缩 |
| 服务器推送 | 无 | 无 | 支持 | 支持 |

HTTP/2 相对 1.1 的三点改进，逐条对应 1.1 的一个具体缺陷：

- **响应可以并行发回**。HTTP/1.1 的流水线允许客户连续发多个请求，但**服务器发回响应时必须按先后顺序排队，逐个发送**。若某个响应迟迟不能发回，排在它后面的响应就得一直等——这就是**队头阻塞（HOL blocking）**。HTTP/2 把响应变成可以在同一条 TCP 连接上并行发回，缩短了响应时间。
- **复用 TCP 连接**，省掉多次建立和释放连接的时间。
- **二进制分帧 + 首部压缩**。HTTP/1.1 报文面向文本，连续请求时首部里大量字段是重复的，开销不小。HTTP/2 把报文划分为许多较小的二进制编码的**帧**，采用新的压缩算法不发送重复的首部字段。

**兼容性**：HTTP/2 是向后兼容的。使用 HTTP/2 的客户向仍跑 HTTP/1.1 的服务器发请求时，服务器仍能收到，发回响应后客户改用 HTTP/1.1 交互。

**HTTP/3 为什么要换到 UDP**：HTTP/2 解决了**应用层**的队头阻塞，但底下仍是单条 TCP 连接——TCP 要求按序交付，一个报文段丢了，后面所有已到达的数据都得在内核里等它重传，**传输层的队头阻塞**依然存在。QUIC 建在 UDP 上，自己实现流的独立可靠传输，一条流丢包不阻塞其他流。

> [!TIP]
>

一条追问链

非持久 → 每对象 2 RTT（持久解决）→ 请求要串行等待（流水线解决）→ 响应要排队（HTTP/2 多路复用解决）→ TCP 按序交付导致跨流阻塞（HTTP/3 换 UDP 解决）。 每一步都只解决上一步剩下的那个问题，顺着这条链走就不必单独记每个版本的特性表。

## 七、Web 缓存与代理服务器

### 代理服务器（Web Cache）

代理服务器又称**万维网高速缓存**，它把最近的一些请求和响应暂存在本地磁盘中。新请求到达时若发现与暂存的请求相同，就直接返回暂存的响应，不必再按 URL 去互联网访问该资源。

要点：**代理服务器有时是服务器（接受浏览器请求时），有时是客户（向源点服务器发请求时）**——这是"角色由通信关系决定、不由机器决定"在 HTTP 上的又一个实例，与 [[04_计算机网络_CN/application/app-model.md|网络应用模型]] 里说的是同一件事。

三项收益，注意它们受益的对象不同：

| 收益 | 受益方 |
| --- | --- |
| 减少响应时间（客户到代理通常比到源点服务器近） | 用户 |
| 减少机构出口链路的流量，缓解那条链路过载 | 机构 |
| 热门资源被缓存后源点请求量大幅下降 | 内容提供方 |

以代理服务器方式构成的**内容分发网络 CDN（Content Distribution Network）**就是这一思路的规模化形态。

### 条件 GET

缓存里的对象可能已经过期。条件 GET 用来验证缓存是否仍有效：

- 代理向源点服务器发一个带 `If-Modified-Since` 首部的 GET，值为上次获取该对象的时间；
- 对象**未修改** → 返回 **304 Not Modified**，**不携带对象体**，代理继续用缓存；
- 对象**已修改** → 返回 **200 OK** + 新对象，代理更新缓存。

**304 省掉的是实体主体的传输，省不掉那一个 RTT。** 条件 GET 仍要一次完整往返，只是回来的报文很小。所以缓存验证只在"对象大、变化少"时划算——这也是为什么静态资源要配长 TTL 而不是每次都验证。

## 八、Cookie 和 Session

HTTP 无状态，但很多应用需要状态，于是把状态**放在报文里带来带去**。

**Cookie 的工作流程**：

- 客户端首次请求服务器；
- 服务器在响应中通过 `Set-Cookie` 首部设置 Cookie；
- 客户端保存 Cookie；
- 客户端后续请求自动在 `Cookie` 首部中携带这个值；
- 服务器根据 Cookie 识别客户端。

**Session** 是服务器端保存的会话信息。服务器为每个会话分配一个 Session ID，通过 Cookie 把 Session ID 发给客户端；客户端后续请求携带 Session ID，服务器据此找到对应的会话状态。

|  | Cookie | Session |
| --- | --- | --- |
| 存在哪 | 客户端 | 服务器端 |
| 随请求传输的内容 | 全部内容 | 只有 Session ID |
| 安全性 | 内容在客户端，可被查看/篡改 | 内容在服务器，客户端只拿到一个 ID |
| 服务器开销 | 无 | 要为每个会话保存状态 |

> [!WARNING]
>

Cookie 没有推翻"HTTP 无状态"

状态是**客户端替服务器背着**的：每个请求都把标识重新带上一遍，服务器仍然不主动记住任何一个客户。协议层面 HTTP 依旧无状态，有状态的是**建在 HTTP 之上的应用**。这个区分在概念辨析里经常被绕。

## 易混淆知识点

**1. HTTP 是无状态的，也是（协议本身）无连接的，但它使用面向连接的 TCP**

三句话各说一件事。"HTTP/1.1 有持久连接，所以 HTTP 不是无连接协议"是错的：持久说的是底下那条 TCP 连接不立即关闭，HTTP 层始终没有自己的连接建立过程。

**2. 取一个文档是 2 个 RTT 不是 3 个**

因为 HTTP 请求报文捎带在三报文握手的**第三个**报文里，握手的第三个报文不额外占一个 RTT。

**3. 持久连接不一定比非持久快**

持久省的是建连 RTT，并行省的是轮数。非持久 + 多条并行连接完全可能快过持久非流水线（例题里 681 ms < 1081 ms）。要比就把 RTT 个数算出来比。

**4. 持久连接不限于同一个页面**

只要文档都在同一个服务器上，就能复用这条连接。

**5. 流水线解决的是"请求要等"，队头阻塞剩下的是"响应要排队"**

HTTP/1.1 流水线允许客户连发请求，但服务器**必须按序**发回响应。真正把响应并行化的是 HTTP/2。

**6. 301 和 302 的区别**

301 永久重定向（搜索引擎更新索引，客户端可缓存跳转），302 临时重定向（下次仍访问原地址）。

**7. 304 不是错误**

它表示资源未修改、可用本地缓存，属于 3xx 而非 4xx。它不带实体主体，但仍占一个完整往返。

**8. 403 与 401 不同**

401 = 没证明你是谁（缺鉴权）；403 = 知道你是谁但不给（授权不足）。

**9. GET 与 POST 的"安全"只是参数不进 URL**

HTTP 明文传输，POST 报文体照样能被抓包看到。传输安全靠 HTTPS。

**10. 幂等性看服务器最终状态，不看返回码**

`DELETE` 重复执行会返回 404，但服务器状态没变，仍是幂等的。

**11. HTTP/2 的多路复用与 HTTP/1.1 的并行连接不是一回事**

并行连接是开 5~10 条 TCP；多路复用是在**一条** TCP 上交错传多个请求响应。前者代价是多份连接缓存与变量，后者没有这个代价，但受制于单条 TCP 的按序交付（HTTP/3 才解决）。

**12. Cookie 没有让 HTTP 变成有状态协议**

状态由客户端每次重新携带，服务器仍不主动保存客户身份。

## 本节小结

按这条主线能自己重讲一遍就算过：

- **HTTP 定位**：面向事务、面向文本的应用层协议，使用 TCP 端口 80。**三句独立的话**：使用 TCP 连接 / 协议本身无连接 / 协议无状态。无状态的理由是简化服务器、支撑高并发。
- **请求方法**看两个属性：有无请求体、是否幂等。幂等判据是"执行 n 次与 1 次的服务器最终状态相同"，与返回码无关。GET/POST 的差别落在参数位置、长度限制、可缓存性、幂等性上，"POST 更安全"只限于参数不进 URL。
- **报文结构**：开始行 + 首部行 + 空行 + 实体主体，请求与响应**只在开始行不同**。面向文本导致字段长度不定，靠 CRLF 划界。
- **状态码**记五类首位含义 + 8 个必背码；401/403、301/302、304 三组界线要能说清。
- **RTT 计数是本节的计算核心**。地基是"请求捎带在握手第三个报文里，所以取一个文档 2 RTT"。四个公式：非持久串行 2(1+N)、非持久 M 并行 2+2⌈N/M⌉、持久非流水线 2+N、持久流水线 3。恒定的那个 "2" 是取 HTML 的开销，四种方式都躲不掉。
- **不要背"持久比非持久快"**——例题里非持久 5 并行（681 ms）快过持久非流水线（1081 ms）。持久省建连、并行省轮数、流水线省排队，三者优化维度不同。并行的代价是多份连接缓存与变量。
- **版本演进是一条追问链**：非持久 → 持久 → 流水线 → HTTP/2 多路复用 → HTTP/3 换 UDP，每一步只解决上一步剩下的那个阻塞。
- **代理服务器**兼具客户与服务器双重身份；三项收益分别归用户、机构、内容提供方。**条件 GET** 用 `If-Modified-Since` 换 304，省的是实体主体不是往返。
- **Cookie 在客户端、Session 在服务器端**；两者都没有把 HTTP 变成有状态协议，状态是客户端每次重新携带的。

## 教材出处

- **谢希仁《计算机网络》（第 7 版）印刷 p276**，6.4.3 节：「协议 HTTP 定义了浏览器（即万维网客户进程）怎样向万维网服务器请求万维网文档，以及服务器怎样把文档传送给浏览器」「HTTP 是面向事务的(transaction-oriented)应用层协议」，脚注给出事务的定义「一系列的信息交换，而这一系列的信息交换是一个不可分割的整体，也就是说，要么所有的信息交换都完成，要么一次交换都不进行」。同页：「每个万维网网点都有一个服务器进程，它不断地监听 TCP 的端口 80。」
- **印刷 p277**，6.4.3 节：无连接与无状态的两段原文——「HTTP 使用了面向连接的 TCP 作为运输层协议，保证了数据的可靠传输……但是，协议 HTTP 本身是无连接的。这就是说，虽然 HTTP 使用了 TCP 连接，但通信的双方在交换 HTTP 报文之前不需要先建立 HTTP 连接」；「协议 HTTP 是无状态的(stateless)……HTTP 的无状态特性简化了服务器的设计，使服务器更容易支持大量并发的 HTTP 请求」。同页还有本篇第五节的地基：「当建立 TCP 连接的三报文握手的前两个报文完成后（即经过了一个 RTT 时间后），万维网客户就把 HTTP 请求报文，作为建立 TCP 连接的三报文握手中的第三个报文的数据，发送给万维网服务器」，结论是「请求一个万维网文档所需的时间是该文档的传输时间（与文档大小成正比）加上两倍往返时间 RTT」。
- **印刷 p278**，6.4.3 节：非持久的两项代价——「每一次链接下载都导致 2×RTT 的开销。另一种开销就是万维网客户和服务器每一次建立新的 TCP 连接都要分配缓存和变量」「好在浏览器都能够打开 5~10 个并行的 TCP 连接」。持久连接的定义与两种工作方式：「非流水线方式的特点，是客户在收到前一个响应后才能发出下一个请求……客户每访问一次对象都要用去一个往返时间 RTT。这比非持续连接要用去两倍 RTT 的开销，节省了建立 TCP 连接所需的一个 RTT 时间」；「流水线方式的特点，是客户在收到 HTTP 的响应报文之前就能够接着发送新的请求报文……使用流水线方式时，客户访问所有的对象只需花费一个 RTT 时间」。HTTP/2 的三点改进与队头阻塞描述也在本页：「但服务器发回响应时必须按先后顺序排队，逐个地发送给客户。有时遇到某个响应迟迟不能发回，那么排在后面的一些响应就必须等待很长的时间。HTTP/2 把服务器发回的响应变成可以并行地发回（使用同一个 TCP 连接）」。
- **印刷 p279**，6.4.3 节 2. 代理服务器：「代理服务器(proxy server)是一种网络实体，它又称为万维网高速缓存(Web cache)。代理服务器把最近的一些请求和响应暂存在本地磁盘中。」以及代理访问互联网的五个步骤。
- **印刷 p280**：「代理服务器有时是作为服务器（当接受浏览器的 HTTP 请求时），但有时却作为客户（当向互联网上的源点服务器发送 HTTP 请求时）」，以及 CDN 的定义。同页 3. HTTP 的报文结构：请求报文与响应报文「这两种报文格式的区别就是开始行不同」，「由于 HTTP 是面向文本的，因此在报文中的每一个字段都是一些 ASCII 码串，因而各个字段的长度都是不确定的」。
