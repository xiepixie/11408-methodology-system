## 知识框架

本节回答 6 个问题：

- 分层能带来模块化，那为什么不分成 20 层？层数的上界和下界分别被什么卡住？
- OSI 七层"概念清楚、理论完整"，为什么反而没被用起来？
- 五层模型不是标准，为什么教材和考试都用它？
- "协议是水平的、服务是垂直的"——这句话到底在说什么？同一层内做的事，凭什么有的叫服务、有的不叫？
- n-SDU+n-PCI=n-PDU 这个恒等式什么时候不成立？
- 每层都加首部，这些首部占了多少？为什么大文件传输时开销可以忽略、小报文时不行？

## 为什么要分层

计算机网络是一个极其复杂的系统：涉及硬件、软件、协议、数据格式、差错处理、路由选择……如果把所有功能塞进一个模块，任何一处改动都要重新验证整体。

分层的核心思想只有一句：**每一层只关注自己的功能，向上层提供服务，使用下层提供的服务**。

好处：

- **模块化设计**：每层功能独立，便于分工开发
- **接口标准化**：层与层之间通过接口交互，某一层的实现变化不影响其他层
- **易于理解和调试**：问题定位可以逐层排查
- **促进标准化**：每层的功能与接口可以独立制定标准

分层的基本原则：

- 每层实现一种相对独立的功能，降低系统复杂度
- 各层之间接口清晰、简洁，相互依赖尽可能少
- 各层功能的定义独立于具体实现方法
- 保持下层对上层的独立性，上层单向使用下层提供的服务
- 整个分层结构应有利于标准化工作

### 层数为什么恰好是这么几层

这一条比记住"分层有三大好处"有用得多。层数被**两个相反方向的代价**夹住：

- **层数太少**：每一层要处理的功能过多，层内又会自发长出子结构，等于把分层的复杂度藏进了层内部，标准化和替换都做不了。极端情形就是不分层。
- **层数太多**：每多一层，就多一次**首部封装**（带宽开销）、多一次**跨层数据拷贝与接口调用**（处理开销），而且描述整个体系结构的工作量增加。更要命的是层与层的职责会开始重叠——OSI 的表示层和会话层就是典型：功能太弱，在实际协议里几乎无事可做，最后被 TCP/IP 直接并进应用层。

所以判据是：**一个功能应该单独成层，当且仅当它有明确的、可以独立标准化的抽象边界，并且这个边界上的接口足够窄**。物理层与数据链路层之间的边界是"比特流 vs 帧"，网络层与传输层之间的边界是"主机到主机 vs 进程到进程"——都足够窄。而"会话管理"这个边界不够窄，所以它没能守住独立的一层。

### 体系结构与实现

计算机网络的各层及其协议的集合，称为网络的**体系结构（architecture）**。要点是：**体系结构是抽象的定义，实现是具体的硬件和软件**。教材用了一个很好的类比——我们可以走进一座明代的建筑物，却不能走进"明代的建筑风格"之中。同理，不能把某台具体的路由器说成是一个体系结构。

## 两个重要的体系结构

### OSI 七层参考模型

OSI（Open Systems Interconnection）是 ISO 提出的标准化体系结构，分为七层。它**概念清楚、理论完整，但既复杂又不实用**，最终没有被市场采纳。

从上到下：

| 层次 | 名称 | 主要功能 | PDU |
| --- | --- | --- | --- |
| 7 | 应用层 | 为用户应用程序提供网络服务接口 | 报文（Message） |
| 6 | 表示层 | 数据格式转换、加密解密、压缩 | — |
| 5 | 会话层 | 建立、管理和终止会话，同步控制 | — |
| 4 | 传输层 | 端到端的可靠/不可靠数据传输 | 段（Segment） |
| 3 | 网络层 | 路由选择，逻辑寻址（IP 地址） | 分组 / 数据报（Packet） |
| 2 | 数据链路层 | 帧的封装、差错检测、介质访问控制 | 帧（Frame） |
| 1 | 物理层 | 比特流的透明传输，定义接口特性 | 比特（Bit） |

记忆顺序：**应表会传网数物**（从上到下）。

OSI 失败的原因不在技术不好，而在三件事同时发生：标准出得太晚（TCP/IP 已经在 ARPANET 上跑起来并免费随 UNIX 分发）、协议实现效率低、层次划分中的表示层与会话层功能过弱。这也反过来解释了为什么 TCP/IP 把这两层并进应用层。

### TCP/IP 四层模型

TCP/IP 是因特网使用的实际体系结构，分为四层：应用层、运输层、网际层、链路层（网络接口层）。"网际层"这个名字强调本层解决的是**不同网络的互连**问题。

| TCP/IP 四层 | TCP/IP 五层 | 对应 OSI 层 | 典型协议 |
| --- | --- | --- | --- |
| 应用层 | 应用层 | 应用层 + 表示层 + 会话层 | HTTP、FTP、DNS、SMTP |
| 运输层 | 运输层 | 传输层 | TCP、UDP |
| 网际层 | 网络层 | 网络层 | IP、ICMP、OSPF |
| 网络接口层 | 数据链路层 + 物理层 | 数据链路层 + 物理层 | 以太网、PPP、IEEE 802.11 |

有一点值得注意：**从实质上讲 TCP/IP 只有最上面的三层**，因为最下面的链路层并没有属于 TCP/IP 体系的具体协议——它使用的各种局域网标准是 IEEE 802 委员会制定的，不是 IETF 制定的。所以 TCP/IP 的第四层与其说是"一层"，不如说是"IP 需要的一个与网络的接口"。

正因为链路层是个空壳，讲授网络原理时通常综合 OSI 与 TCP/IP 的优点，采用**五层协议的体系结构**：应用层、运输层、网络层、数据链路层、物理层。这也是本站与考试默认的参考框架。

### 沙漏：为什么核心是 IP

TCP/IP 协议族还有一种画法，上下两头大、中间小：

图源：谢希仁《计算机网络》（第 7 版）图 1-22「沙漏计时器形状的 TCP/IP 协议族示意」，印刷版 **p37**。

这张图把 TCP/IP 的两条设计哲学画了出来：

- **Everything over IP**：IP 层可以支持多种运输层协议，不同的运输层协议上面又可以有多种应用层协议——上面的一切都可以架在 IP 之上
- **IP over Everything**：IP 协议也可以在多种类型的网络上运行——下面的一切都可以承载 IP

腰部只允许有一个协议，是这套体系能长成全球规模的关键：**新增一种应用不必改网络，新增一种链路技术也不必改应用**，两边的创新彼此解耦。代价是 IP 本身极难演进——IPv6 从提出到普及走了二十多年，正是"腰部只有一个"的另一面。

这张图还反映了互联网的一个设计理念：**网络的核心部分越简单越好，把一切复杂的部分让网络的边缘部分去实现**。

### OSI vs TCP/IP 对比

| 对比项 | OSI 七层 | TCP/IP 四（五）层 |
| --- | --- | --- |
| 层数 | 7 层 | 4 层（讲原理时用 5 层） |
| 制定组织 | ISO | IETF |
| 实际使用 | 仅作为参考模型 | 因特网实际采用 |
| 设计顺序 | **先有模型，后制定协议**，通用性好但可能脱离实际 | **先有协议栈，后归纳出模型**，实用但通用性差 |
| 表示层/会话层 | 独立设置 | 合并到应用层 |
| 网络层 | 面向连接与无连接**都支持** | **仅无连接**（IP） |
| 传输层 | **仅面向连接** | 面向连接（TCP）+ 无连接（UDP） |
| 服务/接口/协议 | 明确区分三者 | 未清晰区分 |

最后一行是对 TCP/IP 的一条常见批评：它没有清晰地阐明服务、接口与协议之间的关系，而链路层并非真正的一个层次。**"先有协议后有模型"这条设计顺序，同时解释了它的实用性和它的不严谨**。

## 各层的功能详解

### 应用层

体系结构中的最高层，任务是**通过应用进程间的交互来完成特定网络应用**。应用层协议定义的是应用进程间通信和交互的规则。不同的网络应用需要不同的应用层协议，交互的数据单元称为**报文（message）**。

核心协议：HTTP（万维网）、FTP（文件传输）、SMTP/POP3/IMAP（邮件）、DNS（域名解析）。

### 运输层

任务是**向两台主机中进程之间的通信提供通用的数据传输服务**。"通用"是关键词——它不针对某个特定网络应用，多种应用可以共用同一个运输层服务。

由于一台主机可同时运行多个进程，运输层必须具有**复用**与**分用**功能：复用是多个应用进程可同时使用下面运输层的服务；分用是运输层把收到的信息分别交付上面应用层中的相应进程。二者靠**端口号**实现。

三层通信粒度的区别是这一章的骨架：数据链路层实现**相邻节点之间**的通信（MAC 地址），网络层实现**主机到主机**的通信（IP 地址），运输层实现**端到端 / 进程到进程**的通信（端口号）。

- TCP：面向连接、可靠传输、有流量控制与拥塞控制，单位是**报文段（segment）**
- UDP：无连接、尽最大努力交付、开销小，单位是**用户数据报**

术语提醒：教材使用"**运输层**"而非"传输层"，理由是 OSI 定义的第 4 层用的词是 Transport 而不是 Transmission。两个译名指同一层，答题时都可用。

### 网络层

负责**为分组交换网上的不同主机提供通信服务**。发送数据时，网络层把运输层产生的报文段或用户数据报封装成分组（在 TCP/IP 体系中也叫 IP 数据报）。

网络层的具体任务有两个：

- 通过一定的算法，在互联网中的每一个路由器上**生成用来转发分组的转发表**（这是路由选择）
- 每个路由器收到分组时，**依据转发表把分组转发到下一个路由器**（这是分组转发）

网络层提供的是**无连接、不可靠**的数据报服务，可靠性交由运输层的 TCP 保证。

注意区分：运输层的"用户数据报（UDP）"和网络层的"IP 数据报"是两回事，只是中文都带"数据报"三个字。

### 数据链路层

两台主机之间的数据传输总是**一段一段链路**地传送。数据链路层把网络层交下来的 IP 数据报**组装成帧**，在两个相邻节点间的链路上传送。每一帧包括数据和必要的控制信息（同步信息、地址信息、差错控制等）。

- **封装成帧**：加首部和尾部，使接收端能知道一个帧从哪个比特开始、到哪个比特结束
- **差错检测**：控制信息使接收端能检测出帧中有无差错；**发现差错就简单丢弃这个帧**，以免继续在网络中传送而白白浪费资源
- **介质访问控制**：解决多节点共享信道时的冲突问题

要强调的是：**标准的数据链路层只检错、不纠错**。如果需要改正差错，就要在其上采用可靠传输协议——这会让链路层协议复杂不少，而互联网选择了不这么做。

### 物理层

在传输介质上传送**比特流**。发送方发送 1（或 0）时，接收方应当收到 1（或 0）而不是 0（或 1）。物理层要考虑：

- **机械特性**：接口形状、引脚数目与排列
- **电气特性**：用多大的电压代表 1 或 0、信号电平范围
- **功能特性**：各引脚的功能定义
- **规程特性**：各种功能可能出现的事件顺序

物理层的任务是**透明传输比特流**——解释比特代表的意思不是物理层的任务。

一个容易被绕进去的点：**传输媒体（双绞线、光纤等）不在物理层之内**，而在物理层协议的下面。所以有人把物理传输媒体称为"第 0 层"。

## PDU、SDU 与 PCI

三个术语分别对应三个不同的问题：

- **协议数据单元（PDU）**：**对等层之间**传送的数据单位。OSI 参考模型把对等层次之间传送的数据单位称为该层的 PDU
- **服务数据单元（SDU）**：**相邻层之间**通过服务访问点交换的数据单位
- **协议控制信息（PCI）**：控制协议操作的信息，也就是首部（有时还有尾部）

常规情形下三者的关系是：n-SDU+n-PCI=n-PDU=(n−1)-SDU

即第 n 层把上层交下来的 PDU 当作本层的 SDU，加上本层的 PCI 封装成本层的 PDU，再交给第 n−1 层。

### 这个恒等式什么时候不成立

**SDU 与 PDU 并不总是一一对应。** 教材写得很明确：SDU"可以与 PDU 不一样。例如，可以是多个 SDU 合成为一个 PDU，也可以是一个 SDU 划分为几个 PDU"。

现实中两种偏离都很常见：

- **一个 SDU 划分为多个 PDU**：IP 数据报大于链路 MTU 时要**分片**，一个网络层 SDU 变成多个 IP 分组；TCP 把应用交下来的字节流按 MSS 切成多个报文段，也是这种情形
- **多个 SDU 合成一个 PDU**：TCP 把多次 `send` 的少量数据攒在一起发（Nagle 算法就是干这个的），多个应用层 SDU 合进一个报文段

所以那条恒等式的准确说法是：**它描述的是"不分片、不合并"这个最常见的一对一情形**，而不是一条普适定律。判断题里出现"n 层的 SDU 一定等于 n+1 层的 PDU"这类绝对化说法时，反例就在分片和合并里。

## 封装与解封装

数据在发送方从上层往下层传递时，每经过一层都会加上该层的**首部**（数据链路层还要加尾部），这叫**封装**；到达接收方后从下往上逐层剥掉，叫**解封装**。

各层数据单元的名称：

| 层次 | PDU 名称 | 说明 |
| --- | --- | --- |
| 应用层 | 报文（Message） | 应用层产生的完整数据 |
| 运输层 | 报文段（Segment）/ 用户数据报 | TCP 的叫报文段，UDP 的叫用户数据报 |
| 网络层 | IP 数据报 / 分组 | 教材把"分组"与"数据报"作为同义词 |
| 数据链路层 | 帧（Frame） | 加了帧首部和尾部 |
| 物理层 | 比特（Bit） | 比特流，**不再加控制信息** |

两条容易被跳过的细节：

- **物理层不加首部**。封装只发生在上面四层；物理层做的是把比特变成信号。
- **数据链路层是唯一既加首部又加尾部的**。尾部放的是帧检验序列 FCS，必须在数据后面——接收端要先收完全部数据才能算出校验值来比对。

### 例题：分层封装的开销占多大

**题**：一台主机用以太网发送数据，应用层数据分别为 100 B 和 1460 B。TCP 首部 20 B、IP 首部 20 B、以太网帧首部 14 B、帧尾 FCS 4 B。求两种情形下的**帧总长**与**有效载荷率**（应用数据占帧总长的比例）。

**解**：

**（1）应用数据 100 B**帧长=100+20+20+(14+4)=158 B有效载荷率=100158≈63.29%

这一步为什么这么做：各层首部是**逐层叠加**的，所以直接相加即可；帧首部 14 B 与帧尾 4 B 要合并成 18 B 的链路层开销，因为它们同属数据链路层的 PCI。

**（2）应用数据 1460 B**帧长=1460+20+20+18=1518 B有效载荷率=14601518≈96.18%

这一步为什么这么做：1518 B 正是以太网帧的最大长度，1460 B 也正是以太网上 TCP 的典型 MSS（1500−20−20）。这组数字不是巧合——**MSS 就是按"把帧撑到刚好不分片"倒推出来的**。

**结论与边界**：固定开销 58 B 是常数，载荷越大它占比越小。所以

- **大文件传输**：分层开销约 4%，可以忽略，这也是分层这套设计能被接受的经济前提
- **小报文**（键盘输入、ACK、DNS 查询）：开销占比可达三分之一甚至更高。一个只带 1 字节数据的 TCP 段，帧长仍有 59 B，有效载荷率不到 2%

这正是 Nagle 算法、TCP 延迟确认这类"攒一攒再发"机制存在的理由——它们不是在优化带宽本身，而是在**摊薄固定的分层开销**。

## 协议、接口与服务

这三个概念长得像，方向完全不同。

- **协议**：控制两个**对等实体**（或多个实体）进行通信的规则的集合，是**水平**的。协议由三要素组成：

- **语法**：数据与控制信息的结构或格式
- **语义**：需要发出何种控制信息、完成何种动作以及做出何种响应
- **同步**：事件实现顺序的详细说明（这里的"同步"是广义的，指时序，不是同频同相）
- **服务**：下层为紧邻的上层提供的功能，是**垂直**的。第 n 层向上提供的服务已经**包括了它以下各层所提供的服务**。上层使用下层服务要通过交换一些命令，这些命令在 OSI 中称为**服务原语**
- **接口（SAP，服务访问点）**：同一系统中相邻两层实体交互（交换信息）的地方，是一个**逻辑接口**，有点像邮政信箱——可以把邮件放入信箱和从信箱中取走邮件，但它与两个设备之间的硬件接口不是一回事

这里最要紧的是"**实体**"这个词：实体指任何可发送或接收信息的硬件或软件进程。有了实体的概念，三者的定义才干净——协议约束的是**两个对等实体之间**，服务发生在**同一系统的上下相邻实体之间**。

### 并非层内所有功能都叫服务

这是最容易被跳过的一句话，也是判断题最爱做文章的地方：**只有那些能够被高一层实体"看得见"的功能，才能称之为服务**。

一层内部为了实现协议而做的工作——超时重传、序号管理、校验和计算——上层完全感知不到，它们不是服务，是**协议的实现细节**。上层看得见的只是"数据被可靠地送到了"这一个结果。

由此推出协议的**透明性**：**使用本层服务的实体只能看见服务，而无法看见下面的协议**。所以"TCP 提供可靠传输服务"是对的，"TCP 提供三次握手服务"是错的——三次握手是协议内部行为。

注意图里第 n 层和第 n+1 层用的是**不同的协议**——每一层都有自己的协议，对等实体之间只按本层协议对话。

### 服务的分类

| 分类方式 | 类型 | 说明 |
| --- | --- | --- |
| 按连接方式 | 面向连接服务 | 通信前建立连接、分配资源，结束后释放（如 TCP） |
|  | 无连接服务 | 无须建立连接，各分组独立传输，"尽最大努力交付"（如 UDP、IP） |
| 按可靠性 | 可靠服务 | 具备检错、纠错、应答机制，确保数据正确送达 |
|  | 不可靠服务 | 仅"尽最大努力交付"，可靠性由高层保障 |
| 按应答方式 | 有应答服务 | 接收方**自动**返回确认（如文件传输） |
|  | 无应答服务 | 接收方不自动返回应答（应答由高层应用完成，如浏览网页） |

三个维度是**正交**的：IP 是无连接 + 不可靠，TCP 是面向连接 + 可靠，而"面向连接"并不自动等于"可靠"——OSI 的网络层就可以提供面向连接但不保证可靠的服务。

### 协议必须把不利条件事先都估计到

计算机网络协议有一个很重要的特点：**协议必须把所有不利的条件事先都估计到，而不能假定一切都是正常的和非常理想的**。教材举了个反例：两个朋友约好下午 3 时在公园门口碰头，并约定"不见不散"。这是个很不科学的协议——任何一方临时来不了又无法通知对方时，另一方就必须永远等下去。

顺着这条思路，教材给了一个著名的例子（两军问题）：

占据东、西两个山顶的蓝军 1 与蓝军 2 要协同攻击山谷中的白军。单独任一支蓝军打不过白军，两军协同则能取胜。蓝军 1 拟于次日正午发起攻击，用不可靠的信道发电文给蓝军 2，要求收到者回确认，但确认本身也可能丢失。**能否设计出一种协议，使双方 100%（而不是 99.999…%）确保协同？**

推演：蓝军 2 收到并回了确认，但它不知道这个确认对方收到没有——没收到的话蓝军 1 不敢进攻，此时蓝军 2 单独进攻必败。于是要等蓝军 1 的"对确认的确认"。而蓝军 1 同样关心自己这个确认有没有被收到，于是要"对（确认的确认）的确认"……无限循环。

**结论：在给定条件下不存在这样的协议。**

这个结论的价值不在结论本身，而在它划出了一条**下界**：任何基于不可靠信道的握手协议，都无法做到"双方对最后一条消息的到达达成共识"。TCP 的三次握手不是解决了这个问题，而是**接受了这个问题**——它把无限的确认链条截断在第三次，用"足够好"替代"绝对确定"。理解了这一点，[[04_计算机网络_CN/transport/tcp-connection.md|TCP 连接管理]]里"为什么是三次而不是两次、四次"就不再是一条要背的结论。

## 疑难点

**为什么互联网的网络层被设计为"不可靠"的？**

这是端到端原则的直接结果。IP 层只负责尽力而为地转发分组，不保证到达、不保证顺序、不保证不重复，可靠性交给运输层的 TCP。这样做换来三件事：

- **网络核心保持简单**。路由器只需查表转发，不必为每条连接维护状态，因而能做到极高的转发速率、也更容易扩展到全球规模
- **应用可以按需选择**。要可靠就用 TCP，要低时延就用 UDP。如果可靠性被强制做进网络层，实时音视频这类"宁可丢一帧也不要等"的应用就没有出路
- **可靠性本来就得在端上再做一遍**。即使每一跳链路都可靠，主机崩溃、缓存溢出、路由环路造成的丢失仍然存在——端到端的检查无论如何省不掉，那么在网络层再做一遍就成了纯粹的重复开销

**端到端通信和逐跳（点到点）通信有什么区别？**

端到端通信指源主机到目的主机之间跨越整个网络的通信，属运输层概念，通信双方是两端的进程；逐跳通信指一条链路两端相邻节点之间的通信，属数据链路层概念。一次端到端通信在路径上会经过多次逐跳转发。

网络层的位置比较微妙：**IP 的转发动作是逐跳的**（每个路由器只决定下一跳），但**IP 提供的服务是主机到主机的**（源 IP 到目的 IP 全程不变）。"动作逐跳、语义端到端"这两件事同时成立，正是[[04_计算机网络_CN/overview/packet-journey.md|数据包的网络之旅]]那一篇要逐跳拆开看的东西。

## 五层模型综合速查表

| 层次（自顶向下） | PDU | 核心功能（一句话） | 关键设备 | 寻址 | 典型协议 |
| --- | --- | --- | --- | --- | --- |
| 应用层 | 报文 | 给用户进程提供网络服务 | — | 进程标识（端口由运输层管） | HTTP、HTTPS、FTP、SMTP/POP3/IMAP、DNS、DHCP |
| 运输层 | 报文段 / 用户数据报 | **端到端**（进程到进程）传输，复用与分用 | — | 端口号 | TCP、UDP |
| 网络层 | IP 数据报 / 分组 | **主机到主机**寻址 + 路由转发 | 路由器、三层交换机 | IP 地址 | IP、ICMP、IGMP、ARP（按教材归此层）、OSPF、BGP、RIP |
| 数据链路层 | 帧 | **相邻节点**之间成帧 + 差错检测 + 介质访问控制 | 网桥、二层交换机 | MAC 地址 | 以太网（IEEE 802.3）、PPP、IEEE 802.11 |
| 物理层 | 比特 | 透明传输比特流 | 中继器、集线器（Hub） | — | RS-232、SONET/SDH 等 |

两条串起来的线索：

- PDU 串：**报文 → 报文段 → IP 数据报 → 帧 → 比特**
- 寻址三跃迁：**进程间（端口）→ 主机间（IP）→ 相邻节点间（MAC）**

## 判定一个动作属于哪一层

给一个具体行为定位到某一层，判据只有一条：**这个动作处理的最小数据单元是什么**。比特 → 物理层；帧 → 数据链路层；分组 / IP 首部 → 网络层；报文段 / 端口 → 运输层；应用语义 → 应用层。

| 行为 / 协议 / 设备 | 所属层 | 判断依据 |
| --- | --- | --- |
| 浏览器解析 URL 拼出 HTTP 请求 | **应用层** | 处理的是业务语义 |
| TCP 三次握手 | 运输层 | "建立连接"是 TCP 的行为，发生在两端进程之间 |
| 给分组加上目的 IP 并选下一跳 | 网络层 | 处理 IP 首部、做路由选择 |
| ARP 把 192.168.1.1 解析成 MAC | **网络层**（按教材） | 谢希仁版归在网络层；功能上跨链路层，但归属固定 |
| 把以太帧切成比特并加电平 | 物理层 | 处理的最小单元是比特 |
| 路由器丢弃 TTL = 0 的分组 | 网络层 | TTL 是 IP 首部字段 |
| 交换机按 MAC 表自学习转发 | 数据链路层 | 处理帧、看 MAC 地址 |
| 集线器把信号广播到所有端口 | 物理层 | 不识别帧，只放大转发信号 |
| TLS / SSL 加密 | 应用层（五层模型下） | OSI 中归表示层，TCP/IP 把表示层并入应用层 |
| DNS 把域名解析为 IP | 应用层 | 是一次完整的应用层请求-响应，虽然结果给下层用 |
| ICMP 差错报告（ping） | 网络层 | ICMP 报文虽封装在 IP 数据报里，但它是 IP 的配套协议 |
| DHCP 给主机分配 IP | 应用层 | 分的是 IP，但 DHCP 报文走 UDP/IP，本身是应用层协议 |
| 端口号 80 | 运输层 | 端口是运输层的寻址概念 |

最后三行值得单独记：**"这个协议处理的是什么"与"这个协议被谁使用"是两回事**。DNS、DHCP 处理的都是网络层信息，但它们自己是跑在 UDP 上的应用程序，所以归应用层；ARP 处理的是 MAC 地址，但它被 IP 直接调用、报文不封装在 IP 里，所以按教材归网络层。

## 设备能力对照表

| 设备 | 工作层 | 能识别 | 隔离冲突域 | 隔离广播域 |
| --- | --- | --- | --- | --- |
| 中继器 / 集线器 | 物理层 | 信号 | 否 | 否 |
| 网桥 / 二层交换机 | 数据链路层 | 帧（看 MAC） | **是** | 否（除非划 VLAN） |
| 路由器 / 三层交换机 | 网络层 | 分组（看 IP） | **是** | **是** |
| 网关 / 协议转换器 | 高层 | 应用语义 | 是 | 是 |

这张表不需要死记，它是从"设备处理到第几层"直接推出来的：

- **隔离冲突域 = 会不会存储转发**。集线器收到信号立刻向所有端口放大转发，两路信号照样会撞在一起；交换机必须先把整帧收下来、查表、再发出去，两个端口的传输在时间上天然分开，冲突就不存在了
- **隔离广播域 = 会不会转发广播帧**。交换机对目的 MAC 为全 1 的广播帧一律向所有其他端口泛洪，所以广播域不被切断；路由器只按目的 IP 查路由表，广播帧根本进不了它的转发流程

一句话：**层越高，"切"得越狠**——物理层什么都切不开，路由器既切冲突域也切广播域。

## 易混淆知识点

**1. OSI 与 TCP/IP 在网络层、传输层上正好相反**

OSI 的网络层**既支持面向连接也支持无连接**，传输层**只支持面向连接**；TCP/IP 的网络层**只有无连接**（IP），运输层**两种都有**（TCP 与 UDP）。这两行经常被记串，一个不容易记反的抓手是：**TCP/IP 把选择权交给了端**（网络层只提供一种最简服务，可靠与否由端上的 TCP/UDP 决定），而 OSI 把选择权留在了网络里。

**2. ARP 到底属于哪一层？**

408 教材（谢希仁版）把 ARP 放在**网络层**。从功能上看它做的是 IP → MAC 的映射，涉及链路层概念，所以争议长期存在。判据按教材统一为网络层即可；如果要理解为什么，看它的**被调用关系**：ARP 是 IP 转发流程的一部分（IP 要发帧才去问 MAC），且 ARP 报文不封装在 IP 数据报里，而是直接由链路层承载。

**3. "对等层通信"是逻辑上的**

物理上数据只能从上层往下层走、过物理链路、再往上层走；对等层之间没有直接的物理连接。所谓"第 n 层与对方第 n 层通信"，是指它们在逻辑上使用相同的协议处理数据。

**4. 服务和协议不能互换说法**

服务是纵向的（下层给上层提供），协议是横向的（对等实体之间的规则）。更进一步：**层内不被上层看见的功能不是服务**。所以"TCP 提供可靠传输服务"对，"TCP 提供三次握手服务"错。

**5. SDU 与 PDU 不是一一对应**

n-PDU=(n−1)-SDU 只描述最常见的不分片、不合并情形。**一个 SDU 可以划分为多个 PDU**（IP 分片、TCP 按 MSS 切分），**多个 SDU 也可以合成一个 PDU**（Nagle 算法攒包）。

**6. 传输媒体属于物理层吗？**

不属于。双绞线、光纤、无线信道在**物理层协议的下面**，有人称之为"第 0 层"。物理层规定的是接口的四大特性，不是介质本身。

**7. 五层模型是不是标准？**

不是。OSI 七层是国际标准，TCP/IP 四层是事实标准，**五层模型只是讲授原理时的折中**（综合两者优点）。但它是本站与考试的默认框架，答题时用五层不会有问题。

## 本节小结

- **分层的核心思想**：每层只关注自己的功能，向上层提供服务、使用下层服务。好处是模块化、接口标准化、易调试、利于标准化。
- **层数被两个方向夹住**：太少则功能过载、层内自发长出子结构；太多则每层一次封装（带宽开销）+ 一次跨层调用（处理开销），且职责开始重叠。判据是"这个功能有没有窄到能独立标准化的接口边界"——OSI 的表示层与会话层就是没守住边界的反例。
- **体系结构是抽象的定义，实现是具体的软硬件**。不能把某台具体设备说成一个体系结构。
- **OSI 七层**：应表会传网数物。概念清楚、理论完整，但复杂不实用；败因是出标准太晚、实现效率低、表示层与会话层功能过弱。
- **TCP/IP 四层**：应用层 / 运输层 / 网际层 / 网络接口层。**实质上只有上三层**——链路层没有属于 TCP/IP 的具体协议（那是 IEEE 802 的地盘），它只是"IP 需要的一个与网络的接口"。讲原理时用**五层模型**。
- **沙漏形状**：腰部只有一个 IP。**Everything over IP**（IP 之上可有多种运输层、多种应用）+ **IP over Everything**（IP 之下可跑多种网络），代价是 IP 本身极难演进。背后是"核心尽量简单、复杂性推到边缘"这条设计理念。
- **OSI 与 TCP/IP 在两层上正好相反**：OSI 网络层两种服务都有、传输层只面向连接；TCP/IP 网络层只无连接、运输层两种都有。设计顺序也相反（先模型后协议 vs 先协议后模型），这同时解释了 TCP/IP 的实用与不严谨（未清晰区分服务/接口/协议）。
- **五层各自的一句话职责**：应用层完成特定网络应用；运输层提供**通用**的进程间数据传输并做**复用/分用**；网络层为不同主机提供通信服务，两个任务是**生成转发表**与**按表转发**；数据链路层在相邻节点间成帧，**只检错不纠错，发现差错就丢弃**；物理层透明传输比特流，规定机械/电气/功能/规程四大特性，**传输媒体不在其内**。
- 三层通信粒度：**相邻节点（MAC）→ 主机到主机（IP）→ 进程到进程（端口）**。
- **PDU 是对等层之间的单位，SDU 是相邻层之间的单位，PCI 是首部（尾部）**。常规关系 n-SDU+n-PCI=n-PDU=(n−1)-SDU，但**一个 SDU 可拆成多个 PDU（分片 / 按 MSS 切分），多个 SDU 也可合成一个 PDU（攒包）**。
- **封装只发生在上四层**（物理层不加控制信息），**只有数据链路层既加首部又加尾部**（FCS 必须在数据之后）。
- **分层的固定开销**：以太网上 TCP/IP 的封装开销恒为 20+20+18=58 B。载荷 100 B 时有效载荷率仅 63%，载荷 1460 B 时达 96%。**1460 = 1500 − 20 − 20 就是按"把帧撑到刚好不分片"倒推出来的 MSS**。小报文开销占比高，正是 Nagle 算法与延迟确认存在的理由。
- **协议三要素：语法（格式）、语义（做什么）、同步（时序）**。协议是**水平**的（对等实体之间），服务是**垂直**的（下层给上层），接口 SAP 是相邻层交换信息的逻辑地点。
- **只有能被上层看见的功能才叫服务**；层内为实现协议做的事（重传、序号、校验）不是服务。由此得出协议对上层是**透明**的——上层只看得见服务，看不见协议。
- **服务的三个正交维度**：面向连接/无连接、可靠/不可靠、有应答/无应答。"面向连接"不自动等于"可靠"。
- **协议必须把所有不利条件事先估计到**。两军问题证明：在不可靠信道上，**不存在**能让双方对最后一条消息达成共识的协议。TCP 三次握手不是解决了它，而是**在第三次截断了无限的确认链条**。
- **网络层被设计成不可靠**的三个理由：核心保持简单可扩展、应用可按需选可靠或低时延、端到端检查本来就省不掉（做两遍是纯重复）。
- **IP 的动作是逐跳的，IP 提供的服务是端到端的**——这两件事同时成立。
- **定位一个动作属于哪一层，看它处理的最小数据单元**。注意"处理什么"与"被谁使用"是两回事：DNS/DHCP 处理网络层信息但自己跑在 UDP 上，归应用层；ARP 处理 MAC 地址但被 IP 直接调用、报文不封装在 IP 里，按教材归网络层。
- **设备能力可推不必背**：隔离冲突域 = 会不会**存储转发**（集线器不会、交换机会）；隔离广播域 = 会不会**转发广播帧**（交换机会泛洪、路由器不会）。层越高切得越狠。

## 教材出处

- 谢希仁《计算机网络》（第 7 版）印刷版 **p29** 给出协议的定义与三要素："这些为进行网络中的数据交换而建立的规则、标准或约定称为网络协议"；三要素为"**语法**，即数据与控制信息的结构或格式；**语义**，即需要发出何种控制信息，完成何种动作以及做出何种响应；**同步**，即事件实现顺序的详细说明"。同页说明这里的同步"不是狭义的（即同频或同频同相）而是广义的……因而同步含有时序的意思"。
- 同书印刷版 **p31** 区分体系结构与实现："**体系结构是抽象的，而实现则是具体的**，是真正在运行的计算机硬件和软件"，并以"可以走进一个明代的建筑物中，但却不能走进一个明代的建筑风格之中"作比。同页说明 TCP/IP"从实质上讲……只有最上面的三层，因为最下面的链路层并没有属于 TCP/IP 体系的具体协议"，以及讲授原理时"综合 OSI 和 TCP/IP 的优点，采用……**五层协议的体系结构**"。
- 同书印刷版 **p31–p33** 逐层给出五层职责：运输层"负责向两台主机中进程之间的通信提供**通用的**数据传输服务"并具有复用与分用功能（p32）；网络层的两个任务是"生成一个用来转发分组的转发表"与"依据转发表中指明的路径把分组转发到下一个路由器"（p32）；数据链路层"如发现有差错，数据链路层就**简单地丢弃这个出了差错的帧**"（p32）；物理层"解释比特代表的意思，不是物理层的任务"，且传输媒体"并不在物理层协议之内，而是在物理层协议的下面。因此也有人把物理层下面的物理传输媒体当作**第 0 层**"（p33）。
- 同书印刷版 **p34**（1.7.4 实体、协议、服务和服务访问点）给出本篇三概念辨析的全部依据：实体"表示任何可发送或接收信息的硬件或软件进程"；"协议是'水平的'……但服务是'垂直的'"；"**并非在一个层内完成的全部功能都称为服务。只有那些能够被高一层实体'看得见'的功能才能称之为'服务'**"；"下面的协议对上面的实体是透明的"；服务访问点 SAP"实际上就是一个逻辑接口，有点像邮政信箱"。同页明确 SDU 与 PDU 的关系不是一一对应："**可以是多个 SDU 合成为一个 PDU，也可以是一个 SDU 划分为几个 PDU**"。
- 同书印刷版 **p35** 给出"协议必须把所有不利的条件事先都估计到，而不能假定一切都是正常的和非常理想的"，并以"不见不散"为反例；同页【例 1-1】即两军问题，结论是"在本例题给出的条件下，**没有一种协议可以使蓝军 1 和蓝军 2 能够 100% 地确保胜利**"。
- 同书印刷版 **p37** 解释沙漏形状："IP 层可以支持多种运输层协议……而不同的运输层协议上面又可以有多种应用层协议（所谓的 everything over IP），同时 IP 协议也可以在多种类型的网络上运行（所谓的 IP over everything）"，并指出该图"反映出互联网的一个十分重要的设计理念，这就是**网络的核心部分越简单越好，把一切复杂的部分让网络的边缘部分去实现**"。
- 同书印刷版 **p36** 列出对 TCP/IP 体系结构的批评："这个体系结构没有清晰地阐明区分开服务、接口和协议之间的关系，而链路层并非真正的一个层次，而仅仅是强调了 IP 层需要这样一个与网络的接口。"
- 同书印刷版 **p33–p34** 说明 PDU 术语来历："OSI 参考模型把对等层次之间传送的数据单位称为该层的**协议数据单元 PDU**"，并给出"每经过一层就包上一个新的信封，写上必要的地址信息"的封装比喻。[[04_计算机网络_CN/overview/network-overview.md|上一篇计算机网络概述]][[04_计算机网络_CN/overview/packet-journey.md|下一篇数据包的网络之旅]]
