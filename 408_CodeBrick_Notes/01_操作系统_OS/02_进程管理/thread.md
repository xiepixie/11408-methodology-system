# 线程（内核级与用户级）

2026 大纲 **二（一）3 线程的实现**，补充说明点名**内核支持的线程**与**线程库支持的线程**两类。

## 速查

| **考纲用词 ↔ 通行缩写** | 内核支持的线程 = 内核级线程 **KLT**；线程库支持的线程 = 用户级线程 **ULT** |
| --- | --- |
| 🔴 **分界只有一刀：内核认不认识线程** | 能不能用多核、一个阻塞会不会拖垮全体、切换要不要进内核态，全部由这一刀推出来 |
| **线程库 / 运行时系统** | 用户级线程管理的例行程序包（创建、调度、管理），是这些线程的**运行支撑环境**——线程的"操作系统"是这个库而不是内核。汤小丹称之为**运行时系统**，一组**驻留在用户空间**的函数集合 |
| 🔴 **ULT 切换为什么快** | 存现场进**线程自己的堆栈** → 按库内算法选一个就绪线程 → 装入其 CPU 状态 → 切换栈指针与 PC。**不陷入内核、无模式切换、不换地址空间** |
| 🔴 **"一阻塞全阻塞"的物理来源** | ULT **不能直接使用系统调用**，请求要交给运行时系统代发，而它发出的是一个**进程级**的阻塞式调用，内核眼里只有进程 ⇒ 整个进程被阻塞 |
| 🔴 **ULT 用不了多核** | 内核只调度它看得见的对象，整个进程同一时刻只能占一个核 |
| **ULT 的三条优点** | 切换不进内核；**调度算法可以是进程专用的**（与 OS 的低级调度无关）；可在**不支持线程机制的 OS** 上实现 |
| **Jacketing 技术** | 孙钟秀给出的补救：改造系统调用，一发现线程要等待就把控制权交回用户级线程调度程序另选线程。需要改动系统调用，不是免费的 |
| **KLT 的组织** | 内核在**内核空间**为每个线程建 TCB；典型组织是每进程一个**任务数据区 PTDA**，内含若干 TCB 空间；撤销线程时可**保留 TCB 供复用**以摊薄创建开销 |
| **KLT 的代价** | 切换要做**用户态→内核态→用户态**模式切换；每个线程都要在内核建 TCB、分配栈，创建与管理开销大于 ULT |
| 🔴 **调度单位不同导致公平性反转** | 进程 A 有 1 个线程、B 有 100 个：ULT 按进程分时间片，A 那个线程比 B 的每个快 100 倍；KLT 按线程分，B 拿到的 CPU 时间是 A 的 100 倍。**"哪种更公平"取决于把谁当公平的对象** |
| **组合方式的中间层 = LWP** | 轻型进程（内核控制线程）：用户级线程连到 LWP 上才具有内核支持线程的属性，每个 LWP 再连一个内核线程。内核只看到若干 LWP，**LWP 隔离了内核与用户级线程** |
| 🔴 **不与内核通信就不需要 LWP** | 一旦要通信，每个要通信的线程都得占一个 LWP；LWP 做成缓冲池即**线程池**，**只有当前连在 LWP 上的线程才能与内核通信** |
| 🔴 **"多对一为什么一阻塞全阻塞"** | 多个 ULT 共用**一个**内核控制线程 ⇒ 它是内核眼里唯一的调度对象 ⇒ 任一 ULT 发起阻塞式调用，阻塞的是这个唯一载体 ⇒ 其余 ULT 没有可运行的内核载体。**判据浓缩成一句：数一数这些用户线程背后有几个内核调度对象** |
| 🔴 **纯用户级线程 = 多对一模型** | 所以两处的结论字字相同，不是两条独立的知识 |
| 🔴 **一对一的开销大在创建，不在切换** | 每建一个用户线程就要建一个内核线程，所以必须限制系统线程总数 |
| 🔴 **线程切换便宜，最大一笔是"不换地址空间"** | 同进程线程共享页表 ⇒ **PTBR 不动、TLB 不失效**、Cache 工作集不换人；进程切换要换页表并（无地址空间标识时）整体刷 TLB，切换后有一段 TLB 缺失密集期。判据就一句：**这次切换换不换页表** |

## 一、两类线程的分界

| 考纲用词 | 教材用词 | 缩写 | 分界判据 |
| --- | --- | --- | --- |
| **内核支持的线程** | 内核支持线程 KST / 内核级线程 | **KLT** | 线程的创建、阻塞、撤销、切换**都在内核空间实现**，内核为每个线程建 TCB，调度以线程为单位 |
| **线程库支持的线程** | 用户级线程 | **ULT** | 线程的创建、撤销、同步、调度**全部由用户空间的线程库完成**，内核完全不知道线程存在，调度仍以进程为单位 |

TCB 里具体存哪些字段、与 PCB 有什么对应关系，见 [[01_操作系统_OS/02_进程管理/process-control.md|进程的组织与控制]]。

## 二、两类线程的优缺点，逐条从那一刀推出来

|  | ULT（线程库支持） | KLT（内核支持） |
| --- | --- | --- |
| 切换开销 | **不需转入内核空间**，管理数据结构与切换代码都在用户空间 | 要经"用户态→内核态→用户态"模式切换，但不换地址空间，仍比进程切换快 |
| 调度算法 | **可以是进程专用的**，不同进程各选各的 | 归内核的低级调度管 |
| 移植性 | 可在**不支持线程机制的 OS** 上实现（属用户程序的一部分） | 依赖内核支持 |
| 一个线程阻塞 | **整个进程阻塞**（大多数系统调用是阻塞型的） | 内核可**调度同进程的其他线程**占用处理机 |
| 多处理机 | **用不了**：内核每次只给一个进程分配一个 CPU | 可**同时调度同一进程的多个线程并行执行** |
| 创建与管理开销 | 小 | 大：每个线程都要建 TCB、分配栈空间 |
| 附带 | 时间片按进程分配，对进程内线程数不敏感 | **内核自身也可采用多线程技术** |

## 三、组合方式与三种多线程模型

内核支持多个内核线程的建立、调度和管理，同时也允许应用程序建立、调度和管理用户级线程；**若干内核支持线程对应多个用户级线程**，由用户级线程通过时分多路复用内核支持线程来实现，程序员可按应用需要和机器配置调整内核支持线程的数目。效果是两个缺点同时被拿掉：同进程的多个线程**可以在多处理机上并行**，且**阻塞一个线程不必阻塞整个进程**。

实现组合方式的中间层是**内核控制线程**，又称**轻型进程 LWP**：

- 每个进程可拥有多个 LWP，**每个 LWP 有自己的数据结构（如 TCB），包括线程标识符、优先级、状态、栈和局部存储区**——正因为它自带这一套，它才是内核看得见、调度得动的实体；
- LWP 可通过系统调用获得内核服务。一个用户级线程只要连接到某个 LWP 上，就具有了内核支持线程的**全部属性**；
- 用户级线程可能很多，不可能配同样多的 LWP，于是把 LWP 做成缓冲池即**线程池**。多个用户级线程可多路复用同一个 LWP，但**只有当前连接在 LWP 上的线程才能与内核通信**，其余的或阻塞、或等待 LWP。

| 模型 | 映射关系 | 能否用多核 | 一个线程阻塞的后果 | 主要代价 |
| --- | --- | --- | --- | --- |
| **多对一** | 多个 ULT → 1 个内核控制线程 | **不能**：任一时刻只有一个线程能访问内核 | **整个进程都被阻塞** | 并发度受限 |
| **一对一** | 1 个 ULT → 1 个 KLT | 能：多线程可并行运行在多处理机上 | 只阻塞该线程，可调度另一个线程运行 | 每建一个用户线程就要建一个内核线程，开销大，需限制系统线程总数 |
| **多对多** | m 个 ULT → n 个 KLT（m ≥ n） | 能 | 只阻塞该线程 | 实现复杂 |

## 四、线程切换 vs 进程切换：开销的量化口径

| 这笔账 | 用户级线程切换 | 同进程内的内核级线程切换 | 进程切换 |
| --- | --- | --- | --- |
| 保存/恢复通用寄存器、PC、PSW | 要（存进线程自己的栈） | 要（存进 TCB） | 要（存进 PCB） |
| **用户态↔内核态模式切换** | **不需要** | 需要（一进一出） | 需要 |
| **切换地址空间**（换页表基址寄存器 PTBR） | **不需要** | **不需要** | **需要** |
| **TLB 是否失效** | **不会** | **不会** | **会**（未做地址空间标识时须整体刷新，此后一段时间连续 TLB 缺失） |
| Cache 命中率 | 基本不受影响 | 基本不受影响 | 显著下降（工作集换人） |

地址变换的细节见 [[01_操作系统_OS/03_内存管理/paging.md|页式管理]]，切换过程本身见 [[01_操作系统_OS/02_进程管理/context-switch.md|上下文切换机制]]。把三种切换的开销算成具体数字，看清差距落在哪一笔上（想量化"尽量把协作任务放进同一个进程"时展开）

设某单处理机实测：一次模式切换 0.4 µs；保存并恢复一套执行现场 1.2 µs；切换 PTBR 0.3 µs；TLB 整体失效导致的后续重填折算 3.0 µs；用户级线程切换全程在用户态，实测 0.5 µs。

按上表逐笔加——每种方案只把它真正发生的那几笔算进去：tULT=0.5 μs(纯用户态，无模式切换、无地址空间切换)tKLT=2×0.4⏟进出内核+1.2⏟现场=2.0 μst进程=2×0.4⏟进出内核+1.2⏟现场+0.3⏟换 PTBR+3.0⏟TLB 重填=5.3 μs

KLT 比进程切换少 3.3 µs，全部来自**同进程线程共享页表，PTBR 不动、TLB 不失效**。10000 次切换：ULT 5 ms、KLT 20 ms、进程 53 ms，比为 **1 : 4 : 10.6**。

若其中 30% 必须跨进程、70% 是同进程内的 KLT 切换，必须按比例加权（两种切换的单次代价差 2.65 倍，不能取端点平均）：t¯=0.3×5.3+0.7×2.0=2.99 μs,T=29900 μs=29.9 ms

比纯 KLT 方案多 **49.5%**——仅 30% 的切换跨了进程，总开销就涨了近一半。

**变一个条件结论就变**：若 TLB 带地址空间标识（进程切换无须整体刷新），t进程 降为 2.3 μs，与同进程线程切换只差 0.3 µs，那 49.5% 会缩到 4.5%。**"进程切换贵"贵在 TLB 那一笔上。**

## 本节小结

- 两类线程的分界只有一刀——**内核认不认识线程**；能不能用多核、一阻塞会不会全阻塞、切换进不进内核态，全是它的推论。
- ULT 的切换与调度都在用户空间完成因而最快、还能自选调度算法，代价是**不能直接发系统调用**（一阻塞全阻塞）且**用不了多核**；KLT 反之，代价是模式切换与创建开销。组合方式用 **LWP** 当中间层同时拿掉两个缺点。
- **纯用户级线程等价于多对一模型**；线程切换比进程切换便宜，最大的一笔是**不换地址空间**（PTBR 不动、TLB 不失效）。教材出处

- 汤小丹《计算机操作系统》2.7.2、2.7.3，印刷 p77–p78：线程仅拥有 TCB、程序计数器、一组寄存器和堆栈；线程的三种状态；"在把某个进程挂起时，该进程中的所有线程也都将被挂起"
- 汤小丹《计算机操作系统》2.8.1 线程的实现方式，印刷 p79–p81：内核支持线程 KST 的四条优点与模式切换缺点；用户级线程 ULT 的三条优点与两条缺点（系统调用阻塞问题、不能利用多处理机）；组合方式 ULT/KST；三种多线程模型
- 汤小丹《计算机操作系统》2.8.2 线程的实现，印刷 p81–p82：内核支持线程的任务数据区 PTDA 与 TCB 组织，撤销线程时保留 TCB 供复用；运行时系统的定义与用户态切换步骤；轻型进程 LWP 与线程池
- 孙钟秀、费翔林《操作系统教程》（第 6 版）2.4.2 内核级线程与用户级线程，印刷 p67–p68：线程库是"用户级线程管理的例行程序包，主要功能有线程的创建、调度、管理"，是线程的运行支撑环境；Jacketing 技术
