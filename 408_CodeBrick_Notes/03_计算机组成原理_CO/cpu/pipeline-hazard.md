# 流水线冒险及其处理

## 大纲定位

**五（六）3　结构冒险、数据冒险和控制冒险的处理**

要求：能判断给定指令序列中存在哪一类冒险、发生在哪两条指令的哪两段之间，并给出阻塞、转发、分支预测等处理办法及其代价。

流水线的基本结构见 [[03_计算机组成原理_CO/cpu/pipeline-basic.md|指令流水线的基本概念与实现]]。

## 知识框架

本节回答四个问题：

- 三类冒险的根源各是什么？为什么恰好是三类？
- 数据冒险的三种相关，哪些在按序流水线中真会出问题？
- 转发能解决什么，不能解决什么？
- 控制冒险的代价由什么决定？

## 一、三类冒险的根源

流水线的前提是"多条指令同时在机器里跑"。一旦同时存在多条指令，就会在三个层面上出冲突：

| 冒险类型 | 根源 | 冲突的是 |
| --- | --- | --- |
| **结构冒险** | 硬件资源不够 | **部件** |
| **数据冒险** | 指令间存在数据依赖 | **数据** |
| **控制冒险** | 分支改变了执行流 | **指令地址** |

> [!TIP]
>

三类冒险不是列举出来的，是穷举出来的

一条指令要顺利执行，需要三件东西各就各位：**要用的部件空着、要读的数据已备好、自己确实该被执行**。

三个条件各对应一类冒险，不多不少。

## 二、结构冒险

**定义**：两条指令在同一时钟周期争用同一硬件资源。

### 场景一：取指与访存撞车

lw 指令在 MEM 段访问数据存储器，而此时后面第三条指令正在 IF 段取指令。若指令和数据放在同一个存储器里，两者冲突。

**解决**：指令存储器和数据存储器**分开**（哈佛结构）。这就是为什么流水线 CPU 必须用分离的 I-Cache 和 D-Cache。

### 场景二：寄存器堆的读写撞车

一条指令在 WB 段写寄存器堆，另一条指令同时在 ID 段读寄存器堆。

**解决**：让寄存器堆支持**前半周期写、后半周期读**。

> [!WARNING]
>

这个假设会改变停顿周期数

"前半周期写、后半周期读"不只是消除结构冒险，它同时也**减少了数据冒险的停顿数**：同一周期内先写后读⇒WB 和 ID 可以落在同一拍

后面计算气泡数时会看到，这个假设成立与否，答案相差整整一个周期。这是本节最容易被忽略的前提。

## 三、数据冒险

**定义**：后续指令需要用到前面指令尚未产生的结果。

### 三种相关

| 类型 | 全称 | 定义 | 示例 |
| --- | --- | --- | --- |
| **RAW**（写后读） | Read After Write | 指令 j 要读指令 i 将写入的寄存器 | I1: `ADD R1,R2,R3` → I2: `SUB R4,R1,R5` |
| WAR（读后写） | Write After Read | 指令 j 要写的寄存器，指令 i 还没读完旧值 | I1: `ADD R3,R1,R2` → I2: `SUB R1,R4,R5` |
| WAW（写后写） | Write After Write | i 和 j 写同一寄存器，语义要求 j 的结果是最终值 | I1: `ADD R1,R2,R3` → I2: `SUB R1,R4,R5` |

> [!CAUTION]
>

按序流水线中只有 RAW 是真问题

原因是**读发生在 ID 段、写发生在 WB 段，且指令严格按序前进**：

- **WAR**：i 的读（ID）永远早于 j 的写（WB），因为 i 排在 j 前面，且 ID 在 WB 之前。不可能出问题
- **WAW**：写的顺序天然等于程序顺序，最终值必定是 j 的。不可能出问题
- **RAW**：j 的读（ID）**可能早于** i 的写（WB）——i 只领先几拍，而 ID 段离 WB 段有三拍距离。**会出问题**

三种相关只有 RAW 会真正违反语义，这就是它被称为**真相关**（true dependence）的原因。

**乱序（非按序）流水线**中三种都可能出现：

- **WAR**：若 j 因乱序先完成写回，i 就会读到错误的新值
- **WAW**：若 i 因乱序后完成写回，最终值变成 i 的结果，违反程序语义

WAR 和 WAW 被称为**名相关**（name dependence）——本质不是数据流依赖，只是两条指令恰好用了同一个寄存器名。因此可以用**寄存器重命名**消除：把逻辑寄存器映射到不同的物理寄存器，两条指令实际操作不同的存储位置，冲突自然消失。

**RAW 无法用重命名消除**，因为它是真实的数据流动。

### 处理办法一：阻塞（插入气泡）

让后面的指令停在原地等，直到数据可用。

```
I1: ADD R1, R2, R3    # R1 在 EX 段（T3）末尾算出，T5 才写回
I2: SUB R4, R1, R5    # 原本 T3 就要在 ID 段读 R1
```

| 指令 / 周期 | T1 | T2 | T3 | T4 | T5 | T6 | T7 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| I1: `ADD R1,R2,R3` | IF | ID | EX | MEM | **WB** |  |  |
| I2: `SUB R4,R1,R5` |  | IF | 停 | 停 | **ID** | EX | MEM |

I2 原本在 T3 进入 ID 读 R1，但 I1 要到 T5 才写回。若寄存器堆支持**前半周期写、后半周期读**，I2 的 ID 可以和 I1 的 WB 同在 T5 完成——ID 从 T3 推迟到 T5，**停顿 2 个周期**。

若寄存器堆**不支持**同周期先写后读，ID 只能等到 T6，**停顿 3 个周期**。

两种假设都成立，答案却差一拍。判断停顿数之前，必须先确定寄存器堆的这个性质。

### 处理办法二：数据转发

既然 ALU 的结果在 EX 段末尾就已经算出来了，何必等它绕一圈写回寄存器堆再读出来？

**转发**（forwarding，也叫旁路 bypassing）就是把结果从流水段寄存器直接送到需要它的部件输入端：

| 指令 / 周期 | T1 | T2 | T3 | T4 | T5 |
| --- | --- | --- | --- | --- | --- |
| I1: `ADD R1,R2,R3` | IF | ID | **EX** | MEM | WB |
| I2: `SUB R4,R1,R5` |  | IF | ID | **EX** | MEM |
| 转发 |  |  | └──→ | I1 的 EX 结果送入 I2 的 EX 输入 |  |

**大部分 RAW 相关都能被转发完全消除，一个气泡都不用插。**

> [!TIP]
>

转发的判据：数据"产生"的时刻是否早于"需要"的时刻

转发能不能救，只看两个时间点：数据在哪一段末尾产生vs.数据在哪一段开头被需要

只要产生不晚于需要，就能转发；晚了，就必须先停顿，把时间差抹平再转发。

ALU 结果在 EX 末产生、下一条在 EX 初需要——刚好够，所以能救。

### 转发救不了的情况：lw-use 相关

```
I1: lw  R1, 0(R2)     # R1 在 MEM 段（T4）末尾才拿到
I2: ADD R3, R1, R4    # I2 的 EX 段在 T4 开头就要 R1
```

数据 T4 末才有，却要在 T4 初使用——**晚了整整一拍**，转发来不及。必须先停 1 拍：

| 指令 / 周期 | T1 | T2 | T3 | T4 | T5 | T6 | T7 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| I1: `lw R1,0(R2)` | IF | ID | EX | **MEM** | WB |  |  |
| I2: `ADD R3,R1,R4` |  | IF | ID | 停 | **EX** | MEM | WB |
| 转发 |  |  |  | └──→ | MEM/WB 送入 EX 输入 |  |  |

**load-use 相关是数据冒险中唯一即使有转发也必须停顿的情形**，代价是 1 个周期。

这也解释了编译器为什么会在 `lw` 后面插入一条无关指令（指令调度）——把那一拍填上有用的活，停顿就被隐藏了。图 6.11　存在数据冒险的流水线例子（袁春风《计算机组成与系统结构》第 3 版，见文末教材出处）

图中 add 在 Wr 段才写回 `$1`，而随后四条指令都要读 `$1`（灰底的 Reg 段）。斜线标出的是数据依赖：前两条读到的是旧值（真冒险），第三条正好在同一周期先写后读，第四条已经在写回之后。

**判冒险要精确到"哪两条指令的哪两段落在同一周期"**，不能只看寄存器名相同——名字相同但时间错开的，根本不是冒险。

## 四、控制冒险

**定义**：遇到分支指令时，流水线不知道下一条该从哪里取，已经取入的后续指令可能全是错的。

| 指令 / 周期 | T1 | T2 | T3 | T4 | T5 |
| --- | --- | --- | --- | --- | --- |
| `BEQ R1,R2,target` | IF | ID | **EX（判定）** | MEM | WB |
| 顺序指令 I2 |  | IF | ID | flush |  |
| 顺序指令 I3 |  |  | IF | flush |  |
| 目标地址指令 T |  |  |  | IF | ID |

分支在 EX 段才确定，此时流水线已经按顺序取了 I2、I3。若实际发生跳转，这两条必须清除（flush），**代价 2 个周期**。

> [!TIP]
>

控制冒险的代价 = 分支结果确定得有多晚代价（周期数）=判定所在段的编号−1

- 在 **EX 段**判定（标准五段）：已取入 2 条错误指令，代价 **2 周期**
- 硬件把比较器和地址计算**提前到 ID 段**：只取入 1 条，代价降为 **1 周期**

因此优化控制冒险的方向永远是同一个——**让分支结果尽早出来**。

### 处理办法一：延迟分支

把分支指令**之后的一条或多条指令**定义为"延迟槽"，这些指令无论分支是否发生**都会执行**。

| 指令 / 周期 | T1 | T2 | T3 | T4 | T5 | 说明 |
| --- | --- | --- | --- | --- | --- | --- |
| `BEQ R1,R2,target` | IF | ID | EX | MEM | WB | 分支本身 |
| 延迟槽指令 D |  | IF | ID | EX | MEM | 跳不跳都执行 |
| 目标或顺序后继 |  |  |  | IF | ID | 从这里开始取正确路径 |

延迟槽不是"把分支延后执行"，而是**体系结构规定分支后一条指令一定执行**。编译器负责往里塞一条无副作用且有用的指令；塞不进去才填 NOP。

> [!WARNING]
>

延迟分支在现代处理器中已被淘汰

它有两个致命问题：

- **延迟槽的数量被写进了指令集**。流水线一加深，需要的延迟槽变多，但旧程序只填了一个——指令集与实现细节绑死了
- 编译器往往找不到合适的指令可填，只能填 NOP，等于没省

它是特定年代的产物，属于"用软件迁就硬件"。现代处理器一律改用分支预测，把复杂性留在硬件里。

### 处理办法二：分支预测

**静态预测**——预测结果与运行时历史无关：

| 策略 | 适合 |
| --- | --- |
| 总是预测不发生 | **前向分支**（if 的条件跳转，通常不跳） |
| 总是预测发生 | **后向分支**（循环回边，通常跳） |
| 按跳转方向预测 | 向后预测发生、向前预测不发生，综合上面两条 |

第三条之所以有效，是因为**循环的回边一定是向后跳的**，而循环体通常要执行很多次。这是一条零成本却相当准的规则。

**动态预测**——依据运行时的历史记录：

- **1 位预测器**：记录上次是否发生，本次按上次结果预测
- **2 位预测器**（饱和计数器）：四个状态，需要**连续错两次**才改变预测方向图 6.23　两位预测位的状态转换（袁春风《计算机组成与系统结构》第 3 版，见文末教材出处）

四个状态排成一条线：强发生(11) ↔ 弱发生(10) ↔ 弱不发生(01) ↔ 强不发生(00)。**预测正确就往本方向的"强"端走一格**（到头不动），**预测错误就往反方向退一格**。

> [!TIP]
>

为什么需要两位

关键在于**连错两次才翻转预测方向**。考虑一个循环：它连续很多次"发生"，只有最后一次退出时"不发生"。

- **1 位预测器**：最后那次错误立刻把预测翻成"不发生"，下一轮循环第一次又错——**一个循环错两次**
- **2 位预测器**：最后那次错误只是从"强发生"退到"弱发生"，方向没变，下一轮第一次仍预测"发生"，是对的——**一个循环只错一次**

这就是 2 位预测器更准的全部原因：**它对偶发的例外有容忍度**，不会因为一次意外就推翻长期规律。

## 例题

**例 1**：某程序中分支指令占 20%，采用 2 位预测器，预测准确率 90%，预测错误代价 2 个周期。求因分支导致的额外 CPI 与实际 CPI。额外 CPI=0.20×(1−0.90)×2=0.04

若理想 CPI =1，则实际 CPI=1.04。

可以看出：**分支带来的损失同时取决于三个量**——分支频率、预测准确率、错误代价。任一项改善都能降低损失，而流水线越深，第三项越大，预测准确率的价值也就越高。

**例 2**：设某段程序中 30% 的指令是 load，其中一半紧跟着使用其结果的指令；分支指令占 15%，预测准确率 85%，错误代价 2 周期。求实际 CPI。

load-use 停顿：0.30×0.5×1=0.15

分支停顿：0.15×(1−0.85)×2=0.045CPI=1+0.15+0.045=1.195

两类冒险的贡献可以直接相加，因为它们发生在不同的指令上。

## 易混淆知识点

**1. RAW / WAR / WAW 什么时候需要处理？**

按序流水线**只需处理 RAW**。WAR 和 WAW 在按序流水线中不会出问题——指令严格按程序顺序经过各段，读永远早于后面指令的写，写的先后顺序也天然正确。

只有在**乱序执行**的处理器中，WAR 和 WAW 才成为真问题，且可以用寄存器重命名消除。

**2. 转发能解决所有 RAW 吗？**

不能。**load-use 相关**必须插入 1 个气泡，因为 lw 在 MEM 段末尾才拿到数据，而下一条指令的 EX 段在同一周期开头就需要它。

判据始终是那一条：数据产生的时刻是否早于需要的时刻。

**3. 分支预测错误的代价到底是几个周期？**

取决于分支结果在**哪个阶段确定**。标准五段流水线在 EX 段判定，已取入 2 条错误指令，代价 2 周期；若硬件把比较提前到 ID 段，代价降为 1 周期。

**4. 插入气泡和 flush 是一回事吗？**

不是，两者的方向相反：

|  | 插入气泡（stall） | 清除（flush） |
| --- | --- | --- |
| 场合 | **数据**冒险 | **控制**冒险预测错误 |
| 做什么 | 让后面的指令**停在原地等** | 把已进入流水线的错误指令**作废** |
| 那些指令 | 之后还会正常执行 | **永远不会执行** |

**5. 结构冒险为什么在标准五段流水线里不常提？**

因为已经被设计消除了：指令存储器与数据存储器分开、寄存器堆前半周期写后半周期读。这两项措施把结构冒险提前解决在了结构设计里，所以讨论时主要剩下数据冒险和控制冒险。

## 本节小结

- 三类冒险对应三个条件：**部件空着、数据备好、该被执行**，穷举而非列举
- **按序流水线中只有 RAW 是真问题**；WAR、WAW 是名相关，可用**寄存器重命名**消除，且只在乱序时出现
- 转发的判据：**数据产生的时刻是否早于被需要的时刻**
- **load-use 是唯一转发也救不了的数据冒险**，必须停 1 拍
- 寄存器堆"前半周期写、后半周期读"这个假设，直接决定停顿是 2 拍还是 3 拍
- 控制冒险代价 = **判定所在段编号 −1**；优化方向永远是让分支结果尽早出来
- **延迟分支已被淘汰**——延迟槽数量被写死进指令集，流水线加深后无法适配
- 2 位预测器更准，是因为它**对偶发例外有容忍度**，不会因一次意外推翻长期规律
- 结构冒险靠**哈佛结构 + 寄存器堆先写后读**在设计阶段就消除了
