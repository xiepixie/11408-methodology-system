## 知识框架

学完 BF 和 KMP 之后，有个朴素的疑问应该会冒出来：

**所有搜索引擎、所有 IDE 的全局搜索、所有文档站的 Ctrl+K，背后用的真的是 KMP 吗？**

不是。本节回答 4 个问题：

- "全文搜索"和查找章里的"按关键字查找"差在哪？为什么顺序查找、折半查找都干不了这件事？
- 把 BF / KMP 套上"遍历所有文档"的外层循环，复杂度各是多少？KMP 到底提速了哪一段？
- 倒排索引凭什么再快两个数量级？它用的是哪些已经学过的数据结构？
- 既然倒排索引这么好，为什么大纲不教它？

## 先把"全文搜索"的需求说清楚

给定：

- 一份**语料库**（corpus）——一堆文档，每篇有标题和正文
- 一个**查询串**（query）——用户输入的几个字

要求：

- 返回所有"包含"该 query 的文档（"包含"可以定义成含子串，也可以定义成分词后命中）
- 按相关性排序
- 越快越好（用户每敲一个字就想看到新结果）

这跟查找章里讲的"在一批关键字里找等值元素"是**两回事**：

| 场景 | 关键字形态 | 比较语义 | 可用算法 |
| --- | --- | --- | --- |
| 六（一）～（七）的查找 | 单值（数字、字符串整体） | `==`（或按序比大小） | 顺序查找、折半查找、树形查找、散列表 |
| 全文搜索 | 整篇文档的字符流 | "是否含某段连续子串" / "是否含某个词项" | BF、KMP、倒排索引 |

**顺序查找和折半查找做不了全文搜索**，原因很具体：

- **顺序查找**比的是"关键字是否等于给定值"。文档正文不是一个关键字，`doc.body == "哈希"` 永远为假。
- **折半查找**还额外要求**有序**且能按序比大小。文档集合按什么排序？按正文的字典序排完，"含子串"这个性质在有序序列上**不具有单调性**——含 `"哈希"` 的文档不会聚成一段连续区间，二分的前提直接不成立。

能做"含子串"判断的，只有[串这一章的两个老朋友](./kmp.html)：BF 和 KMP。

## BF 做全文搜索：把每篇文档扫一遍

最朴素的做法，就是把 BF 套进"遍历所有文档"的外层循环：text

```
对语料库中每篇文档 doc：
    对 doc.body 中每个起始位置 i：
        从 i 开始逐字符比较 pattern
        若全部相等，则 doc 命中，跳出
```

复杂度（N 篇文档，每篇长 n，query 长 m）：

- **单篇文档 O(n⋅m)**：候选起始位置有 n−m+1≈n 个，每个位置最坏比 m 次。来历与推导见 [BF 算法](./bf.html)的复杂度一节。
- **整个语料 O(N⋅n⋅m)**：外层再乘 N。

代入这个博客的实际规模：百余篇文章、平均每篇约 5000 字符、query 取 4 个字，最坏约100×5000×4=2000000 次字符比较

在普通笔记本上是几十毫秒级——**能用，但用户每敲一个字都要等这么久，体感已经明显卡顿了**。

## KMP 做全文搜索：把单篇扫描提速

KMP 的本质是**主串指针永不回退**：失配时按 next 数组把模式指针退到合适位置，主串指针 i 始终向前走。把它套进同样的外层循环：text

```
预处理 pattern 得 next 数组（O(m)，只依赖 pattern）
对语料库中每篇文档 doc：
    用 KMP 扫描 doc.body（O(n)）
```

- **单篇文档 O(n+m)**
- **整个语料 O(m+N⋅n)**

这里有个值得单独指出的工程细节：**next 数组只依赖模式串，与被扫描的文档无关**，所以它应该在循环外算一次，而不是每篇文档重算。写成循环内重算就变成 O(N⋅(n+m))——量级上因为 m≪n 看不出差别，但这是 KMP"预处理与扫描分离"这一结构的直接推论，值得在写代码时留意。（本站搜索框里的实现为了让每种算法各自独立、便于对照，`next` 是在每篇文档内重算的。）

把上面的数字换算一下：100×5000=500000 次比较，**约为 BF 的四分之一**——这个 4 正是 m 的值，符合 O(Nnm)→O(Nn) 的预期。

听起来不错，但**两个本质问题一个都没解决**：

- **每次 query 都要重扫所有文档。** 无论用户输入什么，都要把整个语料从头扫到尾。O(N⋅n) 里的 N⋅n 是**整个语料的总字符数**——这意味着响应时间随语料规模线性增长，语料翻倍就慢一倍。
- **没有评分。** BF 和 KMP 给的答案是"命中 / 不命中"二值的，而用户想要的是"最相关的排在最上面"。

工业级搜索是怎么解决的？**把循环倒过来。**

## 倒排索引：把循环倒过来

BF 和 KMP 的循环是：text

```
对每篇文档：扫一遍全文，看是否含 query
```

倒排索引的循环是：text

```
对 query 的每个词项：直接查"哪些文档含这个词"
```

后者听起来像废话——"直接查"是怎么做到的？答案在[散列表](./../search/hash-chaining.html)。

### 索引构造（离线，只做一次）

把每篇文档分词，对每个词项建立映射：text

```
词项 → 包含该词项的文档 ID 列表
```

举例（简化）：text

```
"哈希"   → [hash-chaining, hash-open-addressing, bst]
"冲突"   → [hash-chaining, hash-open-addressing]
"二叉树" → [bst, avl, rbt, preorder, ...]
"kmp"    → [kmp, bf]
```

这就是**倒排索引**——"倒排"是相对于"文档 → 词项列表"（正排）而言的。

**底层数据结构就是散列表**：词项作为 key，文档列表作为 value，用[拉链法](./../search/hash-chaining.html)处理 key 冲突，平均 O(1) 查找。这正是查找章（七）散列表那一节学的东西，只不过 value 从"一个记录"换成了"一个文档 ID 列表"。

构造索引的复杂度是 O(语料总词数)——它要把每篇文档完整扫一遍，**并不比 KMP 扫描便宜**。关键在于**它只做一次**：发生在用户输入之前（页面冷启动时建好，常驻内存），之后每次查询都不再需要碰原文。

**"把一次昂贵的预处理换来后续每次的廉价查询"，这个思路和 KMP 求 next 数组是同一个套路，只是尺度大了几个数量级。**

### 查询（每次 query 都跑）
text

```
1. 把 query 分词
2. 对每个词项查散列表，各得到一个"倒排列表"
3. 求并集（OR）或交集（AND），得到候选文档集合
4. 对每个候选打分，按分数排序
5. 返回前 k 条
```

第 2 步每个词项 O(1)。整个查询的开销只跟**词项数与命中文档数**有关，**跟语料总规模几乎无关**——这是它与在线扫描路线的根本区别：语料翻倍，KMP 的耗时翻倍，倒排索引基本不变。

在这个博客的数据量上，单次查询通常落在 **0.5–2 ms**，比 KMP 快**一个数量级**，比 BF 快两个数量级。 （下表给的是区间，两端相除得到的倍数跨度很大，**只有数量级的差距是稳定的**。）

### 第 3 步和第 5 步也是学过的东西

**求交集 / 求并集 = 二路归并。** 倒排列表按文档 ID **升序**存放（这是刻意的），于是两个列表求交、求并都可以用两个指针同步前移的方式一次扫完：text

```
i, j 分别指向两个有序列表的表头
  A[i] == B[j] → 收入交集，i++, j++
  A[i] <  B[j] → i++
  A[i] >  B[j] → j++
```

复杂度 O(|A|+|B|)。这段代码和[二路归并排序](./../sorting/merge-sort.html)里的 merge 过程是同一套骨架，区别只在"相等时怎么处理"。**倒排列表之所以要排序存放，就是为了让求交能用归并而不是嵌套循环**（后者是 O(|A|⋅|B|)）。

**取前 k 条 = 堆。** 候选可能有成千上万条，但只需要最相关的前 10 条。用一个大小为 k 的[小顶堆](./../tree/heap.html)扫一遍候选，复杂度 O(Clog⁡k)（C 为候选数），远优于全排序的 O(Clog⁡C)。

### BM25 评分（了解即可）

排序公式 BM25 的形状大致是：score(d,q)=∑t∈qIDF(t)⋅f(tf(t,d), |d|)

核心思想三条：

- **词频高的文档得分高**：query 里的词在这篇文档中出现得越多，越可能相关（tf）。
- **罕见词权重高**：一个词在越少的文档里出现，它对区分文档就越有用（IDF，逆文档频率）。搜"数据结构的哈希"时，"的"几乎不提供信息，"哈希"提供的信息量大得多。
- **长文档要惩罚**：同样出现 5 次，5000 字的文章比 500 字的文章相关性低，所以要按文档长度归一化。

这三条也解释了为什么倒排索引能排序而 BF / KMP 不能：**打分需要"某词在某文档中出现了几次""该词一共出现在几篇文档里"这类统计量，而这些量正是建索引时顺手统计好的**。在线扫描路线只知道"找到 / 没找到"，拿不到这些统计量。

## 三种算法的对比

| 算法 | 单次查询耗时（本站量级） | 查询复杂度 | 预处理 | 排序能力 | 对应学过的知识 |
| --- | --- | --- | --- | --- | --- |
| BF 朴素匹配 | 约 30–60 ms | O(N⋅n⋅m) | 无，O(1) 空间 | 只有命中／未命中 | [BF 算法](./bf.html) |
| KMP | 约 5–15 ms | O(m+N⋅n) | next 数组 O(m) | 只有命中／未命中 | [KMP 算法](./kmp.html) |
| 倒排索引 + BM25 | 约 0.5–2 ms | 与语料规模基本无关 | 建索引，O(语料总词数)，且**占内存** | 按相关性排序 | [散列表](./../search/hash-chaining.html)、[二路归并](./../sorting/merge-sort.html)、[堆](./../tree/heap.html) |

三条读表时必须带上的限定：

- **具体毫秒数会因机器、浏览器和当前语料快照而变，只有数量级的差距是稳定的。**
- **三者的命中集合并不完全相同。** BF / KMP 判的是"正文里有没有这段**连续子串**"；倒排索引判的是"分词之后有没有命中**词项**"。所以同一个 query，倒排索引可能多命中一些（词项匹配更宽松），也可能漏掉一些（跨词边界的子串）。**它们不是同一个函数的三种实现，只能比耗时量级，不能当成等价替换。**
- **倒排索引不是免费的**：它用空间和一次离线构造，换来了每次查询的速度和排序能力。语料一旦更新，索引就要重建或增量更新——这是在线扫描路线完全没有的负担。

## 回到搜索框：这个博客的搜索就是上面三个算法

打开这个博客**右上角的搜索按钮**（或按 `Ctrl / ⌘ + K`），会看到三个算法切换按钮：text

```
算法： [• 倒排索引]  [ KMP ]  [ BF 朴素匹配 ]
```

默认用倒排索引。切到 KMP 或 BF，搜索框会用同一个 query 立刻重跑一次，并在结果上方显示：命中条数、当前算法名、耗时（毫秒）、以及与倒排索引相比慢了几倍。

几个适合拿来体感对比的 query：

- **「哈希」**——常见词，三种算法都能命中很多文档，耗时差距最直观。
- **「KMP」**——英文短串。BF 与 KMP 的差距会被"KMP"在各篇正文中出现位置的靠前／靠后放大：出现得越靠后，BF 白比的前缀就越长。
- **一串重复度高的字**——人为构造的极端 query，用来观察 BF 最坏情形与 KMP 的差别，对应 [BF 那篇里最坏情形的构造](./bf.html)。

顺带说一句实现细节：本站的分词是**中文按单字切、英文按空白切并转小写**，不是 jieba 那类基于词典和统计的分词器。这也是为什么搜中文短语时，倒排索引的命中会比"严格含子串"更宽松——它命中的是"这几个字都出现过"，而不是"这几个字连着出现过"。

## 为什么大纲不教倒排索引

合理的疑问：既然（七）教了散列表、（八）教了 KMP，为什么不顺手把它们捏在一起讲倒排索引？

两层原因：

- **倒排索引绕不开分词。** 中文分词本身是个独立的工程领域（词典、统计、歧义消解各成流派），而分词质量直接决定索引质量。把它塞进一门基础课，考的就不再是数据结构了。
- **大纲的目标是基础数据结构本身。** 倒排索引是散列表的**应用**，而且与工程实践绑得很紧（索引更新、压缩、分片、持久化，每一项都能再展开一门课）。基础课负责给零件，不负责给成品。

但你应该意识到：**理解倒排索引所需要的零件，你已经全部学完了**——

| 零件 | 在倒排索引里干什么 | 出处 |
| --- | --- | --- |
| 散列表（拉链法） | 词项 → 倒排列表的映射 | [散列表：拉链法](./../search/hash-chaining.html) |
| 数组 / 链表 | 存放倒排列表本身 | [线性表](./../linear/concepts.html) |
| 二路归并 | 多个倒排列表求交 / 求并 | [二路归并排序](./../sorting/merge-sort.html) |
| 堆 | 从大量候选里取 top-k | [堆](./../tree/heap.html) |
| KMP | 精确短语匹配、高亮片段定位 | [KMP 算法](./kmp.html) |

把它们按上面的方式组装起来，就是一个工业级搜索引擎的核心骨架。

## 易混淆知识点

| 对比项 | 一方 | 另一方 | 判别依据 |
| --- | --- | --- | --- |
| **正排 vs 倒排** | 文档 → 它含哪些词 | 词 → 哪些文档含它 | 看映射的 key 是文档还是词项 |
| **模式匹配 vs 全文检索** | 在一个主串里定位一个子串 | 在 N 篇文档里筛出相关的若干篇并排序 | 输出是"一个位置"还是"一批文档 + 分数" |
| **等值查找 vs 含子串** | 顺序／折半／散列的比较语义 | BF / KMP 的比较语义 | "含子串"在有序序列上不单调，所以折半失效 |
| **在线扫描 vs 离线索引** | 无预处理，每次全扫，耗时随语料线性增长 | 一次构造常驻内存，查询与语料规模基本无关 | 看这次查询要不要碰原始文档正文 |
| **子串命中 vs 词项命中** | BF / KMP：字符连续相等 | 倒排索引：分词后词项相同 | 同一 query 下两者命中集合可以不同 |
| **本篇内容的性质** | 延伸阅读，**不在大纲范围** | 大纲范围在另外三篇 | 倒排索引、BM25、分词一律不必复习 |

## 本节小结

> [!TIP]
>

再强调一次

本篇不在 2026 大纲范围内。下面这些"能做到"是理解上的收获，不是需要准备的内容。

读完本篇，应该能做到：

- **说清顺序查找与折半查找为什么做不了全文搜索**：前者比较语义是等值，后者要求的单调性在"含子串"上不成立。
- **推出把 BF / KMP 套上外层循环后的复杂度** O(Nnm) 与 O(m+Nn)，并指出 next 数组只依赖模式串、应当提到循环外算一次。
- **说出在线扫描路线的两个本质缺陷**：每次查询都要重扫全部语料（耗时随语料线性增长）、只有二值命中而无法排序。
- **解释倒排索引凭什么快**：把"遍历文档"换成"查词项"，底层是散列表的 O(1) 查找，代价是一次离线构造与常驻内存。
- **把倒排索引拆回学过的零件**：散列表（映射）、有序表的二路归并（求交并）、堆（top-k）、KMP（短语定位与高亮）。
- **说清三种算法的命中集合并不相同**，因此对比只在耗时量级上有意义。

一个最关键的结论：**"用一次昂贵的预处理，换后续每次的廉价查询"是同一个思想在两种尺度上的体现**——小尺度是 KMP 预先算出 next 数组，大尺度是搜索引擎预先建好倒排索引。看懂这条，本篇的目的就达到了。

- 同书印刷第 97 页：「KMP 算法的最大特点是指示主串的指针不需回溯，整个匹配过程中，对主串仅需从头至尾扫描一遍，这对处理从外设输入的庞大文件很有效，可以边读入边匹配，而无需回头重读。」——这正是把 KMP 用于扫描大规模语料时的价值所在。
- 同书 4.6 节案例 4.1「病毒感染检测」，印刷第 105–106 页：把 BF 算法用在真实问题（在患者 DNA 序列中检测环状病毒 DNA 序列）上的完整实现，是"模式匹配算法落到应用"的教材内示例。

倒排索引、BM25、中文分词均**不在**上述教材范围内，本篇这几节没有教材出处，按事实标注。
