# 顺序查找

## 大纲定位

本篇对应 2026 大纲 **六、查找 （二）顺序查找法**。

**分工边界**：本篇负责顺序查找（线性查找）本身——算法的三个版本、监视哨的作用、 无序表与有序表两种情形下成功与失败 ASL 的完整推导。

- ASL 的定义、判定树模型、"失败入口数"这套通用工具在 [《查找基本概念》](./concepts.html) 里建立，本篇直接使用；
- 顺序查找与折半查找的取舍见 [《折半查找》](./binary-search.html) 与 [《查找算法分析与对比》](./comparison.html)；
- 顺序查找作为**块内查找**出现在 [《分块查找》](./block-search.html) 中；
- 顺序查找作为**结点内查找**出现在 [《B 树》](./b-tree.html) 中。

## 知识框架

本节回答 4 个问题：

- **顺序查找几乎没有前提条件，那它到底"要求"了什么？**
- **监视哨省掉的是哪一次判断？为什么能让耗时接近减半，而时间复杂度不变？**
- **有序表上的顺序查找，失败 ASL 为什么不是 (n+1)/2，也不是 n？**
- **顺序查找在什么场景下反而比折半查找划算？**

## 算法：三个版本与它们的差别

### 基本思想

从表的**一端**出发，依次把每个元素的关键字与目标值比较：

- 某个元素的关键字与目标值相等 → **查找成功**，返回该元素位置；
- 扫描完整个表仍未找到 → **查找失败**。

顺序查找**对表结构没有任何要求**：顺序存储、链式存储都行，有序、无序都行。 它是本章唯一一个**对链表也适用**的比较型查找方法——折半查找、分块查找都做不到。

说它"没有前提"并不准确，准确的说法是：它只要求能**逐个访问下一个元素**。 这个要求低到几乎任何线性结构都满足，代价则是每次比较只能排除一个候选， 因而 ASL 是 O(n) 量级。

### 版本一：不带监视哨

约定顺序表元素存放在 `ST.elem[1..length]`，**下标 0 空出不用**（这是本章的统一约定， 后面的监视哨要用到这个位置）。c

```
// 顺序查找（不带监视哨）
// 在 ST.elem[1..length] 中查找关键字等于 key 的元素
// 返回其下标；返回 0 表示查找失败
int SeqSearch(SSTable ST, int key) {
    for (int i = ST.length; i >= 1; i--)   // 从表尾往前扫
        if (ST.elem[i] == key)             // 每轮要判两件事：i>=1（循环条件）与是否相等
            return i;
    return 0;                              // 0 号位置不存数据，可以安全地当作"失败"的返回值
}
```

**为什么从表尾往前扫**：并不是因为更快，而是为了让"失败"落在下标 0 上—— 这样返回值 0 天然表示失败，不需要另设标志。下一版的监视哨也正是利用这个空出来的 0 号位置。

**这个版本的成本**：循环体每转一圈要做**两次判断**——`i >= 1`（是否走到头）与 `ST.elem[i] == key`（是否命中）。整个失败查找一共做 2n 次判断左右。

### 版本二：带监视哨（哨兵）
c

```
// 顺序查找（设置监视哨）
// 查找前把 key 写进 ST.elem[0]，循环一定会停下来
int SeqSearch_Sentinel(SSTable ST, int key) {
    ST.elem[0] = key;                 // 监视哨：让"走到头"这件事变成一次普通的命中
    int i = ST.length;
    while (ST.elem[i] != key)         // 只剩一个判断条件，不需要再检查 i >= 1
        i--;
    return i;                         // 返回 0 说明是撞上了监视哨，即查找失败
}
```

**监视哨的本质**：把"越界检查"这件事，用一次**必然命中的数据**替代掉。 既然 `elem[0]` 已经等于 `key`，循环最迟在 i=0 时终止，`i >= 1` 这个判断就成了多余。

- **判断次数**：从每轮 2 次降到每轮 1 次，总判断次数从约 2n 降到约 n；
- **关键字比较次数**：**没有变少**。成功查找仍是原来那么多次； 失败查找则从 n 次变成 n+1 次（多和监视哨比了一次）；
- **时间复杂度**：仍是 O(n)，量级没变。

⚠️ **边界**：表长为 0 时，i=0，`elem[0] == key` 立即成立，返回 0——正确地报告失败。 这一版对空表是安全的。

严蔚敏教材在这里给了一个实测结论：当表长达到 1000 以上时，监视哨版本一次查找所需的 平均时间"几乎减少一半"。监视哨也可以设在**高下标处**（此时从表头往后扫）， 效果对称。

### 版本三：有序表的顺序查找

当表按关键字**升序**存放时，一旦遇到比 `key` 大的元素，就可以断定后面不可能有 `key`， 于是能**提前终止**：c

```
// 有序表（升序）的顺序查找，从表头往后扫
// 返回下标；返回 0 表示查找失败
int SeqSearch_Ordered(SSTable ST, int key) {
    for (int i = 1; i <= ST.length; i++) {
        if (ST.elem[i] == key)
            return i;       // 查找成功
        if (ST.elem[i] > key)
            return 0;       // 当前元素已经比 key 大，后面只会更大，提前判失败
    }
    return 0;               // 扫完全表也没遇到更大的，说明 key 比所有元素都大
}
```

⚠️ **提前终止只改善失败查找，不改善成功查找**。成功时的比较次数与无序表完全一样—— 第 i 个元素仍需比较 i 次。这是下面 ASL 推导里最容易被想当然搞错的一点。

## ASL 的完整推导

### 查找成功

等概率假设下（Pi=1n），从表头开始扫时，第 i 个元素需要比较 i 次； 从表尾开始扫时，第 i 个元素需要比较 n−i+1 次。两种扫法得到的**比较次数集合完全相同** （都是 {1,2,⋯,n}），所以 ASL 相同：ASL成功=1n∑i=1ni=1n⋅n(n+1)2=n+12

这条结论**对有序表与无序表都成立**。

### 查找失败：无序表

无序表里没有任何信息能让你提前放弃，所以必须扫完全部 n 个元素：

- **不带监视哨**：比较 n 次即可确认失败；
- **带监视哨**：还要和 `elem[0]` 里的监视哨比一次才跳出循环，共 n+1 次。ASL失败=n（不带监视哨）ASL失败=n+1（带监视哨）

失败的情况只有一种（扫完全表），所以这里不需要求平均，直接就是这个值。

⚠️ **判据**：题目给的代码里如果出现"把 key 存进 0 号（或 n+1 号）位置"， 就按 n+1 算；如果是显式的边界判断循环，就按 n 算。**题目没给代码时， 408 的通行口径按 n+1**，因为教材给的标准实现就是监视哨版本。

### 查找失败：有序表（本篇最容易算错的一处）

有序表可以提前终止，所以不同的 `key` 会在不同位置停下，必须求平均。

用[《查找基本概念》](./concepts.html)里的判定树工具：n 个关键字把取值范围切成 **n+1 个开区间**，每个区间对应一个失败结点。

图源：殷人昆《数据结构——用面向对象方法与 C++ 描述》（第 2 版），p303 图 7.1

图中 n=6，有序表为 {10,20,30,40,50,60}，7 个方形失败结点分别标着 (−∞,10)、(10,20)、⋯、(60,+∞)。**顺序查找的判定树是一条单支链**—— 这正是它效率低的图形化解释：折半查找的判定树是平衡的，顺序查找的判定树退化成了链表。

逐个失败区间数比较次数：

| 失败区间 | 停在哪 | 比较次数 |
| --- | --- | --- |
| key<10 | 比第 1 个元素，发现 10>key，终止 | 1 |
| 10<key<20 | 比到第 2 个 | 2 |
| 20<key<30 | 比到第 3 个 | 3 |
| 30<key<40 | 比到第 4 个 | 4 |
| 40<key<50 | 比到第 5 个 | 5 |
| 50<key<60 | 比到第 6 个 | 6 |
| key>60 | 扫完全表也没遇到更大的 | **6**（不是 7） |

ASL失败=1+2+3+4+5+6+67=277≈3.857

**推广到一般的 n**：前 n 个区间分别比较 1,2,⋯,n 次； 最后一个区间（key 比所有元素都大）扫完全表，也只比较 n 次。于是ASL失败=(1+2+⋯+n)+nn+1=n(n+1)2+nn+1=n2+nn+1

代入 n=6 验证：3+67=277 ✓ 与逐项求和一致。

n 较大时 nn+1→1，故 ASL失败≈n2+1， 约为无序表（n+1 次）的**一半**。

⚠️ **最后一个区间只比较 n 次而不是 n+1 次**，是这条公式里唯一的坑： 分子是 (1+2+⋯+n)+n，不是 (1+2+⋯+n)+(n+1)。 从判定树上看就很清楚——最右边那个失败结点是第 n 个内部结点的右空指针， 它的路径上只有 n 个内部结点。

### 汇总

| 情况 | 无序表 | 有序表 |
| --- | --- | --- |
| 查找成功 ASL | n+12 | n+12 |
| 查找失败 ASL | n（无监视哨）/ n+1（有监视哨） | n2+nn+1 |
| 失败情况的种数 | 1 种 | n+1 种 |

### 一个完整算例（n=8）

有序表 {12,25,31,40,47,56,68,79}，从表头往后扫。

**成功**：查 12 比 1 次、查 25 比 2 次……查 79 比 8 次。ASL成功=1+2+3+4+5+6+7+88=368=4.5=8+12 ✓

**失败**：9 个失败区间。前 8 个分别比 1,2,⋯,8 次； 最后一个（key>79）扫完全表也只比 8 次。ASL失败=(1+2+⋯+8)+89=36+89=449≈4.89

代入公式核对：n2+nn+1=4+89=449 ✓

**同一张表若按无序表处理**（不利用有序性提前终止），失败 ASL 是 8（无监视哨）或 9（有监视哨） ——比有序表的 4.89 差了将近一倍。**这个差距就是"有序性"在顺序查找里唯一的价值。**

### 链式存储上的顺序查找

顺序查找是本章唯一能用在链表上的比较型查找方法。代码形态变了，比较次数没变：c

```
typedef struct LNode {
    int data;
    struct LNode *next;
} LNode;

// 带头结点的单链表上的顺序查找
// 返回结点指针；返回 NULL 表示查找失败
LNode* ListSearch(LNode *head, int key) {
    LNode *p = head->next;        // 跳过头结点，从第一个数据结点开始
    while (p != NULL) {
        if (p->data == key)
            return p;             // 查找成功
        p = p->next;              // 每前进一步就是一次关键字比较
    }
    return NULL;                  // 走到链尾，查找失败
}
```

三点差别：

- **ASL 完全相同**：第 i 个结点仍需比较 i 次，ASL成功=n+12；
- **常数因子略大**：每前进一步要跟一次指针，而顺序表只是下标加一；
- **设不了监视哨**：单链表末尾之后没有可写的位置。真要用这个技巧， 只能在表尾**追加一个结点**存放 `key`，找到后再摘掉——通常不值得。

## 复杂度的来历

| 指标 | 复杂度 | **怎么来的** |
| --- | --- | --- |
| 最好时间 | O(1) | 第一次比较就命中（目标恰好在扫描起点） |
| 最坏时间 | O(n) | 目标在扫描的另一端，或查找失败，都要走完 n 个元素 |
| 平均时间 | O(n) | 等概率下成功需 n+12 次比较，是 n 的线性函数，故量级为 O(n) |
| 空间 | O(1) | 只用了循环变量 `i` 一个辅助单元；监视哨占用的是表内已有的 0 号位置，**不算额外空间** |

**为什么平均是 O(n) 而不是 O(n/2)**：n+12 与 n 只差一个常数因子， 渐近记号里常数因子被吸收。但在**具体计算题里必须写 n+12**—— 问"平均比较次数"和问"时间复杂度"是两个问题。

**链式存储上的顺序查找**：比较次数与顺序表完全相同（仍是 n+12）， 但每次前进要跟一次指针，常数因子略大，且**无法设监视哨式的优化**（单链表最后一个结点 之后没有可写入的位置，只能改成在表尾追加一个结点）。

## 什么时候顺序查找反而划算

顺序查找并不总是"最差选项"，它在三种情形下有实际优势：

- **n 很小**。折半查找每轮要算 `mid`、做区间收缩，常数开销比顺序查找大。 n 只有十几个时，顺序查找的实际耗时往往更低。
- **表频繁增删**。有序表要维护有序性，一次插入平均要移动一半元素； 顺序查找的表随便往末尾追加即可。
- **访问分布高度倾斜**。按查找概率递减排列后， ASL=∑Pi⋅i 可以远小于 n+12。

第 3 条给一个可验证的例子：n=5，概率为 0.5,0.2,0.15,0.1,0.05。

- 按概率递减排列：ASL=0.5×1+0.2×2+0.15×3+0.1×4+0.05×5=1.9
- 等概率时的 ASL=5+12=3

**边界**：这个优化只在**静态表**上成立，而且要求概率分布已知且稳定。 概率会随时间漂移的场景，维护排序的代价通常超过收益。

## 易混淆知识点

| 易混对象 | 区别 | **判别依据** |
| --- | --- | --- |
| 有序表的成功 ASL vs 无序表的成功 ASL | **完全相同**，都是 n+12 | 有序性只能帮你"提前放弃"，帮不了"提前找到"——成功时该比几次还是几次 |
| 有序表失败 ASL n2+nn+1 vs n+12 | 前者是失败，后者是成功，形近但含义不同 | 看分母：失败的分母是**失败区间数 n+1**，成功的分母是**元素个数 n** |
| 失败 ASL 的分子里最后一项 | 是 n，不是 n+1 | 画判定树：最右侧失败结点挂在第 n 个内部结点上，路径上只有 n 个内部结点 |
| 无序表失败 ASL 取 n 还是 n+1 | 取决于**有没有监视哨** | 代码里有"把 key 写进 0 号位置"就是 n+1；只有显式边界判断就是 n |
| 监视哨减少的是什么 | 减少的是**循环条件判断次数**，不是关键字比较次数 | 比较次数由数据决定，监视哨改的只是控制流；带哨兵的失败查找反而**多比一次** |
| 顺序查找 vs 折半查找的存储要求 | 前者顺序/链式都行，后者只能顺序存储 | 问"能不能 O(1) 取到中间元素"——不能就用不了折半 |
| 顺序查找 vs 分块查找的块内查找 | 后者的块内部分**就是**顺序查找 | [分块查找](./block-search.html)的 LS 项等于块内顺序查找的 ASL |

## 本节小结

学完本篇，应当能够：

- 写出顺序查找的**三个版本**（不带监视哨、带监视哨、有序表提前终止）的 C 代码， 并说清各自的循环终止条件；
- 解释**监视哨省掉的是循环边界判断**，把每轮 2 次判断压成 1 次， 时间复杂度不变、关键字比较次数不减、失败时反而多比一次；
- 推导 ASL成功=n+12，并说明它**与表是否有序无关**；
- 分别给出无序表失败 ASL（n 或 n+1，看有无监视哨）与有序表失败 ASL n2+nn+1，并能画出**单支链形态的判定树**逐项求和验证；
- 说清有序表失败 ASL 的分子为什么是 (1+2+⋯+n)+n 而不是 +(n+1)；
- 判断顺序查找在**小规模表、频繁增删、访问分布倾斜**三种场景下的适用性， 并在给定概率分布时用 ∑PiCi 算出实际 ASL。

两条最关键的结论：**有序性只优化失败查找，不优化成功查找**； **监视哨是控制流优化而非比较次数优化**。
