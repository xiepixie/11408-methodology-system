## 知识框架

本节要回答四个问题：

- 一般树为什么不能照搬二叉链表？三种存储方式各自解决了什么、牺牲了什么？
- 孩子表示法用"多重链表"时，空链域会浪费多少？（有精确公式）
- 孩子兄弟表示法凭什么能把一棵一般树"变成"二叉树？
- 一般树为什么**没有中根遍历**？森林为什么**没有后序遍历**？

## 一、一般树为什么需要单独讲

二叉树有一个隐藏的便利：每个结点**最多两个**孩子，于是可以用固定大小的结点（`lchild`、`rchild`）表示。一般树的结点的度可能是 1、2、3，甚至几十，**指针域开几个都不对**：

- 按最大度 k 开 k 个 → 大量结点的度远小于 k，空指针泛滥
- 按每个结点的实际度开 → 结点大小不统一，无法用数组，指针运算全失效

这一节要解决两个问题：

- **一般树怎么存**——三种主流存储方式，各自的"找双亲 / 找孩子"代价不同
- **一般树和森林怎么遍历**——以及它们与二叉树遍历的对应关系

### 先补三个概念

| 概念 | 定义 |
| --- | --- |
| **一般树** | 每个结点孩子数不固定的树（区别于二叉树） |
| **森林** | m（m≥0）棵互不相交的树的集合 |
| **空森林** | m=0 时合法存在（空集也是森林） |

一般树有一条比二叉树更简单的**边数性质**：n结点=n边+1

因为除根外每个结点恰有一条入边。等价地写成"**结点数 = 所有结点的度之和 + 1**"——这是[树的性质 T1](./concepts.html)，一切"数指针域"的推导都从它出发。

## 二、双亲表示法

**思路**：用一维数组存所有结点，每个结点带一个 `parent` 字段指向双亲在数组中的下标。**只保存向上的那一条边。**c

```
#define MAX_TREE_SIZE 100
typedef struct {
    ElemType data;      // 数据域
    int parent;         // 双亲下标，根的 parent = -1
} PTNode;

typedef struct {
    PTNode nodes[MAX_TREE_SIZE];
    int n;              // 当前结点数
} PTree;
```

**存储示例**：

```
        A
      / | \
     B  C  D
    / \    |
   E   F   G
```

| 下标 | data | parent |
| --- | --- | --- |
| 0 | A | -1 |
| 1 | B | 0 |
| 2 | C | 0 |
| 3 | D | 0 |
| 4 | E | 1 |
| 5 | F | 1 |
| 6 | G | 3 |

### 性能与代价

| 操作 | 代价 | 原因 |
| --- | --- | --- |
| 找双亲 | O(1) | 直接读 `parent` 字段 |
| 找根 | O(h) | 沿 `parent` 一路向上直到 −1 |
| 找孩子 | O(n) | 没有向下的指针，必须扫描整个数组，找 `parent == i` 的项 |
| 找兄弟 | O(n) | 同上，扫描找 `parent` 相同的项 |
| 判断两结点是否同属一棵树 | O(h) | 各自找根，比较根是否相同 |

**这种存储结构的设计取向非常明确**：它利用了"除根之外每个结点只有唯一双亲"这条性质，把每个结点的存储压缩成一个整数，代价是彻底放弃了向下的可达性。

**典型应用**：[并查集](./union-find.html)——并查集的两个核心操作恰好是"沿双亲找根"和"把一个根挂到另一个根下"，全部是向上操作，一个 `parent[]` 数组就够。这不是巧合，而是**先有需求、后选结构**的典型例子。

**一个实现细节**：根的 `parent` 有两种约定，一是置 −1，二是**指向自己**。后者的好处是找根的循环可以写成 `while (parent[x] != x) x = parent[x];`，不需要额外判负。并查集里两种写法都常见，做题时看清题面给的约定。

## 三、孩子表示法

### 方案一：多重链表（每个结点开 k 个指针）

最直接的想法是让每个结点带 k 个指针域（k = 树的度），每个指向一棵子树的根。两种结点格式：

```
格式一（同构，d = 树的度）：
  ┌──────┬───────┬───────┬─────┬───────┐
  │ data │child1 │child2 │ ... │childd │
  └──────┴───────┴───────┴─────┴───────┘

格式二（不同构，d = 该结点的度）：
  ┌──────┬────────┬───────┬─────┬───────┐
  │ data │ degree │child1 │ ... │childd │
  └──────┴────────┴───────┴─────┴───────┘
```

**格式一浪费多少空间——有精确公式**：设树有 n 个结点、度为 k，则每个结点开 k 个指针域，总指针域数为 nk；其中非空的与树中的边一一对应，共 n−1 个。故空链域数=nk−(n−1)=n(k−1)+1

**验算**：n=7、k=3（上面那棵树），空链域 =7×2+1=15；实际数一数，21 个指针域里只有 6 条边占用，剩 15 个 ✓。

**k 越大浪费越严重**：空链域占全部指针域的比例为n(k−1)+1nk=k−1k+1nk≈k−1k

k=3 时约 2/3≈67%（上面 n=7 的那棵树精确是 15/21≈71%），k=10 时约 90%。**比例只由 k 决定，与结点数几乎无关。**

格式二按实际度分配，省了空间，但结点大小不统一，读写都要先看 `degree`，操作很不方便。**两种格式各自不可接受，所以实际用的是下面这种。**

### 方案二：孩子链表（教材主推）

把每个结点的孩子看成一个线性表，用**单链表**存；n 个结点就有 n 个孩子链表（叶子的链表为空）；n 个头指针再组成一个顺序表便于随机访问。c

```
typedef struct ChildNode {
    int childIdx;               // 孩子在数组中的下标
    struct ChildNode *next;     // 下一个孩子
} ChildNode;

typedef struct {
    ElemType data;
    ChildNode *firstChild;      // 指向该结点的孩子链表
} CTBox;

typedef struct {
    CTBox nodes[MAX_TREE_SIZE];
    int n, root;                // 结点数和根的下标
} CTree;
```

**存储示例**（同上一棵树）：

```
下标  data   孩子链表
 0    A   →  [1] → [2] → [3] → ∧
 1    B   →  [4] → [5] → ∧
 2    C   →  ∧
 3    D   →  [6] → ∧
 4    E   →  ∧
 5    F   →  ∧
 6    G   →  ∧
```

**性能**：

- **找孩子：O(度)**——遍历当前结点的孩子链表
- **找双亲：O(n)**——没有反向指针，只能扫描所有孩子链表
- **空间**：链表结点总数恰为边数 n−1，**没有空链域浪费**（每个链表结点都对应一条真实的边）

**典型应用**：以"自上而下"操作为主的场景，如组织架构展开、文件系统目录遍历。

**常见折中——孩子双亲表示法**：在 `CTBox` 里再加一个 `parent` 字段。这样找双亲 O(1)、找孩子 O(度)，只多一个整数域。教材把它作为"孩子链表 + 双亲"的组合形式给出。

## 四、孩子兄弟表示法

**思路**：每个结点只用两个指针——**第一个孩子**（`firstchild`）和**右兄弟**（`nextsibling`）。又称**二叉树表示法**或**二叉链表表示法**。c

```
typedef struct CSNode {
    ElemType data;
    struct CSNode *firstchild;   // 第一个孩子
    struct CSNode *nextsibling;  // 右兄弟（同一双亲下的下一个孩子）
} CSNode, *CSTree;
```

### 为什么两个指针就够

一般树的困难在于"孩子有多少个不知道"。孩子兄弟法把这件事**改写成一条链**：

- 一个结点的**全部孩子**，被串成一条以 `firstchild` 为表头、以 `nextsibling` 为链的**单链表**
- 于是每个结点只需要"指向自己孩子链表的表头"和"指向自己在兄弟链表中的下一个"两个指针

**存储示例**：

```
原一般树                 孩子兄弟表示法（firstchild 向下、nextsibling 向右）

      A                      A
    / | \                    │
   B  C  D                   B ──→ C ──→ D
  / \    |                   │           │
 E   F   G                   E ──→ F     G

  竖线 │ 是 firstchild（指向第一个孩子）
  箭头 ──→ 是 nextsibling（指向右兄弟）
```

**关键洞察**：把 `firstchild` 当作二叉树的**左指针**、`nextsibling` 当作**右指针**，整个结构在内存里与一棵二叉链表**一模一样**。所以：

**孩子兄弟表示法把一般树映射成了一棵二叉树。** 这就是"树 / 森林 ↔ 二叉树"转换成立的全部理由——它不是一个"技巧"，而是同一份存储的两种读法。

由于 n 个结点、每个 2 个指针域，非空的仍是 n−1 个（对应树中的 n−1 条边，只是这些边有的表示父子、有的表示兄弟），空链域为 n+1——与[二叉链表](./concepts.html)完全一致。

### 性能

| 操作 | 代价 | 说明 |
| --- | --- | --- |
| 找第一个孩子 | O(1) | 直接读 `firstchild` |
| 找第 i 个孩子 | O(i) | 先到 `firstchild`，再沿 `nextsibling` 走 i−1 步 |
| 找右兄弟 | O(1) | 直接读 `nextsibling` |
| 找双亲 | 不方便 | 需从根查找，或额外加 `parent` 域 |
| 空间 | 固定 2 个指针 / 结点 | 结构规整，可直接套用二叉树的全部算法 |

**典型应用**：树 ↔ 二叉树转换、需要用二叉树算法处理一般树的场合。**这是应用最广的一种一般树表示法**，原因就是它能把一般树的操作全部转成二叉树的操作。

详细的转换规则见 [树与森林和二叉树的转换](./forest-conversion.html)。

## 五、三种存储方式对比

| 存储方式 | 找双亲 | 找孩子 | 空间开销 | 存的是哪些边 | 适用场景 |
| --- | --- | --- | --- | --- | --- |
| 双亲表示法 | **O(1)** | O(n) | 1 个整数域 / 结点，无浪费 | 只存向上的边 | 并查集、以"查双亲 / 判连通"为主 |
| 孩子表示法（多重链表） | O(n) | O(1) 直接下标 | k 个指针 / 结点，空链域 n(k−1)+1 | 向下的边，但预留冗余槽位 | 度很整齐时才划算 |
| 孩子表示法（孩子链表） | O(n) | O(度) | 链表结点数 = 边数，无浪费 | 只存向下的边 | 目录展开、自上而下为主 |
| 孩子兄弟表示法 | 不方便 | 第一个 O(1)、第 i 个 O(i) | 固定 2 个指针 / 结点 | 长子边 + 兄弟边 | 树 ↔ 二叉树转换、要复用二叉树算法 |

**选择的判据只有一条**：**看主要操作是往上走还是往下走。**

- 主要问"某结点属于哪一组 / 它的祖先是谁" → 双亲表示法
- 主要问"某结点的所有后代 / 展开子树" → 孩子表示法
- 要把树当二叉树处理（转换、遍历、套二叉树算法） → 孩子兄弟表示法

## 六、树的遍历

一般树（非二叉树）的遍历有三种：

| 遍历方式 | 规则 | 对应的二叉树遍历 |
| --- | --- | --- |
| **先根遍历** | 先访问根，再依次先根遍历根的每棵子树 | 转换后二叉树的**先序遍历** |
| **后根遍历** | 先依次后根遍历根的每棵子树，再访问根 | 转换后二叉树的**中序遍历** |
| **层次遍历** | 按层从上到下、每层从左到右（用队列实现） | 无严格对应 |

### 为什么没有"中根遍历"

二叉树的中序之所以能定义，是因为"根"两侧的子树数量固定为 2——"在左子树之后、右子树之前"是一个**无歧义**的位置。

一般树的孩子数不固定，"在第几个孩子之后访问根"完全没有依据：度为 3 的结点可以在第 1、第 2 个孩子之后访问根，度为 5 的结点又有 4 个可选位置。**不同结点之间无法统一，所以这个次序定义不出来。**

这也解释了下面森林为什么只有先序和中序两种：森林的两种遍历是从"森林 ↔ 二叉树"的对应关系里**继承**过来的，二叉树有三种遍历，但后序对应到森林上的次序在森林自身的定义里没有意义。

### 示例

```
      A
    / | \
   B  C  D
  / \    |
 E   F   G
```

- **先根遍历**：**A B E F C D G** 推导：访问 A → 先根遍历子树 B（访问 B → 子树 E → 子树 F）→ 先根遍历子树 C → 先根遍历子树 D（访问 D → 子树 G）
- **后根遍历**：**E F B C G D A** 推导：后根遍历子树 B（E → F → B）→ 后根遍历子树 C（C）→ 后根遍历子树 D（G → D）→ 访问 A
- **层次遍历**：**A B C D E F G**

**手工技巧**：一般树的先根 / 后根遍历和二叉树的先序 / 后序在写法上完全一样，只是"两棵子树"变成"若干棵子树、从左到右"。写的时候按层缩进分组，不容易漏。

## 七、森林的遍历

森林由若干棵树组成。由于"森林与树是相互递归定义的"（一棵树去掉根就是森林，一个森林加个公共根就是树），可以从树的两种遍历推出森林的两种遍历：

| 遍历方式 | 规则 | 对应的二叉树遍历 |
| --- | --- | --- |
| **先序遍历森林** | ① 访问第一棵树的根 → ② 先序遍历第一棵树的**子树森林** → ③ 先序遍历除第一棵树之外剩余树构成的森林 | 转换后二叉树的**先序遍历** |
| **中序遍历森林** | ① 中序遍历第一棵树的**子树森林** → ② 访问第一棵树的根 → ③ 中序遍历剩余树构成的森林 | 转换后二叉树的**中序遍历** |

**三步结构不是随意的**：它精确对应转换后二叉树的"根 / 左子树 / 右子树"——第一棵树的根就是二叉树的根，第一棵树的子树森林转成左子树，剩余树的森林转成右子树。推导见 [转换](./forest-conversion.html)。

### 为什么没有"后序遍历森林"

若照搬"左、右、根"写成"先遍历子树森林、再遍历剩余森林、最后访问第一棵树的根"，得到的次序里，**第一棵树的根会排在后面所有树之后**——这与"森林中各树有先后次序"的直觉严重冲突（第一棵树的根跑到了最后一棵树的所有结点之后）。这个次序没有对应的应用语义，所以不定义。

**注意术语**：森林的**中序遍历**在部分材料里也叫"森林的后根遍历"，因为它对每棵树内部实际执行的正是后根次序。两个名字指同一件事。

### 示例

```
森林 F = { T1, T2, T3 }

   T1         T2        T3
    A          E         G
   / \         |        / \
  B   C        F       H   I
      |
      D
```

- **先序遍历森林**：访问 A → 先序遍历 A 的子树森林 {B,C}（B → C → D）→ 先序遍历剩余森林 {T2,T3}（E → F → G → H → I） 结果：**A B C D E F G H I**
- **中序遍历森林**：中序遍历 A 的子树森林（B → D → C）→ 访问 A → 中序遍历剩余森林（F → E → H → I → G） 结果：**B D C A F E H I G**

**逐层核对第二条**：{B,C} 这个子森林的中序 = 中序遍历 B 的子树森林（空）→ 访问 B → 中序遍历剩余森林 {C}；{C} 的中序 = 中序遍历 C 的子树森林（{D} → 得 D）→ 访问 C。故 {B,C} 的中序为 **B D C** ✓。同理 {T2,T3}：T2 的子树森林 {F} → F，访问 E，再处理 {T3}：T3 的子树森林 {H,I} → H、I，访问 G，得 **F E H I G** ✓。

## 八、树 / 森林 / 二叉树遍历对应表

| 树（一般树）的遍历 | 森林的遍历 | 对应二叉树的遍历 |
| --- | --- | --- |
| 先根遍历 | 先序遍历 | **先序遍历** |
| 后根遍历 | 中序遍历 | **中序遍历** |

**这张表的推导（为什么恰好是这两组对应）放在 [树与森林 ↔ 二叉树的转换](./forest-conversion.html)**，因为它完全依赖转换规则。这里只说怎么用：

题目给一棵一般树或一片森林，要求"转换为二叉树后的先序 / 中序序列"，两种走法结果相同：

- **走法 A**：先按孩子兄弟法画出对应的二叉树，再做二叉树的先序 / 中序遍历
- **走法 B**：直接对原树 / 森林做先根 / 后根（或先序 / 中序）遍历

走法 B 更快，因为不用画转换图；走法 A 更稳，画出来的图还能用来核对。**建议用 B 求答案、用 A 抽查一两个结点的位置。**

## 复杂度分析

| 操作 | 复杂度 | 来历 |
| --- | --- | --- |
| 建立 n 个结点的一般树（任一存储方式） | O(n) | 每个结点写入一次 |
| 树 / 森林的先根、后根、层次遍历 | O(n) | 每个结点访问一次，每条边走一次 |
| 双亲表示法：查双亲 | O(1) | 读一个字段 |
| 双亲表示法：查根 / 判同集合 | O(h) | 沿双亲链向上 |
| 双亲表示法：查孩子 / 兄弟 | O(n) | 全表扫描 |
| 孩子链表：查孩子 | O(度) | 遍历该结点的孩子链表 |
| 孩子兄弟表示法：查第 i 个孩子 | O(i) | 沿兄弟链走 i−1 步 |
| 多重链表的空间浪费 | n(k−1)+1 个空链域 | 总域数 nk 减去边数 n−1 |

## 易混淆知识点

| 对比项 | 一方 | 另一方 | 判别依据 |
| --- | --- | --- | --- |
| 树的度 vs 结点的度 | 全树中最大的结点度 | 某个结点的孩子个数 | 问的是"这棵树"还是"某结点" |
| 双亲表示法 vs 孩子表示法 | 找双亲 O(1)、找孩子 O(n) | 找孩子 O(度)、找双亲 O(n) | 存的是向上的边还是向下的边 |
| 多重链表 vs 孩子链表 | 每结点固定 k 个指针，空链域 n(k−1)+1 | 链表结点数 = 边数，无浪费 | 是否为不存在的孩子预留槽位 |
| 一般树有没有中根遍历 | **没有** | 二叉树有中序 | 孩子数不固定，"在第几个孩子后访问根"无法统一 |
| 森林有没有后序遍历 | **没有**，只有先序和中序 | 二叉树有后序 | 森林的遍历是从二叉树对应关系继承的，后序在森林上无语义 |
| 森林的中序 vs 森林的后根 | 是同一件事的两个名字 | — | 中序对每棵树内部执行的正是后根次序 |
| 森林的中序遍历次序 | 先第一棵树的**子树森林**，再第一棵树的**根**，最后**剩余森林** | 不是"先遍历完整个第一棵树再遍历剩余" | 访问根的时机夹在两段森林之间 |
| 孩子兄弟表示法 vs 二叉链表 | 逻辑上是一般树 | 内存布局与二叉链表完全一致 | 二者是同一份存储的两种读法 |
| 树转二叉树后根有无右子树 | 一棵**树**转出来的二叉树，**根没有右子树** | 一片**森林**转出来的二叉树，根**有**右子树（除非只有一棵树） | 根有没有兄弟 |
| 双亲表示法根的约定 | `parent = -1` | `parent = 自己` | 以题面为准；后者写找根循环更简洁 |

## 本节小结

学完本篇，应该能够：

- **说清一般树不能照搬二叉链表的理由**：结点的度不固定，指针域开几个都不合适
- **默写三种存储结构的类型定义**，并对照说出各自"找双亲 / 找孩子 / 找兄弟"的代价
- **推出多重链表的空链域数 n(k−1)+1**（总域数 nk 减去边数 n−1），并由此说明为什么实际用的是孩子链表而不是多重链表
- **解释孩子兄弟表示法为什么等价于一棵二叉链表**：`firstchild` 当左指针、`nextsibling` 当右指针，内存布局完全一致——这是树 ↔ 二叉树转换成立的根据
- **根据使用场景选存储结构**：主要向上走选双亲表示法、主要向下走选孩子表示法、要复用二叉树算法选孩子兄弟表示法
- **写出一般树的先根、后根、层次遍历序列**，并说明**为什么没有中根遍历**
- **写出森林的先序、中序遍历序列**，准确记住中序的三步次序（子树森林 → 第一棵树的根 → 剩余森林），并说明**为什么没有后序遍历**

**两条最关键的结论**：三种存储结构的差别可以用一句话概括——**双亲表示法只存向上的边、孩子表示法只存向下的边、孩子兄弟表示法把"多个孩子"改写成"长子 + 兄弟链"**；一般树没有中根遍历、森林没有后序遍历，两者的原因都是"次序在定义上无法统一"，不是遗漏。
