# 408 学科架构

当前状态：框架已采用，专题正文待建。

## 1. 架构目标

408 不是四门教材的并排目录，而是四种不同问题语言共同解释计算系统：

$$
\text{Data Structure}
\to \text{Program}
\to \text{Machine}
\to \text{Operating System}
\to \text{Network}
$$

统一系统只负责连接四科，不用一套抽象强行覆盖四科。每科必须有自己的生成性内核和 Question Control Adapter。

## 2. 四科学科内核

| 学科 | 研究对象 | 生成性内核 | 最容易混淆的维度 |
| -------------- | ----------------- | --------------- | --------------- |
| 数据结构 | 数据关系及其表示 | Problem -> Relation -> Operations -> Representation -> Algorithm -> Invariant -> Cost | 逻辑关系、存储表示、操作集合 |
| 计算机组成原理 | ISA 语义的硬件实现 | ISA Semantic -> Data Movement -> Hardware Path -> Timing -> Commit | 数据位置、通路、资源、时序 |
| 操作系统 | 资源、抽象与控制流 | Objects/Relations/Queues + Event/Mechanism/Policy -> New State | 对象身份、状态、事件、机制与策略 |
| 计算机网络 | 独立机器间的通信 | Scope -> State -> Event -> Transition -> Feedback -> Cost | 作用域、名字、状态所有者与反馈 |

共同的八槽语言 `Object / State / Scope / Mapping / Resource / Event / Invariant / Cost` 只用于跨科比较，不替代各科学科内核。

## 3. 产品层级

每科都采用同一产品关系：

```text
Atlas
-> Topic
-> Bridge
-> Integration

Subject Rules 与上述 Knowledge 并列
Inbox 为学习输入，不属于稳定知识
```

- Atlas 只提供母问题、专题地图和导航；
- Topic 拥有局部机制；
- Bridge 拥有接口，不重写两侧机制；
- Integration 拥有一条真实过程，不拥有参与机制；
- Rules 保存可执行做题动作；
- Inbox 允许模糊、重复和未验证想法。

## 4. 目录决策

学科内部 Topic、Bridge 和 Integration 留在学科目录；真正跨学科的内容统一放在 `50_桥梁专题/` 或 `60_综合专题/`。

例如：

- 网络内部的“一个网络请求的一生”属于网络 Integration；
- 数据结构的“遍历统一模型”属于数据结构内部 Bridge；
- `Cache x VM x OS` 属于跨学科 Bridge；
- `OS x Network` 属于跨学科 Bridge；
- “程序通过 socket 读取网络数据的一生”属于跨学科 Integration。

这样既保留专题的自然归属，也避免同一 Bridge 在两科各维护一份。

## 5. 四科规模与核心 Topic 映射

| 学科      | Atlas | 核心 Topic 清单                                                                                               |         科内 Bridge | 科内 Integration |
| -------- | ------: | ------------------------- | ---------: | ------------: |
| 数据结构    |     1 | 14 个 Topic（分属 6 个知识域：线性表、树与二叉树、图、查找、排序、抽象数据类型）                                                            |                 3 |     1：从需求到结构选择 |
| 计算机组成原理 |     1 | 8 个 Topic（数据表示、运算器、存储器、指令系统、CPU控制、总线、中断、流水线）                                                              |   1：C x ISA x CPU |      1：一条指令的一生 |
| 操作系统    |     1 | **5 个核心 Topic**：<br>1. 进程线程调度与控制权<br>2. 并发专题与信号量 PV<br>3. 内存虚拟化与页生命周期<br>4. I/O 系统与请求搬运<br>5. 文件系统与名称对象索引 | 以 VM x File 等接口为主 |     1：内核跨子系统过程 |
| 计算机网络   |     1 | 8 个 Topic（物理层、数据链路、网络层 IP、传输层 TCP/UDP、应用层、网络安全等）                                                          | 跨 OS 部分放全局 Bridge |    1：一个网络请求的一生 |

专题数量表示独立母问题的数量，不规定篇幅。短专题不必扩成大册，核心册也不为追求整齐而压缩。

## 6. 跨学科主桥梁

1. `C x ISA x CPU`：程序语义怎样落实为指令和数据通路；
2. `Cache x VM x OS`：地址翻译、缓存访问和缺页修复怎样接力；
3. `Interrupt / DMA x OS`：硬件完成机制怎样触发内核状态变化；
4. `OS x Network`：socket、协议栈、NIC 与进程怎样交接；
5. `Data Structure x Systems`：队列、树、Hash、Heap 等结构怎样成为系统机制的实现手段。

## 7. Control 架构

通用做题内核只维护一份，各科 Adapter 只增加本学科必须观察的维度：

| 学科 | 起手检查 |
|---|---|
| 数据结构 | Relation / Representation / Operation / Invariant / Boundary / Cost |
| 计组 | State / Location / Path / Resource / Timing / Commit |
| OS | Object / Relation / Queue / Event / Mechanism / Policy / New State / Cost |
| 网络 | Scope / Object / Name / State Owner / Event / Transition / Feedback / Cost |

性能是跨 Topic 的评价语言，默认进入 Rules/工具箱，不因为公式很多就成为虚假的硬件或协议 Topic。

## 8. 发布与既有材料

现有 LaTeX/PDF 保持 `legacy-unregistered`，按以下顺序渐进纳管：

1. 先确认它对应哪个 Atlas、Topic、Bridge 或 Integration；
2. 再确认 Owns、Uses 和停止边界；
3. 处理重复和事实错误；
4. 只有发生真实内容修订时才同步 LaTeX/PDF。

框架文件不证明专题已经完成，也不把大纲列项直接升级为心智模型。

## 9. 覆盖来源的使用原则

考试大纲只用于检查“有没有漏掉考试范围”，不决定知识架构。当前用户提供的新东方 2026 版 408 大纲转载可作为临时覆盖清单；正式发布覆盖声明前，应再与当年官方考试大纲核对。

协议与工程事实优先参考原始标准，例如 TCP 的 RFC 9293、HTTP 语义的 RFC 9110 和 DNS 的 RFC 1034，但工程扩展必须与 408 教材模型分层呈现。

## 10. 框架完成的判据

框架搭建完成不等于专题完成。当前阶段只要求：

- 四科学科内核不互相冒充；
- 每个计划 Topic 有唯一母问题和规划 Owner；
- 跨学科内容只有一个入口；
- Atlas、Rules 和 Inbox 能够被直接使用；
- 旧发布物有明确的渐进纳管路径。
