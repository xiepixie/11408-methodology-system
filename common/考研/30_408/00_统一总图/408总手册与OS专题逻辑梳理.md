# 408 总手册与 OS 专题逻辑梳理

> 当前状态：工作梳理稿。本文先确定产品职责、母模型和边界，不直接改写既有 LaTeX。

## 1. 先给结论

现有材料不是“一个总手册加五本补充讲义”，而是四个不同层级的产品：

1. **系统三科总手册**：统一网络、计组和 OS 的观察语言；
2. **OS 五本 Topic**：分别拥有进程、并发、虚存、I/O、文件系统的局部机制；
3. **OS 综合手册**：拥有跨专题状态轨迹；
4. **408 Rules**：以后拥有题目识别、起手、检查和退出规则。

最重要的重分类是：

> `408三科统一方法论手册_网络_计组_OS_v1.tex` 只覆盖网络、计组、OS，不包含数据结构。它适合定位为“系统三科 Atlas + Integration”，不能单独充当完整 408 Atlas。

完整 408 Atlas 以后才回答：

$$
\text{Data Structure}
\to \text{Program}
\to \text{Machine}
\to \text{Operating System}
\to \text{Network}
$$

## 3. 两层统一模型

### 3.1 系统三科共同观察语言

现有总手册最有价值的部分，是用以下问题观察任意计算系统：

$$
\text{Object}+
\text{State}+
\text{Scope}+
\text{Mapping}+
\text{Resource}+
\text{Event}+
\text{Invariant}+
\text{Cost}
$$

它的职责不是解释所有知识点，而是让网络、计组、OS 能够比较：

- 什么对象正在变化；
- 状态由谁保存；
- 事件在哪一层发生；
- 哪些映射跨越层级；
- 哪个资源成为瓶颈；
- 什么不变量必须维持；
- 代价最终落在哪里。

### 3.2 OS 统一状态模型

OS 综合手册已经给出更适合 OS 内部的唯一语言：

$$
S_t=(O_t,R_t,Q_t)
$$

- $O$：Objects，当前存在的内核对象及内部状态；
- $R$：Relations，引用、映射、所有权和命名关系；
- $Q$：Queues，运行、等待、请求和回收队列。

事件到来后：

$$
\mathcal A_t=M(S_t,E_t),
\qquad
a_t=\pi(S_t,E_t,\mathcal A_t),
$$

$$
S_{t+1}=T(S_t,E_t,a_t),
\qquad
I(S_{t+1})=\mathrm{true},
\qquad
\min C.
$$

因此 OS 总图只需要反复问：

```text
现在有哪些对象、关系和队列？
发生了什么事件？
机制允许怎样改变？
是否需要策略选择？
新状态是否合法？
代价是什么？
```

五本 Topic 都应当是这一个模型在不同对象类型上的投影，不再各自发明另一套“总方法论”。

## 4. 五本 OS Topic 的唯一职责

### 4.1 Process / Control

**母问题**：用户程序怎样直接使用 CPU，而内核仍能安全收回控制权，并把 CPU 分给多个执行流？

**Owns**：

- program、process、thread、task 的边界；
- 用户态、内核态和受控入口；
- syscall、exception、interrupt 的抽象区别；
- Ready、Running、Blocked、Zombie 等状态；
- block、wakeup、schedule、context switch；
- fork、exec、exit、wait 的进程生命周期；
- 调度机制、策略和经典算法。

**Uses**：

- 地址空间和 COW：VM Topic；
- fd、OFD、inode：File System Topic；
- 设备请求与完成：I/O Topic；
- 锁和条件等待：Concurrency Topic。

**停止边界**：只追踪 task 的状态和资源引用。不得完整解释文件对象、页表或设备路径。

### 4.2 Concurrency

**母问题**：在所有允许的执行交错中，怎样保持安全性、顺序、进展和可接受成本？

**Owns**：

- interleaving 与原子性；
- mutual exclusion 与 condition synchronization；
- semaphore、mutex、condition variable、monitor 的同步语义；
- wait、signal、lost wakeup 等并发关系；
- safety、liveness、fairness；
- deadlock、livelock、starvation；
- 经典 PV 模型作为并发结构模式。

**Uses**：

- task block/wakeup 和调度：Process Topic；
- 硬件原子指令：计组 / CPU x OS Bridge；
- 具体 I/O 或文件条件：对应 Topic。

**停止边界**：负责同步约束，不拥有调度算法、设备完成路径或某个业务对象的完整生命周期。

### 4.3 Virtual Memory

**母问题**：怎样让每个进程看到独立、连续、受保护且可按需扩展的地址空间？

**Owns**：

- VA、VPN、Offset、PTE、Frame 和地址翻译；
- TLB 与页表层次；
- Page Fault 的分类、修复与 retry；
- page lifecycle、demand paging、replacement；
- working set、thrashing、frame allocation；
- COW、anonymous mapping 和 file-backed mapping 的 VM 语义；
- 物理页分配和回收的 OS 侧模型。

**Uses**：

- MMU、Cache 和 TLB 硬件实现：计组 / CPU x OS Bridge；
- 文件身份、offset 和 block mapping：File System Topic；
- 文件页请求和 writeback：VM x File Bridge / I/O Topic；
- task 与地址空间关系：Process Topic。

**停止边界**：`mmap` 只追到“文件成为虚拟页的 backing object”。路径、OFD、inode 和设备请求分别交给文件系统与 I/O。

### 4.4 I/O

**母问题**：同步执行的 CPU 和进程，怎样接入速度不同、异步完成的外部设备？

**Owns**：

- request、submit、wait/continue、complete、notify 的 OS 路径；
- controller、driver、device-independent I/O 的软件边界；
- polling 与 interrupt-driven I/O 的控制差异；
- blocking/nonblocking 与 synchronous/asynchronous 的正交关系；
- buffer、spooling、设备分配、请求队列和磁盘调度；
- I/O completion、错误和持久性边界请求；
- OS 如何配置和使用 DMA。

**Uses**：

- DMA 控制器、总线周期和硬件传输：计组 I/O Topic；
- task block/wakeup：Process Topic；
- file、block mapping 和 durability protocol：File System Topic；
- page residency 和 reclaim：VM Topic。

**停止边界**：I/O 负责请求进入设备层以后直到完成通知；不拥有路径解析、页表或完整进程生命周期。

### 4.5 File System

**母问题**：怎样在块式持久存储上建立可命名、可共享、可随机访问、可恢复的对象世界？

**Owns**：

- pathname、directory、dentry、inode、VFS 和 mount；
- fd、Open File Description、offset 和共享关系；
- name lifetime 与 open/reference lifetime；
- byte range、logical block 和 physical layout；
- 连续、链接、索引分配与空闲空间；
- open/read/write/close/unlink/rename 的文件系统侧语义；
- dirty metadata/data、journal、fsck、crash consistency 和 durability contract。

**Uses**：

- task 的 files 引用：Process Topic；
- cached page 的内存驻留和回收：VM Topic；
- block request、driver 和 completion：I/O Topic。

**停止边界**：`read()` 只追到“形成 block I/O request”；之后的 DMA、interrupt 和 wakeup 交给 I/O 与 Process。

## 5. 三个最需要明确的共享边界

### 5.1 Page Cache

当前 I/O、VM 和文件系统手册都在解释 Page Cache，不能简单指定其中一本完整拥有全部语义。

建议边界：

| 问题 | Owner |
|---|---|
| `(file, page index)` 怎样对应文件内容 | File System Topic |
| cached page 怎样驻留、映射、回收 | VM Topic |
| cache miss 怎样形成请求，dirty page 怎样进入 writeback | I/O Topic |
| file object、cached page、mapping 和 writeback 的共同生命周期 | VM x File Bridge |

因此 Page Cache 本身应登记为一个 Bridge 问题。三本 Topic 只拥有自己的投影。

### 5.2 DMA

| 问题 | Owner |
|---|---|
| DMA 控制器、总线占用、传输方式 | 计组 I/O Topic |
| 内核/驱动怎样准备 buffer、描述符和请求 | OS I/O Topic |
| CPU 与 OS 如何交接控制权和地址 | CPU x OS Bridge |
| DMA 完成后怎样 interrupt、complete、wake | OS I/O + Process 接口 |

现有 OS I/O 手册中的 DMA 总线方式属于计组机制，后续应压缩为引用；OS 侧保留“怎样使用 DMA”。

### 5.3 Open File Description

OFD 的完整定义归 File System Topic。Process Topic 只需要知道：

```text
task/process -> fd table -> OFD
```

用来解释 fork、dup、资源继承和生命周期即可，不再展开 dentry、inode 和 block mapping。

## 6. `read()` 的唯一完整轨迹

`read()` 是跨专题 Integration，不属于任何单一 Topic。完整轨迹应只由 OS 综合手册拥有：

```text
User task
-> controlled kernel entry
-> fd / OFD / file / offset
-> Page Cache lookup
-> block mapping if needed
-> submit I/O request
-> task blocks and scheduler runs another task
-> controller / DMA transfers
-> interrupt and completion
-> wake task to Ready
-> later reschedule
-> copy/map result and return
```

各手册只保留自己的投影：

| 手册 | `read()` 中保留的部分 |
|---|---|
| Process | syscall entry、Running -> Blocked、Wake -> Ready、reschedule |
| VM | user buffer validation、page residency、file-backed page 关系 |
| I/O | request、driver、transfer、completion、interrupt |
| File System | fd、OFD、offset、cache key、block mapping |
| OS Integration | 上述各段怎样交接，拥有唯一完整时间线 |
| 系统三科总手册 | 只保留一条压缩跨科路径，用于展示统一语言 |

并发专题只在 `read()` 涉及锁、wait queue 或条件同步时被引用，不应为了完整而固定插入每条路径。

## 7. 现有手册的主要越界与处理建议

| 当前位置 | 当前问题 | 后续动作 |
|---|---|---|
| 系统三科总手册 OS 章节 | 从 trap 一直重讲到文件系统，实质上是另一套压缩 OS 教材 | 收缩为 OS Atlas：母问题、五张 Topic 卡、接口图、两条超级轨迹 |
| Process 手册的 fd/OFD/dentry/inode 章节 | 完整解释文件系统对象，越过 task resource reference 边界 | 只保留 task -> files -> fd table 引用图，详细定义链接 File System |

### 应当下沉

2. 完整进程状态生命周期；
3. PV 模式、页面置换算法、磁盘调度算法；

5. 各学科完整解题清单；

### 总手册的合格停止条件

读完总手册后，读者应当能够：

- 说清三科分别研究什么；
- 把一个新概念挂到正确 Topic；
- 识别一次跨层事件涉及哪些 Owner；
- 选择下一本应该阅读的专题；
- 用共同语言描述状态、事件、映射、不变量和成本。

读者不需要仅凭总手册完成所有专题计算题。

## 10. 五本 Topic 的共同阅读骨架

不要求机械使用相同章节名，但逻辑顺序应稳定：

```text
Position / Boundary
-> Mother Problem
-> Mother Model
-> Objects / Relations / Queues
-> Events / Mechanisms / Policies
-> Lifecycle
-> Invariants / Cost
-> Interfaces
-> 408 Exam Interface
-> Compression
```

其中 `408 Exam Interface` 只告诉读者怎样进入对应 Rules，不再在每本 Topic 中维护一套彼此不同的通用解题内核。

## 11. 推荐学习顺序

```text
系统三科统一底座
-> Process / Control
-> Concurrency
-> Virtual Memory
-> I/O
-> File System
-> CPU x OS Bridge
-> OS Integration
-> 408 Rules 与真实题目验证
```

原因：

- 进程提供控制权、task state 和 block/wakeup 语言；
- 并发建立等待、互斥和进展约束；
- VM 建立地址和页的对象世界；
- I/O 建立异步请求与完成路径；
- FS 使用前面四者建立持久对象世界；
- Integration 最后让这些机制同时运行。

## 12. 需要优先修正的事实表达

系统三科总手册的 OS 压缩章包含一些把 x86 示例写成通用结论的表达，正式修订时应优先处理：

1. “CPU 只有一个核心”应改为“每个逻辑 CPU 在一个时刻只有一条当前执行流，CPU 时间仍是受竞争资源”；
2. `CPL` 与 segment selector 的 `RPL` 不能并写成同一个用户态值；
3. `syscall` 与 `int/exception` 的入口、栈切换和保存现场路径不能统一写成“都经 IDT 并自动保存同一组寄存器”；
4. Context Switch 不一定切换地址空间，切换地址空间也不等于现代硬件必然清空全部 TLB；
5. Timer Interrupt 提供抢占机会，不等于每次都发生 Context Switch；
6. Page Fault 不一定产生 I/O；
7. `read()` 的完整慢路径必须明确假设 page cache miss、需要设备 I/O 且调用线程选择阻塞。

这些内容在专题手册中已经有部分校准。总手册后续应引用专题的准确抽象，不再维护一套更具体但更脆弱的实现叙述。
