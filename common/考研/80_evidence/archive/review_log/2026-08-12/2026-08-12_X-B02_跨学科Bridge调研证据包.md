# X-B02 地址翻译硬件 × OS 虚拟内存：首轮调研证据包

## 结论等级

- **Canonical Update**：X-B02 可以从“目录已建立，正文未建”升级为有唯一深度正文的 Bridge。
- **事实**：现有 CO07 / OS03 两个独立 Owner 已存在；交接可以稳定写成 `mapping state -> hardware consumption -> result/fault -> OS repair -> retry`。
- **模型判断**：首轮采用“配置—消费—失败—修复—重试”模型，比“硬件翻译 + OS 缺页”并列清单更能生成题目起手和反例。
- **未决**：不同 ISA 的具体 trap frame、TLB shootdown 和 page-walk 责任不能在 X-B02 中统一成同一条实现细节。

## 一手来源与可复核事实

| 来源 | 复核事实 | 在 Bridge 中的用途 |
|---|---|---|
| [Linux Kernel: Page Tables](https://docs.kernel.org/mm/page_tables.html) | 页表把 CPU 看到的虚拟地址映射到外部总线看到的物理地址；层级表可用高层条目表达大范围映射并减少稀疏空间开销 | 支撑“OS 维护映射状态，硬件消费映射”的共同语言 |
| [RISC-V ISA Manual: supervisor.adoc](https://github.com/riscv/riscv-isa-manual/blob/main/src/priv/supervisor.adoc) | `satp` 保存根页表 PPN、ASID 与翻译模式；trap 进入 S-mode 时写入 `sepc` 与 `scause`；原因码包含 U/S environment call、load/store page fault；`SRET` 按 `SPP` 恢复特权级 | 给出一个可检查的架构实例，约束“fault 后保存现场、识别原因、恢复/终止” |
| [Linux Kernel: Dynamic DMA mapping Guide](https://docs.kernel.org/core-api/dma-api-howto.html) | CPU virtual、CPU physical、device bus address 不是同一地址空间；IOMMU 可能把 DMA 地址映射到物理内存 | 暂不纳入 X-B02 正文主线；作为 X-B03 后续调研的边界提醒，防止把 CPU 地址翻译与 DMA 地址翻译混写 |
| [POSIX `read()`](https://pubs.opengroup.org/onlinepubs/9699919799/functions/read.html) | blocking `read()` 在无数据时可以阻塞；socket 上 `read()` 等价于 `recv()` | 支撑 X-I02 / X-B04 的后续候选，但不把文件阻塞生命周期误并入 X-B02 |

## 形成的心智模型

```text
OS mapping policy
  -> page-table/PTE state
  -> MMU/TLB consumes state
  -> success (PA + permission) OR fault (cause + saved context)
  -> OS repairs / rejects
  -> invalidate-or-isolate stale translation
  -> retry instruction or terminate
```

## 明确阻断的类比

1. TLB miss 不是 page fault；前者可能由硬件 page walk 完成。
2. Page fault 不是 Cache miss；前者涉及映射/驻留/权限合法性，后者涉及数据副本。
3. CPU virtual-to-physical translation 不是 device bus address mapping；后者可能经过 IOMMU，留给 X-B03。

## 下一轮研究顺序

1. X-B03：以 Linux DMA API + generic IRQ 文档验证“地址空间—设备所有权—完成事件—唤醒”的接口，重点查清 DMA mapping/sync 与中断分层。
2. X-B01：用同一 RISC-V trap 规范补齐 system call/exception/return 的 Bridge 正文，并与 X-B02 共享“保存现场—原因—恢复/终止”词汇。
3. X-B04：再用 POSIX `read` 与 RFC 9293 的 endpoint/state 约束 Candidate 是否值得升格，不因工程真实自动晋升 408 Core。
