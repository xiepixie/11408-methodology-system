# 408-2018-Q46

## Model Anchor

- Topic：inode 多级索引的可达数据簇数量、元数据瓶颈与访问路径长度。
- 题目信号：簇 4 KB、地址项 4 B、8 个直接地址 + 一级/二级/三级间接各 1 个。
- 第一动作：先算“一簇索引块能装多少簇号”，建立 fan-out；之后三问分别是容量、双资源瓶颈、最后一簇的索引路径深度。

## Problem Representation

每个间接索引块大小就是 1 个簇 4 KB；每个地址项 4 B，因此一个索引块可保存

$$N=\frac{4\text{ KB}}{4\text{ B}}=1024=2^{10}$$

个簇号。

于是 inode 的 11 个地址入口形成：

```text
8 direct          -> 8 data clusters
1 single indirect -> 1024 data clusters
1 double indirect -> 1024^2 data clusters
1 triple indirect -> 1024^3 data clusters
```

这里“索引块本身占数据区簇”与“文件可寻址的数据内容”是两个不同计数对象；第 (1) 问问最大文件长度，只统计可指向的数据簇容量。

## Decision Points

1. 最大文件长度：按可寻址的数据簇数乘簇大小。
2. 最多文件数：同时受 inode 数量与数据簇数量约束，取二者较小值。
3. 最后一簇定位时间：看最后一簇落在 direct 还是 indirect 区间；比较的是元数据访问路径，而不是单纯文件大小。

## Solution Chain

### (1) 最大文件长度

可寻址数据簇总数：

$$8+1024+1024^2+1024^3.$$

每簇 4 KB，因此最大文件长度为

$$\boxed{(8+1024+1024^2+1024^3)\times4\text{ KB}}.$$

也可以分层看成约：

```text
8 direct      -> 32 KB
single        -> 4 MB
double        -> 4 GB
triple        -> 4 TB
```

故总容量约为 `4 TB + 4 GB + 4 MB + 32 KB`。

### (2) 最多可存多少个 5600 B 图像文件

先看 inode 资源。

inode 区有 $1M=2^{20}$ 个簇，每簇 4 KB，每个 inode 64 B，所以 inode 总数

$$2^{20}\times\frac{2^{12}}{2^6}=2^{26}=64M.$$

因此文件数最多不能超过

$$64M.$$

再看数据簇资源。5600 B 文件需要

$$\left\lceil\frac{5600}{4096}\right\rceil=2$$

个数据簇。

数据区共有 512M 个簇，所以仅按文件数据计算可容纳

$$\frac{512M}{2}=256M$$

个文件。

两个独立资源上界取最小：

$$\min(64M,256M)=\boxed{64M\text{ 个}}.$$

inode 数量是本题真正的瓶颈。

### (3) F1=6 KB 与 F2=40 KB 获取最后一簇号时间是否相同

#### F1：6 KB

需要

$$\left\lceil\frac{6}{4}\right\rceil=2$$

个数据簇。前 8 个数据簇都可以直接由 inode 中的 8 个 direct address 指向，所以 F1 最后一簇号直接在 inode 内得到，无需读取间接索引块。

#### F2：40 KB

需要

$$\frac{40}{4}=10$$

个数据簇。

前 8 个由直接地址覆盖；第 9、10 个已经进入一级间接区。因此要得到最后一个数据簇号，需要：

```text
inode
-> single-indirect pointer
-> read indirect index block
-> obtain 10th data-cluster number
```

比 F1 多一次间接索引块访问。

所以

$$\boxed{\text{所需时间不相同，F2 更长}}.$$

## Verification

边界检查：

- `8 × 4 KB = 32 KB` 是 direct/indirect 的准确分界；
- F1=6 KB <32 KB，必在 direct 区；
- F2=40 KB >32 KB，只超出 8 KB，即还只需要一级间接，不可能触发二级间接。

第 (2) 问也可做数量级检查：数据簇资源能供 256M 个文件，但只有 64M 个 inode，显然 inode 先耗尽。

## Compression

```text
4KB block / 4B address = 1024 pointers
-> capacity = (8 + 1024 + 1024^2 + 1024^3)*4KB
-> max file count = min(inode capacity, data-cluster capacity)
-> locate last block by index depth
-> 32KB is direct/indirect boundary
```

## 易错边界

- “文件占 2 个数据簇”不代表文件系统总共只消耗 2 个簇；若进入间接区还可能消耗索引簇。但本题 5600 B 文件完全由 direct 地址覆盖，不需要额外索引簇。
- 最大文件长度统计的是**数据内容可寻址范围**，不要把间接索引块自身容量再当文件数据加进去。
- inode 数与数据簇数是两个独立资源池，最大文件数必须取瓶颈。
