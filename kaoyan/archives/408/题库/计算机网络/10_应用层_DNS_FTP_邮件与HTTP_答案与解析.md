# 10｜应用层：DNS、FTP、邮件与 HTTP｜答案与解析

> 对应题面：[`10_应用层_DNS_FTP_邮件与HTTP_选择题.md`](10_应用层_DNS_FTP_邮件与HTTP_选择题.md)

## 解题总轴

应用层题最容易把“应用语义”和“下层连接状态”混在一起。固定按事件链推进：

- DNS：`stub resolver → local recursive resolver → root/TLD/authoritative → cache`；
- FTP：`control connection` 与 `data connection` 分开；
- HTTP：先确定 TCP 是否已建立，再确定 persistent / non-persistent / pipeline / parallel；
- NAT：按 tuple 查已有映射，不能只看某个 IP 是否出现过。

> 使用方式：先看“答案速查”；需要理解时点击题号跳到逐题解析。原有解析与高频模型完整保留，只改阅读结构。

## 逐题解析

### 959

**答案：C**

C/S 模型中客户端通常先发起请求，但连接建立后服务器当然可以发送响应和后续数据，因此只有 IV 错。

### 960

**答案：B**

P2P 是应用/逻辑组织方式，不是与 Internet 并行的一张独立物理网络；peer 的请求方/服务方角色可以动态变化。

### 961

**答案：D**

通常 client 面向用户交互，server 面向服务/任务处理；D 把两者角色倒置。

### 962

**答案：C**

P2P overlay 运行在现有网络之上，不是另建一张独立物理 Internet。

### 963

**答案：D**

域名可对应多个 IP，多个域名也可指向同一 IP/主机，因此与 IP、MAC、主机都不存在严格一一对应。

### 964

**答案：D**

DNS 的核心是域名空间、分布式数据库、域名服务器/解析器体系；NAT 地址转换不是 DNS 组成部分。

### 965

**答案：C**

主机 stub resolver 只需知道本地递归解析器地址；根 hints、上级委派等是递归解析器侧知识，因此 II、III 不必由终端预先知道。

### 966

**答案：A**

递归语义是“最开始接受客户端递归请求的 resolver 负责把最终结果带回来”，不是让最终权威服务器绕过中间层直接回复原客户端。

### 967

**答案：C**

本地没有缓存和更具体 delegation 时，迭代解析从 root 开始：root 返回 `.com` referral，随后再查 TLD 和权威服务器。

### 968

**答案：A**

手机二层已接入但尚无 IP 配置时，首先要通过 DHCP 获得地址、前缀、网关、DNS 等，之后才进入 DNS/TCP/ARP 等步骤。

### 969

**答案：B**

普通终端通常把递归请求交给本地递归解析器，由 resolver 代表终端执行后续迭代；终端自己逐级问 root/TLD 并不是普遍工作模式。

### 970

**答案：A**

Internet 服务可以直接通过 IP 地址访问，域名不是协议硬条件；B、C、D 都可以出现。

### 971

**答案：C**

权威 DNS 保存 zone 中的权威 RR，负责对其管辖名字给出权威答案。

### 972

**答案：B**

host→local resolver 只有 1 条递归请求；local resolver 在迭代解析中通常要向多个层级服务器发送多条查询。

### 973

**答案：A**

题设明确是理论“全递归链”：host 只发 1 条给 local；local 只向上级发 1 条递归请求，后续由被查询服务器继续代查。

### 974

**答案：C**

经典 FTP 可通过控制命令选择数据表示类型等传输表示方式，因此可对文件类型/表示进行相应配置。

### 975

**答案：C**

FTP server 的控制连接熟知端口是 TCP 21；client 本地控制端口通常动态分配，不固定为 20。

### 976

**答案：C**

control connection 先建立并贯穿会话；data connection 按需要后建、传输完成后先释放。

### 977

**答案：D**

FTP server 在 TCP 21 监听新的 control connection。

### 978

**答案：C**

FTP 主控制进程监听 21，不是 20；TCP 20 是经典主动模式数据连接的服务器侧源端口。

### 979

**答案：D**

客户端并不默认使用本地 20；主动模式中通常是 server:20 主动连接客户端指定的数据端口。

### 980

**答案：D**

FTP 会话先建立控制连接，之后才根据命令建立数据连接。

### 981

**答案：C**

一次数据传输结束只关闭对应 data connection，control connection 保持到 FTP 会话结束。

### 982

**答案：A**

**判断抓手：先看这两个协议需要什么传输语义。** SMTP 负责邮件服务器之间/客户端到服务器的可靠命令与邮件内容传送，POP3 也需要可靠的命令—响应和邮件下载，因此两者都建立在 TCP 之上，而不是使用无连接 UDP。

### 983

**答案：A**

客户端可通过 POP3 的删除操作决定是否把已取回邮件标记删除；不是服务器单方面决定。

### 984

**答案：A**

SMTP 使用 TCP；SMTP 本身不天然提供端到端加密。MIME 的目的之一是支持非 ASCII 与多媒体内容表示。

### 985

**答案：B**

From/To/Subject 等字段可以由用户或应用生成，不能说全部“只能由系统自动生成”。

### 986

**答案：B**

传统 USER/PASS 在无 TLS 等保护时不会自动加密密码。

### 987

**答案：C**

URL 使用域名且 DNS 未缓存时，必须先得到服务器 IP，才能建立到目标服务器的 TCP connection。

### 988

**答案：D**

同一 IP、同一端口仍可承载多个基于名称的虚拟主机；HTTP/1.1 使用 `Host` 字段（HTTP/2/3 对应 authority）告诉服务器当前请求属于哪个站点。

### 989

**答案：D**

HTTP/1.0 默认 non-persistent；在不使用扩展时，每个独立对象通常建立独立 TCP connection。

### 990

**答案：D**

查询目标资源支持哪些方法应使用 `OPTIONS`；`PUT` 的核心语义是创建/替换目标资源表示。

### 991

**答案：D**

persistent connection 的价值就是同一 TCP connection 连续承载多个请求/响应，不要求每个对象都另开一条“持续连接”。

### 992

**答案：A**

HTML 本体 + 3 图片=4 个对象；HTTP/1.0 默认每对象 1 条 TCP connection，共 4 条。HTTP 本身不建立 UDP connection。

### 993

**答案：D**

已排除 TCP 建连时间，从第一个 HTTP request 开始：HTML 1 RTT，5 个图片非流水线逐个各 1 RTT，共 6 RTT。

### 994

**答案：B**

TCP 已建立且 persistent non-pipelined：HTML 1 RTT + 3 个 JPEG 各 1 RTT=4 RTT。

### 995

**答案：A**

先用 1 RTT 取得 `rfc.html`；拿到 HTML 后一次流水线发送 3 个图像请求，这一批再用 1 RTT，因此总计 2 RTT。

### 996

**答案：B**

TCP handshake 1 RTT=150 ms；HTML 请求/响应 1 RTT=150 ms；10 图像各需 `150+35=185 ms`，总计 `150+150+1850=2150 ms`。

### 997

**答案：C**

正常成功访问需要 DNS、HTTP、TCP；题设指定 next-hop MAC 未缓存，因此还要 ARP。没有异常就不必使用 ICMP。

### 998

**答案：A**

Cookie 保存在 client/browser 并随后续请求回送；server 可维护关联 session state，但不能说 Cookie 只存在服务器端。

### 999

**答案：D**

页面包含基本 HTML + 100 图片，共 101 个对象；non-persistent 模型需要 101 条 TCP connections，不是 100。

### 1000

**答案：B**

NAPT 映射按 tuple 区分。`192.168.32.56:80` 与已有同主机的 `:21/:20` 是不同内部端点，需要分配新的公网端口并建立新映射。

## 高频模型

### DNS 先区分 recursion 与 iteration

- recursion：被请求服务器替客户端继续查，并把最终结果带回来；
- iteration：服务器返回“我不知道最终答案，但下一步可以去问谁”的 referral。

典型缓存为空的 resolver 流程是：

```text
local resolver → root → TLD → authoritative → answer
```

### HTTP 时延题必须先写四个前提

1. TCP 是否已建立；
2. persistent 还是 non-persistent；
3. pipelined 还是 non-pipelined；
4. 多对象是串行、流水线还是并行多连接。

不把这四个状态先写出来，就不能直接从“HTTP/1.1”推出 RTT 数。
