## 逐题解析

### 912

**答案：D**

**判断抓手：先区分“连接语义、可靠性、数据边界”三个维度。** TCP 在通信前建立连接状态，通过序号、确认、超时重传等机制实现可靠且按序交付；向应用暴露的是连续字节流，而不是保留一次次应用写入的消息边界。

### 913

**答案：D**

可靠性来自 Seq/ACK/Timer/重传/重复抑制等闭环，不是“有连接”或“有窗口”自动产生。

### 914

**答案：D**

给定传输协议后，IP 地址定位主机，端口号定位主机中的传输端点。

### 915

**答案：C**

socket endpoint 可以区分同一主机上的不同应用端点；TCP connection 还要结合对端 endpoint。

### 916

**答案：D**

UDP 不提供可靠重传/排序；若应用仍要求可靠语义，只能由应用协议自行补足。

### 917

**答案：D**

HTTP 服务器常监听 80，但客户端通常使用动态短暂端口；TCP/UDP 的同数字端口又属于不同协议命名空间。

### 918

**答案：B**

UDP Length 只统计 UDP header + data；pseudo-header 只参与 checksum 计算，不在线传输，也不计入 UDP Length。

### 919

**答案：D**

UDP 无连接，不保证顺序，不维护流量控制窗口，但支持多路复用/分用。

### 920

**答案：C**

UDP 相比 IP 增加端口命名和传输层分用能力，不增加路由、流控或拥塞控制。

### 921

**答案：B**

IPv4 UDP 若计算出的 checksum 为全 0，线上用 `0xFFFF` 表示该校验值，以免与“checksum 未使用”的 `0x0000` 混淆。

### 922

**答案：A**

UDP/TCP checksum 按 16 bit 字做反码加法，不是按 4 B 对齐。奇数字节时只为计算临时补 1 个零字节。校验失败的 datagram 应视为损坏并丢弃；pseudo-header 把源/目的 IP 等也纳入完整性检查。

### 923

**答案：B**

UDP payload 9192 B，加 8 B UDP header 得 9200 B IP payload；每个非末片最多承载 1480 B，`ceil(9200/1480)=7`。

### 924

**答案：C**

不分片时线上总字节 `2000+20(TCP)+20(IP)+18(Ethernet)=2058`，效率 `2000/2058≈97.19%`。

### 925

**答案：B**

TCP segment 2020 B 作为 IP payload，被分成 1480+540；两片各加 20 B IP header 与 18 B Ethernet 开销，总计 2096 B，效率约 95.42%。

### 926

**答案：C**

总线上字节 `200+8+60+18=286 B`，应用效率 `200/286≈69.9%`。

### 927

**答案：D**

端口是主机本地命名空间，不同主机当然可以使用相同 TCP 端口号。

### 928

**答案：D**

TCP 在 IP 伪首部中的 Protocol 值为 6；17 是 UDP。

### 929

**答案：C**

TCP 是 byte stream，segment 尺寸可受 MSS、路径 MTU、rwnd、cwnd 和当前发送状态共同约束，不保留应用 write 边界。

### 930

**答案：B**

TCP 首部 `Window` 字段通告的是接收端 `rwnd`，用于**流量控制**；`cwnd` 是发送端本地拥塞状态，并不直接写入 TCP 首部 Window 字段。A、C、D 均成立。

### 931

**答案：D**

TCP 把应用数据解释成连续字节流，再按需要切成 segment；不会保留应用一次 write 的消息边界。

### 932

**答案：C**

`ack=100` 表示下一期望 byte 是 100，因此此前连续收到的最后一个 byte 是 99。

### 933

**答案：C**

`cwnd` 由发送端根据网络反馈维护；接收端通告的是 `rwnd`。

### 934

**答案：A**

第一步 `SYN,seq=X`；第二步 `SYN+ACK,seq=Y,ack=X+1`，对应 I、VI。

### 935

**答案：D**

第二次握手既确认 client SYN，又发送 server SYN，因此 SYN、ACK 都置 1。

### 936

**答案：C**

第三次握手的知识增量是：server 终于知道 client 已经收到 server 的 SYN/ISN，双方序号空间同步闭环完成。

### 937

**答案：C**

A 发送 byte 200、201，所以 B 的累计确认应为 `ack=202`；若 B 没有新数据，其 next seq 可仍为 201。

### 938

**答案：C**

三次握手中 ACK=1 出现在第 2、3 段共 2 次；SYN=1 出现在第 1、2 段共 2 次；FIN 一次也没有。

### 939

**答案：C**

server ISN 可以取 1001，只要返回 `SYN=1,ACK=1,ack=1001` 即合法；C 是一个可能实例。

### 940

**答案：B**

FIN 只关闭本方向发送，TCP 支持 half-close；反方向未关闭时仍可继续接收对方数据。

### 941

**答案：C**

client FIN 到 server 0.5 RTT；server 立即 ACK+FIN 回 client 再 0.5 RTT；最终 ACK 回 server再 0.5 RTT，共 1.5 RTT。

### 942

**答案：C**

SYN 占用一个 sequence number；ISN=200 后第一个数据 byte 序号为 201。

### 943

**答案：C**

首数据从 1667 开始，1000 B 覆盖 1667–2666，下一期望 byte 为 2667。

### 944

**答案：C**

TCP Window 的量纲是 byte；3000 B 发送窗口意味着最多约 3000 B 未确认数据受当前窗口约束。

### 945

**答案：C**

第 3 段 `seq=1000`，第 2 段长 300 B，所以第 2 段从 700 开始；乙缺少第 2 段时累计 ACK 停在 700。

### 946

**答案：C**

`ack=311` 表明 A 刚发送的 10 B 覆盖 301–310，所以 A 的 `seq=301`；乙 `seq=401` 表示 A 对反向数据的 ACK 可为 401。

## 高频模型

### UDP pseudo-header 是校验输入，不是在线首部

它把 source IP、destination IP、protocol、length 等三层信息纳入端到端完整性检查，但不会被当成 UDP 首部额外发送一次，也不能计入 UDP Length。

### `rwnd` 与 `cwnd` 的 Owner 完全不同

$$
W_{send}\le\min(rwnd,cwnd).
$$

- `rwnd`：receiver 通告，保护接收缓冲；
- `cwnd`：sender 本地维护，保护网络路径。

930 就是在考“首部 Window 字段属于谁”的 Owner 判定。
