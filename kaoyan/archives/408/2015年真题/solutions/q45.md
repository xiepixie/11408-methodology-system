# 408-2015-Q45

> 原题：[[../2015 年全国硕士研究生招生考试#45|Q45]]

## 模型锚点

- Topic：OS03｜有界资源的计数信号量：`full / empty`。
- 题目信号：两个有限容量信箱；取邮件要求非空，放邮件要求未满；A 只从 A 箱取、向 B 箱放，B 方向相反。
- 第一动作：先把每个信箱看成一个独立 bounded buffer，分别问两种 permit：**可取邮件数**与**可放空槽数**；不要看到共享对象就先机械加 mutex。

## 问题表征

两个信箱的状态分别是：

```text
A mailbox:
capacity = M
initial full = x
initial empty = M-x
consumer = A
producer = B

B mailbox:
capacity = N
initial full = y
initial empty = N-y
consumer = B
producer = A
```

每取一个邮件：

```text
full --
empty ++
```

每放一个邮件：

```text
empty --
full ++
```

因此计数信号量正好就是资源状态本身，不需要另造一个“是否能取/是否能放”的布尔锁。

## 关键决策

1. **为什么每个信箱需要两个计数信号量？** `full` 和 `empty` 是两个不同等待条件：一个防空取，一个防满放。
2. **为什么本题语义层不需要额外 mutex？** 每个信箱只有一个 producer 与一个 consumer；题目把“取出一个邮件/放入一个邮件”作为抽象操作。同步目标是容量条件，而不是要求我们实现底层队列结构的复合指针更新。
3. **如果具体实现的 mailbox 操作不是原子的呢？** 那属于更低实现层，可以为每个信箱再加 mutex；但它不是题目给出的同步约束所必需的最小状态。
4. **P/V 顺序为什么先申请条件再做操作？** 必须先获得 `full`/`empty` permit，成功修改信箱后再把对应反向 permit 归还。

## 求解链

### 信号量定义与初值

```c
semaphore A_full  = x;      // A 信箱当前可取邮件数
semaphore A_empty = M - x;  // A 信箱当前空槽数

semaphore B_full  = y;      // B 信箱当前可取邮件数
semaphore B_empty = N - y;  // B 信箱当前空槽数
```

### A 的过程

```c
A() {
    while (true) {
        P(A_full);          // A 箱必须非空
        从 A 的信箱中取出一个邮件;
        V(A_empty);         // 归还一个 A 箱空槽

        回答问题并提出一个新问题;

        P(B_empty);         // B 箱必须未满
        将新邮件放入 B 的信箱;
        V(B_full);          // B 箱新增一个可取邮件
    }
}
```

### B 的过程

```c
B() {
    while (true) {
        P(B_full);          // B 箱必须非空
        从 B 的信箱中取出一个邮件;
        V(B_empty);         // 归还一个 B 箱空槽

        回答问题并提出一个新问题;

        P(A_empty);         // A 箱必须未满
        将新邮件放入 A 的信箱;
        V(A_full);          // A 箱新增一个可取邮件
    }
}
```

### Safety

对任一信箱始终有：

$$
full+empty=capacity.
$$

只有成功 `P(full)` 才能取，保证不会从空箱取；只有成功 `P(empty)` 才能放，保证不会向满箱写。

### Progress

初始条件：

$$0<x<M,\qquad0<y<N.$$

因此两人最初都能取得一个邮件，同时每个信箱也至少有一个空槽。更重要的是，每次“取”都会为对方未来的“放”创造一个空槽，所以不会形成双方都持有某种资源、却永久等不到对方释放的闭环等待。

## 校验

用资源守恒独立检查：

```text
A_full + A_empty = M
B_full + B_empty = N
```

每次 A 取 A 箱：`A_full-1, A_empty+1`，和保持 M；A 放 B 箱：`B_empty-1, B_full+1`，和保持 N。B 同理。

因此任何状态都不会出现 `full<0`、`empty<0` 或超过容量。

## 压缩

```text
bounded mailbox
-> two permits per mailbox: full / empty
-> take: P(full) -> remove -> V(empty)
-> put : P(empty) -> insert -> V(full)
-> verify full+empty=capacity
```

复原检查：如果题目改成“多个生产者和多个消费者同时操作同一个链式信箱”，容量信号量仍然保留，但还要重新判断底层队列操作是否需要 mutex 保护结构不变量。

## 易错边界

- `full/empty` 是容量/可消费 permit，不是互斥锁。
- Legacy 解答额外加入 `A_mutex/B_mutex`。在“取/放邮件”为原子抽象操作的本题模型中，这是安全但不最小的实现；若底层容器操作本身需要互斥，再在实现层补 mutex。
- 不要把 `V(empty)` 推迟到回答问题之后；邮件一取出，那个槽位已经立即空闲。
