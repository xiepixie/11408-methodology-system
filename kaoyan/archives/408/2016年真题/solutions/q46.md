# 408-2016-Q46

> 原题：[[../2016 年全国硕士研究生招生考试#46|Q46]]

## 模型锚点

- Topic：OS-01/02｜动态优先级、aging 与饥饿。
- 题目信号：**priority 数值越小越先运行**，并给出 `nice / cpuTime / waitTime` 三个状态变量的更新规则。
- 第一动作：先确定每个变量应该让 priority 往哪个方向变化：长期占 CPU 要降低优势，长期等待必须提高优势。

## 问题表征

调度决策合同：

```text
smaller priority value -> selected earlier
nice      = static base preference
cpuTime   = current running burst accumulation
waitTime  = time accumulated while Ready
```

题设状态变化：

```text
Running: cpuTime++, waitTime=0
Ready  : cpuTime=0, waitTime++
```

要避免饥饿，等待越久的进程必须拥有一个会持续改善其竞争键的反馈通道。

## 关键决策

- 因为数值**越小越优先**，所以 `cpuTime` 应正向增加 priority，使长时间占 CPU 的进程逐渐变得不那么有利；`waitTime` 应负向进入 priority，使久等进程数值逐渐下降。
- 只写 `priority=nice+cpuTime` 仍不能保证低优先级等待者最终反超；真正承担 anti-starvation 的状态是 `waitTime`。
- 具体系数不是唯一答案，重要的是方向、边界和最终能够让等待者获得服务。

## 求解链

### (1) 为什么静态 `priority=nice` 会饥饿

如果就绪队列持续存在 `nice` 更小的进程，那么一个 `nice` 较大的进程每次调度都输掉比较：

```text
higher numeric nice
-> lower scheduling rank forever
-> possibly never dispatched
```

因此可能无限等待，形成 starvation。

### (2) 一种动态优先数设计

可以定义：

$$\boxed{priority=nice+k_1\,cpuTime-k_2\,waitTime},$$

其中：

$$k_1>0,\qquad k_2>0.$$

解释：

- 进程持续 Running：`cpuTime` 增大，使 priority 数值增大，调度优势下降；
- 进程持续 Ready：`waitTime` 增大，使 priority 数值减小，调度优势不断上升；
- 一旦等待足够久，`-k_2 waitTime` 最终可以抵消原先较大的 nice，从而获得运行机会。

这就是 aging 的负反馈。

`waitTime` 的作用可概括为：

$$\boxed{把等待时间转化为逐渐提高的调度优先级，防止长期饥饿。}$$

## 校验

设两个就绪进程的 nice 相差固定常数 $\Delta>0$。若其中一个一直等，`waitTime` 持续增长，则其 priority 每单位时间下降 $k_2$；经过有限时间后总能抵消 $\Delta$。因此静态优先级差不再能永久阻止它被选择。

同时，正在运行的进程 `waitTime=0` 且 `cpuTime` 增长，不会靠“运行得越久”获得更多优势，反馈方向自洽。

## 压缩

```text
priority smaller is better
-> running time: + penalty
-> waiting time: - aging bonus
-> wait long enough must eventually compete successfully
```

## 易错边界

aging 的关键不是公式长相，而是**等待越久，调度键必须单调变优**。若把 `+waitTime` 写进“数值越小越优先”的系统，反而会让久等者越来越吃亏。
