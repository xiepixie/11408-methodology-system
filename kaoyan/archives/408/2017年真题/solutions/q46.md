# 408-2017-Q46

## Model Anchor

- Topic：并发读写冲突、临界资源粒度与最大并发。
- 题目信号：thread1/thread2 都读共享变量，而 thread3 写 `z`、写 `y`；题目不仅要求正确互斥，还要求“最大程度地并发执行”。
- 第一动作：先建立 Read/Write conflict matrix，只为真正的 `R-W/W-W` 冲突加约束；`R-R` 不应被一个粗粒度全局 mutex 无谓串行化。

## Problem Representation

共享对象的访问集合：

```text
thread1: R(x), R(y)
thread2: R(y), R(z)
thread3: W(z), W(y)
```

冲突关系：

```text
t1 <-> t3 : y 上 R/W 冲突
t2 <-> t3 : y 上 R/W 冲突
t2 <-> t3 : z 上 R/W 冲突

t1 <-> t2 : 只共同读取 y，不冲突
x          : 只有 t1 读，不需要保护
```

所以若给 `y` 一个普通 mutex，让 t1 与 t2 都抢它，会把两个只读操作也串行化，虽然安全，但不是“最大程度并发”。

## Decision Points

### 1. 为什么可以给不同冲突边使用不同信号量？

题目只有固定的 3 个线程和这几处访问，完全可以把信号量理解成“冲突边的许可证”：

```text
sy13 -> 禁止 t1 读 y 与 t3 写 y 重叠
sy23 -> 禁止 t2 读 y 与 t3 写 y 重叠
sz23 -> 禁止 t2 读 z 与 t3 写 z 重叠
```

这样 t1 持有 `sy13`、t2 持有 `sy23` 时仍可并行读 y；而 t3 写 y 时必须同时拿到两个 y 许可证，确保没有任何读者正在访问。

### 2. 为什么 thread3 的 z 更新与 y 更新分开加锁？

`z=add(z,w)` 与 `y=add(y,w)` 是两个不同共享对象的临界操作。若 thread3 一次性锁住 y 和 z 再完成两次写，会扩大临界区并降低并发度。分别保护更符合“最小冲突范围”。

### 3. 如何避免人为制造死锁？

让 thread3 更新 z 时只持有 `sz23`，释放后再进入 y 临界区；不要持有 z 锁再等待 y 锁。对 y 的两个信号量统一按固定顺序申请。

## Solution Chain

设 3 个互斥信号量，初值均为 1：

```c
semaphore sy13 = 1;   // t1 read(y)  vs t3 write(y)
semaphore sy23 = 1;   // t2 read(y)  vs t3 write(y)
semaphore sz23 = 1;   // t2 read(z)  vs t3 write(z)
```

一种满足要求的实现如下：

```c
thread1 {
    cnum w;

    P(sy13);
    w = add(x, y);        // x 只有读；保护 y 的 t1/t3 冲突
    V(sy13);

    ...
}

thread2 {
    cnum w;

    // add(y,z) 必须在本次读取过程中同时防止 t3 改 y 或 z
    P(sy23);
    P(sz23);
    w = add(y, z);
    V(sz23);
    V(sy23);

    ...
}

thread3 {
    cnum w;
    w.a = 1;
    w.b = 2;

    // 只写 z：只阻止 t2 对 z 的读
    P(sz23);
    z = add(z, w);
    V(sz23);

    // 写 y：必须同时阻止 t1、t2 的 y 读
    P(sy13);
    P(sy23);
    y = add(y, w);
    V(sy23);
    V(sy13);

    ...
}
```

这里 thread1 与 thread2 可以同时执行各自的 `add()`：它们对 `y` 都是读，对 `x/z` 又没有彼此写冲突，因此保持了题目要求的最大并发。

### Safety

检查每个冲突对：

```text
t1 R(y) / t3 W(y) -> 共用 sy13，不能重叠
t2 R(y) / t3 W(y) -> 共用 sy23，不能重叠
t2 R(z) / t3 W(z) -> 共用 sz23，不能重叠
```

所以所有 R-W 冲突都被覆盖。

### Progress / Concurrency

- t1 与 t2 没有共同信号量，因此两个只读计算可以并行；
- t3 写 z 只阻塞需要读 z 的 t2，不阻塞 t1；
- t3 写 y 才同时阻塞 t1/t2；
- t3 不会在持有 z 锁时等待 y 锁，避免形成 `z -> y` 的长持锁依赖链。

## Verification

用 conflict graph 做独立验证：图中恰有三条需要禁止重叠的边，我们的三个 semaphore 一一覆盖；没有给 `t1-t2` 这条不存在的冲突边加锁，因此既不漏 Safety，也没有不必要地减少并发。

再检查题面常量：thread3 的局部复数必须是：

```c
w.a = 1;
w.b = 2;
```

旧解析曾把 `w.b` 写成 1，这是 Derived Reference 的抄写错误，正式解答以 Canonical Source 为准。

## Compression

```text
build R/W table
-> R-R: no lock
-> R-W/W-W: protect exact conflict
-> keep lock scope minimal
-> verify Safety + maximal concurrency
```

## 易错边界

1. 一个 `y_mutex` 同时锁 t1、t2 虽然安全，却会把两个 reader 串行化，不满足“最大程度并发”的精神。
2. “局部变量 w”不共享，不需要锁；真正临界资源是全局 `y,z` 的冲突访问。
3. 多锁设计必须同时检查死锁；减少临界区不等于可以随意改变加锁顺序。
