# 程序查询方式与程序中断方式

## 大纲定位

**六（三）I/O 方式**

- 程序查询方式
- 程序中断方式

中断的基本概念，中断响应过程，中断处理过程，多重中断和中断屏蔽的概念。

要求：说清两种方式下 CPU 与外设是串行还是并行工作、接口里的状态寄存器与控制寄存器各自起什么作用；完整复述一次中断的**响应过程**（三个条件、中断隐指令的三个动作）与**处理过程**（ISR 的四大部分），区分**单重中断与多重中断**、说清**中断屏蔽**管的是哪一种优先级；并能定量算出 CPU 用于 I/O 的时间占比、判断某设备能否用中断方式。

> [!TIP]
>

与「异常和中断机制」一节的分工

本节第四部分给出中断响应与处理的**完整骨架**——五个阶段、中断隐指令的三个动作、ISR 的四大部分、单重与多重中断的分界、屏蔽机制的作用——读完本篇即可独立复述这条流程，不必先去别处补课。

再往下一层的**构造性细节**：中断向量表怎么查、向量地址与中断向量差在哪一层、屏蔽字按什么规则逐位写出来、异常与中断在检测时机上为什么不同、精确中断，属于**五（五）异常和中断机制**，见 [[03_计算机组成原理_CO/cpu/exception-interrupt.md|异常和中断机制]]。

本节的主线仍是 **I/O 的视角**：中断把 CPU 的哪一段时间还了回来，接口需要为此增加什么部件，以及什么情况下这种方式根本用不了。

## 知识框架

本节回答五个问题：

- 查询方式浪费掉的到底是哪一段时间？为什么"查得快一点"消除不了这种浪费？
- 中断方式省下来的是什么——I/O 本身的 CPU 开销变小了吗？
- 接口里的状态寄存器和控制寄存器，在两种方式下分别扮演什么角色？
- 从设备提出请求到回到原程序，中间这段流程哪一半是硬件做的、哪一半是软件做的？分界为什么正好画在那里？
- 什么情况下中断方式不是"慢"，而是**物理上不成立**？

## 一、程序查询方式

### 从"无条件"到"有条件"

最简单的一类外设不需要问状态：开关、继电器、七段数码管、机械式传感器——它们随时可读可写。对这类设备，程序只要在**约定的时刻**用 I/O 指令读写数据端口即可，接口里连状态寄存器都不需要，只要地址译码和读 / 写控制。这叫**无条件传送**（同步传送）。

但绝大多数设备做不到"随时就绪"。打印机在打上一个字符，磁盘的磁头还在移动，键盘等着人按下去。对这类设备，传送之前**必须先确认条件成立**，于是接口里多出一个**状态寄存器**，程序先读状态、再决定动作。这叫**条件传送**（异步传送），也就是**程序查询方式**。

**接口在这里多出的东西是可以推出来的**：既然要"先问后做"，接口就至少要有

- 一个 CPU 可读的**状态触发器**（记录设备是否"完成 / 就绪"），
- 一个 CPU 可写的**命令触发器**（记录设备是否已被"启动"）。

一次完整的输入握手因此长成六步：

- CPU 执行 I/O 指令送出"启动"命令，地址译码选中本接口 → **命令触发器置 1、状态触发器清 0**
- 接口通过电缆向外设发"启动设备"命令
- 外设准备好一个数据，送入接口的**数据缓冲寄存器**
- 外设回送"设备工作结束"信号 → **状态触发器置 1、命令触发器清 0**
- CPU 反复读**状态端口**，直到读到"准备就绪"
- CPU 执行 I/O 指令，从**数据端口**把数据取走

第 5 步就是"查询"二字的全部含义：**CPU 用执行指令的方式，反复去读一个位。**

```
开始:
  CPU 向设备发出启动命令
循环:
  读状态端口
  if (未就绪)
    goto 循环          // 忙等待：执行了指令，但没有任何有效产出
  else
    从数据端口取一个数据
    if (还有数据)
      goto 循环
    else
      结束
```

### 两种查询模型

按"查询由谁触发、查完做什么"，程序查询方式分成两种，**它们的 CPU 开销完全不是一回事**：

| 模型 | 含义 | CPU 与外设的关系 | CPU 占比 |
| --- | --- | --- | --- |
| **独占查询** | 设备一被启动，CPU 就一直查下去直到传送完成 | **完全串行** | **100%** |
| **定时查询** | 周期性地去查一次接口状态，条件满足就传一个数据然后返回 | 查询的那些瞬间串行 | 要算，见下式 |

独占查询没什么可算的：CPU 把 100% 的时间花在这台设备的 I/O 上。

定时查询才有定量空间。查询间隔由**设备的数据传输率**倒推：每秒查询次数=数据传输率 R每次传输的字节数 uCPU 占比=(R/u)×单次查询周期数主频 f

> [!CAUTION]
>

u 由数据缓冲寄存器的宽度决定，不是默认 1 字节

题面里"I/O 数据端口 32 位""每次传送一个 16 字节的数据块"这类条件，给的就是 u。按 1 字节算，结果会差 u 倍。

> [!WARNING]
>

查询间隔的方向别写反

查询间隔必须 **≤ 设备准备一个数据的时间**，否则数据还没被取走就被下一个覆盖。

所以问的是"**最长**多久查一次"或"**至少**每秒查多少次"，而不是"最短间隔"。

### 为什么"查快点"救不了它

定时查询的开销随设备速度线性上涨：设备每秒产生的数据越多，就必须查得越勤。而且这个浪费**不能靠优化查询程序来消除**——问题不在于每次查询贵，而在于：

**在外设准备数据的那一整段时间里，CPU 和外设是串行工作的。**

CPU 执行的确实是指令，但执行的全是读状态位的指令，**对程序毫无贡献**。忙等不是停机，是空转。设备越慢，空转越久。

这就把改进方向逼了出来：**不要让 CPU 去问，让设备准备好了自己来说。**

## 二、程序中断方式

### 换掉的是"谁发起"

中断方式对上面那条通路只改了一处：**第 5 步的轮询被删掉了**。

CPU 启动设备之后不再等待，直接切去执行别的程序（在操作系统看来是把发起 I/O 的进程阻塞、调度另一个进程上 CPU）。设备准备好一个数据后，**主动向 CPU 发中断请求**；CPU 在当前指令执行结束时响应，转去执行中断服务程序，在服务程序里把数据搬走并启动下一次传送，然后返回被打断的程序继续跑。设备准备数据⏟CPU 跑别的程序⟶中断请求⏟设备发起⟶ISR 搬一个数据⏟CPU 介入⟶返回

于是**外设与 CPU 从串行变成并行**。这是中断方式相对程序查询方式的**全部收益**。

### 接口为此要增加什么

| 部件 | 作用 |
| --- | --- |
| **中断请求触发器** | 设备就绪时置 1，向中断控制器发出请求 |
| **中断屏蔽触发器** | 决定本设备的请求能否送达 CPU |
| **设备编号 / 中断类型号电路** | 中断响应周期经**数据线**把类型号送回 CPU |

状态寄存器并没有消失——它仍然记录设备状态，只是 **CPU 不再靠"反复读它"来推进流程**，改由请求触发器主动捅一下。控制寄存器的角色也没变：启动设备、设置传送方向、开关本设备的中断允许位，仍然靠 CPU 往命令端口写命令字。

> [!TIP]
>

这条通路的完整展开在第四节

"响应—服务—返回"这三个字里还压着五个阶段、一条软硬件分界线和一套屏蔽机制，见下面的第四节。

这里先记住 I/O 视角的一条：**中断在每条指令执行结束时才被检测**，所以外设发出请求后并不会立刻被响应，最多要等当前这条指令做完。

### 中断方式的 CPU 开销

骨架和查询方式完全一样，只是把"查询"换成"中断"：每秒中断次数=Ru,CPU 占比=(R/u)×mf

其中 m 是**单次中断的总开销**（中断响应 + 中断处理，含保存与恢复现场）。题目常常不直接给 m，而是给指令条数：m=(服务程序指令数+其他开销折合指令数)×CPI

两部分**先相加再乘 CPI**。公式的完整推导与一道走通的算例见 [[03_计算机组成原理_CO/cpu/exception-interrupt.md|异常和中断机制]]。

> [!WARNING]
>

中断方式并没有让 I/O 的 CPU 开销变小

把两个公式并排看：分子从"查询周期数"换成了"中断周期数"，分母和次数都没变。而**单次中断的开销通常比单次查询更大**——它多了保存断点、保护现场、恢复现场、中断返回。

中断方式省下的**不是 I/O 开销本身，而是外设准备数据期间那一大段等待时间**。这一点在 [[03_计算机组成原理_CO/io/io-compare.md|I/O 方式对比]] 里有并排的数字。

## 三、一次中断从头走到尾

上一节只说了"设备发请求、CPU 响应、ISR 搬数据"。把这条通路展开，一次完整的程序中断分**五个阶段**：中断请求→中断判优→中断响应→中断服务→中断返回

| 阶段 | 谁在做 | 做什么 |
| --- | --- | --- |
| **中断请求** | 接口硬件 | 设备就绪 → 状态触发器置 1；若本设备未被屏蔽（MASK =0），在**指令执行阶段的结束时刻**由 CPU 发出中断查询信号，把该设备的**中断请求触发器 INTR 置 1** |
| **中断判优** | 排队器（硬件）或轮询程序（软件） | 多个 INTR 同时为 1 时，按响应优先级选出一个 |
| **中断响应** | **硬件**（中断隐指令） | 关中断 → 保存断点 → 形成入口地址送 PC |
| **中断服务** | **软件**（中断服务程序 ISR） | 保护现场 → 设备服务（把数据搬走）→ 恢复现场 |
| **中断返回** | 软件 | 一条中断返回指令回到断点，原程序继续 |

**软硬件的分界画在第三与第四阶段之间**：前面是硬件自动完成的动作，后面是一段用指令写出来的程序。这条分界不是约定俗成——第三阶段要保存断点，而此刻软件根本还没拿到控制权，只能由硬件做。

### 中断响应过程：三个条件、三个动作

CPU 并不是一看到请求就转走。响应一个可屏蔽中断要**同时**满足三条：

| # | 条件 | 由什么表示 |
| --- | --- | --- |
| 1 | 该中断源**确实提出了请求**且未被屏蔽 | 中断请求触发器 INTR =1，屏蔽触发器 MASK =0 |
| 2 | CPU **处于开中断状态** | 允许中断触发器 EINT =1 |
| 3 | **一条指令执行完毕** | CPU 在每条指令执行阶段结束前才发出中断查询信号 |

第 3 条就是上一节那句"最多要等当前这条指令做完"的来历：指令执行到一半时，中间结果散落在 MDR 和各暂存器里，此刻打断根本无法准确保存现场。

三条都满足后，由**硬件自动**完成三个动作，合称**中断隐指令**——它叫"指令"，但指令系统里并没有这条指令，程序员也写不出它：

| 动作 | 为什么必须在这里做 |
| --- | --- |
| **关中断** | 保存断点这一步本身不能被新的中断打断，否则新断点会覆盖旧断点，原程序再也回不去 |
| **保存断点**（PC、PSW） | 断点不保存就回不去；此刻软件尚未接管，**这一步只能由硬件做** |
| **形成中断服务程序入口地址并送 PC** | 交出控制权 |

> [!WARNING]
>

中断隐指令不保存通用寄存器

它只保存**断点**（PC 与 PSW）。通用寄存器的保存叫**保护现场**，属于下一阶段，由 ISR 用一串存数指令或 PUSH 指令完成。

"断点由硬件保存、现场由软件保存"是这两个词的全部差别。

入口地址具体怎么形成——中断类型号如何经数据线送回、向量地址与中断向量差在哪一层、向量中断与非向量中断的分别，见 [[03_计算机组成原理_CO/cpu/exception-interrupt.md|异常和中断机制]]。

### 中断处理过程：ISR 的四大部分

不同设备的服务程序内容各异，但流程是同一个：保护现场→中断服务（设备服务）→恢复现场→中断返回

- **保护现场**——把通用寄存器和状态寄存器的内容存到存储器或压入堆栈。断点已由中断隐指令存好，这里存的是**其余寄存器**。
- **中断服务**——I/O 场景下就是从数据端口取走一个数据（或送出一个数据），必要时启动下一次传送。这是整段程序里唯一与"这台设备是什么"有关的部分。
- **恢复现场**——用取数指令或 POP 把保存的内容送回原寄存器。恢复的顺序与保护时相反。
- **中断返回**——最后一条指令是中断返回指令，从栈中取回 PC 与 PSW，回到断点。

### 多重中断：区别只在"开中断"放在哪一步

ISR 执行到一半时，可能又有新的中断请求到来。按 CPU 理不理它，分成两种：

|  | 含义 | ISR 里"开中断"的位置 |
| --- | --- | --- |
| **单重中断** | 执行 ISR 期间对新请求**一律不理**，做完再说 | 放在**中断返回之前**，整个服务过程全程关中断 |
| **多重中断**（中断嵌套） | 允许**处理优先级**更高的中断**打断当前 ISR**，处理完再回来 | 提前到**保护现场之后**，此后就能被打进来 |

两者的服务程序流程**只差这一处**。道理很直接：CPU 一旦响应中断，硬件已自动把 EINT 置 0（中断隐指令的第一步），此后若不执行开中断指令，任何新请求都进不来。开中断放得越早，能被打断的窗口越大。单重：保护现场→服务→恢复现场→开中断→返回多重：保护现场→开中断→服务→关中断→恢复现场→开中断→返回

多重中断里，恢复现场之前要**再关一次中断**——恢复现场同样是一段不能被打断的操作，理由与中断隐指令里关中断排第一完全相同。

> [!TIP]
>

多重中断成立的两个条件

- 当前 ISR 里**已经开中断**（EINT =1）；
- 新来的中断**处理优先级更高**。

两条缺一不可。每嵌套一层就多占一份栈空间保存断点与现场，所以**嵌套深度受栈容量限制**。

### 中断屏蔽：给"谁能打断谁"留一个软件旋钮

每个中断源在接口里都有一个**中断屏蔽触发器**（MASK）。MASK =1 表示该设备的请求被挡在外面，送不到 CPU；MASK =0 才放行。把所有中断源的屏蔽位排成一个字，就是**中断屏蔽字**。

由此产生两种性质完全不同的优先级：

|  | 由什么决定 | 能否改 | 管的是什么 |
| --- | --- | --- | --- |
| **响应优先级** | 硬件排队器的连线次序 | **不能** | 同时提出请求时，先响应谁 |
| **处理优先级** | **中断屏蔽字** | **能，由软件改** | 已经在处理的中断，能被谁打断 |

两者可以不一致：一个中断被优先响应，不代表它在处理途中不会被别人打断。屏蔽字按什么规则逐位写出来，见 [[03_计算机组成原理_CO/cpu/exception-interrupt.md|异常和中断机制]]。

从 I/O 的角度看，这套机制解决的是一个很实际的问题：**慢速设备的服务程序不该挡住快速设备**。打印机的 ISR 可能要跑很久，如果它把磁盘的请求一直屏蔽着，磁盘就会丢数据。把磁盘的处理优先级调到打印机之上，磁盘就能在打印机的 ISR 执行途中打进来。

**这也正是两种优先级必须分开的原因**：硬件排队器的次序是焊死的，而"谁更耽误不起"随设备配置而变，得留一个软件可调的旋钮。

DMA 请求不参与这套优先级体系——它争的是总线，走的是总线仲裁，见 [[03_计算机组成原理_CO/io/dma.md|DMA 方式]]。

## 四、什么时候中断方式根本不能用

把上一节那条流程整个走一遍是要花时间的，而设备不会等。中断方式成立因此有一个**物理前提**：T设备准备一个数据>T中断响应+中断处理

不等式右边就是上一节那五个阶段的总耗时。违反它的后果不是"性能差"，而是**丢数据**——上一个数据还没被 ISR 搬走，设备已经把下一个覆盖上去了。

所以这类判断的起手式固定为**算两个时间、比大小**：

- T准备=u÷R（每次传输字节数 ÷ 数据传输率）
- T中断=m÷f（单次中断周期数 ÷ 主频）
- 前者 > 后者 → 中断方式可行；否则**必须改用 DMA**

高速设备正是卡在这一条上：速度越快，T准备 越短，而 T中断 由中断机制本身决定、压不下去——保存断点、保护现场、恢复现场这几步一步也省不掉。两条线一交叉，中断方式就出局了——这就是 [[03_计算机组成原理_CO/io/dma.md|DMA 方式]] 存在的理由。

## 例题

**例 1（定时查询的 CPU 占比）**：某机主频 800 MHz，采用定时查询方式，每次查询（读状态、判断、传送数据）共占 60 个时钟周期。外设数据传输率 200 KB/s，接口的数据缓冲寄存器为 **16 位**，要求不丢失任何数据。求 CPU 用于该设备 I/O 的时间占比。

**解**：

数据缓冲寄存器 16 位，故每次传送 u=2 B。每秒至少查询次数=200×1032=105 次/秒每秒用于查询的时钟周期数=105×60=6×106占比=6×106800×106=0.75%

若误按 u=1 B 计算，会得到 1.5%，正好差 2 倍。**u 永远从题面的端口位宽或传送单位里读**。

单位口径：本文取 1 KB/s=103 B/s、1 MB/s=106 B/s，这是 I/O 速率的惯例。

**例 2（中断方式能否成立）**：某机主频 1 GHz，某外设数据传输率 2 MB/s，接口数据缓冲寄存器 **32 位**，一次中断的响应与处理共需 1500 个时钟周期。问该设备能否采用中断方式？CPU 占比是多少？

**解**：先比时间，再算占比。

**① 设备准备一个数据的时间**（u=4 B）：T准备=4 B2×106 B/s=2 μs

**② 一次中断的总耗时**：T中断=15001×109 Hz=1.5 μs

**③ 判定**：2 μs>1.5 μs，**不会丢数据，中断方式在物理上成立**。

**④ 占比**：(2×106/4)×15001×109=5×105×1500109=75%

成立不等于合适。CPU 有四分之三的时间在伺候这一台设备，只剩四分之一跑其他程序。**再快一点（比如 3 MB/s）就会越过那条线开始丢数据**，此时唯一的出路是 DMA。

结论要写"会丢数据"，只写"CPU 占用率太高"没有触及问题的性质。

## 易混淆知识点

**1. 无条件传送和条件传送，差别在哪？**

差一个"先问"。

|  | 传送前是否查状态 | 接口里要不要状态寄存器 | 适用设备 |
| --- | --- | --- | --- |
| **无条件传送**（同步） | 否，按约定时刻直接读写 | 不需要 | 开关、数码管、简单传感器 |
| **条件传送**（异步，即程序查询） | **是**，就绪才传 | **需要** | 打印机、键盘等有准备时间的设备 |

**2. 独占查询和定时查询，题面上怎么分？**

看 CPU 在设备准备期间干什么：

- 出现"**CPU 循环等待直到就绪**""期间不执行其他程序"→ **独占查询**，占比 **100%**
- 出现"**每隔 T 查询一次**""每秒查询 N 次""每次查询占 c 个周期"→ **定时查询**，套公式

**3. 中断方式减少了 I/O 的 CPU 开销吗？**

**没有，甚至更大。** 单次中断要保存断点、保护 / 恢复现场、中断返回，开销通常高于单次查询。

它省的是**外设准备数据期间 CPU 的空转时间**——那段时间从"轮询"变成了"跑别的程序"。判断这类说法的口径是：**看省的是"每次传送的开销"还是"等待的时间"。**

**4. 查询方式里，"查询"和"传送"是同一件事吗？**

不是，是两步。查询是读**状态端口**判断就绪与否，传送是读写**数据端口**搬数据。定时查询的开销公式里，"单次查询周期数"通常把两步都算进去了（题面一般会写明"包括读端口、分析状态、传送数据"）。

**5. 程序中断和子程序调用有什么区别？**

|  | 子程序调用 | 程序中断 |
| --- | --- | --- |
| 发起者 | 程序自己（CALL 指令） | **外部设备**，随机发生 |
| 时机 | 编译时就确定 | **异步**，事先不可知 |
| 与主程序的关系 | 主从关系，为主程序服务 | **平行关系**，与被打断的程序通常毫无关联 |
| 实现 | 纯软件 | 需要中断控制器、判优电路等**硬件支持** |

**6. "保存断点"和"保护现场"是同一件事吗？**

不是，差在**存什么**和**谁来存**：

|  | 存什么 | 谁做 | 在哪一步 |
| --- | --- | --- | --- |
| **保存断点** | PC 和 PSW | **硬件**（中断隐指令） | 中断响应阶段 |
| **保护现场** | 通用寄存器、状态寄存器的其余内容 | **软件**（ISR 的开头） | 中断服务阶段 |

判据是**"这一步执行时，软件拿到控制权了没有"**：没拿到就只能硬件做，所以断点只能由硬件存。

**7. 单重中断和多重中断，服务程序上到底差在哪？**

只差**"开中断"指令的位置**。CPU 响应中断时硬件已自动关中断，此后不执行开中断指令就谁也进不来。单重中断把开中断放在中断返回之前，全程不可打断；多重中断把它提前到保护现场之后，此后更高处理优先级的中断就能嵌套进来——代价是恢复现场之前必须再关一次中断。

**8. 设备发出中断请求后，CPU 会立刻停下当前指令吗？**

不会。中断在**每条指令执行结束时**才被采样——只有一条指令完整做完，PC 和 PSW 才处于一个可恢复的干净状态。与之相对，异常由当前指令自身引发，在**指令执行过程中**就被检测到。详见 [[03_计算机组成原理_CO/cpu/exception-interrupt.md|异常和中断机制]]。

## 本节小结

- **无条件传送**不查状态（简单设备），**条件传送 = 程序查询方式**先读状态端口再传送
- 查询方式下接口必须有**状态触发器**（就绪 / 完成）和**命令触发器**（启动）
- **独占查询**占 CPU 100%；**定时查询**才有定量空间，占比=(R/u)×单次查询周期数f
- **u 由数据缓冲寄存器 / 数据端口的位宽决定**，不是默认 1 字节
- 查询间隔必须 ≤ 设备准备一个数据的时间，问的是"**最长**间隔"
- 查询方式的根本缺陷是 **CPU 与外设串行工作**，忙等是空转而非停机，优化查询程序无法消除
- 中断方式把"CPU 去问"换成"设备来报"，**外设与 CPU 变成并行工作**——这是它的全部收益
- 中断方式**没有减少 I/O 的 CPU 开销**（单次开销反而更大），减少的是**等待时间**
- 接口为中断增加的是**中断请求触发器**和**中断屏蔽触发器**；状态 / 命令寄存器的角色不变
- 一次中断五阶段：**中断请求 → 中断判优 → 中断响应 → 中断服务 → 中断返回**；软硬件分界画在**响应与服务之间**
- 响应可屏蔽中断要同时满足三条：**有请求且未屏蔽**（INTR =1、MASK =0）、**开中断**（EINT =1）、**一条指令执行完毕**
- **中断隐指令**（硬件自动）三个动作：**关中断 → 保存断点 → 形成入口地址送 PC**；关中断必须排第一，且**不保存通用寄存器**
- **断点由硬件保存，现场由软件保存**——这是"保存断点"与"保护现场"的全部差别
- ISR 四大部分：**保护现场 → 设备服务 → 恢复现场 → 中断返回**
- **单重中断**执行期间不理新请求，开中断放在**返回之前**；**多重中断（中断嵌套）**把开中断提前到**保护现场之后**——两者流程只差这一处
- 多重中断成立要两条：当前 ISR **已开中断** 且新中断的**处理优先级更高**；嵌套深度受**栈容量**限制
- **中断屏蔽**：MASK =1 挡住该设备的请求；**响应优先级**由硬件排队器定且不可改，**处理优先级**由屏蔽字定且软件可调
- 屏蔽机制的 I/O 意义：让**耽误不起的设备**能打断慢速设备的服务程序
- DMA 请求不进中断优先级体系，它走**总线仲裁**
- 中断方式的物理前提：T准备>T响应+处理（右边就是那五个阶段的总耗时），违反就**丢数据**，必须改用 DMA
