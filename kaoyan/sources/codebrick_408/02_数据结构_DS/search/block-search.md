# 分块查找（索引顺序查找）

## 大纲定位

本篇对应 2026 大纲 **六、查找 （三）分块查找法**。

**分工边界**：本篇负责分块查找（索引顺序查找）本身——索引表的结构、 "块间有序、块内无序"这条核心约束、两种索引查找方式下的 ASL， 以及**块长取 n 时 ASL 最小**的推导。

- 块内查找就是 [《顺序查找》](./sequential-search.html)，索引表查找可以是顺序也可以是 [《折半查找》](./binary-search.html)，这两篇的 ASL 结论本篇直接引用；
- "把索引组织成树"是[《B 树》](./b-tree.html)与[《B+ 树》](./b-plus-tree.html)，是同一思路的多级推广；
- 各方法的横向对比见[《查找算法分析与对比》](./comparison.html)。

## 知识框架

本节回答 4 个问题：

- **"块间有序、块内无序"这条约束是怎么同时换来"能跳过整块"和"插入删除不必移动元素"的？**
- **索引表里为什么存的是每块的最大关键字，而不是最小关键字？**
- **为什么块长取 n 时 ASL 最小？这个 n 是怎么解出来的？**
- **索引表改用折半查找之后，最优块长还是 n 吗？**

## 结构：块间有序、块内无序

### 核心约束

把长度为 n 的查找表分成 b 块，每块 s 个元素（b=⌈n/s⌉）。 额外建立一张**索引表**，每个索引项记录对应块的**最大关键字**与**块的起始地址**。

两条约束：

- **块间有序**（分块有序）：第 i 块中**所有**元素的关键字，都小于第 i+1 块中**所有**元素的关键字。 等价说法：第 i 块的最大关键字 < 第 i+1 块的最小关键字。
- **块内无序**：每一块内部的元素**可以任意排列**，不要求有序。

```
索引表:  [max₁, addr₁]  [max₂, addr₂]  [max₃, addr₃]
              ↓               ↓               ↓
数据表:  [ 块1: 无序 ]   [ 块2: 无序 ]   [ 块3: 无序 ]

约束:    块1 全部元素 ≤ max₁ < 块2 全部元素 ≤ max₂ < 块3 全部元素 ≤ max₃
```

### 这条约束买到了什么

**块间有序买到了"跳过整块"的权力**：既然第 1 块的最大值是 22，那么查 38 时可以 一次性排除整个第 1 块，不必看里面任何一个元素。这就是分块查找比顺序查找快的全部来源。

**块内无序省下了维护有序性的代价**：插入一个新元素时，只要它落在正确的块里， **往块内任意空位一放就行，不需要移动任何元素**；删除同理。相比之下， [折半查找](./binary-search.html)要求全表有序，插入一次平均要移动一半元素。

**这是一次典型的"退一步换灵活性"**：分块查找放弃了"全表有序"这个强条件， 只保留"块间有序"这个弱条件，于是换来了动态增删的可行性， 代价是 ASL 从 O(log⁡n) 退到 O(n)。 教材把它总结成一句话：**如果线性表既要快速查找又经常动态变化，则可采用分块查找。**

### 索引表为什么存最大关键字

因为查找时要判断的是"目标**是否可能落在这一块**"。块间有序意味着 "key≤maxi 且 key>maxi−1" 就唯一确定了目标所在的块。 如果索引项存的是**最小**关键字，判定条件要写成"key≥mini 且 key<mini+1"， 需要同时看相邻两项，写起来更绕；存最大关键字则只要**找第一个 maxi≥key 的索引项**即可， 恰好是一次标准的"查找第一个不小于 key 的元素"操作。

索引表按 max **递增排列**，因此**索引表本身是有序表**——这就是它可以用折半查找的原因。c

```
// 索引表项定义
typedef struct {
    int maxKey;  // 该块内的最大关键字
    int addr;    // 该块在数据表中的起始下标
} IndexItem;
```

## 查找过程与代码

**第一步：确定目标所在的块。** 在索引表中找**第一个 maxKey≥key 的索引项**。 索引表有序，这一步可以顺序查找，也可以折半查找。

**第二步：块内顺序查找。** 从该块起始位置扫到块尾。**块内无序，所以只能顺序查找**—— 这一点没有选择余地。c

```
// 分块查找（索引表用折半查找，块内用顺序查找）
// A[0..n-1] 数据表，idx[0..b-1] 索引表（按 maxKey 递增）
// 返回下标；返回 -1 表示查找失败
int blockSearch(int A[], int n, IndexItem idx[], int b, int key) {
    // 第一步：折半查找索引表，找第一个 maxKey >= key 的索引项
    int lo = 0, hi = b - 1, blockIdx = -1;
    while (lo <= hi) {
        int mid = lo + (hi - lo) / 2;
        if (idx[mid].maxKey >= key) {
            blockIdx = mid;     // 记下候选，继续往左找更小的下标
            hi = mid - 1;       // 这一步是"找第一个满足条件的位置"的标准写法
        } else {
            lo = mid + 1;
        }
    }
    if (blockIdx == -1) return -1;  // 所有块的最大值都比 key 小，key 不在表中

    // 第二步：在确定的块内顺序查找
    int start = idx[blockIdx].addr;
    int end = (blockIdx + 1 < b) ? idx[blockIdx + 1].addr : n;  // 下一块起点即本块终点
    for (int i = start; i < end; i++) {
        if (A[i] == key) return i;
    }
    return -1;  // 块内没有，就一定不在表中——块间有序保证了这一点
}
```

三处值得注意的写法：

| 写法 | 为什么这么写 |
| --- | --- |
| `blockIdx = mid; hi = mid - 1;` | 这是"找**第一个**满足条件的位置"的标准折半模板。找到一个满足的还要继续往左，才能保证拿到下标最小的那个 |
| `blockIdx == -1` 时直接失败 | 说明 `key` 比全表最大值还大，不存在候选块 |
| 块内扫完就判失败，不去看下一块 | **块间有序**保证了目标要么在这一块、要么不在表中。这是这条约束的直接回报 |

### 一次完整的查找走查

18 个记录分成 3 块，每块 6 个（n=18、b=3、s=6），索引与块内均用顺序查找：

```
索引表:   [22, 起始 1]   [48, 起始 7]   [86, 起始 13]

数据表:   下标 1~6:   22  12  13   8   9  20      ← 块内乱序，但全部 ≤ 22
          下标 7~12:  33  42  44  38  24  48      ← 全部在 (22, 48]
          下标 13~18: 60  58  74  49  86  53      ← 全部在 (48, 86]
```

先验证块间有序：块 1 的最大值 22 < 块 2 的最小值 24 ✓； 块 2 的最大值 48 < 块 3 的最小值 49 ✓。**块内怎么乱都不影响这条约束。**

**查找 38（成功）**

- 查索引表：38>22（第 1 次比较）→ 38≤48（第 2 次比较）→ 确定在**块 2**；
- 块内从下标 7 顺序扫：33（1 次）→ 42（2 次）→ 44（3 次）→ **38（4 次，命中）**。

合计 2+4=6 次比较。

**查找 29（失败）**

- 查索引表：29>22、29≤48 → 块 2（2 次比较）；
- 块内从下标 7 扫到下标 12，6 个元素全部比完仍未命中（6 次比较）；
- **到此即可判失败**——块间有序保证了 29 若存在必在块 2 内。

合计 2+6=8 次比较。

**注意第 3 步**：不需要再去看块 1 和块 3。这是"块间有序"这条约束的直接回报， 也是分块查找相对纯顺序查找的全部性能来源。

## ASL 分析

分块查找是两段查找的**串联**，所以它的 ASL 就是两段之和：ASL=LI+LS

- LI：在索引表中确定块的平均比较次数；
- LS：在块内顺序查找的平均比较次数。

设表长 n，均匀分成 b 块、每块 s 个元素（n=b×s），且**查找每个元素等概率**。 于是查到每一块的概率都是 1b，块内每个元素的概率都是 1s。

### 情况一：索引表与块内都用顺序查找

索引表有 b 项，顺序查找的成功 ASL 是 b+12； 块内有 s 个元素，顺序查找的成功 ASL 是 s+12。所以ASL=b+12+s+12=b+s2+1

把 b=ns 代入，得到只含 s 的函数：ASL(s)=12(ns+s)+1=s2+2s+n2s

### 块长取多少最优：s=n 的推导

对 ASL(s)=12(ns+s)+1 求极值。

**方法一：均值不等式。** 对正数 ns 与 s，ns+s≥2ns⋅s=2n

等号成立当且仅当 ns=s，即 s=n。代回：ASLmin=12⋅2n+1=n+1

**方法二：求导（作为交叉验证）。**ddsASL(s)=12(1−ns2)， 令其为 0 得 s2=n；二阶导 ns3>0，是极小值点。两法一致。

**这个极值点的含义**：ns 是索引表的长度、s 是块长， 两者一个随 s 增大、一个随 s 减小。s 取小了索引表变长，s 取大了块内扫得久， **最优点就是让两段的工作量相等**——b=s=n，此时索引表长度与块长都是 n。

**数值验证**（n=16）：

| 块长 s | 块数 b | ASL=b+12+s+12 |
| --- | --- | --- |
| 1 | 16 | 8.5+1=9.5 |
| 2 | 8 | 4.5+1.5=6 |
| **4** | **4** | 2.5+2.5=5 |
| 8 | 2 | 1.5+4.5=6 |
| 16 | 1 | 1+8.5=9.5 |

16+1=5，与 s=4 那一行完全吻合 ✓。 两端 s=1 与 s=16 的 ASL 都是 9.5，正好退化成**长度 16 的纯顺序查找**（16+12=8.5） 再加一层多余的开销——这两个极端说明分块查找是"介于顺序与折半之间"的折中， 分块分得不对就白分了。

⚠️ **易漏的"+1"**：b+12+s+12 里两个 12 相加正好是 1， 所以最优值是 n+1 而不是 n。

### 情况二：索引表用折半查找，块内用顺序查找

此时 LS 不变，仍是 s+12；LI 换成折半查找在 b 个索引项上的平均比较次数。 按[折半查找](./binary-search.html)的结论，LI≈log2⁡(b+1)−1，两段相加：ASL≈log2⁡(b+1)−1+s+12=log2(ns+1)+s2−12

教材把末尾这个 −12 一并吸收进近似号，写成ASL≈log2(ns+1)+s2

**这就是严蔚敏教材给出的形式**——它是在"LI 本身已经是个近似式"的基础上再抹掉一个常数， 所以拿它去对一道给了具体 b 与 s 的题，差个零点几很正常。 ⚠️ **不要把这个式子当成可以逐项核对的等式**：要精确值就回到 ASL=LI+LS， LI 按索引表的判定树逐层数。

⚠️ **两种口径要分清**：

| 写法 | 它是什么 | 什么时候用 |
| --- | --- | --- |
| LI=log2⁡(b+1)−1 | 折半查找的**平均**比较次数（近似式） | 求平均 ASL，且题目按近似式给答案 |
| LI=⌈log2⁡(b+1)⌉ | 折半查找判定树的**高度**，即**最坏**比较次数 | 求"最多比较几次"；用它算出的 ASL 是**上界**不是平均值 |

题目若给出具体的 b，**最稳的做法是画出索引表的判定树逐层统计 LI**， 而不是套哪一个近似式。例如 b=4 时，折半查找的判定树各层结点数为 1、2、1， LI=1×1+2×2+3×14=2， 配上 s=4 得 ASL=2+2.5=4.5——比顺序索引的 5 略好。

**最优块长仍在 n 附近**：LI 变成了对数项，随 b 增长得很慢， 所以最优 s 会比 n 略大一些；但 408 范围内按 s=n 回答即可， 教材也是在顺序索引的前提下给出这个结论的。

### 查找失败怎么算

教材只给了成功 ASL。**失败 ASL 没有可背的封闭公式**，题目若要求就按定义逐个失败入口累加。 框架是固定的：

一次失败查找的比较次数 = 索引表上定位块所用的比较次数 + **扫完整个块**的 s 次比较。 特殊情形：key 大于全表最大值时，索引表全部比完就判失败，**不进入任何块**。

举例（n=16，s=4，b=4，索引表 maxKey 为 14、26、42、60，索引与块内均顺序查找）：

| 失败入口 | 索引比较 | 块内比较 | 合计 |
| --- | --- | --- | --- |
| key≤14 | 1 | 4 | 5 |
| 14<key≤26 | 2 | 4 | 6 |
| 26<key≤42 | 3 | 4 | 7 |
| 42<key≤60 | 4 | 4 | 8 |
| key>60 | 4 | 0（无块可查） | 4 |

ASL失败=5+6+7+8+45=305=6

**这个数不必记**，要记的是**推法**：先数清有几个互不等价的失败入口， 再对每个入口把两段比较次数加起来。这正是[《查找基本概念》](./concepts.html)里那条通用判据的应用。

## 复杂度

| 查找方式 | 时间复杂度 | 最优 ASL | 前提 |
| --- | --- | --- | --- |
| 顺序查找 | O(n) | n+12 | 无 |
| 折半查找 | O(log2⁡n) | ≈log2⁡(n+1)−1 | 有序 + 顺序存储 |
| 分块查找（顺序索引） | O(n) | n+1 | 块间有序 |
| 分块查找（折半索引） | O(log2⁡b+s) | ≈log2⁡(ns+1)+s2 | 块间有序 + 索引表有序 |

**O(n) 是怎么来的**：把 s=n 代进 ASL=b+s2+1， 两段各贡献 n2，合计 n+1，量级即 O(n)。 注意这是**取最优块长时**的量级；块长取得不好（如 s=1 或 s=n）会退化成 O(n)。

**空间复杂度**：O(b)，即索引表占用的额外空间。取最优块长时 b=n，故为 O(n)。

**插入删除的代价**：O(1) 次元素移动（找到块后直接放进块内空位）， 但可能需要更新该块的索引项。这是分块查找相对折半查找的**核心优势**。

## 易混淆知识点

| 易混对象 | 区别 | **判别依据** |
| --- | --- | --- |
| 块间有序 vs 块内有序 | 分块查找只要求**块间**有序，块内可以任意排列 | 问一句"第 i 块的最大值和第 i+1 块的最小值谁大"——必须前者小；块内两个元素的大小关系**没有任何约束** |
| 索引表存最大关键字 vs 最小关键字 | 标准做法存**最大**关键字 | 查找条件是"找第一个 maxKey≥key"，只需看一项；存最小值则要同时看相邻两项 |
| 块内能否用折半查找 | **不能** | 块内无序，折半的前提不成立。索引表有序，所以索引表可以折半 |
| n 是块长还是块数 | 最优时**块长与块数都等于 n** | 这正是极值条件 ns=s 的含义：两段工作量相等 |
| 最优 ASL 是 n 还是 n+1 | 是 n+1 | b+12+s+12 里的两个 12 加起来是 1，别丢 |
| LI=log2⁡(b+1)−1 vs ⌈log2⁡(b+1)⌉ | 前者是平均比较次数，后者是判定树高度（最坏比较次数） | 问"平均"用前者，问"最多"用后者；给了具体 b 就画判定树逐层统计最稳 |
| 分块查找适合静态还是动态表 | **动态**（相对折半而言） | 插入删除只需在块内放/摘一个元素，不必保持块内有序，故无需大量移动 |
| 分块查找 vs B 树的索引 | 分块查找是**一级**索引，B 树是**多级**索引且索引本身组织成平衡树 | 数一数"从索引到数据要经过几层"：分块查找恒为 1 层 |

## 本节小结

学完本篇，应当能够：

- 说清**块间有序、块内无序**这条约束，并解释它为什么同时买到了"跳过整块"与 "插入删除无需移动元素"两项好处；
- 说明索引表为什么存**每块的最大关键字**，以及索引表因此是有序表、可以折半查找；
- 写出分块查找的两阶段过程与 C 代码，并解释"块内扫完就判失败、不必再看别的块" 是**块间有序**的直接推论；
- 用 ASL=LI+LS 这个框架，分别写出顺序索引（b+12+s+12） 与折半索引（≈log2⁡(ns+1)+s2）两种情况的公式；
- **用均值不等式或求导推出 s=n 时 ASL 取最小值 n+1**， 并解释这个极值点的含义是"两段工作量相等"；
- 给定具体的 n 与 s 算出 ASL，并对多个 s 做数值比较验证最优点；
- 按定义逐个失败入口推出失败 ASL，而不是去背一个不存在的公式。

两条最关键的结论：**分块查找的 ASL 是两段查找之和，优化就是让这两段平衡**； **块长取 n 时最优，最优值是 n+1。**

- 把一级索引推广成多级、并把索引组织成平衡树，就得到 [B 树](./b-tree.html) 与 [B+ 树](./b-plus-tree.html)； B+ 树的叶结点链正是"块间有序"思想在外存上的极致形式
- [查找算法分析与对比](./comparison.html)中，分块查找在"ASL 与是否支持动态增删"两栏上 正好卡在顺序查找与折半查找之间
