# 链表题的三种通用解法

## 大纲定位

本篇对应 2026 大纲 **二、线性表 —— （三）线性表的应用**。

这一条目由本篇独立承担。本篇讲的是**在链式存储上做算法设计时反复出现的三类指针技巧**： 快慢指针、双指针间距法、有序合并。它们不是解题窍门，而是三个**结构性问题**各自的标准答案：

| 结构性问题 | 它为什么在链表上成立 | 对应技巧 |
| --- | --- | --- |
| 单链表不存表长，要定位"与表长成比例的位置"（如中点） | 无法算，只能走；但**两个速度不同的指针可以互相当尺子** | 快慢指针 |
| 单链表不能倒着走，要定位"距表尾 k 个"的位置 | 把"距尾 k"翻译成"前面那个指针出界" | 双指针间距法 |
| 两条有序链要并成一条，且不许开新空间 | 结点可以整个摘走再挂上，元素本身不必搬动 | 有序合并 |

**与相邻篇的边界**：单链表的结点定义、带头结点约定、插入删除的通用指针范式、 **头插法逆置**都在[单链表](./singly-linked-list.html)（大纲二·（二）2 的主篇），本篇不重复， 只在需要时链回去。

下文所有代码都按**带头结点**的单链表写，并要求**空间复杂度 O(1)**（就地操作， 不借助与表长成正比的辅助数组）。这两条是链表算法设计最常见的约束组合， 换成不带头结点时，全部代码需按主篇给的口径调整起始指针与计数器。

## 知识框架

本节回答四个问题：

- 两个速度不同的指针"同时出发"，为什么能定位到一个与表长成比例的位置？这个比例由什么决定？
- 两个指针保持固定间距前进，"前面那个走到头"这件事为什么恰好等价于"后面那个距尾 k 个"？
- 合并有序链表时那个 `<=`，改成 `<` 会错吗？错在哪一类要求上？
- 这三类技巧能不能拼起来用？拼的时候最容易在哪一步坏掉？

## 一、快慢指针：用速度比换位置比

### 它解决的结构性问题

要取顺序表的中间元素，直接算 `data[n/2]` 就行——因为顺序表**知道自己有多长**， 而且**能按下标直接定位**。单链表这两条都不成立：`length` 字段不存在， 下标定位也不存在。朴素做法是扫两遍（第一遍数出 n，第二遍走 n/2 步）， 但如果要求**只扫一遍**，就必须换思路。

**关键观察**：既然无法知道"终点在哪"，那就**让另一个指针替我们去探路**。 若 `fast` 每次走 2 步、`slow` 每次走 1 步，两者同时出发，则在任意时刻恒有(fast 已走的步数)=2×(slow 已走的步数)

于是 `fast` 走到表尾的那一刻，`slow` 必然停在**大约一半**的位置。 **位置比是由速度比换来的**，全程不需要知道 n。

### 代码与口径
c

```
// 求带头结点单链表的中间结点
// 口径：结点数 n 为偶数时取第 n/2 个，即两个中点里偏左的那个
LNode *middle(LinkList L) {
    if (L->next == NULL) return NULL;              // 空表
    LNode *slow = L->next, *fast = L->next;        // 都从首元结点起
    while (fast->next != NULL && fast->next->next != NULL) {
        slow = slow->next;                          // 慢指针走 1 步
        fast = fast->next->next;                    // 快指针走 2 步
    }
    return slow;
}
```

**循环不变量**：每轮循环开始时，`slow` 停在第 t+1 个结点、`fast` 停在第 2t+1 个结点 （t 为已循环的轮数）。循环终止的条件是 `fast` 后面不足两个结点， 即 2t+1≥n−1，取最小的 t 得 t=⌈n/2⌉−1， 于是 `slow` 停在第 ⌈n/2⌉ 个结点。

**逐个长度验算**：

| n | 循环轮数 t | `fast` 终止于 | `slow` 终止于 | 是否偏左中点 |
| --- | --- | --- | --- | --- |
| 1 | 0 | a1 | a1 | ✓ |
| 2 | 0 | a1 | a1 | ✓（n/2=1） |
| 3 | 1 | a3 | a2 | ✓ |
| 4 | 1 | a3 | a2 | ✓（n/2=2） |
| 5 | 2 | a5 | a3 | ✓ |
| 6 | 2 | a5 | a3 | ✓（n/2=3） |

### 循环条件决定的是"偏左"还是"偏右"

⚠️ 循环条件写成 `fast != NULL && fast->next != NULL`，代码同样"能跑"， 但 `slow` 会多走一步，偶数长度时停在**偏右**的中点（n=4 时停在 a3 而非 a2）。

| 循环条件 | 偶数 n 时 `slow` 停在 | 常用于 |
| --- | --- | --- |
| `fast->next && fast->next->next` | 第 n/2 个（**偏左**） | 要把表**均分成前后两段**时——前半正好 n/2 个 |
| `fast && fast->next` | 第 n/2+1 个（**偏右**） | 要让**后半段不长于前半段**时 |

**两种都不算错，错的是中途换口径**：分半时用了偏左中点、后续合并却按偏右中点算边界， 循环次数就会差一个，尾部结点被漏掉或被处理两次。 **动笔前先定死要哪个中点，全程只用这一个口径。**

### 推广：速度比 k:1 定位到 1/k 处

这个技巧不限于"一半"。若 `fast` 每次走 k 步、`slow` 走 1 步， 则 `fast` 到尾时 `slow` 大约停在**全表的 1/k 处**。要取三分点就令 k=3。 **看清这一点，你就不必把"找中点"当成一个孤立的招式来记**—— 它是"用速度比换位置比"这条通法的一个特例。

### 另一个用途：判断链表是否有环

同样是快慢指针，换一个观察角度就能解决另一个结构性问题：**单链表有没有环**。

**原理**：若无环，`fast` 必然先走到 `NULL`；若有环，两个指针最终都会进入环内， 此时 `fast` 相对 `slow` 的**相对速度是每轮 1 步**，环长有限， 所以 `fast` 一定会从后面追上 `slow`——**相对位移每轮减少 1，不可能跳过**。c

```
// 判断带头结点单链表是否有环；有环则返回环内相遇结点，无环返回 NULL
LNode *hasCycle(LinkList L) {
    LNode *slow = L->next, *fast = L->next;
    while (fast != NULL && fast->next != NULL) {
        slow = slow->next;
        fast = fast->next->next;
        if (slow == fast) return slow;   // 追上了，说明有环
    }
    return NULL;                          // fast 走到尽头，无环
}
```

**如果还要求出环的入口**，有一条能推出来的结论。先把原点定死：`slow` 与 `fast` 都是从 **首元结点 `L->next`** 出发的，下面所有距离一律以这个出发点为起算点—— 设**首元结点到环入口**的距离为 a、 入口到相遇点的距离为 b、环长为 c。相遇时 `slow` 走了 a+b、`fast` 走了 a+b+kc （k≥1 为 `fast` 多绕的圈数），由 `fast` 走的是 `slow` 的两倍得2(a+b)=a+b+kc⟹a+b=kc⟹a=(k−1)c+(c−b)

右边的含义是"从相遇点再走 c−b 步到入口，外加绕 k−1 整圈"。 所以**让一个指针从首元结点（也就是两针的出发点 `L->next`）出发、另一个从相遇点出发， 同速前进，二者必在环入口相遇**。

⚠️ **第二趟的起点必须与 `slow`/`fast` 的出发点严格一致。** 带头结点时若改从头结点 `L` 起走， 两条路径整体错开一个结点，a 与 a+1 差的那一步补不回来，**两针再也碰不上**。 拿一个最小的例子验：链为 L→a1→a2→a3→a4→a2（入口 a2，环长 3）。 按上面的代码跑，第 3 轮时 `slow` 与 `fast` 同时停在 a4，相遇点即 a4。 此时从 a1 与 a4 同速齐走，一步之后双双到达 a2，正是入口 ✓； 而从 L 与 a4 出发，两针的位置依次是 (L,a4),(a1,a2),(a2,a3),(a3,a4),(a4,a2),… 之后按环长循环，**永远不相等**。

想上机验证判环与找入口：[链表判环](https://www.codebrick.tech/oj/problems/ds-drill-singly-linked-list-107-detect-cycle)。

## 二、双指针间距法：把"距表尾 k 个"前移成"出界"

### 它解决的结构性问题

单链表**只能向后走**，所以"从表尾往回数 k 个"这个动作在结构上根本不可能直接执行。 必须把它**翻译成一个只涉及向前走的等价条件**。

翻译的办法是引入一个"尺子"：让 `fast` 先走 k 步，此后两针**同速**前进， 于是它们之间的**间距恒为 k 个结点**。当 `fast` 恰好走出表外（变成 `NULL`）时， `slow` 与表尾之间就正好隔着 k−1 个结点——它就是**倒数第 k 个**。

**"距表尾 k"这个向后的条件，被固定间距转换成了"`fast` 出界"这个向前的条件。** 这是本技巧的全部内容。c

```
// 查找带头结点单链表中倒数第 k 个结点（k ≥ 1）
// 找到则输出该结点的 data 并返回 1，链长不足 k 则返回 0
int findKthFromTail(LinkList L, int k) {
    LNode *fast = L->next, *slow = L->next;   // 都从首元结点起算
    for (int i = 0; i < k; i++) {
        if (fast == NULL) return 0;            // 链长不足 k，查找失败
        fast = fast->next;                     // fast 先独自走 k 步
    }
    while (fast != NULL) {                     // 两针同速齐走
        fast = fast->next;
        slow = slow->next;
    }
    printf("%d", slow->data);
    return 1;
}
```

**循环不变量**：进入第二个循环后，恒有 "`slow` 是第 j 个结点 ⇒ `fast` 是第 j+k 个结点（或已越过表尾）"。 第二个循环终止时 `fast` 恰好越过第 n 个结点，即 j+k=n+1，故 j=n−k+1—— 这正是倒数第 k 个的位序。

**边界验算**（设链长 n=5）：

| k | 第一循环后 `fast` 在 | 齐走步数 | `slow` 终止于 | 是否为倒数第 k |
| --- | --- | --- | --- | --- |
| 1 | a2 | 4 | a5 | ✓ |
| 2 | a3 | 3 | a4 | ✓ |
| 5 | `NULL`（恰好走完） | 0 | a1 | ✓（k 等于表长） |
| 6 | 第 6 步前已是 `NULL` | — | 返回 0 | ✓（链长不足） |

⚠️ **三处最容易写错的地方**：

- **先走的步数是 k，不是 k−1。** 写成 k−1 会定位到倒数第 k+1 个。 检验办法就是拿 k=1 代进去：走 1 步后 `fast` 在 a2，齐走到 `fast` 出界时 `slow` 恰在 a5（最后一个），正确。
- **带头结点时必须从 `L->next` 起算**。若两针都从头结点 `L` 起，整体错位一个结点， 结果会变成倒数第 k+1 个。
- **"链长不足 k"的判断必须放在第一个循环里**。放到循环外再判，`fast` 已经解引用过 `NULL`了。加载可视化中...

### 与两遍扫描法的对比

另一种做法是：先遍历一遍数出表长 n，再从头走 n−k 步。

|  | 双指针间距法 | 两遍扫描法 |
| --- | --- | --- |
| 扫描遍数 | 1 遍 | 2 遍 |
| 总步数 | n+k | n+(n−k)=2n−k |
| 时间复杂度 | O(n) | O(n) |
| 空间复杂度 | O(1) | O(1) |
| 正确性 | 相同 | 相同 |

**两者同阶，双指针的优势只在"单遍扫描"这一条**。 若数据来自只能读一次的流（读过就没了），两遍法直接不可用，这才是它的真实价值。 **不要把"更优"理解成"复杂度更低"**——它们的复杂度是一样的。

## 三、有序合并：就地归并，O(1) 空间

### 它解决的结构性问题

把两条递增有序链并成一条递增链。在顺序表上这件事必须另开一个数组 （否则会覆盖还没读的元素），空间 O(m+n)。 但**链表上不必**——因为链表的元素不需要"住在哪儿"， **把结点整个摘下来挂到新链的尾部即可，数据一个字节都不用搬**。

于是只要维护一个结果链的尾指针 `tail`，两条链各出一个指针比大小， 小的那个结点摘走挂到 `tail` 后面。全程只用了常数个指针，空间 O(1)。c

```
// 就地合并两个带头结点的递增链表 La、Lb（不新建结点，复用 La 的头结点）
LinkList mergeLists(LinkList La, LinkList Lb) {
    LNode *pa = La->next, *pb = Lb->next;
    LNode *tail = La;                     // 结果链的尾指针，从 La 的头结点起
    while (pa != NULL && pb != NULL) {
        if (pa->data <= pb->data) {       // 相等时取 La 的结点 → 保持稳定
            tail->next = pa;
            pa = pa->next;
        } else {
            tail->next = pb;
            pb = pb->next;
        }
        tail = tail->next;                // 尾指针跟着后移
    }
    tail->next = (pa != NULL) ? pa : pb;  // 剩余段整体挂接，不必逐个搬
    free(Lb);                             // Lb 的头结点已无用
    return La;
}
```

### 三个设计点，各自为什么这么写

**1. `<=` 而不是 `<`：这一个字符决定了归并稳不稳定。**

"稳定"指的是**关键字相同的元素，合并后仍保持它们原来的相对次序**。 取 `<=` 时，两边关键字相等就先取 `La` 的，于是"La 中的元素排在 Lb 的同值元素之前" 这一相对次序被保住；取 `<` 则会先取 `Lb` 的，同值元素次序被颠倒。

举个可验证的例子：La=(1A, 3A, 3A)、Lb=(2B, 3B)，下标标注元素来自哪条链。 用 `<=` 合并得 (1A, 2B, 3A, 3A, 3B)——A 的两个 3 仍在 B 的 3 之前 ✓； 用 `<` 则得 (1A, 2B, 3B, 3A, 3A)，次序被换。

⚠️ **当数据只有关键字、没有附加信息时，两种结果"看起来一样"**（都是 1,2,3,3,3）， 所以稳定性问题只在**元素带附加数据**时才暴露。 这与[归并排序](./../sorting/merge-sort.html)靠 `<=` 保稳定是同一件事，判据也完全相同。

**2. 剩余段整体挂接，不要逐个搬。**

`tail->next = pa ? pa : pb;` 一句就把没走完的那一段全接上了。 理由是那一段**内部已经有序，且它的每个元素都不小于已合并部分的最后一个**—— 再逐个比较是纯粹的无用功。这一句同时覆盖了"某条链为空"的边界： 若 `pa` 为 `NULL` 就接 `pb`，反之接 `pa`，两条都空时接的是 `NULL`，仍然正确。

**3. 递增用尾插，递减改头插。**

上面的代码用**尾插**（挂到 `tail` 之后），所以结果保持递增。 若要求结果**递减**，只需把"挂到 tail 之后"改成"头插到结果链的头结点之后"—— 边摘边头插自动产生逆序，**不需要先合并再逆置**，仍是一遍扫描。

### 复杂度

- **时间 O(m+n)**：每轮循环至少让 `pa` 或 `pb` 前进一个结点，结点总数为 m+n。
- **比较次数**：最少 min(m,n) 次（一条链的元素全部小于另一条时， 较短的那条走完就退出循环），最多 m+n−1 次（两条链交替取，最后一个结点不必再比）。
- **空间 O(1)**：只用了 `pa`、`pb`、`tail` 三个指针，且不新建任何结点。

## 四、三种技巧的组合：链表重排

**问题**：带头结点单链表 L=(a1,a2,…,an)， 要求在 O(1) 辅助空间内把它就地重排为L′=(a1, an, a2, an−1, a3, an−2, …)

直接看目标序列，很难下手；但把它拆开看，**它就是"前半段"与"逆置后的后半段"交替取**：(a1,a2,…)⏟前半段与(an,an−1,…)⏟后半段逆置交替

于是三步：

| 步骤 | 用到的技巧 | 结果 |
| --- | --- | --- |
| ① 找中点，从中点后断开 | 快慢指针（本篇一） | 前半段 (a1,…)、后半段 (…,an) |
| ② 把后半段逆置 | [头插法逆置](./singly-linked-list.html) | 后半段变成 (an,an−1,…) |
| ③ 两段交替合并 | 有序合并的变体（本篇三） | 目标序列 |

第 ③ 步是合并的**变体**：不比较大小，而是**轮流各取一个**。合并的骨架（维护结果链的 尾指针、摘一个挂一个、剩余段整体挂接）原封不动，只是把"比大小"换成了"轮流"。

**每一步都是 O(n) 时间、O(1) 空间，三步串起来仍然是 O(n) / O(1)。**

⚠️ **最容易坏在第 ① 步的断链上。** 找到中点 `mid` 后必须： **先把后半段的起点 `second = mid->next` 保存下来，再执行 `mid->next = NULL`**。 顺序反了就丢掉整个后半段（这正是[单链表](./singly-linked-list.html)那条通用范式说的事）。 若干脆忘了断链，前半段仍然连着后半段，逆置时会把整条链搅乱，交替合并的结果是一个**环**。

想上机验证重排：[重排链表](https://www.codebrick.tech/oj/problems/p2313-reorder-list)。 合并类的训练题：[合并两个有序链表](https://www.codebrick.tech/oj/problems/p2310-merge-two-lists)、 进阶的[合并 K 个有序链表](https://www.codebrick.tech/oj/problems/p2311-merge-k-lists)。 逆置：[链表逆置](https://www.codebrick.tech/oj/problems/p2307-reverse-list)。

## 链表算法的三条正确性自查

链表算法写完之后，**沿 `next` 从头走一遍**，逐条查下面三件事。 这三条覆盖了链表算法几乎全部的错误来源：

| 查什么 | 怎么查 | 典型症状 |
| --- | --- | --- |
| **断链了没有** | 从头结点出发数结点个数，是否等于预期 | 中途某个 `next` 被覆盖，后半段丢失。多半是"先覆盖、后读取"的顺序错误 |
| **成环了没有** | 走到某处是否再也遇不到 `NULL` | 分段时忘了把前半段的尾置 `NULL`，或交换两段时首尾接反 |
| **边界对不对** | 拿**空表**、**单结点**、**表长为偶数**三个输入手工跑一遍 | 空表解引用 `NULL`；单结点时 `fast->next->next` 越界；偶数长度时中点口径不一致 |

**每一次指针赋值之前，先在草稿上把当前的箭头画出来**——链表算法的错误几乎全部集中在 "指针改动的先后次序"上，而这类错误在代码里看不出来，在图上一眼就能看出来。

## 三种技巧的适用条件对照

| 技巧 | 适用的问题特征 | 前提 | 时间 / 空间 |
| --- | --- | --- | --- |
| **快慢指针** | 要定位"与表长成比例"的位置，或判断有无环 | 表长未知；只允许扫一遍；速度比决定定位到哪个比例位置 | O(n) / O(1) |
| **双指针间距法** | 要定位"距表尾固定距离"的位置 | 距离 k 是常量且事先已知；只允许扫一遍 | O(n) / O(1) |
| **有序合并** | 两条（或多条）**已有序**的链要并成一条 | **两条链各自必须已经有序**——无序时合并结果无意义 | O(m+n) / O(1) |

⚠️ 第三行的前提最容易被忽略：合并算法本身**不做排序**，它只是把两条有序链交错起来。 若输入无序，输出既不有序也没有任何有用性质。

## 易混淆知识点

| 易混对 | 判别依据 | 结论 |
| --- | --- | --- |
| `fast->next && fast->next->next` vs `fast && fast->next` | 偶数长度时 `slow` 停在偏左还是偏右中点 | 前者偏左（第 n/2 个），后者偏右（第 n/2+1 个）。两者都对，但全程必须只用一个口径 |
| 快指针先走 k 步 vs k−1 步 | 拿 k=1 代进去检验 | 必须是 k 步；k−1 步会定位到倒数第 k+1 个 |
| 从 `L` 起算 vs 从 `L->next` 起算 | 这张表带不带头结点 | 带头结点时两针都从 `L->next` 起，从 `L` 起会整体错位一个结点 |
| 双指针法 vs 两遍扫描法 | 问的是"复杂度"还是"扫描遍数" | 复杂度同为 O(n)/O(1)；差别只在单遍与两遍 |
| 合并用 `<=` vs `<` | 关注的是元素次序还是仅仅关键字次序 | 只看关键字时两者结果相同；元素带附加数据时，只有 `<=` 保持稳定 |
| 就地合并 O(1) 空间 vs 新建结点 O(m+n) | 有没有 `malloc` 新结点 | 就地合并只摘挂已有结点，不新建；新建一份是另一种写法，空间是 O(m+n) |
| 判环的相遇点 vs 环的入口 | 相遇点在环内的任意位置，入口是环的起点 | 相遇点不等于入口；求入口要再从**首元结点**（两针的出发点）与相遇点同速齐走一次。起点错一个结点（如从头结点 `L` 起）会导致两针永不相遇 |
| 断链 vs 成环 | 走一遍数个数 vs 走一遍找 `NULL` | 断链是"少了"，成环是"停不下来"；分段类算法两种都要查 |
| 交替合并 vs 有序合并 | 决定"下一个取谁"的规则 | 有序合并按大小，交替合并按轮次；骨架完全相同 |

## 本节小结

学完本节，你应该能够：

- 说清三类技巧各自解决的是**哪一个结构性问题**，而不是把它们当成三个孤立的写法；
- 写出**快慢指针**求中点的代码，给出循环不变量，并说明**速度比 k:1 会定位到 1/k 处** 这一推广；同时能指出两种循环条件分别得到偏左 / 偏右中点，以及中途换口径的后果；
- 用快慢指针**判断链表有无环**，并推出"从**首元结点**与相遇点同速齐走必在入口相遇"的结论 （由 2(a+b)=a+b+kc 推得 a=(k−1)c+(c−b)）， 同时说清 a 必须以两针的**出发点**起算、第二趟起点错一个结点就永远不相遇；
- 写出**双指针间距法**，解释它把"距表尾 k"翻译成"前指针出界"的机理， 并验算 k=1、k=n、k>n 三个边界；说明它与两遍扫描法**复杂度同阶**， 优势只在单遍扫描；
- 写出**就地有序合并**，说清 `<=` 与稳定性的关系、剩余段为什么可以整体挂接、 递减结果为什么改头插即可；给出比较次数的上下界 min(m,n) 与 m+n−1；
- 把三类技巧**组合**起来完成链表重排，并指出组合时最脆弱的一步是**分段处的断链**；
- 用三条自查（断链、成环、边界）检查自己写出的任何链表算法。

三条最关键的结论：

- **这三类技巧都是在绕开单链表的两条先天限制**——不存表长、不能回头。 认出限制，技巧就是自然推论，不必当口诀背。
- **链表算法的错误几乎全部出在"指针改动的先后次序"上。** 判据只有一条：即将被覆盖的那个地址，此刻是否还有别的地方存着它。
- **就地操作之所以能做到 O(1) 空间，是因为链表的元素不必搬家**—— 摘下一个结点再挂到别处，只动指针。这是链式存储相对顺序存储最本质的红利。
