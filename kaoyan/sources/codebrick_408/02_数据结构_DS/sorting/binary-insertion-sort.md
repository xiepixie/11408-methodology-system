# 折半插入排序

## 大纲定位

本篇对应 2026 大纲 **七、排序 （三）折半插入排序**。

分工边界：

- 本篇负责折半插入排序本身——**它优化了什么、没优化什么、比较次数的推导、为什么时间复杂度仍是 O(n2)、为什么不能用于链表、稳定性靠哪一行保证**。
- 插入排序的基本框架（已排序区 / 未排序区、逐个插入、哨兵）在 [直接插入排序](./insertion-sort.html)，本篇默认读者已掌握，只讲"查找插入位置"这一段的替换。
- 折半查找本身的判定树、ASL 与边界写法在 [折半查找](./../search/binary-search.html)（大纲六（四）），本篇只用它的结论。
- 另一条改进方向——**减少每次要越过的元素个数**——在 [希尔排序](./shell-sort.html)。

## 知识框架

本节回答四个问题：

- 直接插入排序的一趟里，比较和移动各占多少？替换掉"查找"能省下哪一半？
- 折半查找的比较次数为什么**几乎与关键字取值无关**？这与直接插入排序的"随初始序列剧烈变化"形成什么对照？
- 既然比较次数从 O(n2) 降到了 Θ(nlog2⁡n)，为什么总时间复杂度还是 O(n2)？
- 折半查找找到的是"第一个大于它的位置"还是"最后一个不大于它的位置之后"？这个选择怎样决定稳定性？

## 相比直接插入排序的改进

直接插入排序的一趟做两件事：

- **查找**——从后向前顺序比较，找到插入位置；
- **移动**——把插入位置及其之后的元素逐个后移一位。

既然已排序区**本来就是有序的**，第 1 步的顺序查找就是浪费——有序表上应该用折半查找。这就是折半插入排序：**只把第 1 步换成折半查找，第 2 步一个字不改**。

于是收益与代价都很清楚：

|  | 直接插入排序 | 折半插入排序 |
| --- | --- | --- |
| 查找插入位置的比较次数（第 i 趟） | 1∼i，取决于要越过几个元素 | 约 ⌊log2⁡(i−1)⌋+1，几乎只取决于 i |
| 需要后移的记录个数（第 i 趟） | 待插元素与前面元素构成的逆序对数 | **完全相同** |
| 总比较次数 | n−1∼(n+2)(n−1)2 | 恒为 Θ(nlog2⁡n) |
| 总移动次数 | 最坏 ≈n2/2 | **最坏 ≈n2/2，一模一样** |
| 总时间复杂度 | O(n2) | O(n2) |

**结论先说：折半插入排序把"比较"这一半从平方级压到了 nlog⁡n 级，但"移动"那一半原封不动，而移动才是瓶颈，所以总复杂度纹丝不动。**

## 核心思想

算法流程示意（把 9 插进已排好的 `[3, 5, 8, 12, 15]`）：

```
已排序区: [3, 5, 8, 12, 15]    待插入: 9

折半查找过程（区间用下标 [low, high] 表示）:
  low=0, high=4, mid=2 → a[2]=8  ≤ 9  → low = mid+1 = 3
  low=3, high=4, mid=3 → a[3]=12 > 9  → high = mid-1 = 2
  low=3 > high=2 → 循环结束，插入位置 = low = 3

后移元素: 把 a[3..4] 即 12, 15 各右移一位
插入:     [3, 5, 8, 9, 12, 15]
```

注意循环结束时的关键性质：**`low` 恰好停在"第一个大于待插元素的位置"上**，而 `high = low - 1` 停在"最后一个不大于待插元素的位置"上。所以插入点取 `low`（等价地取 `high + 1`）。

## 操作详解
c

```
void BinaryInsertionSort(int a[], int n) {
    int i, j, low, high, mid, temp;
    for (i = 1; i < n; i++) {        // 共 n-1 趟，趟数与初始序列无关
        temp = a[i];                 // 暂存待插入元素：a[i] 随后会被覆盖
        low = 0;
        high = i - 1;                // 在有序区 a[0..i-1] 中折半查找
        while (low <= high) {        // 区间为空时退出，此时 low 就是插入位置
            mid = (low + high) / 2;
            if (a[mid] > temp)
                high = mid - 1;      // 待插元素更小，去左半区
            else
                low = mid + 1;       // a[mid] <= temp，去右半区
                                     // 相等时也走这一支 —— 稳定性的关键
        }
        for (j = i - 1; j >= low; j--)
            a[j + 1] = a[j];         // 统一把 a[low..i-1] 整体后移一位
        a[low] = temp;               // 落位
    }
}
```

三处边界值得单独确认：

- **`i = 1` 时**：`low = 0, high = 0`，区间只有一个元素，折半查找做 1 次比较后必然退出（`high` 变 −1 或 `low` 变 1），插入位置为 0 或 1，都正确。
- **待插元素比所有元素都小**：查找过程中 `high` 一路减到 −1，`low` 保持 0，后移循环把 `a[0..i-1]` 全部右移，`a[0] = temp`。正确。
- **待插元素比所有元素都大**：`low` 一路加到 i，后移循环的初值 `j = i-1 < low = i`，**一次都不执行**，然后 `a[i] = temp` 把元素放回原位。正确，且这正是"正序输入时 0 次后移"的来源。
- **`n <= 1`**：外层循环不执行，安全。

与直接插入排序的一处写法差别：直接插入排序有一句 `if (A[i] < A[i-1])` 的快速跳过，折半插入**没有**这一句——它对每个元素都要走一遍折半查找。这就是"最好情况仍是 Θ(nlog2⁡n) 而不是 O(n)"的直接原因。

### 逐趟推演

以 `[49, 38, 65, 97, 76, 13, 27, 49*]` 为例（`49*` 是第二个 49）：

| 趟 i | 待插 | 有序区 | 折半查找过程 | 插入位置 | 后移个数 | 本趟结果 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 38 | [49] | mid=0：49 > 38 → high=−1 | 0 | 1 | 38 49 65 97 76 13 27 49* |
| 2 | 65 | [38,49] | mid=0：38 ≤ 65 → low=1；mid=1：49 ≤ 65 → low=2 | 2 | 0 | 38 49 65 97 76 13 27 49* |
| 3 | 97 | [38,49,65] | mid=1：49 ≤ 97 → low=2；mid=2：65 ≤ 97 → low=3 | 3 | 0 | 38 49 65 97 76 13 27 49* |
| 4 | 76 | [38,49,65,97] | mid=1：49 ≤ 76 → low=2；mid=2：65 ≤ 76 → low=3；mid=3：97 > 76 → high=2 | 3 | 1 | 38 49 65 76 97 13 27 49* |
| 5 | 13 | [38,49,65,76,97] | mid=2：65 > 13 → high=1；mid=0：38 > 13 → high=−1 | 0 | 5 | 13 38 49 65 76 97 27 49* |
| 6 | 27 | [13,38,49,65,76,97] | mid=2：49 > 27 → high=1；mid=0：13 ≤ 27 → low=1；mid=1：38 > 27 → high=0 | 1 | 5 | 13 27 38 49 65 76 97 49* |
| 7 | 49* | [13,27,38,49,65,76,97] | mid=3：**49 ≤ 49* → low=4**；mid=5：76 > 49* → high=4；mid=4：65 > 49* → high=3 | 4 | 3 | 13 27 38 49 49* 65 76 97 |

第 7 趟是稳定性的现场：`a[mid] = 49` 与 `temp = 49*` 相等，条件 `a[mid] > temp` **为假**，走 `low = mid + 1` 这一支，于是插入位置落在 49 的**右边**，`49*` 排在 `49` 之后。

## 复杂度分析

### 比较次数：为什么"几乎与初始序列无关"

折半查找的执行路径由**区间长度**驱动：长度为 m 的区间取中点后，被排除掉中点自身，剩下左半 ⌊(m−1)/2⌋ 或右半 ⌈(m−1)/2⌉ 个元素。不论关键字取什么值，**区间长度都是按对半的速度收缩到 0 的**，因此第 i 趟的比较次数是⌊log2⁡(i−1)⌋+1(上界)

总比较次数KCN=∑i=2n(⌊log2⁡(i−1)⌋+1)=Θ(nlog2⁡n)

以 n=8 为例，各趟比较次数的上界依次是 1,2,2,3,3,3,3，合计 **17 次**（上面那个逐趟推演实际用了 16 次）；而直接插入排序在同样 n=8 下，正序只要 7 次、逆序要 35 次。这个对照就是"比较次数与初始序列无关"这句话的全部含义。

**一处需要说准的细节**：当待查区间长度为**偶数**时，左右两半差一个元素，走左边和走右边的后续比较次数可能差 1 次。所以严格地说，总比较次数会在一个宽度约 n 的小范围内浮动（n=8 时实测在 13～17 之间），而不是一个恒定值。举个最小的例子：n=3 时，`[2, 3, 1]` 共比较 2 次，`[2, 3, 4]` 共比较 3 次。

但这不影响结论——**比较次数的量级与主项只由 n 决定，不随初始序列的有序程度而改变**。这才是它与直接插入排序（n−1 到 n2/2，差了整整一个数量级）的本质差别。

### 移动次数：一次都没省

后移循环 `for (j = i - 1; j >= low; j--)` 执行 i−low 次，而 i−low 恰是"待插元素前面有多少个比它大的元素"，也就是**待插元素贡献的逆序对数**——这与直接插入排序内层循环执行的次数**完全相同**。

于是：RMNmin=0 (正序),RMNmax≈n22 (逆序),RMNavg≈n24

**移动次数完全依赖初始序列，与直接插入排序逐个记录地相同。**

### 总复杂度

单趟开销 =Θ(log2⁡i)+Θ(后移个数)。求和后：T(n)=Θ(nlog2⁡n)+Θ(总逆序对数)

第二项在最坏与平均情况下都是 Θ(n2)，**它压倒了第一项**，所以T最坏(n)=T平均(n)=O(n2)

只有在**正序**（逆序对数为 0）时第二项才消失，此时 T最好(n)=Θ(nlog2⁡n)——注意这里是 nlog2⁡n 而**不是** O(n)，因为折半查找一趟也不能省。这一点与直接插入排序（最好 O(n)）正好相反：**基本有序的序列上，折半插入排序反而不如直接插入排序**。

| 指标 | 结果 | 取到该值的输入 |
| --- | --- | --- |
| 最好时间复杂度 | O(nlog2⁡n) | 正序：0 次后移，但折半查找一趟不省 |
| 最坏时间复杂度 | O(n2) | 逆序：后移约 n2/2 次 |
| 平均时间复杂度 | O(n2) | 随机：后移约 n2/4 次 |
| 比较次数 | Θ(nlog2⁡n) | **几乎与初始序列无关** |
| 空间复杂度 | O(1) | 只需 `temp`、`low`、`high`、`mid` 等常数个变量 |
| 趟数 | 固定 n−1 趟 | 与初始序列无关 |
| 稳定性 | **稳定** | 相等时 `low = mid + 1`，插到右边 |
| 存储结构 | **只能用顺序表** | 折半查找要按下标随机存取，链表做不到 |

### 稳定性

折半插入排序是**稳定**的。

保证稳定的是这一行：c

```
if (a[mid] > temp) high = mid - 1;
else               low = mid + 1;   // a[mid] == temp 时走这里
```

当 `a[mid] == temp` 时归入 `else` 分支（往**右**半区继续找），最终 `low` 会停在**所有与 temp 相等的元素之后**，待插元素被放在它们右边，相对次序不变。

**改成往左找就不稳定**：若把判断写成 `if (a[mid] >= temp) high = mid - 1;`，相等元素会被划进"待越过"的一侧，插入位置落到它们**前面**。反例 `[2a, 2b]`：正确版本插入位置为 1，输出 `2a, 2b`；错误版本插入位置为 0，输出 `2b, 2a`。

### 为什么不能用于链表

折半查找每一步都要取出区间中点 `a[mid]`。在顺序表上这是 O(1) 的下标运算；在链表上要从头结点走 `mid` 步，单次取中点就要 O(n)。这样一来，"折半"省下的比较次数被"找中点"的遍历吃干净，还不如直接顺序扫。

所以：**直接插入排序可以用于链表（甚至因为不用后移而更划算），折半插入排序不行。** 需要随机存取的还有 [希尔排序](./shell-sort.html)、[快速排序](./quick-sort.html)、[堆排序](./heap-sort.html)。

### 适用场景

正因为"比较次数固定为 nlog2⁡n、移动次数照旧"，它的定位很窄：

- **适合**：n 不太大、**初始序列比较无序**、且比较关键字的代价明显高于移动记录的场合（例如关键字是长字符串，一次比较要逐字符扫）。
- **不适合**：初始序列基本有序时——直接插入排序此时只要 n−1 次比较、0 次移动，折半插入却仍要跑满 Θ(nlog2⁡n) 次比较，反而更慢。
- **不适合**：n 很大时——瓶颈在 O(n2) 的移动上，换查找方式救不了。

## 易混淆知识点

| 对比项 | A | B | 判别依据 |
| --- | --- | --- | --- |
| **优化了比较还是移动** | 折半插入：只优化**比较** | 希尔排序：主要减少**移动**（元素可跨越 d 个位置一步到位） | 看改动落在哪一半：折半插入换的是"查找插入位置"的方法，后移循环一行没动 |
| **时间复杂度是否改善** | 比较次数：O(n2)→Θ(nlog2⁡n)，**确有改善** | 总时间复杂度：O(n2)→O(n2)，**没有改善** | 总复杂度由两项之和的**较大者**决定；移动那一项仍是 Θ(n2) |
| **最好情况谁更快** | 基本有序：**直接插入更快**（O(n)） | 基本无序：**折半插入比较更少** | 直接插入的比较次数随有序程度下降，折半插入不随之下降——有序时它反而吃亏 |
| **比较次数是否与初始序列有关** | 折半插入：几乎无关（Θ(nlog2⁡n)） | 直接插入：强相关（n−1∼n2/2） | 看内层循环的次数由"区间长度"还是"要越过几个元素"决定 |
| **稳定性靠哪一支** | 相等时 `low = mid + 1`：稳定 | 相等时 `high = mid - 1`：不稳定 | 反例 `[2a, 2b]`：插入位置分别为 1 和 0 |
| **可否用于链表** | 直接插入：**可以**（改指针即可） | 折半插入：**不可以** | 判据是"算法要不要按下标随机存取"。折半查找每步取中点，链表上取中点是 O(n) |

## 本节小结

学完本节，应该能够：

- **说清折半插入排序只替换了插入排序的哪一段**（查找插入位置），以及后移循环为什么一行都没变
- **推出比较次数**：第 i 趟约 ⌊log2⁡(i−1)⌋+1 次，总计 Θ(nlog2⁡n)；并说明它"几乎与初始序列无关"的根据是"区间长度对半收缩与关键字取值无关"
- **推出移动次数**与直接插入排序**逐记录相同**（都等于逆序对数），因此最坏、平均仍是 Θ(n2)
- **回答"折半插入的时间复杂度是否优于直接插入"**：比较次数优于，**总时间复杂度不优于**，因为瓶颈在移动
- **指出最好情况是 O(nlog2⁡n) 而非 O(n)**，并据此说明基本有序时它反而慢于直接插入排序
- **证明其稳定性**，并说清 `a[mid] == temp` 时必须往右半区找
- **说清它只能用于顺序表**的原因：折半查找依赖随机存取

两条最关键的结论：

- **只优化了一半的算法，复杂度由没被优化的另一半决定**——这是本篇最值得迁移的思路。
- **"比较次数与初始序列无关"与"移动次数完全依赖初始序列"在同一个算法里并存**，这正是"两个指标必须分开数"的最好例证。
