# SDN 软件定义网络

## 知识框架

本节回答 5 个问题：

- 传统网络里"控制面和数据面在同一台设备里"，究竟具体坏在哪三处？
- SDN 的"分离"到底分开了什么——是把路由消灭了吗？
- **流表**和路由器的转发表、交换机的 MAC 地址表，是同一类东西吗？差在哪？
- 一个分组进了 OpenFlow 交换机，**匹配不上任何流表项**会怎样？
- SDN 把控制集中了，**代价是什么**？

## 一、传统网络的问题

在传统网络中，每台路由器 / 交换机既负责**转发数据**（数据平面），又负责**计算路由**（控制平面），两个功能紧密耦合在同一台设备里。这带来三个层面的问题，**注意它们不在同一个层面上**：

| 层面 | 问题 | 根源 |
| --- | --- | --- |
| **算法层面** | 网络行为是所有设备**分布式决策**的结果，每台只按自己的局部目标（最短路）算，**难以做全局优化** | 没有任何一个实体拥有并能作用于全网视图 |
| **管理层面** | 不同厂商的设备使用私有配置方式，网络管理复杂 | 控制逻辑被封在设备固件里，只暴露厂商定义的配置接口 |
| **演进层面** | 想部署新的网络策略，需要**逐台设备配置**，效率低下；想部署新协议，得等厂商出固件 | 控制平面不可编程 |

**第一条最值得追问**：分布式路由协议算出来的是"每一对源宿之间的最短路"，但网络运营者真正想要的常常是**别的目标**——比如"让所有链路的利用率都不超过 70%""让 A 到 B 的流量走这条贵但可靠的线""晚上把备份流量挤到闲置链路"。这些都是**全局的、带约束的优化问题**，而 OSPF 只会闷头算最短路。**你能改的只有链路代价这一个旋钮**，用它去逼近一个复杂的运维目标，既笨拙又容易顾此失彼。这才是 SDN 出现的根本动因。

## 二、核心思想：把控制平面抽出来

SDN（Software Defined Networking，软件定义网络）的核心思想就一句话：

**把控制平面从网络设备中分离出来，集中到一个独立的控制器上。**

拆开这句话的两个动作：

- **分离（decoupling）**：设备不再自己算路由，只保留数据平面的转发功能；
- **集中（centralization）**：控制逻辑集中到控制器，控制器拥有**全网视图**，统一计算转发规则再下发。

分离之后的责任划分：

|  | 传统设备 | SDN |
| --- | --- | --- |
| 谁掌握全网视图 | 没有人（每台只有局部视图） | **控制器** |
| 谁计算转发规则 | 每台设备各自计算 | **控制器统一计算** |
| 谁执行转发 | 设备自己 | **仍然是设备**（交换机） |
| 谁定义网络行为 | 协议标准 + 厂商实现 | **控制器上的软件**（所以叫"软件定义"） |

❗ **两个必须掰清的误解**：

**（1）SDN 不是"消灭了路由"。** 转发依然在做，"匹配 + 动作"依然在做；只是**算路的地点**从每台设备挪到了控制器。**分离的是位置，不是功能。**

**（2）"软件定义"不是"用软件替代硬件"。** 指的是通过软件（控制器程序）来**定义**网络行为和转发策略；硬件交换机仍然存在，并且仍然负责高速转发。**变的是"谁说了算"，不是"谁在干活"。**

## 三、三层架构与两个接口

| 层次 | 组成 | 职责 |
| --- | --- | --- |
| **应用层** | 各种网络应用程序 | 通过北向接口向控制器**提出网络需求**（流量调度、访问控制、监控…） |
| **控制层** | SDN 控制器 | 维护**全网拓扑和状态信息**，计算转发规则，通过南向接口下发给交换机 |
| **数据层** | SDN 交换机 | 根据控制器下发的**流表**做分组转发，**不参与路由计算** |

两个接口，方向和内容都不同：

|  | **北向接口** | **南向接口** |
| --- | --- | --- |
| 连接谁 | 控制器 ↔ **上层应用** | 控制器 ↔ **交换机** |
| 传什么 | 应用的**意图**（"让这类流量走高优先级"） | 具体的**流表项**与设备状态 |
| 典型形态 | **RESTful API** 等，没有统一标准 | **OpenFlow**，有标准规范 |
| 谁定标准 | 各控制器自定 | 开放标准 |

**一个方向感的口诀**：**北是"向上对人"，南是"向下对机器"**。控制器夹在中间，向上把网络能力**抽象**成 API，向下把抽象的意图**翻译**成流表。OpenFlow 是南向的，**不是北向的**——这是最常被问到的一点。

## 四、OpenFlow 与流表

OpenFlow 是 SDN 南向接口的代表性协议，定义了控制器与交换机之间的通信规范。OpenFlow 交换机内部维护**一张或多张流表（flow table）**。

### 4.1 流表项的组成

| 组成部分 | 内容 | 作用 |
| --- | --- | --- |
| **匹配字段**（match fields） | 用于匹配到来的分组：入端口、源/目的 MAC、VLAN 号、源/目的 IP、协议类型、源/目的端口号…… | 描述"什么样的分组" |
| **优先级**（priority） | 一个数值 | 多条流表项同时命中时，**按优先级决定用哪条** |
| **计数器**（counters） | 匹配到的分组数、字节数、流表项存活时间 | 供控制器做统计与流量工程 |
| **动作 / 指令**（actions / instructions） | 转发到某端口、丢弃、修改首部字段、送交控制器、送入下一张流表…… | 描述"怎么处理" |
| **超时**（timeouts） | 空闲超时、硬超时 | 到期自动删除，避免流表无限膨胀 |

### 4.2 流表 ≠ 转发表 ≠ MAC 地址表

这是本篇最值得单独拿出来辨析的一点。三者都是"查表转发"，但**匹配的维度完全不同**：

|  | **MAC 地址表**（二层交换机） | **转发表**（路由器） | **流表**（OpenFlow 交换机） |
| --- | --- | --- | --- |
| 匹配什么 | **只匹配目的 MAC** | **只匹配目的 IP 前缀** | **可以匹配从二层到四层的任意字段组合** |
| 匹配规则 | 精确匹配 | 最长前缀匹配 | 通配 + 优先级 |
| 表从哪来 | **自学习**（看源 MAC） | 路由协议算出的路由表导出 | **控制器下发** |
| 动作有哪些 | 只有"从某端口转出"或泛洪 | 只有"从某端口转出" | 转发 / 丢弃 / **改写首部** / 上送控制器 / 进入下一张表 |
| 决策依据的层次 | 固定第 2 层 | 固定第 3 层 | **跨层，不受层次划分约束** |

**这张表说明了 SDN 真正的能力来源**：传统设备的转发决策**被协议层次锁死**了——二层设备只准看 MAC，三层设备只准看 IP。流表把这个约束拿掉了：**同一台设备可以按"目的 IP + TCP 端口号"这样一个跨层组合来决定动作**。所谓"软件定义"，定义的就是这个"按什么来分类、分完之后怎么处理"。

也正因如此，**SDN 交换机既不是二层交换机也不是三层路由器**，它是一台"按控制器指定的规则做匹配-动作"的通用转发设备。传统的交换、路由都可以看成它的**特例**。

### 4.3 匹配流程与 table-miss

**table-miss（未命中）这一步是理解 SDN 的关键**，它揭示了两种截然不同的工作模式：

| 模式 | 流表什么时候下发 | 首个分组 | 适用 |
| --- | --- | --- | --- |
| **反应式**（reactive） | **等分组来了、miss 了再下发** | 要上送控制器，**多一次往返时延** | 流量模式未知、规则数量大 |
| **主动式**（proactive） | 控制器**预先**把规则装满 | 直接命中，**没有额外时延** | 流量模式已知、追求确定性 |

**反应式的代价是可以量化的**：每条新流的**第一个分组**都要经历"上送控制器 → 控制器决策 → 下发流表 → 分组返回转发"这一整圈。控制器离交换机越远，这一圈越久。**所以真实部署往往是两者混合**：常规流量用主动式预装规则，例外情况才落到反应式。

这也解释了为什么 table-miss 规则本身也是一条流表项——它是**优先级最低、匹配字段全通配**的那一条，动作通常就是"上送控制器"。**"没有规则"在 OpenFlow 里也必须写成一条规则。**

## 五、SDN 的代价

大纲只要求"基本概念"，但只讲好处不讲代价，就没法回答"为什么传统网络没有被 SDN 全部取代"。

| 代价 | 具体表现 |
| --- | --- |
| **控制器是单点** | 控制器故障或与交换机之间的控制通道中断，新的流就无法建立。实际部署要做控制器集群，而集群又带来**状态一致性**问题——这正是分布式协议当初想避开的东西，绕了一圈又回来了 |
| **首包时延** | 反应式模式下每条新流的第一个分组要多一次控制器往返 |
| **控制通道要单独保障** | 控制器与交换机之间的通信本身也要走网络。它一旦拥塞或中断，整个控制面就失灵——**带内控制**（走数据网络）省钱但脆弱，**带外控制**（另建管理网）可靠但贵 |
| **规模** | 全网所有流表项都由控制器计算与维护，网络一大，控制器的计算与状态量都会成为瓶颈 |

**一句话总结这笔交换**：SDN 用**集中带来的全局最优与可编程性**，换掉了分布式协议**天然的容错性与可扩展性**。哪边划算取决于场景——数据中心内部（拓扑规整、运营者单一、需要精细流量工程）划算，广域互联网（跨管理域、规模巨大、必须容忍任意故障）就不划算。**这也是为什么因特网骨干至今仍然跑 BGP。**

## 六、传统网络 vs SDN 总对照

| 对比项 | 传统网络 | SDN |
| --- | --- | --- |
| 控制平面位置 | **分布**在每台设备中 | **集中**在控制器 |
| 转发决策 | 每台设备独立计算 | 控制器统一计算后下发 |
| 网络视图 | 每台设备只有**局部**视图 | 控制器拥有**全局**视图 |
| 转发依据 | 被协议层次锁死（MAC 表 / IP 转发表） | **流表**，可跨层任意字段组合 |
| 可编程性 | 低，依赖厂商实现与协议标准 | 高，通过北向 API 编程 |
| 设备角色 | 既转发又计算路由 | **只负责转发** |
| 全局优化 | 难（只能调链路代价这一个旋钮） | 可以直接表达带约束的优化目标 |
| 容错 | 分布式，天然抗单点故障 | **控制器是单点**，需要集群 |
| 典型场景 | 广域网、因特网骨干 | 数据中心、企业网 |

## 易混淆知识点

**1. SDN 控制器不在数据转发路径上**

控制器只负责计算转发规则并下发，实际的数据转发仍由交换机完成。**只有 table-miss 的首个分组会经过控制器**，正常流量根本不碰它。把控制器画在数据通路上是常见的错误理解。

**2. OpenFlow 是南向接口协议，不是北向**

南向 = 控制器 ↔ 交换机（OpenFlow），北向 = 控制器 ↔ 应用（RESTful API 等）。**北向接口没有统一标准，南向有。** 记忆钩子：**北向对人、南向对机器**。

**3. "软件定义"不是"用软件替代硬件"**

定义的是网络**行为和策略**；硬件交换机仍然存在，仍然负责高速转发。变的是"谁说了算"。

**4. 分离的是"控制面的位置"，不是"取消了路由"**

SDN 交换机依然在做"匹配 + 动作"，依然在转发。只是路由由控制器算完下发，而不是各设备自己算。

**5. 流表不是转发表，也不是 MAC 地址表**

MAC 表只匹配目的 MAC 且靠自学习；转发表只匹配目的 IP 前缀且由路由表导出；**流表可以匹配二到四层的任意字段组合、由控制器下发、动作还包括改写首部与上送控制器**。这是 SDN 能力的真正来源。

**6. table-miss 也是一条流表项**

它是优先级最低、字段全通配的那一条，动作通常是"上送控制器"。**OpenFlow 里"没有匹配"这件事也要被显式定义。**

**7. 集中控制不等于没有代价**

控制器单点、首包时延、控制通道的保障、大规模下的控制器瓶颈，都是实打实的成本。**因特网骨干至今跑 BGP 而不是 SDN，正是因为这些代价在广域场景下不划算。**

**8. 大纲对 SDN 的要求是"基本概念"**

抓住"控制平面与数据平面分离""集中式 vs 分布式控制""三层架构 + 南北向接口""流表 = 匹配 + 动作"这四条即可，不必去背 OpenFlow 的版本差异与字段数量。

## 本节小结

**为什么要有 SDN**：传统网络控制面与数据面耦合在同一台设备里，三个层面出问题——算法上，分布式决策各算各的最短路，**难以做全局优化**（运营者手里只有"改链路代价"这一个笨拙的旋钮）；管理上，各厂商私有配置方式使管理复杂；演进上，新策略要逐台配、新协议要等厂商。

**核心思想**：把控制平面**分离**出设备、**集中**到控制器。分离的是**位置**不是功能——转发仍在设备上做，"匹配 + 动作"照旧；"软件定义"定义的是**网络行为**，不是"用软件替代硬件"。

**三层两接口**：应用层（提需求）— 北向接口（RESTful API 等，对人，无统一标准）— 控制层（SDN 控制器，维护全网拓扑与状态、算规则）— 南向接口（**OpenFlow**，对机器，有标准）— 数据层（SDN 交换机，只按流表转发）。**北向对人，南向对机器。**

**流表**：由匹配字段、优先级、计数器、动作/指令、超时组成。它与 MAC 地址表、路由器转发表的根本差别是——后两者被协议层次锁死（只准看 MAC / 只准看 IP 前缀），**流表可以按二到四层的任意字段组合来分类**，动作还包括改写首部与上送控制器。传统的交换与路由都可视为它的特例。

**匹配流程与 table-miss**：从第一张流表开始匹配，多条命中取优先级最高，动作可以是转发 / 丢弃 / 改写 / 送入下一张表。未命中时按 table-miss 规则（**优先级最低、全通配的那条流表项**）把分组上送控制器，控制器决策并可能下发新规则。由此分出**反应式**（miss 了才下发，首包多一次控制器往返）与**主动式**（预先装满，无额外时延）两种模式，实际部署常混用。

**代价**：控制器单点（集群又带回状态一致性问题）、首包时延、控制通道需单独保障（带内省钱但脆弱、带外可靠但贵）、大规模下控制器成为瓶颈。**SDN 用集中带来的全局最优与可编程性，换掉了分布式协议天然的容错与可扩展。** 数据中心划算，广域互联网不划算——这就是因特网骨干至今跑 BGP 的原因。
