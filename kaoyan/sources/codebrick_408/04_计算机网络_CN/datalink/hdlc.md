## 知识框架

本节回答 4 个问题（按"理解即可"的深度）：

- HDLC 用一个统一的帧格式承载三类完全不同的功能，靠的是什么机制？

- HDLC 的 REJ / SREJ 与 [[04_计算机网络_CN/datalink/gbn.md|GBN]] / [[04_计算机网络_CN/datalink/sr.md|SR]] 是什么关系？

## 一、HDLC 是什么

HDLC（High-Level Data Link Control，高级数据链路控制）是 ISO 制定的**面向比特**的数据链路层协议，由 IBM 的 SDLC 协议发展而来。

核心特征：

- **面向比特**：以比特为单位处理，帧中的数据可以是任意比特串
- **使用零比特填充法**实现透明传输
- **支持可靠传输**：信息帧带序号，可以进行差错控制和流量控制
- 适用于**点对点**和**多点链路**

### 为什么 HDLC 提供可靠传输，而 PPP 不提供

这不是"谁更先进"的问题，而是**两个时代的产物**。

谢希仁在讲数据链路层可靠传输时给了这段背景（印刷 p78）：

"过去 OSI 的观点是：必须让数据链路层向上提供可靠传输。因此在 CRC 检错的基础上，增加了帧编号、确认和重传机制。收到正确的帧就要向发送端发送确认。发送端在一定的期限内若没有收到对方的确认，就认为出现了差错，因而就进行重传，直到收到对方的确认为止。**这种方法在历史上曾经起到很好的作用。但现在的通信线路的质量已经大大提高了，由通信链路质量不好引起差错的概率已经大大降低。** 因此，现在互联网就采取了区别对待的方法：对于通信质量良好的有线传输链路，数据链路层协议不使用确认和重传机制……"

**把这段和 [[04_计算机网络_CN/datalink/ppp.md|PPP 篇]]引的"简单是首要需求"合起来看，整条线索就清楚了**：

- **HDLC 诞生的年代**，链路误码率高，一帧从 A 到 B 很可能就坏了。若不在链路层立刻重传，坏帧要一路传到目的地才被端到端机制发现，重传的代价（时延 × 距离）极大。**所以链路层做可靠传输是划算的。**
- **PPP 诞生的年代**，光纤和高质量铜缆已经普及，链路层重传的收益急剧下降，而它带来的复杂度（序号、确认、超时、窗口）却一分不少。**于是干脆把可靠性整个交给 TCP。**

**同一个功能在不同的误码率下，值不值得做，答案是相反的。** 这也是为什么无线链路（[[04_计算机网络_CN/datalink/wireless-lan.md|802.11]]）又把逐帧确认捡了回来——**无线的误码率高，链路层确认重新变得划算。**

**这条"随误码率而变的取舍"，是本篇最值得带走的东西**，比记住三种站类型有用得多。

## 二、三种站与三种操作方式（了解即可）

HDLC 支持多点链路，所以要区分链路上各节点的角色：

| 站类型 | 功能 | 发送的帧 |
| --- | --- | --- |
| **主站**（Primary Station） | 控制链路操作，发送命令帧 | 命令帧 |
| **从站**（Secondary Station） | 受主站控制，响应主站的命令 | 响应帧 |
| **复合站**（Combined Station） | 既能发命令帧，也能发响应帧 | 两者皆可 |

不同的站类型组合对应三种操作方式：

| 模式 | 全称 | 链路配置 | 从站能否主动发 | 应用 |
| --- | --- | --- | --- | --- |
| **NRM** | 正常响应模式 | **不平衡**（1 主 + N 从） | **不能**，必须等主站轮询 | 主从式网络 |
| **ABM** | 异步平衡模式 | **平衡**（2 个复合站） | 双方都可主动发起 | 点对点链路，**使用最广** |
| **ARM** | 异步响应模式 | **不平衡**（1 主 + N 从） | **可以**不经轮询主动发响应帧 | 实际很少使用 |

**NRM 与 ARM 的唯一区别是"从站要不要等轮询"**，链路配置完全一样（都是不平衡）。ABM 则是配置本身不同（两个对等的复合站）。

顺带一提：**NRM 的"主站轮询从站"正是[[04_计算机网络_CN/datalink/token-passing.md|轮询访问]]那条路线在点对点/多点链路上的体现**——发送权由中心节点集中授予，与令牌传递的分散控制相对。

## 三、HDLC 帧格式

```
┌──────────┬──────────┬──────────┬──────────┬──────────┬──────────┐
│  标志 F  │  地址 A  │  控制 C  │  信息 I  │   FCS    │  标志 F  │
│ 01111110 │   8 位   │ 8/16 位  │  可变长  │   16 位  │ 01111110 │
└──────────┴──────────┴──────────┴──────────┴──────────┴──────────┘
```

**所有帧共享这一个格式**——这是 HDLC 设计上最值得注意的一点。

| 字段 | 长度 | 说明 |
| --- | --- | --- |
| **标志 F** | 8 位 | 固定 `01111110`（`0x7E`）。帧的起始与结束都用它；**两个相邻帧之间可以共用一个标志字段** |
| **地址 A** | 通常 8 位，可扩展 | 命令帧填**对方（从站）**地址，响应帧填**本站（从站）**地址——**始终标识从站** |
| **控制 C** | **8 位或 16 位** | **最重要的字段**，决定帧的类型与功能 |
| **信息 I** | 可变长 | 上层数据。**并非所有帧都有**（S 帧和部分 U 帧没有） |
| **FCS** | 16 位 | CRC 校验，范围是**地址 + 控制 + 信息**三个字段 |

**"地址字段始终标识从站"是一条容易想不通的规定。** 道理在于：多点链路上主站只有一个，**说清"是哪个从站"就足够定位一次通信**——命令帧写"我要跟谁说"，响应帧写"我是谁"，两种情况填的都是从站。若两个方向各填对方，反而需要额外区分方向。

在 ABM 模式下两站都是复合站，此时地址字段标识的是**响应方**。

## 四、三种帧类型

HDLC **靠控制字段的前 1~2 位**区分三类帧——这就是"统一格式承载三类功能"的实现机制。

| 帧类型 | 控制字段格式 | 判定 | 用途 | 有信息字段吗 |
| --- | --- | --- | --- | --- |
| **信息帧（I 帧）** | `0` N(S) P/F N(R) | **第 1 位 = `0`** | 传输用户数据 | 有 |
| **监督帧（S 帧）** | `10` SS P/F N(R) | **前 2 位 = `10`** | 流量控制与差错控制 | **无** |
| **无编号帧（U 帧）** | `11` MM P/F MMM | **前 2 位 = `11`** | 链路管理 | 部分有 |

**这是一种前缀编码**：`0` 一位就够（占掉一半编码空间给最常用的数据帧），`10`、`11` 各占四分之一。**最频繁的帧类型用最短的标识符**——与霍夫曼编码同一种思路。

### 信息帧（I 帧）

控制字段（8 位）：

```
┌───┬─────────┬─────┬─────────┐
│ 0 │ N(S) 3位│ P/F │ N(R) 3位│
└───┴─────────┴─────┴─────────┘
```

- **第 1 位 = 0** → I 帧
- **N(S)**：发送序号，3 位（序号 0~7）
- **P/F**：轮询/终止位（Poll/Final）——命令帧里是 P（轮询对方），响应帧里是 F（表示这是最后一帧）
- **N(R)**：接收序号，表示"我期望收到你的下一帧编号"，即**捎带确认**
- I 帧**既携带数据，又可以捎带确认**

**序号位数决定了窗口上限**：N(S) 与 N(R) 各 3 位，序号空间 23=8，因此 GBN 方式下发送窗口上限是 23−1=7。控制字段扩展到 16 位时，两个序号各 7 位，序号空间 27=128，窗口上限 127。

**窗口上限为什么是 2n−1 而不是 2n，推导在 [[04_计算机网络_CN/datalink/gbn.md|GBN]] 篇**，这里只用结论。

### 监督帧（S 帧）

控制字段（8 位）：

```
┌────┬────────┬─────┬─────────┐
│ 10 │ SS 2位 │ P/F │ N(R) 3位│
└────┴────────┴─────┴─────────┘
```

**SS** 是监督功能码，2 位共四种：

| SS | 名称 | 含义 | 对应机制 |
| --- | --- | --- | --- |
| `00` | **RR**（Receive Ready） | 准备接收，确认 N(R)−1 及之前的所有帧 | 正常确认 |
| `01` | **REJ**（Reject） | 拒绝，请求**从 N(R) 开始重传**后续所有帧 | 对应 [[04_计算机网络_CN/datalink/gbn.md|GBN]] |
| `10` | **RNR**（Receive Not Ready） | 接收方忙，暂时不能接收 | 流量控制 |
| `11` | **SREJ**（Selective Reject） | 选择拒绝，**仅重传 N(R) 号帧** | 对应 [[04_计算机网络_CN/datalink/sr.md|SR]] |

S 帧**没有信息字段**，不携带用户数据。

**REJ 与 SREJ 的差别，正是 GBN 与 SR 的差别在协议字段上的落点**：REJ 说"从这个号往后全部重来"，SREJ 说"只补这一个"。HDLC 把两种重传策略都做进了同一个 2 位字段里，由实现方按链路特性选用。

**RNR 与 RR 的差别是流量控制而非差错控制**：RNR 不是说"你发错了"，而是"我缓冲区满了，先别发"。这是一个显式的刹车信号——对照 [[04_计算机网络_CN/transport/tcp-flow-control.md|TCP 的流量控制]]用接收窗口 rwnd 隐式表达同一件事。

### 无编号帧（U 帧）

控制字段（8 位）：

```
┌────┬────────┬─────┬─────────┐
│ 11 │ MM 2位 │ P/F │ MMM 3位 │
└────┴────────┴─────┴─────────┘
```

- **MM + MMM** 共 5 位编码，可定义 25=32 种命令/响应
- 用于**链路的建立、拆除和管理**
- 常见 U 帧：**SABM**（建立异步平衡模式）、**DISC**（断开连接）、**UA**（无编号确认）
- U 帧**没有序号**，因此叫"无编号帧"

**"无编号"指的是没有 N(S)/N(R) 序号字段，不是"没有编码"。** U 帧里那 5 位 M 码是**功能码**（区分是 SABM 还是 DISC 还是 UA），与序号完全是两回事。

## 五、透明传输：零比特填充

HDLC 用 `01111110` 作帧定界标志。为防止数据中出现相同的比特串：

**发送方**：在标志字段之间的数据部分，每遇到**连续 5 个 1**，自动在其后插入一个 0。

**接收方**：每遇到连续 5 个 1，自动删除其后紧跟的那个 0。

**示例：**

```
原始数据:  0 1 1 1 1 1 1 0     ← 中间有 6 个连续 1
                ↑ 数到第 5 个 1
发送时:    0 1 1 1 1 1 0 1 0   ← 在第 5 个 1 后插入 0
接收时:    0 1 1 1 1 1 1 0     ← 删除那个 0，还原
```

这样保证数据部分永远不会出现 6 个连续 1，自然也就不会出现 `01111110`。

**算例与"插完要重新计数"这个易错点，见 [[04_计算机网络_CN/datalink/ppp.md|PPP 篇]]例题 2**（PPP 在同步链路上用的是完全相同的规则）。k 个连续 1 会插入 ⌊k/5⌋ 个 0，最坏膨胀比趋近 1.2。

## 六、HDLC 与 PPP 的完整对比

**这张表是本篇存在的理由。**

| 对比项 | HDLC | PPP |
| --- | --- | --- |
| **面向类型** | **面向比特** | **面向字节** |
| **传输可靠性** | **支持**（I 帧有 N(S)/N(R)，可确认与重传） | **不支持**（无序号，坏帧直接丢弃） |
| **流量控制** | **支持**（RNR / 滑动窗口） | **不支持** |
| **链路类型** | 点对点 **与多点** 均支持 | **仅点对点** |
| **双工方式** | 半双工与全双工 | **仅全双工** |
| **操作模式** | NRM / ABM / ARM 三种 | 只有点对点一种 |
| **透明传输** | **零比特填充** | 异步用**字节填充**，同步用**零比特填充** |
| **帧定界标志** | `01111110` | `0x7E`（即 `01111110`，**相同**） |
| **帧类型** | I 帧 / S 帧 / U 帧 三种 | **仅一种帧格式** |
| **站类型** | 主站 / 从站 / 复合站 | **无站类型区分**（对等） |
| **地址字段** | **有实际功能**（标识从站） | 固定 `0xFF`，**无实际意义**（可协商省略） |
| **控制字段** | **有实际功能**（区分帧类型、带序号） | 固定 `0x03`（无编号帧） |
| **FCS 长度** | 16 位 | 16 位（2 字节） |
| **FCS 校验范围** | 地址 + 控制 + 信息 | 地址 + 控制 + 协议 + 信息 |
| **网络层支持** | 无专门机制 | **NCP**，支持多种网络层协议并协商参数 |
| **鉴别功能** | 不提供 | **支持 PAP / CHAP** |
| **协议复杂度** | 复杂 | 简单 |
| **应用场景** | 传统广域网链路 | Internet 拨号 / 宽带接入 |

**核心区别记忆口诀：HDLC 面向比特有序号（可靠），PPP 面向字节无序号（不可靠）。**

### 从对比表能读出的三件事

**第一，PPP 是 HDLC 的"简化再扩展"。** 帧定界标志完全相同（`01111110`），帧的骨架（标志 + 地址 + 控制 + 信息 + FCS + 标志）也相同——PPP 的帧格式明显借鉴自 HDLC。但它**砍掉了序号与确认机制**（可靠性交给 TCP），**又加上了 NCP 与鉴别**（适应互联网的多协议与拨号接入场景）。

**砍的是"链路误码率下降后不再划算的东西"，加的是"互联网时代新出现的需求"。** 一减一加，正好是三十年间网络环境变化的写照。

**第二，地址与控制字段的"退化"是场景变化的直接结果。** HDLC 支持多点链路，所以地址字段必须能标识从站、控制字段必须能带序号；PPP 只支持点对点全双工，两个字段就都无事可做，退化成固定值（甚至可以协商省略）。**字段有没有用，取决于协议要解决的问题还在不在。**

**第三，"一个格式三类帧" vs "一种格式"是复杂度的分水岭。** HDLC 用控制字段的前 1~2 位做前缀编码，让 I/S/U 三类帧共用一个骨架，代价是每收一帧都要先解码控制字段；PPP 只有一种帧，用 2 字节的协议字段说明"里面装的是什么"（IP / LCP / NCP / PAP / CHAP），**把分类的负担从控制字段挪到了协议字段上**，而且分类维度从"帧的功能"变成了"载荷的归属"。后者更简单，也更适合"什么都能承载"的通用链路。

## 易混淆知识点

**1. 帧类型看控制字段的前 1~2 位，不看有没有信息字段**

虽然 S 帧和部分 U 帧没有信息字段，但判定标准是控制字段：第 1 位为 `0` 是 I 帧，前 2 位 `10` 是 S 帧，前 2 位 `11` 是 U 帧。

**2. 地址字段填的始终是从站地址**

命令帧填对方（从站），响应帧填本站（从站）。ABM 模式下两站都是复合站，标识的是**响应方**。

**3. HDLC 支持可靠传输，PPP 不支持**

HDLC 的 I 帧有 N(S) 和 N(R)，能确认与重传；PPP 帧没有序号字段。**这个差别的根源是链路误码率的时代变化**，不是技术优劣。

**4. U 帧的"无编号"指没有序号，不是没有功能码**

U 帧控制字段里有 5 位 M 码区分 32 种命令/响应，但没有 N(S)/N(R)。

**5. REJ 对应 GBN，SREJ 对应 SR**

REJ 要求从 N(R) 开始重传后续所有帧，SREJ 只重传 N(R) 一帧。RNR 是流量控制（缓冲区满），不是差错控制。

**6. 序号位数决定窗口上限：3 位 → 7，7 位 → 127**

控制字段 8 位时 N(S)/N(R) 各 3 位，扩展到 16 位时各 7 位。窗口上限 2n−1 的推导在 [[04_计算机网络_CN/datalink/gbn.md|GBN]] 篇。

**7. HDLC 与 PPP 的帧定界标志完全相同**

都是 `01111110` / `0x7E`。**不同的是透明传输方案**：HDLC 只用零比特填充，PPP 按物理层分两套（异步用字节填充、同步用零比特填充）。

**8. 两个相邻帧之间可以共用一个标志字段**

前一帧的结束标志同时充当后一帧的开始标志。

## 本节小结

⚠️ 再次提醒：**本篇不在 2026 大纲范围内**，只作为 [[04_计算机网络_CN/datalink/ppp.md|PPP]] 的对照。以下按"理解即可"的深度归纳。

HDLC 是 ISO 制定的**面向比特**的数据链路层协议，支持点对点与多点链路，**提供可靠传输**。

**它与 PPP 最大的差别是"可不可靠"，而这个差别的根源是时代**：HDLC 诞生时链路误码率高，链路层重传能避免坏帧长途跋涉后才被端到端机制发现，是划算的；PPP 诞生时线路质量已大幅提升，链路层重传收益骤降而复杂度不减，于是把可靠性整个交给 TCP。**同一个功能在不同误码率下值不值得做，答案相反**——无线的 [[04_计算机网络_CN/datalink/wireless-lan.md|802.11]] 又把逐帧确认捡回来，正是这条规律的反向验证。

**三种站**（主站发命令、从站发响应、复合站两者皆可）与**三种操作方式**（NRM 从站须等轮询、ABM 两个复合站对等且最常用、ARM 从站可主动响应）。NRM 的主站轮询就是[[04_计算机网络_CN/datalink/token-passing.md|轮询访问]]在多点链路上的体现。

**帧格式**：标志 F（`01111110`）+ 地址 A（8 位，**始终标识从站**）+ 控制 C（8 或 16 位）+ 信息 I（可变，非必有）+ FCS（16 位，校验地址+控制+信息）+ 标志 F。相邻两帧可共用一个标志。**所有帧共享这一个格式**，靠**控制字段的前 1~2 位**做前缀编码区分三类：`0` → **I 帧**（数据 + 捎带确认，含 N(S)/N(R)），`10` → **S 帧**（无信息字段，SS 两位区分 RR/REJ/RNR/SREJ），`11` → **U 帧**（5 位 M 码，32 种链路管理命令，无序号）。最常用的帧类型用最短的标识符，是霍夫曼式的编码思路。

**REJ 对应 [[04_计算机网络_CN/datalink/gbn.md|GBN]]、SREJ 对应 [[04_计算机网络_CN/datalink/sr.md|SR]]、RNR 是流量控制**。序号 3 位时窗口上限 7，控制字段扩展到 16 位后序号 7 位、窗口上限 127（2n−1 的推导见 GBN 篇）。

**透明传输用零比特填充**：5 个 1 后插 0，接收方 5 个 1 后删 0，保证不出现 6 连 1。算例见 PPP 篇例题 2。

**与 PPP 的对比**可以读出三件事：① PPP 是 HDLC 的"简化再扩展"——帧定界标志与骨架相同，砍掉序号确认、加上 NCP 与鉴别，一减一加正是三十年网络环境变化的写照；② PPP 的地址与控制字段退化成固定值，是因为"点对点全双工"这个场景下寻址与编号本来就不需要——**字段有没有用取决于问题还在不在**；③ HDLC 把分类负担放在控制字段（按帧的功能分），PPP 放在协议字段（按载荷的归属分），后者更简单也更适合通用承载。

**核心口诀：HDLC 面向比特有序号（可靠），PPP 面向字节无序号（不可靠）。**

## 教材出处

- **谢希仁《计算机网络》（第 7 版）印刷 p78，3.1.3 节**：链路层可靠传输取舍随线路质量而变的完整论述——"过去 OSI 的观点是：必须让数据链路层向上提供可靠传输。因此在 CRC 检错的基础上，增加了帧编号、确认和重传机制……**这种方法在历史上曾经起到很好的作用。但现在的通信线路的质量已经大大提高了，由通信链路质量不好引起差错的概率已经大大降低。** 因此，现在互联网就采取了区别对待的方法：对于通信质量良好的有线传输链路，数据链路层协议不使用确认和重传机制"。本篇第一节"为什么 HDLC 可靠而 PPP 不可靠"的全部依据出自这一段。同页还给出"无比特差错"与"无传输差错"的辨析——"在数据链路层使用 CRC 检验，能够实现无比特差错的传输，但这还不是可靠传输"。
- **同书印刷 p80–p81**：PPP 帧格式与两套透明传输方案的原文（详见 [[04_计算机网络_CN/datalink/ppp.md|PPP 篇]]引证），本篇第六节的对比表以此为准。
