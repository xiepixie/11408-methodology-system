# 第一部分：FTP 文件传送协议

## 一、FTP 要解决什么

网络环境中最基本的一项应用就是把文件从一台计算机复制到另一台。初看很简单，实际非常困难，因为各厂商的文件系统多达数百种、差别很大，经常遇到四类问题：

- 计算机存储数据的**格式**不同；
- 文件的**目录结构和命名规定**不同；
- 对于相同的文件存取功能，操作系统使用的**命令**不同；
- **访问控制**方法不同。

**FTP 的主要功能是减少或消除在不同操作系统下处理文件的不兼容性。**

FTP 只提供文件传送的一些基本服务，使用 **TCP** 可靠的运输服务。它提供交互式访问，允许客户指明文件的类型与格式（如是否使用 ASCII 码），并允许文件具有存取权限。

> [!TIP]
>

FTP 属于"文件共享协议"里的哪一类

文件共享协议分两大类：

- **复制整个文件**（FTP、TFTP 属此类）：**若要存取一个文件，就必须先获得一个本地的文件副本**；要修改只能改副本，然后把整个副本传回去。
- **联机访问**（如 NFS）：允许多个程序同时对一个文件进行存取，由操作系统提供透明存取，可以只读写文件中的一小段。

这个分类解释了 FTP 的一个具体短板：想在远地一个很大的文件末尾加一行，用 FTP 得把整个文件传回来、加完再整个传回去，来回传很花时间——而计算机 A 其实根本没用到文件的内容。NFS 则只在网络上传送那少量的修改数据。

## 二、FTP 的服务器进程结构

FTP 使用客户服务器方式。一个 FTP 服务器进程可**同时**为多个客户进程提供服务，靠的是"主进程 + 若干从属进程"的结构：

**主进程的工作步骤**：

- 打开熟知端口（端口号 **21**），使客户进程能够连接上；
- 等待客户进程发出连接请求；
- 启动**从属进程**处理客户进程发来的请求。从属进程处理完毕后即终止，运行期间根据需要还可能创建其他子进程；
- 回到等待状态，继续接受其他客户进程发来的请求。

**主进程与从属进程的处理是并发进行的**——这正是"一个服务器进程同时服务多个客户"的实现方式：主进程只负责"接活"，接完立刻回到监听状态，真正的干活交给从属进程。

服务器端有两个从属进程：**控制进程**和**数据传送进程**。客户端除了这两个进程外，还多一个**用户界面进程**用来和用户接口。

## 三、控制连接与数据连接

图源：谢希仁《计算机网络》（第 7 版）「FTP 使用的两个 TCP 连接」，印刷 p270。图中椭圆表示系统中运行的进程；为简单起见服务器端的主进程没有画出。看这张图要抓住一点：**两条连接分别连着两对不同的进程**——控制进程对控制进程、数据传送进程对数据传送进程，它们在两端都是独立的进程，不是同一个进程开的两个 socket。

| 连接类型 | 端口 | 持续时间 | 用途 |
| --- | --- | --- | --- |
| **控制连接** | **21** | **整个会话期间一直保持打开** | 传输 FTP 命令和响应 |
| **数据连接** | **20**（主动模式） | 每次文件传输时建立，**传完就关闭** | 传输文件数据 |

工作次序：

- 客户进程向服务器进程发出连接请求，寻找服务器进程的熟知端口 **21**，同时**告诉服务器进程自己的另一个端口号码**，用于建立数据传送连接；
- 服务器端的控制进程接到传输请求后，**创建"数据传送进程"和"数据连接"**；
- 服务器进程用自己传送数据的熟知端口 **20** 与客户提供的端口号建立数据传送连接；
- 数据传送进程完成传送后**关闭数据连接并结束运行**；控制连接仍然保持。

**控制连接并不用来传送文件**，实际传输文件的是数据连接。

### 为什么要两条连接：带外控制

**由于 FTP 使用了一个分离的控制连接，因此 FTP 的控制信息是带外（out of band）传送的。**

对照 HTTP：请求和响应都走同一条 TCP 连接，是**带内控制**。

使用两个独立连接的好处，教材给了两条：

- **使协议更加简单、更容易实现**——命令和数据不必在同一条字节流里混着走，就不需要设计转义或长度前缀来区分"这是命令还是文件内容"（对照[[04_计算机网络_CN/datalink/framing.md|组帧]]里的透明传输问题：单连接就必须解决它，双连接直接绕开了）；
- **传输文件时还可以利用控制连接对文件的传输进行控制**。

第 2 条才是带外控制真正独有的能力。举一个只有两条连接才做得到的动作：**文件正在传输的过程中，客户发送"请求终止传输"**。如果命令和数据共用一条连接，这条命令会排在还没传完的文件数据后面，等文件传完了才被读到——那就失去意义了。**带外控制的本质是：控制信息不被数据阻塞。**

顺带解释了为什么两个端口不会乱：**由于 FTP 使用了两个不同的端口号，所以数据连接与控制连接不会发生混乱。**

### 主动模式与被动模式

差别只在**数据连接由谁发起**这一步：

|  | 主动模式（PORT） | 被动模式（PASV） |
| --- | --- | --- |
| 数据连接发起方 | **服务器**（从端口 20 连向客户指定的端口） | **客户** |
| 服务器端数据端口 | 20 | 服务器打开的一个**随机端口**，通过控制连接告知客户 |
| 谁把端口号告诉对方 | 客户告诉服务器自己的数据端口 | 服务器告诉客户自己的数据端口 |
| 防火墙/NAT 友好性 | 差——客户在 NAT 后面时，服务器无法主动连进来 | 好，因此实际中更常用 |

**判据**：看"数据连接的 SYN 由谁发出"。主动模式服务器主动、被动模式服务器被动——名字里的主动/被动说的是**服务器**的姿态，不是客户的。

### 传输模式与其它特点

| 模式 | 说明 | 适用 |
| --- | --- | --- |
| ASCII 模式 | 传输文本文件，自动进行换行符转换 | 文本文件 |
| 二进制模式（Binary/Image） | 逐字节传输，不做任何转换 | 图片、视频、压缩包 |

FTP 的特点小结：

- 使用 **TCP** 传输（可靠）；
- **两个并行连接**：控制连接（21）+ 数据连接（20 或随机端口）；
- **有状态**协议——服务器要维护用户的当前目录、认证状态等；
- 明文传输，安全性差（SFTP/FTPS 是安全替代方案）。

### 例题 1：一次会话中的 TCP 连接数

**题目**（自造场景）：某用户用 FTP 客户端登录服务器后，先执行了 2 次 `ls`（列目录），再下载 3 个文件，最后退出。整个会话期间共建立了多少条 TCP 连接？其中同时存在的最多有几条？

**第 1 步：控制连接。** 整个会话期间只建立一次、一直保持到退出：控制连接=1 条

**第 2 步：数据连接。** 关键判据是——**凡是要通过网络传回"一批内容"的操作，都要开一条数据连接**。列目录传回的是目录列表，同样走数据连接：数据连接=2⏟列目录+3⏟下载文件=5 条

*这一步为什么这么做*：容易漏掉列目录那 2 条。判据是"这次操作要不要通过网络回传一批内容"——`LIST`（列目录）回传的是目录列表、`RETR`（取文件）回传的是文件，两者在这一点上同类，都要开数据连接；而 `CWD`（改变目录）、登录鉴别这类只交换命令与应答的操作**不开**数据连接。教材只写到"数据传送进程实际完成文件的传送"，没有细到命令一级，这条判据要自己补上。

**第 3 步：合计与并发数。**总计=1+5=6 条

同时存在的最多是 **2 条**（1 条控制 + 1 条正在传输的数据连接），因为数据连接**传完就关闭**，5 条数据连接是先后建立的、不是并存的。

**答**：共 6 条 TCP 连接；任一时刻最多同时存在 2 条。

一般化：完成 m 次数据传送（含列目录）的会话共需 m+1 条 TCP 连接，任一时刻最多 2 条并存。

## 四、拓展对照：TFTP

注意：TFTP 不在 2026 大纲的条目里，放在这里只作为"为什么 FTP 要那样设计"的反面参照，**不必背细节**。

TFTP（Trivial File Transfer Protocol，简单文件传送协议）是一个很小、易于实现的文件传送协议。它也用客户服务器方式，但使用 **UDP**，因此需要有自己的差错改正措施。

| 对比项 | FTP | TFTP |
| --- | --- | --- |
| 传输层 | TCP | **UDP**（熟知端口 **69**） |
| 连接数 | 两条（控制 + 数据） | 无连接 |
| 交互 | 支持（列目录、改目录、鉴别） | **不支持交互**，无命令集、不能列目录、不能鉴别用户 |
| 可靠性 | 由 TCP 提供 | **自己实现**，工作很像停止-等待协议 |
| 数据单元 | 字节流 | 每次 512 字节，最后一次可不足 512 |

TFTP 的可靠机制与[[04_计算机网络_CN/datalink/stop-and-wait.md|停止-等待协议]]同构：发完一个文件块就等确认，确认时指明所确认的**块编号**（从 1 开始按序编号）；超时未收到确认就重发。它还有一个巧妙的结束判据：

- 若文件长度**不是** 512 字节的整数倍，最后一个数据报文一定不满 512 字节，**这本身就是结束标志**；
- 若文件长度**恰好是** 512 的整数倍，传完后还必须再发一个**只含首部、无数据**的报文，否则接收方无法判断结束。

TFTP 的两个优点解释了它为何仍然存在：可用于 UDP 环境（同时向许多机器下载时很有用）；**代码所占内存小**——无盘设备只要固化 TFTP + UDP + IP 的小容量只读存储器，通电后就能广播一个 TFTP 请求把可执行程序拉下来。

把两者对照着看，FTP 用两条 TCP 连接换来的正是 TFTP 缺的那些：交互、鉴别、目录操作、可靠传输不用自己写。

# 第二部分：DHCP 动态主机配置协议

再次提醒：**DHCP 属大纲四（三）4，与 ARP、ICMP 并列在网络层**，不属应用层。

## 五、协议配置与 DHCP 的由来

协议软件的编写者不会把所有细节固定在源代码中，而是把协议软件**参数化**，这样同一份编译好的二进制代码可以在很多台计算机上使用。在协议软件运行之前必须给每个参数赋值，这个动作叫作**协议配置**。

连接到互联网的计算机需要配置的项目包括四项：

- **IP 地址**；
- **子网掩码**；
- **默认路由器的 IP 地址**；
- **域名服务器的 IP 地址**。

追问一层：**为什么不能在计算机生产时就烧一个唯一 IP 地址进去（像 MAC 地址那样）？**

因为 **IP 地址不仅包括主机号，还包括网络号**。一个 IP 地址指出了这台计算机连接在哪一个网络上，而计算机还在生产时无法知道它出厂后会被接到哪个网络。

这一条是理解"MAC 地址与 IP 地址为什么不能互相取代"的关键切口：**MAC 地址标识设备本身（出厂即定），IP 地址标识设备的接入位置（换网就得换）**。位置相关的东西不可能在出厂时确定，所以只能动态配置——DHCP 由此而来。它提供的机制称为**即插即用连网**（plug-and-play networking）。

DHCP 对客户机和服务器机器都适用：运行客户软件的计算机移到新网络时用 DHCP 获取配置；对运行服务器软件而**位置固定**的计算机，DHCP 指派一个**永久地址**，重启后地址不改变。

## 六、DHCP 使用 UDP

DHCP 使用 **UDP**，客户端口 **68**，服务器端口 **67**，这两个 UDP 端口都是熟知端口。

**为什么不用 TCP？** 两条理由都要说到：

- 客户在获得 IP 地址之前**连自己的 IP 都没有**，无法建立 TCP 连接（TCP 连接由四元组标识，其中就有源 IP）；
- DHCP 需要**广播**（它还不知道服务器在哪），而 **TCP 不支持广播**。

第一个报文怎么发出去的？靠两个特殊地址：

- **源 IP 设为全 0（`0.0.0.0`）**——因为这台主机目前还没有自己的 IP 地址；
- **目的 IP 设为全 1（`255.255.255.255`）**——因为还不知道 DHCP 服务器在什么地方，所以要"发现"它。

这样本地网络上的所有主机都能收到这个广播报文，**但只有 DHCP 服务器才对它进行回答**。

## 七、DORA 四步

DHCP 地址分配包含四个报文：**Discover → Offer → Request → ACK**（简记 DORA）。

**第一步 DHCPDISCOVER（发现）**：客户从 UDP 端口 68 广播发送发现报文，目的是找出网络中有哪些 DHCP 服务器。

**第二步 DHCPOFFER（提供）**：服务器先在其数据库中查找该计算机的配置信息；**找到则返回找到的信息，找不到则从服务器的 IP 地址池（address pool）中取一个地址分配给它**。Offer 报文的内容包括分配的 IP 地址、子网掩码、默认网关、DNS 服务器地址、租约期限。

注意"先查数据库、查不到再从地址池取"这个次序——它正是"位置固定的服务器能拿到永久地址"的实现方式。

**凡是收到发现报文的 DHCP 服务器都会发出提供报文**，因此客户可能收到多个 Offer。

**第三步 DHCPREQUEST（请求）**：客户从几个服务器中选择其中一个（通常是第一个到达的），**以广播方式**发送请求报文，声明自己选了哪个服务器的 Offer。

追问：**已经选定了，为什么还广播？** 因为要让**落选的那些服务器**知道自己的 Offer 没被采用，好把预留的 IP 地址收回地址池。若用单播，落选的服务器只能干等到某个超时才敢回收，这段时间地址被白白锁着。

**第四步 DHCPACK（确认）**：被选中的服务器发回确认报文。从这时起客户就可以使用这个 IP 地址了，这种状态叫作**已绑定状态**——因为在客户端 IP 地址和 MAC 地址已经完成绑定。

> [!WARNING]
>

广播/单播要分两层看

客户还没有真正绑定 IP 时，Offer/ACK 的 **IP 目的地址常写 `255.255.255.255`**；但**数据链路层**可以用 Discover 里带来的客户 MAC 做 **MAC 单播**。若客户设置了广播标志位，服务器也会退化为 MAC 广播。

所以看到"广播还是单播"这类提法，**先看问的是 IP 地址还是 MAC 地址**——这是两个不同层次上的独立选择。Discover 和 Request 则在两层上都必须是广播（前者不知道服务器在哪，后者要通知落选者）。

## 八、租约机制

DHCP 分配的 IP 地址是**临时**的，客户只能在一段有限时间内使用，这段时间称为**租用期（lease period）**。

几条硬事实：

- 协议**没有规定租用期应取多长或至少多长**，这个数值由 DHCP 服务器自己决定（教材举例：校园网可设为 1 小时）；
- 服务器在提供报文的选项中给出租用期数值；
- **租用期用 4 字节的二进制数字表示，单位是秒**，因此可选范围是 **1 秒到 136 年**（232 秒 ≈ 136 年）；
- **DHCP 客户也可以在自己发送的报文中（例如发现报文）提出对租用期的要求**。

客户拿到租用期 T 后要设置两个计时器：T1=0.5T,T2=0.875T

对应的动作：

| 时刻 | 事件 | 客户做什么 | 服务器可能的回应 |
| --- | --- | --- | --- |
| T1=0.5T | 租用期过半 | 向**原服务器**发 `DHCPREQUEST` 请求更新租用期 | 同意 → `DHCPACK`，客户得到新租用期并**重新设置计时器**；不同意 → `DHCPNACK` |
| 收到 `DHCPNACK` | 被拒 | **必须立即停止使用原来的 IP 地址**，回到第一步重新申请 | — |
| T2=0.875T | 原服务器一直不响应 | **重新发送** `DHCPREQUEST`（重复上一步），然后继续后面的步骤 | — |
| 任意时刻 | 客户想提前退租 | 发送 `DHCPRELEASE` | — |

> [!TIP]
>

两个计时器为什么是 0.5 和 0.875

把两次尝试之间的间隔看一眼就明白：T1 到 T2 之间有 0.375T 的余量给第一次续租重试，T2 到租约到期之间还剩 0.125T 的余量给第二次。**两次机会、逐次收窄、到期前留缓冲**——这是一个典型的"提前很久开始尝试、失败还有第二次"的容错设计，不是随手取的数。

### 例题 2：租约计时器与失效时刻

**题目**（自造数据）：某 DHCP 服务器把租用期设为 2 小时。客户在 09:00:00 收到 `DHCPACK` 并开始使用地址。求：（1）客户第一次请求续租的时刻；（2）若原服务器一直不响应，客户第二次请求续租的时刻；（3）若两次都失败，客户最迟在什么时刻必须停止使用该地址，此时它要做什么。

**第 1 步：统一单位。**T=2 h=7200 s

*这一步为什么这么做*：租用期在协议里以**秒**为单位表示（4 字节二进制），换成秒之后两个系数直接乘就行，不必在时分之间来回换算。

**第 2 步：第一次续租时刻。**T1=0.5T=0.5×7200=3600 s=60 min

即 **09:00:00 + 1 h = 10:00:00**，客户向**原服务器**发 `DHCPREQUEST`。

**第 3 步：第二次续租时刻。**T2=0.875T=0.875×7200=6300 s=105 min

即 **09:00:00 + 1 h 45 min = 10:45:00**，客户重新发送 `DHCPREQUEST`。

*这一步为什么这么做*：T2 是从**租期起点**算的绝对时刻，不是"从 T1 再过 0.875T"。这一点搞错会把答案算成 09:00 + 60 min + 105 min。

**第 4 步：失效时刻与后续动作。**T−T2=7200−6300=900 s=15 min

第二次尝试之后还剩 15 分钟缓冲；到 **11:00:00** 租期届满，若仍未续租成功，客户必须**停止使用该 IP 地址，重新执行完整的 DORA 过程**。

**答**：（1）10:00:00；（2）10:45:00；（3）最迟 11:00:00 停用，之后重新走 Discover → Offer → Request → ACK。

另一种失败路径要分清：若服务器明确回了 `DHCPNACK`，客户**必须立即**停止使用原地址、马上重新申请，不能等到 11:00:00。

## 九、DHCP 中继代理

DHCP 用广播，但**广播不能跨越路由器**（路由器默认不转发广播）。若服务器和客户不在同一子网，客户的 Discover 广播到不了服务器。

解决方案不是"每个子网都放一台 DHCP 服务器"——那会使服务器数量太多。而是让**每一个网络至少有一个 DHCP 中继代理（relay agent）**，通常就是一台路由器，它上面配置了 DHCP 服务器的 IP 地址信息。

要点：**中继代理收到主机以广播形式发送的发现报文后，以单播方式向 DHCP 服务器转发此报文，并等待其回答；收到提供报文后再把它发回主机。**

- 中继代理**只转发**，自己**不分配** IP 地址——它不是 DHCP 服务器；
- 它把"广播 → 单播"这一步做了，正好抵消了"广播不能跨路由器"的限制；
- 顺带一条封装上的提醒：**DHCP 报文只是 UDP 用户数据报的数据**，还要加上 UDP 首部、IP 数据报首部，以及以太网 MAC 帧的首部和尾部，才能在链路上传送。

## 易混淆知识点

**1. FTP 控制连接端口是 21，不是 20**

21 是控制连接（熟知端口），20 是**主动模式**的数据连接。被动模式的数据端口由服务器随机指定，不一定是 20。

**2. 主动/被动说的是服务器的姿态**

主动模式：服务器主动从 20 端口连向客户；被动模式：服务器被动等客户连。判据是"数据连接的 SYN 由谁发"。

**3. 控制连接持久、数据连接临时**

控制连接整个会话期间保持打开；数据连接每次传送建立、传完关闭。所以传 m 个文件要开 m 条数据连接，但任一时刻最多 2 条并存。

**4. 列目录也要开数据连接**

数据连接用于传送"文件或目录列表"，`LIST` 与 `RETR` 同类。只交换命令应答的操作（如改目录）不开数据连接。

**5. 带外控制的独有价值是"控制不被数据阻塞"**

单连接时"终止传输"这条命令会排在未传完的文件数据后面。这是双连接唯一做得到、单连接做不到的事。

**6. FTP 有状态，HTTP 无状态**

FTP 服务器要维护当前目录、认证状态；HTTP 服务器不保留之前请求的任何信息。

**7. DHCP 在大纲里属网络层，不属应用层**

它与 ARP、ICMP 并列在四（三）4。本篇合并只是本站的历史编排。

**8. DHCP 的广播/单播要分两层看**

Discover 和 Request 两层都是广播；Offer 和 ACK 常见组合是"IP 广播、MAC 单播"。看到这类提法先分清问的是哪一层。

**9. Request 用广播是为了通知落选的服务器**

即使已经选定，仍用广播，好让其他服务器立刻收回预留的地址。

**10. T2 是从租期起点算的绝对时刻**

T1=0.5T、T2=0.875T 都以租期开始为原点，不是叠加关系。

**11. 收到 `DHCPNACK` 要立即停用，不能等到期**

这是与"两次续租都超时"不同的一条失败路径。

**12. 中继代理不是 DHCP 服务器**

它只把广播转成单播往外送，自己不分配地址、不维护地址池。

**13. 租用期长度由服务器决定，协议不规定**

协议只规定了表示方式（4 字节、单位秒，范围 1 秒 ~ 136 年）。客户也可以在报文里提出自己的租用期要求。

## 本节小结

按这条主线能自己重讲一遍就算过：

- **FTP 解决的是文件系统不兼容**（格式/目录与命名/命令/访问控制四类差异）。它属"复制整个文件"这一类共享协议——要存取就得先拿到本地副本，这正是它相对 NFS 那类联机访问的短板。
- **服务器是"主进程 + 从属进程"并发结构**：主进程打开 21 端口接活后立刻回到监听，从属进程（控制进程 + 数据传送进程）干活，干完即终止。
- **两条连接的分工**：控制连接（21，整个会话保持，只传命令与响应，**不传文件**）+ 数据连接（20 或随机端口，每次传送建立、传完关闭）。客户在建控制连接时就把自己的数据端口告诉服务器。
- **带外控制的两条好处**：协议更简单（不必在一条流里区分命令与数据），以及**传输过程中还能下命令**（"请求终止传输"是只有双连接才做得到的动作）。两个不同端口号保证两条连接不混乱。
- **主动 vs 被动看数据连接谁发起**；被动模式解决 NAT/防火墙穿越，实际更常用。会话中共需 m+1 条 TCP 连接（m = 数据传送次数，含列目录），任一时刻最多 2 条并存。
- **DHCP 的由来**：IP 地址含网络号，出厂时无法确定接入位置，所以不能像 MAC 那样烧死——必须动态配置。要配的四项是 IP、子网掩码、默认路由器、域名服务器。
- **DHCP 用 UDP（67/68）的两条理由**：客户还没有 IP 无法建 TCP；需要广播而 TCP 不支持广播。第一个报文靠源 IP 全 0、目的 IP 全 1 发出去。
- **DORA 四步**：Discover（广播找服务器）→ Offer（先查数据库、查不到再从地址池取）→ Request（广播，为的是让落选服务器收回预留地址）→ ACK（进入已绑定状态，IP 与 MAC 完成绑定）。
- **租约两个计时器** T1=0.5T、T2=0.875T，均以租期起点为原点；T1 向原服务器续租，T2 重发请求，到期未成则重走 DORA。收到 `DHCPNACK` 要立即停用。租用期 4 字节、单位秒、范围 1 秒~136 年，长度由服务器定，客户可提要求。
- **中继代理把广播转成单播**跨过路由器，自己不分配地址。DHCP 报文最终要被 UDP、IP、MAC 三层首部依次封装才能上链路。
