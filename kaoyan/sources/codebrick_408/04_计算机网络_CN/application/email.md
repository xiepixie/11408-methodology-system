## 知识框架

本节回答 6 个问题：

- 电子邮件为什么必须有三个组成构件而不是两个？少哪一个会怎样？
- 一封邮件从发件人到收件人一共经过几段连接？为什么最后一段非要换协议？
- 邮件服务器凭什么"必须能够同时充当客户和服务器"？
- SMTP 只能传 7 位 ASCII，那中文邮件是怎么发出去的——是 SMTP 改了，还是别的东西改了？
- 邮件的"信封"和"内容"是谁填的？`To:` 到底是信封还是内容？
- POP3 与 IMAP 的差别，能不能归结成一句话而不是背一张表？

第 2 个问题是能算的：跳数、TCP 连接数、SMTP 会话中的应用层报文数都能数清楚，而且能随收件人数、中继台数变化——这是本节唯一需要动笔的地方。

## 一、电子邮件系统的三个组成构件

一个电子邮件系统应具有三个主要组成构件：**用户代理**、**邮件服务器**，以及**邮件发送协议（如 SMTP）和邮件读取协议（如 POP3）**。

注意第三个构件是"两种协议"合起来算一个——这不是凑数，恰恰是本节的核心结构：**发和收用的是两套协议**。

### 用户代理 UA（User Agent）

**用户与电子邮件系统的接口**，通常就是运行在用户计算机上的一个程序，也叫电子邮件客户端软件（Outlook Express、Foxmail 等）。

用户代理至少应具有 4 个功能：

| 功能 | 内容 |
| --- | --- |
| **撰写** | 提供编辑信件的环境，通信录，回信时自动提取对方地址 |
| **显示** | 在屏幕上显示来信（包括附上的声音和图像） |
| **处理** | 发送和接收；对来信进行阅读后删除、存盘、打印、转发、分类保存 |
| **通信** | 用**邮件发送协议**把邮件发到自己的邮件服务器；用**邮件读取协议**从本地邮件服务器接收邮件 |

第 4 项"通信"里那两个协议不是同一个，这一点在下一节会反复用到。

### 邮件服务器

24 小时不间断工作，具有很大容量的邮件信箱。功能是发送和接收邮件，同时还要**向发件人报告邮件传送的结果**（已交付、被拒绝、丢失等）。

邮件服务器按客户服务器方式工作，需要使用两种不同的协议：一种用于用户代理向邮件服务器发送邮件、或在邮件服务器之间发送邮件（SMTP）；另一种用于用户代理从邮件服务器读取邮件（POP3/IMAP）。

> [!TIP]
>

邮件服务器必须能够同时充当客户和服务器

这是理解整条链路的钥匙。看发送方邮件服务器这一台机器：

- 它接收发件人 UA 推来的邮件时，是 **SMTP 服务器**；
- 它把邮件转发给接收方邮件服务器时，是 **SMTP 客户**。

再看接收方邮件服务器：

- 它接收上一跳推来的邮件时，是 **SMTP 服务器**；
- 它响应收件人 UA 的读取请求时，是 **POP3 服务器**。

**同一台机器在不同的通信关系里角色不同**——这正是 [[04_计算机网络_CN/application/app-model.md|网络应用模型]] 里"客户与服务器指的是进程之间服务与被服务的关系、不是机器"那句话最好的例子。

### 为什么必须有第三个构件（两套协议）

追问一层：**为什么不能全程用 SMTP，最后一跳也用 SMTP 推给收件人 UA？**

因为 UA 不是 7×24 在线的。SMTP 是**推**协议，推的前提是接收方随时能收；而收件人的电脑可能关着机。所以邮件只能先推到收件人的邮件服务器上"落地"，等收件人**方便时上网**再自己去拿——最后这一跳只能是**拉**。

教材开篇讲电子邮件的意义时说得更直白：它解决的正是电话通信"主叫和被叫双方必须同时在场"的缺点。**"存储—转发 + 拉取"这个结构，就是"不必同时在场"在协议上的实现。**

## 二、邮件传送的完整路径

图源：谢希仁《计算机网络》（第 7 版）「电子邮件的最主要的组成构件」，印刷 p294。这张图值得逐格看的地方在上半部分：发送方邮件服务器这一个方框里**同时画着 SMTP 服务器和 SMTP 客户两个进程**，接收方邮件服务器里则同时画着 SMTP 服务器和 POP3 服务器——一台机器两种角色，是本节最容易记混的地方。

流程图形式：

分步说明：

- 发件人在 UA 中写好邮件，点击发送；
- UA 用 **SMTP** 把邮件推到发件人的邮件服务器，邮件先进**邮件缓存**（待发送队列）；
- 发送方邮件服务器用 **SMTP** 把邮件推到收件人的邮件服务器；
- 邮件存进收件人邮件服务器上的**用户邮箱**；
- 收件人在方便时用 **POP3 或 IMAP** 从自己的邮件服务器把邮件拉下来。

> [!WARNING]
>

方向判据：看谁发起，不看数据往哪流

POP3 的数据也是从服务器流向 UA，看起来和 SMTP 的"服务器流向服务器"方向一致，于是很容易记成"都是推"。

正确判据是**谁主动发起这次传输**：

- **SMTP：发送方主动**，把邮件推给对方 → 推（Push）；
- **POP3/IMAP：接收方主动**，去服务器上取 → 拉（Pull）。

图里最后那段箭头虽然指向右边的收件人，但发起这次连接的是右边的 POP3 客户。

一句话记住整条链：**发送阶段全部是 SMTP（无论是 UA→MTA 还是 MTA→MTA），只有最后一跳读取邮件才用 POP3/IMAP。**

> [!WARNING]
>

SMTP 不使用中间的邮件服务器

标准情形下发送阶段**只有这两跳**，中间没有第三台邮件服务器：不管两台邮件服务器相隔多远、邮件在传送途中要经过多少个路由器，**TCP 连接总是在发送方和接收方这两个邮件服务器之间直接建立**。

由此还能推出一条容易记反的结论：**接收方邮件服务器出故障时，发送方邮件服务器只能等一段时间后再尝试与它建连，而不能改找一台中间邮件服务器替它转发。**"逐跳转发"是网络层 IP 数据报的做法，别把它套到 SMTP 上——路由器转发的是 IP 数据报，不是邮件。

下面例题第（3）问里那台"中继邮件服务器"是为了把连接计数**一般化**而假设出来的，**不是 SMTP 的常态**；把 n=0 代回去才是标准链路。

### 例题 1：端到端跳数、连接数与 SMTP 报文数

**题目**（自造场景）：用户 A 用 Foxmail 给用户 B 发一封邮件，A 与 B 的邮箱在两台不同的邮件服务器上，B 用 Foxmail 通过 POP3 收信，中途不经过任何中继邮件服务器。求：（1）端到端共建立几条 TCP 连接，各用什么协议；（2）若这封邮件同时发给 3 个收件人（都在同一台接收方服务器上），发送方服务器与接收方服务器之间的那次 SMTP 会话共交换多少个应用层报文；（3）若中间还要经过 1 台中继邮件服务器，第（1）问的答案变成多少。

**第 1 步：数连接。** 链路上有三段，每段是一次独立的 TCP 连接：

| 段 | 协议 | 客户端 | 服务器端 | 端口 |
| --- | --- | --- | --- | --- |
| A 的 UA → 发送方服务器 | SMTP | UA | 邮件服务器 | 25 |
| 发送方服务器 → 接收方服务器 | SMTP | 发送方服务器 | 接收方服务器 | 25 |
| 接收方服务器 → B 的 UA | POP3 | **B 的 UA** | 接收方服务器 | 110 |

TCP 连接数=3,SMTP 会话=2,POP3 会话=1

*这一步为什么这么做*：注意第三行的"客户端"是 **B 的 UA**，不是服务器。SMTP 那两段的客户端都在左边，POP3 这段的客户端在右边——这就是推与拉在连接建立方向上的体现。

**第 2 步：数一次 SMTP 会话的应用层报文。** 按三个阶段展开（k = 收件人数）：

| 阶段 | 交互 | 报文数 |
| --- | --- | --- |
| 连接建立 | 服务器 `220 服务就绪` → 客户 `HELO` → 服务器 `250 OK` | 3 |
| 邮件传送 | `MAIL FROM:` → `250` | 2 |
|  | `RCPT TO:` → `250`，**每个收件人重复一次** | 2k |
|  | `DATA` → `354 开始输入` | 2 |
|  | 邮件内容（以单独一行的 `.` 结束）→ `250` | 2 |
| 连接释放 | `QUIT` → `221` | 2 |
| **合计** |  | 11+2k |

代入 k=3：11+2×3=17 个应用层报文

*这一步为什么这么做*：只有 `RCPT TO` 这一项随收件人数增长——因为 `MAIL FROM` 声明的是发件人（只有一个）、`DATA` 传的是邮件正文（只传一份）。**同一封多收件人邮件在同一台目的服务器上只传一次正文**，这正是 SMTP 把"信封"（`MAIL FROM`/`RCPT TO`）和"内容"（`DATA` 之后的部分）分开的收益所在。作为对照，k=1 时是 13 个报文。

**第 3 步：加一台中继（假设情形，见上面那条提醒）。** 中继邮件服务器同样以 SMTP 收、以 SMTP 发，于是 SMTP 会话从 2 次变成 3 次：TCP 连接数=3+1=4,SMTP 会话=3,POP3 会话仍=1

*这一步为什么这么做*：**POP3 会话数与中继台数无关**——不管邮件在服务器之间转了几手，收件人 UA 始终只与自己的那一台邮件服务器打交道。一般化：经过 n 台中继时，TCP 连接数 =n+3，SMTP 会话数 =n+2，POP3 会话恒为 1。

**答**：（1）3 条 TCP 连接，两段 SMTP（端口 25）+ 一段 POP3（端口 110）；（2）17 个应用层报文；（3）4 条 TCP 连接，SMTP 3 次、POP3 仍 1 次。

**本例最值得带走的一条**：端到端时延不是这三段时延之和。邮件在每台邮件服务器上都要**落盘存储**，收件人不上线取信，邮件就一直躺在接收方服务器上。**电子邮件是存储—转发式应用，"发出去了"和"对方看到了"之间没有时间关系。**

## 三、SMTP 协议

SMTP（Simple Mail Transfer Protocol，简单邮件传送协议）负责邮件的**发送和转发**。

| 特性 | 说明 |
| --- | --- |
| 传输层 | TCP，端口 **25** |
| 传输方向 | **推（Push）**——发送方主动把邮件推给接收方 |
| 编码 | 只能传送可打印的 **7 位 ASCII 码** |
| 通信方式 | 客户服务器方式，发送方是客户、接收方是服务器 |

### 三个阶段

**1. 连接建立**

- 发送方 SMTP 客户与接收方 SMTP 服务器建立 TCP 连接（端口 25）；
- 接收方回复 `220`（服务就绪）；
- 发送方发送 `HELO` 命令，接收方回 `250`。

**2. 邮件传送**

- `MAIL FROM: <sender@example.com>` —— 声明发件人；
- `RCPT TO: <receiver@example.com>` —— 声明收件人，**每个收件人一条**；
- `DATA` —— 开始传送邮件内容，服务器回 `354`；
- 邮件内容以**单独一行的句点 `.`** 结束。

**3. 连接释放**

- 发送方发送 `QUIT`，服务器回 `221`，TCP 连接关闭。

追问一层：**为什么用"单独一行的句点"当结束标志，而不是像 TCP 那样给个长度字段？** 因为 SMTP 是**面向文本**的协议，邮件长度事先不确定、报文里没有长度字段，只能用一个正常正文里不会出现的模式来划界。代价是正文里若真有一行只写一个句点，必须做转义（发送方在行首多加一个句点）——这与[[04_计算机网络_CN/datalink/framing.md|组帧]]里"透明传输"要解决的是同一类问题，只是一个在字符层面、一个在比特层面。

### SMTP 的局限与 ESMTP

SMTP 只能传送 7 位 ASCII 文本，不能直接传中文、图片、视频等二进制内容。两条不同的补救路线，注意它们改的**不是同一层东西**：

| 路线 | 改了什么 | 结果 |
| --- | --- | --- |
| **MIME** | 不改 SMTP，改的是**邮件内容的组织方式** | 把非 ASCII 内容编码成 ASCII 再交给 SMTP |
| **ESMTP** | 改的是 **SMTP 协议本身**（RFC 5321 扩充） | 服务器可以直接接受二进制报文、分块传送大报文等 |

ESMTP（Extended SMTP）新增的功能包括：客户端的鉴别、服务器接受二进制报文、服务器接受分块传送的大报文、发送前先检查报文大小、使用安全传输 TLS、使用国际化地址。

**握手命令因此变了**：使用 ESMTP 的客户端在准备传送报文时，不是发送 `HELO` 而是发送 **`EHLO`**。

- 若 `EHLO` 被服务器**拒绝** → 对方仍是标准 SMTP 服务器，退回按原来的 SMTP 参数传送；
- 若 `EHLO` 被**接受** → 客户端可以使用扩展参数。

这是一种典型的**向下兼容协商**：用一个新命令去探路，被拒绝就降级——与 HTTP/2 向 HTTP/1.1 降级是同一个套路。

## 四、电子邮件的信息格式

### 信封与内容

一个电子邮件分为**信封**和**内容**两大部分。RFC 5322 只规定了邮件**内容中的首部（header）格式**，对邮件的**主体（body）**则让用户自由撰写。

关键的一条流程：**用户写好首部后，邮件系统自动地将信封所需的信息提取出来并写在信封上，所以用户不需要填写电子邮件信封上的信息。**

由此可以回答"`To:` 是信封还是内容"：

|  | 属于 | 谁填 | 在 SMTP 里对应什么 |
| --- | --- | --- | --- |
| `To:` `Cc:` `Subject:` `From:` … | **邮件内容的首部** | 用户（部分由系统自动填） | 系统据此生成 `RCPT TO` 等信封命令 |
| 信封上的发件人/收件人 | **信封** | 邮件系统自动提取 | `MAIL FROM:` / `RCPT TO:` |

这个分离带来一个直接后果：**信封上的收件人和内容首部里的 `To:` 可以不一致**。密送（`Bcc`）就是靠这个实现的——信封上有这个人（所以他能收到），但内容首部里不写他，于是别的收件人看不到。

### 首部关键字

| 关键字 | 含义 | 谁填 |
| --- | --- | --- |
| `To:` | 一个或多个收件人的电子邮件地址 | 用户 |
| `Subject:` | 邮件主题，**类似文件系统的文件名**，便于查找 | 用户 |
| `Cc:` | 抄送（Carbon copy），给某人发一个副本 | 用户 |
| `Bcc:` | 盲抄送/暗送（Blind carbon copy），发副本但**不让收件人知道此事** | 用户 |
| `From:` | 发件人的电子邮件地址 | 一般由系统自动填入 |
| `Date:` | 发信日期 | 一般由系统自动填入 |
| `Reply-To:` | 对方回信所用的地址，**可以与发信时用的地址不同** | 可事先设置 |

最重要的两个关键字是 `To:` 和 `Subject:`。

## 五、MIME（通用互联网邮件扩充）

MIME（Multipurpose Internet Mail Extensions）**不是一个独立的协议**，而是对邮件内容的扩充。它在邮件首部中说明邮件的数据类型（文本、声音、图像、视像等），并允许在一封 MIME 邮件中同时传送多种类型的数据。

做法分两步：

- 在邮件首部增加字段说明内容类型与编码方式；
- 把非 ASCII 内容用 Base64 等方式编码成 ASCII 字符串，再交给 SMTP 传送。

| MIME 首部字段 | 作用 |
| --- | --- |
| `MIME-Version` | MIME 版本（通常 1.0） |
| `Content-Type` | 内容类型（`text/plain`、`text/html`、`image/jpeg` 等） |
| `Content-Transfer-Encoding` | 编码方式（Base64、Quoted-Printable 等） |

> [!WARNING]
>

MIME 没有修改 SMTP

这是本节最关键的一条概念边界。MIME 是**发送前把内容变成 ASCII、接收后再变回去**，中间那段 SMTP 传的仍然是纯 ASCII——SMTP 本身对此一无所知。所以"MIME 使 SMTP 能够传输二进制数据"是错的，正确说法是"**MIME 使二进制数据能够以 SMTP 可接受的形式被传输**"。

真正改动了 SMTP、让它能直接收二进制报文的是 **ESMTP**，不是 MIME。

Base64 的代价也值得知道：它用 4 个 ASCII 字符表示 3 个字节，**编码后体积膨胀约 33%**。这是"不改协议只改内容"这条路线要付的价钱。

408 对 MIME 的要求不深，知道它的作用、以及它与 SMTP 的分工即可。

## 六、邮件读取协议：POP3 与 IMAP

### POP3

POP（Post Office Protocol，邮局协议）经过几次更新，现在使用的是第 3 个版本 **POP3**。

| 特性 | 说明 |
| --- | --- |
| 传输层 | TCP，端口 **110** |
| 传输方向 | **拉（Pull）** |
| 鉴别 | **只有在用户输入用户名和口令后，才允许对邮箱进行读取** |
| 特点 | **只要用户从 POP3 服务器读取了邮件，服务器就把该邮件删除** |

这个"读完即删"的特点带来的麻烦，教材举了一个很具体的场景：某用户在办公室台式机上收了一封邮件，还没来得及回信就出差；等他打开笔记本想写回信时，POP3 服务器上那封邮件已经被删掉了。

补救办法是 POP3 的功能扩充：让用户能够**事先设置**邮件读取后仍在服务器中存放的时间。所以 POP3 有两种工作模式：

- **下载并删除（Delete）**：下载到本地后服务器上删除；
- **下载并保留（Keep）**：下载到本地后服务器上仍保留副本。

但即便设成"保留"，POP3 仍有一个根本限制：**用户在本地对邮件的操作（移到文件夹、标记已读）不会同步到服务器**，不同设备上看到的状态可能不一致。

### IMAP

IMAP（Internet Message Access Protocol，网际报文存取协议）比 POP3 复杂得多。现在较新的版本是 IMAP4，习惯上直接叫 IMAP（而 POP3 却总要写上版本号 3）。

| 特性 | 说明 |
| --- | --- |
| 传输层 | TCP，端口 **143** |
| 传输方向 | **拉（Pull）** |
| 工作模式 | **联机协议**——用户在自己机器上操纵服务器上的邮箱，就像在本地操纵一样 |

IMAP 的行为：客户程序打开服务器邮箱时，用户先看到邮件的**首部**；只有当用户需要打开某个邮件，该邮件才传到用户计算机上。用户可以创建层次式的邮箱文件夹、在文件夹之间移动邮件、按条件查找。**在用户未发出删除命令之前，服务器邮箱中的邮件一直保存着。**

两个具体好处：

- 可以在不同地方用不同计算机随时上网阅读和处理自己在服务器上的邮件；
- **允许只读取邮件中的某个部分**——比如收到带大附件的邮件而当前网速很慢，可以先下载正文，以后再取附件。

缺点：如果用户没有把邮件复制到自己的计算机上，邮件就一直在服务器上，**要看邮件必须先上网**。

### 一句话归纳

不要背那张对照表，记这一句：

**POP3 把邮箱搬到本地（服务器只是中转站），IMAP 把邮箱留在服务器（本地只是一个视图）。**

从这一句能推出整张表：

| 对比项 | POP3 | IMAP |
| --- | --- | --- |
| 邮件存储位置 | 下载到本地 | 保留在服务器 |
| 多设备同步 | 不同步（本地操作不上传） | 所有操作实时同步 |
| 服务器端文件夹 | 不支持 | 支持创建与管理 |
| 离线访问 | 下载后可离线查看 | 需要缓存，否则必须联网 |
| 部分下载 | 全部下载 | 可只下首部，需要时再取正文/附件 |
| 服务器存储压力 | 小 | 大 |
| 协议复杂度 | 简单、功能有限 | 复杂 |

## 七、基于 Web 的电子邮件

用浏览器收发邮件（如网页版邮箱）时，链路的**两端**换了协议，**中间没变**：

- 用户 ↔ 自己的邮件服务器：**HTTP/HTTPS**（不是 SMTP/POP3）；
- 邮件服务器之间：**仍然是 SMTP**。

这条结论要点在于**中间那一跳永远是 SMTP**：不同厂商的邮件服务器之间必须有一个共同语言，而各家的 Web 界面各自为政。**服务器之间的互通性，就是 SMTP 无法被替换掉的原因。**

## 易混淆知识点

**1. SMTP 是推、POP3/IMAP 是拉，判据是"谁发起"**

不是看数据往哪个方向流。POP3 的数据也从服务器流向 UA，但发起连接的是 UA。

**2. 发送阶段的两跳都用 SMTP**

无论 UA → 发件人 MTA，还是发件人 MTA → 收件人 MTA，都是 SMTP。只有最后读取邮件才用 POP3/IMAP。而且标准情形下**只有这两跳**：SMTP 不使用中间的邮件服务器，两台邮件服务器之间的 TCP 连接总是直接建立；收方服务器故障时发方只能等待重试，不能改由中间服务器代转。

**3. 一台邮件服务器同时是 SMTP 服务器和 SMTP 客户**

收邮件时当服务器，转发时当客户。接收方服务器还同时是 POP3 服务器。角色由通信关系决定，不由机器决定。

**4. MIME 没有修改 SMTP，ESMTP 才修改了**

MIME 是在内容层面做编码/解码，SMTP 传的仍是 ASCII。能直接接受二进制报文的是 ESMTP，握手命令是 `EHLO` 而非 `HELO`。

**5. SMTP 只能传 7 位 ASCII，且是"可打印的"**

不是 8 位，也不是"全部 ASCII"。

**6. `To:` 属于邮件内容的首部，不属于信封**

信封由邮件系统自动从首部提取生成。因此信封上的收件人可以与 `To:` 不一致——`Bcc` 就是这么实现的。

**7. `Cc` 与 `Bcc` 的差别在"别的收件人看不看得到"**

`Cc` 抄送，所有人可见；`Bcc` 暗送，发件人不希望此事为其他收件人知道。

**8. POP3 默认读完即删，但可以配置成保留**

"POP3 一定会删除服务器上的邮件"是错的，它做过功能扩充，可事先设置读取后仍存放的时间。但即使保留，本地操作也不会同步到服务器。

**9. IMAP 是联机协议，POP3 不是**

IMAP 允许在服务器上直接操纵邮箱、只下载邮件的一部分；这两条 POP3 都做不到。

**10. Web 邮箱只换掉了两端，中间仍是 SMTP**

用户 ↔ 服务器用 HTTP，服务器 ↔ 服务器仍用 SMTP。

**11. 端口号别记混**

SMTP 25、POP3 110、IMAP 143；对照 HTTP 80、HTTPS 443、DNS 53、FTP 21/20。

**12. "发出去了"不等于"对方看到了"**

电子邮件是存储—转发式的：邮件在收件人服务器上落盘后就算送达，收件人什么时候来拉与发送方无关。

## 本节小结

按这条主线能自己重讲一遍就算过：

- **三个组成构件**：用户代理、邮件服务器、以及"邮件发送协议 + 邮件读取协议"这一对。第三个构件是两种协议合起来算一个，因为发和收本来就不是一套协议。
- **UA 的四个功能**：撰写、显示、处理、通信；其中"通信"要分别调用发送协议和读取协议。
- **必须有两套协议的理由**：SMTP 是推协议，推的前提是接收方在线；而收件人 UA 随时可能离线，所以邮件只能先推到收件人的服务器落地，最后一跳只能是拉。这正是"不必同时在场"在协议上的实现。
- **邮件服务器同时充当客户和服务器**：发送方服务器 = SMTP 服务器 + SMTP 客户；接收方服务器 = SMTP 服务器 + POP3 服务器。
- **跳数能数清楚**：标准情形下 **SMTP 不使用中间的邮件服务器**，两台邮件服务器之间直接建 TCP 连接，全程 3 条（SMTP 25 两段 + POP3 110 一段）；若题面另行假设经 n 台中继，则连接数 =n+3、SMTP 会话 =n+2、POP3 恒为 1。一次 SMTP 会话的应用层报文数 =11+2k（k 为收件人数），只有 `RCPT TO` 随 k 增长，正文只传一份。
- **SMTP 三阶段**：连接建立（220 / `HELO` / 250）→ 邮件传送（`MAIL FROM` / `RCPT TO` / `DATA` / 单独一行的 `.`）→ 连接释放（`QUIT` / 221）。用句点划界是面向文本协议的必然选择，代价是要做转义。
- **两条突破 7 位 ASCII 的路线改的不是同一层**：MIME 改内容（Base64 编码，体积膨胀约 33%，SMTP 毫不知情）；ESMTP 改协议本身（`EHLO` 探路，被拒则降级回 `HELO`）。
- **信封 vs 内容**：RFC 5322 只规定内容首部格式，信封由邮件系统自动从首部提取。`To:`/`Subject:`/`Cc:`/`Bcc:`/`From:`/`Date:`/`Reply-To:` 都属内容首部；信封与 `To:` 可以不一致，`Bcc` 靠这一点实现。
- **POP3 vs IMAP 归结成一句**：POP3 把邮箱搬到本地，IMAP 把邮箱留在服务器。由这一句可推出同步、文件夹、离线、部分下载、存储压力五项差别。POP3 默认读完即删但可配置保留；IMAP 是联机协议、可只取首部。
- **Web 邮箱只换两端**：用户↔服务器走 HTTP，服务器↔服务器仍走 SMTP——服务器之间的互通性是 SMTP 不可替代的原因。

- **印刷 p298**，6.5.2 节末：ESMTP 的说明——「2008 年 10 月颁布的草案标准 RFC 5321 对 SMTP 进行了扩充，成为扩充的 SMTP(Extended SMTP)，记为 ESMTP……新增加的功能有：客户端的鉴别，服务器接受二进制报文，服务器接受分块传送的大报文，发送前先检查报文的大小，使用安全传输 TLS，以及使用国际化地址等」「使用 ESMTP 的客户端在准备传送报文时，不是发送 HELO 而是发送 EHLO 报文。如果 EHLO 报文被对方服务器端拒绝，就表明对方仍然是一个标准的 SMTP 邮件服务器」。同页 6.5.3 节：「一个电子邮件分为信封和内容两大部分。在草案标准 RFC 5322 文档中只规定了邮件内容中的首部(header)格式，而对邮件的主体(body)部分则让用户自由撰写。用户写好首部后，邮件系统自动地将信封所需的信息提取出来并写在信封上。所以用户不需要填写电子邮件信封上的信息」，以及 `To:`/`Subject:`/`Cc:`/`Bcc:`/`From:`/`Date:`/`Reply-To:` 各关键字的含义。
- **印刷 p299**，6.5.4 节：POP3 的鉴别与删除特性——「POP3 服务器只有在用户输入鉴别信息（用户名和口令）后，才允许对邮箱进行读取」「POP3 协议的一个特点就是只要用户从 POP3 服务器读取了邮件，POP3 服务器就把该邮件删除」，以及出差换机器看不到旧邮件那个具体例子与功能扩充。IMAP 一段：「用户在自己的计算机上就可以操纵邮件服务器的邮箱，就像在本地操纵一样，因此 IMAP 是一个联机协议……若用户需要打开某个邮件，则该邮件才传到用户的计算机上」「IMAP 还允许收件人只读取邮件中的某个部分」；缺点「如果用户没有将邮件复制到自己的计算机上，则邮件一直存放在 IMAP 服务器上。要想查阅自己的邮件，必须先上网」。同页结尾正是本篇那条方向判据的依据：「最后再强调一下，不要把邮件读取协议 POP3 或 IMAP 与邮件传送协议 SMTP 弄混。发件人的用户代理向发送方邮件服务器发送邮件，以及发送方邮件服务器向接收方邮件服务器发送邮件，都是使用 SMTP 协议。而 POP3 或 IMAP 则是用户代理从接收方邮件服务器上读取邮件。」
