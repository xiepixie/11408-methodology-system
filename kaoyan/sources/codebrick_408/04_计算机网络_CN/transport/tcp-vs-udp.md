## 知识框架

本节回答 6 个问题：

- IP 已经能把分组送到目的主机了，为什么还需要传输层？它比网络层多做了哪几件网络层做不到的事？
- 既然操作系统里已经有进程标识符，为什么还要另发明一套"端口号"？
- 复用与分用听上去像是同一件事的两个方向，为什么 TCP 和 UDP 的分用规则不一样？

- 同一个 80 端口如何同时服务成千上万个客户？

## 一、传输层的功能：为什么 IP 不够

### 网络层送到主机，传输层送到进程

谢希仁给出的分界线只有一句话，但这句话是整章的地基：

**网络层为主机之间的通信提供服务，而运输层则在网络层的基础上，为应用进程之间的通信提供服务。**

为什么这个区分是必要的？因为 IP 数据报的首部里只有源 IP 与目的 IP，它明确标志的是**两台主机**。可"两台主机之间的通信"这个说法不够明确——真正在交换数据的是主机里的**应用进程**。一台机器上可能同时开着浏览器和邮件客户端，浏览器在和网站的 Web 进程通信、邮件客户端在和邮件服务器通信，IP 把分组送到网络层就停下了，**它没有任何字段能说明这一份该交给哪个进程**。

所以传输层要做的第一件事，是把"主机到主机"补成"进程到进程"。

### 逻辑通信：好像是这样通信，但事实上并非真的这样

教材用了一个很准确的措辞——传输层提供的是应用进程间的**逻辑通信**：

"逻辑通信"的意思是：从应用层来看，只要把应用层报文交给下面的运输层，运输层就可以把这报文传送到对方的运输层（哪怕双方相距很远），好像这种通信就是沿水平方向直接传送数据。但事实上这两个运输层之间并没有一条水平方向的物理连接……**"逻辑通信"的意思是"好像是这样通信，但事实上并非真的这样通信"。**

数据实际上是**竖着走**的：传输层 → 网络层 → 数据链路层 → 物理层 → 中间若干路由器 → 一路向上回到对方的传输层。所谓"水平"只是应用程序眼里的假象，而制造这个假象正是传输层的职责。

图里有两条虚线，正好说明分层的递进关系：**网络层制造的假象是"主机之间直连"，传输层在它之上再制造一层"进程之间直连"。** 而路由器只有下三层——它转发分组时**根本不需要传输层**，这也是"传输层是端到端的、只存在于主机中"的由来。

### 传输层比网络层多做的四件事

| 功能 | 网络层做不到的原因 |
| --- | --- |
| **复用与分用** | IP 首部里没有能标识进程的字段 |
| **对整个报文做差错检测** | IP 首部的检验和**只检验首部、不检查数据部分** |
| **可选的可靠传输**（仅 TCP） | IP 只承诺尽最大努力交付，不做确认与重传 |
| **可选的流量控制与拥塞控制**（仅 TCP） | IP 无状态，不知道对端缓存有多满、网络有多堵 |

前两条是**传输层必须做的**（UDP 也做），后两条是**可选的**（只有 TCP 做）。这个"必做 / 可选"的划分，就是 TCP 与 UDP 分道扬镳的地方——两个协议都提供端口与校验和，差别全在后两条要不要。

> [!TIP]
>

一条容易被忽略的功能

传输层还**向高层屏蔽了网络核心的细节**（网络拓扑、用的什么路由协议）。应用程序写代码时只面对"一条端到端的逻辑信道"，从不关心中间走了几跳、经过了以太网还是无线。这条逻辑信道的**性质**由所选协议决定：用 TCP 时它相当于一条**全双工的可靠信道**；用 UDP 时它**仍然是一条不可靠信道**。

## 二、传输层寻址：为什么是端口，不是进程号

### 三条否掉进程标识符的理由

单台计算机里，进程是用**进程标识符**（一个不大的整数）来标志的。那为什么互联网上不直接用它？教材给了三条理由，逐条都能追问出后果：

**理由一：进程标识符的格式与操作系统绑定。** 互联网上运行着各种操作系统，不同系统用不同格式的进程标识符。要让运行不同操作系统的机器互相通信，就**必须用一种与特定操作系统无关的统一方法**来标志应用进程。

**理由二：进程是动态创建和撤销的。** 通信的一方几乎无法知道对方机器上此刻正在跑哪些进程、编号是多少。今天服务器进程号是 3721，重启一次就变了——**没有任何办法让全世界的客户端跟着更新**。

**理由三：我们要找的是"功能"，不是"某个进程"。** 想访问某个邮件服务器时，我们关心的是"这台机器上提供邮件服务的那个东西"，而**不需要知道这个功能具体由哪个进程实现**。用进程号寻址等于强迫调用方关心实现细节。

三条合起来指向同一个解法：**在应用层与传输层的界面上设一个抽象的"门"，用一个与操作系统无关的编号来标志它。** 这个抽象终点的正式名称就是**协议端口**，简称端口；编号叫端口号。

### 软件端口不是硬件端口

教材专门强调了这一点：

这种在协议栈层间的抽象的协议端口是**软件端口**，和路由器或交换机上的**硬件端口**是完全不同的概念。硬件端口是不同硬件设备进行交互的接口，而软件端口是应用层的各种协议进程与运输实体进行**层间交互的地点**。

判据很清楚：**硬件端口连的是"两台设备"，软件端口连的是"同一台机器里的两层"。** 交换机上插网线的那个口和 HTTP 的 80 端口，除了共用一个中文词之外没有任何关系。

### 端口号只有本地意义

端口号是 **16 位**，因而共有 216=65536 个（0～65535）。但要特别注意教材的这句话：

端口号**只具有本地意义**，它只是为了标志本计算机应用层中的各个进程在和运输层交互时的层间接口。在互联网不同计算机中，**相同的端口号是没有关联的**。

也就是说，A 机器的 5000 端口和 B 机器的 5000 端口毫无关系。这也解释了为什么单靠端口号无法标识一条连接——必须配上 IP 地址。

### 端口号的三类划分

| 范围 | 名称 | 说明 |
| --- | --- | --- |
| **0 ~ 1023** | 熟知端口号（全球通用端口号） | IANA 指派给最重要的一批应用程序，所有用户都知道。相当于 110、120 这类人人皆知的电话号码 |
| **1024 ~ 49151** | 登记端口号 | 给没有熟知端口的应用程序用，必须在 IANA 登记，防止重复 |
| **49152 ~ 65535** | 短暂端口号（客户端端口） | 客户进程运行时**动态选择**，通信结束后由系统收回给别的客户进程用 |

数一下：1024+48128+16384=65536，三段刚好铺满 16 位空间，中间没有空隙。

前两类叫"服务器端使用的端口号"，第三类叫"客户端使用的端口号"。这个划分的逻辑是：**服务器的端口必须固定且众所周知**（否则客户端无从找起），**客户端的端口只需在本机唯一**（它是为了让回信能找回来，用完即弃）。

>

常见熟知端口号

教材表 5-2 给出的一组：FTP **21**、TELNET **23**、SMTP **25**、DNS **53**、TFTP **69**、HTTP **80**、SNMP **161**、SNMP(trap) **162**、HTTPS **443**。 再补几个常用的：FTP 数据连接 **20**、SSH **22**、POP3 **110**、IMAP **143**、DHCP 服务器 **67** / 客户端 **68**、RIP **520**。

## 三、复用与分用

**复用（Multiplexing）**：发送方**不同的应用进程都可以使用同一个传输层协议传送数据**（各自加上适当的首部）。 **分用（Demultiplexing）**：接收方的传输层在**剥去报文的首部后，能够把这些数据正确交付目的应用进程**。

教材用了一个很好的比方：一个机构所有部门向外发的公文一律交由收发室寄出，这相当于各部门"复用"这个收发室；收到外来公文时按信封上的部门地址正确交付，这就是"分用"。

### TCP 与 UDP 的分用规则不同

这是本篇最值得记牢的一处差别：

|  | UDP 分用 | TCP 分用 |
| --- | --- | --- |
| 依据 | **目的 IP + 目的端口**（二元组） | **源 IP + 源端口 + 目的 IP + 目的端口**（四元组） |
| 后果 | 只要目的端口相同，就交给同一个套接字，**不管是谁发来的** | 四元组完全匹配才交给对应连接，**不同来源是不同连接** |

**为什么会不一样？** 追问一层就清楚了：UDP 是无连接的，接收方**没有为任何一个对端保存过状态**，它手里只有"哪个端口上有进程在等"这一条信息，自然只能按目的端口分。TCP 是面向连接的，它为每条连接维护了一份状态（缓存、序号、窗口……），**这份状态是"对某一个特定对端"的**，所以必须靠四元组把不同对端区分开。

**分用规则的差异，是"有没有连接状态"的直接推论，不是另外规定的一条。**

### 例题：分用判定

**题目**：Web 服务器 198.51.100.7 的 80 端口上，此刻到达三个 TCP 报文段，源套接字分别是 ① (203.0.113.9, 49230)　② (203.0.113.9, 49231)　③ (203.0.113.20, 49230)。 问：这三个报文段被交给几条 TCP 连接？如果 80 端口上跑的是 UDP 服务，答案又是什么？

**第 1 步：写出三条的四元组。**

| 报文段 | 源 IP | 源端口 | 目的 IP | 目的端口 |
| --- | --- | --- | --- | --- |
| ① | 203.0.113.9 | 49230 | 198.51.100.7 | 80 |
| ② | 203.0.113.9 | **49231** | 198.51.100.7 | 80 |
| ③ | **203.0.113.20** | 49230 | 198.51.100.7 | 80 |

为什么第一步就把四元组全列出来：TCP 的分用判据只看这四个数，列齐了才能逐位比较，凭"看上去差不多"最容易漏掉只差一位的那个字段。

**第 2 步：两两比较。** ①②只有源端口不同 → **不是同一条连接**。 ①③只有源 IP 不同 → **不是同一条连接**。 ②③源 IP、源端口都不同 → **不是同一条连接**。

**第 3 步：结论。** 三条互不相同 → **交给 3 条独立的 TCP 连接**，服务器为它们各维护一份状态。

**第 4 步：换成 UDP。** UDP 只看目的二元组 (198.51.100.7, 80)，三条完全相同 → **全部交给同一个套接字、同一个进程**，进程要靠 `recvfrom()` 返回的源地址自己区分是谁发来的。

最后一步才是关键：**"同一个 80 端口能同时服务上万个客户"这件事，是 TCP 四元组分用的结果，不是端口本身的能力。** UDP 用同一个端口也能收所有人的数据，但它不替你区分，得自己做。

## 四、面向连接与无连接：连接到底是什么

### 连接的端点是套接字

教材把这一点问得很直白，答案也很反直觉：

每一条 TCP 连接有两个端点。那么，TCP 连接的端点是什么呢？**不是主机，不是主机的 IP 地址，不是应用进程，也不是运输层的协议端口。** TCP 连接的端点叫作**套接字**（socket）……端口号拼接到 IP 地址即构成了套接字。

于是有两个公式：套接字 socket=(IP 地址:端口号)TCP 连接={socket1, socket2}={(IP1:port1), (IP2:port2)}

由此直接推出两条结论：**同一个 IP 地址可以有多个不同的 TCP 连接，同一个端口号也可以出现在多个不同的 TCP 连接中**——只要整个套接字对不重复，就是不同的连接。上一节那道例题的三条连接，正是"同一个 (198.51.100.7 : 80)"出现在三个不同套接字对里。

### 连接是两端各存的一份状态，不是一条线路

"面向连接"这个词最容易造成的误解是：以为网络里真的开辟了一条专用通路。并没有。

TCP 连接是**逻辑连接**：它由三次握手在两端**各自的内存里**建立起一份状态（初始序号、窗口、缓存、计时器……），此后所有报文段照样是一个个独立的 IP 数据报，走各自的路由，中间的路由器**完全不知道存在这条连接**。所谓"释放连接"，释放的也只是这两份状态。

教材把连接建立要解决的问题列了三条，正好对应"状态里存了什么"：

- **要使每一方能够确知对方的存在**；
- **要允许双方协商一些参数**（最大窗口值、是否使用窗口扩大选项和时间戳选项、服务质量等）；
- **能够对传输实体资源进行分配**（缓存大小、连接表中的项目等）。

### 无连接与面向连接的本质差别

把两者拆成四个维度对照，就能看清"可靠不可靠"只是结果之一，不是定义：

| 维度 | 无连接（UDP） | 面向连接（TCP） |
| --- | --- | --- |
| **两端是否保存对端状态** | 不保存 | **保存**（连接表、缓存、序号、窗口） |
| 发送前的开销 | 想发就发 | 先握手，付出至少 1 个 RTT |
| 分用依据 | 二元组 | 四元组（因为状态是"对某个对端"的） |
| 能否可靠 | 协议层不做，可由应用层自己做 | 协议层做（序号 + 确认 + 重传） |
| 能否一对多 | **能**（广播、多播） | **不能**（连接只有两个端点） |
| 对端异常时能否察觉 | 不能 | 能（超时、RST） |

**第一行是根，其余五行都是它的推论。** "有没有为对方存一份状态"才是无连接与面向连接的本质分界：存了状态，就能编序号、能重传、能开窗口、能区分对端，也就必须先建立、后释放，还必然只能是点对点的（状态是成对的，没法一份状态对一万个人）。

> [!WARNING]
>

三个常见的误判

- **"面向连接 = 可靠"**：不成立。可靠是连接状态带来的**可能性**，不是定义。理论上完全可以设计一个面向连接但不重传的协议。
- **"无连接 = 不可靠"**：也不成立。TFTP、QUIC 都建在 UDP 之上并做到了可靠，见 [[04_计算机网络_CN/transport/udp.md|UDP 协议]]最后一节。
- **"连接建立时协商 MSS"**：教材脚注明确说这个流行说法是**错误的**——"这里并不存在任何的协商，而只是一方把 MSS 值设定好以后通知另一方而已"。两个方向可以有不同的 MSS。

## 五、全面对比

| 对比项 | TCP | UDP |
| --- | --- | --- |
| 是否面向连接 | 面向连接（先握手再传数据） | 无连接（直接发） |
| 两端是否维护对端状态 | 维护（连接表、缓存、序号、窗口） | 不维护 |
| 可靠性 | 可靠交付：无差错、不丢失、不重复、按序到达 | 尽最大努力交付 |
| 传输方式 | 面向字节流 | 面向报文 |
| 通信模式 | 只能一对一（点对点） | 一对一、一对多、多对一、多对多 |
| 首部开销 | 最少 20 字节，最多 60 字节 | 固定 8 字节 |
| 分用依据 | 四元组 | 目的二元组 |
| 流量控制 | 有（rwnd） | 无 |
| 拥塞控制 | 有（cwnd） | 无 |
| 校验和 | 强制 | 可选（不算时填 0） |
| 端口不存在时的响应 | 自己回 RST 报文段 | 借 ICMP 回"端口不可达" |
| 适用场景 | 文件传输、网页、邮件等要求完整有序的场景 | 实时音视频、DNS 查询等要求低时延或需广播的场景 |

### 面向字节流 vs 面向报文

**TCP 面向字节流。** 教材的定义是："TCP 中的'流'指的是流入到进程或从进程流出的字节序列……TCP 把应用程序交下来的数据仅仅看成是一连串的无结构的字节流。TCP 并不知道所传送的字节流的含义。"

关键推论是那句：**TCP 不保证接收方应用程序所收到的数据块和发送方应用程序所发出的数据块具有对应大小的关系。** 发送方连续写 3 次（100、50、200 字节），TCP 可能合成一个 350 字节的报文段发出，也可能拆成两个。**但接收方收到的字节流必须和发送方发出的字节流完全一样**——顺序和内容一字不差，只是分块方式不一样。

于是**消息边界必须由应用层自己维护**（例如加长度前缀或分隔符）。这就是所谓"TCP 粘包"问题的来源：它根本不是 bug，而是"面向字节流"的定义本身。

**UDP 面向报文。** 发 3 个报文（100、50、200 字节），对方就收到 3 个独立报文，边界清晰，`sendto()` 与 `recvfrom()` 一一对应。

**TCP 凭什么可以随便切？** 因为它有序号——每个字节都编了号，怎么切都能在接收端按号拼回原样。UDP 没有序号，一旦拆分就再也拼不回去，所以它只能选择"不拆"。**"面向字节流 / 面向报文"这个差别，同样是"有没有序号"的推论。**

## 六、适用场景与端口号

### 适合 TCP 的

| 应用 | 端口 | 原因 |
| --- | --- | --- |
| HTTP | 80 | 网页数据不能丢、不能乱序 |
| HTTPS | 443 | 同上，另加加密 |
| FTP 控制 / 数据 | 21 / 20 | 文件内容必须完整正确 |
| SSH | 22 | 命令与输出必须可靠 |
| TELNET | 23 | 同上（明文） |
| SMTP | 25 | 邮件内容不能丢 |
| POP3 / IMAP | 110 / 143 | 同上 |

### 适合 UDP 的

| 应用 | 端口 | 原因 |
| --- | --- | --- |
| DNS | 53 | 一问一答、报文短，建连接的开销超过查询本身 |
| DHCP 服务器 / 客户端 | 67 / 68 | 客户端尚无 IP，必须广播，TCP 做不到 |
| TFTP | 69 | 场景简单，可靠性放到应用层自己做 |
| SNMP / SNMP trap | 161 / 162 | 管理报文简短，丢了重新查询即可 |
| RIP | 520 | 周期性广播路由表，下一周期自然更新 |
| 实时音视频（RTP） | — | 重传回来的帧已经过期，重传反而有害 |

### 既用 TCP 又用 UDP：DNS

DNS 默认用 UDP，两种情况改用 TCP：

- **响应超过 512 字节**（DNS 报文在 UDP 上的长度上限），此时截断标志置位，客户端改用 TCP 重查；
- **区域传送**（主域名服务器与辅助域名服务器同步全部记录），数据量大且必须完整。

判据其实还是那三条：一问一答的短查询走 UDP，一旦变成"大块数据且必须完整"就切 TCP。

## 易混淆知识点

**1. 传输层与网络层的分界**

判据是**服务的对象是谁**：网络层为**主机**之间的通信提供服务，传输层为**应用进程**之间的通信提供服务。由此直接推出：路由器只有下三层，转发分组时不需要传输层；传输层只存在于端系统中，是"端到端"的。

**2. 软件端口 vs 硬件端口**

判据是**它连接的是什么**：软件端口是应用层协议进程与传输实体进行**层间交互的地点**（同一台机器的两层之间）；硬件端口是不同**硬件设备**交互的接口。二者除了共用一个中文词毫无关系。

**3. 端口号只有本地意义**

A 机器的 5000 端口与 B 机器的 5000 端口没有任何关联。所以单个端口号无法标识连接，必须与 IP 地址拼成套接字才行。

**4. TCP 连接的端点是套接字，不是主机 / IP / 进程 / 端口**

判据是教材的定义式：套接字 = (IP 地址 : 端口号)，连接 = 套接字对。由此推出"同一 IP 可有多条连接、同一端口可出现在多条连接中"。

**5. 面向连接与可靠是两件事**

判据是**这条性质由什么支撑**：面向连接说的是"两端各存一份对端状态"，可靠说的是"序号 + 确认 + 重传"。后者建立在前者之上，但前者不必然导出后者，UDP 之上也能由应用层做出后者（TFTP、QUIC）。

**6. TCP 与 UDP 的分用依据不同**

判据是**接收方手里有没有对端状态**：UDP 无状态 → 只能按目的二元组分用，同一端口收所有人的数据；TCP 有状态 → 按四元组分用，不同对端是不同连接。"一个 80 端口服务上万客户"是四元组分用的结果。

**7. DNS 不是只用 UDP**

判据是**响应大不大、要不要完整**：普通查询用 UDP；响应超 512 字节或做区域传送时用 TCP。"DNS 只使用 UDP"是错的。

**8. "不可靠"是特性描述，不是质量评价**

UDP 的"不可靠"指协议本身不提供确认与重传，不是说它不好用。选它往往正是因为不需要那套机制——实时流里重传回来的数据已经过期。

**9. TCP 面向字节流不等于会丢数据**

TCP 可以任意合并 / 拆分应用交下来的数据块，但**接收方收到的字节流必须与发送方发出的完全一样**。变的只是分块方式，消息边界要由应用层自己维护。

**10. MSS 不是"协商"出来的**

教材脚注点名了这个流行说法是错误的：连接建立时**并不存在协商，只是一方把自己的 MSS 值设定好后通知另一方**，两个方向可以有不同的 MSS。

## 本节小结

- **传输层的分界线只有一句：网络层为主机之间的通信提供服务，传输层为应用进程之间的通信提供服务。** IP 首部只有源 / 目的 IP，标志的是两台主机，没有任何字段能说明"这一份该给哪个进程"，传输层补上的正是这一层。由此推出：路由器只有下三层，传输层只存在于端系统中。
- **"逻辑通信"= 好像是这样通信，但事实上并非真的这样通信。** 数据实际是竖着走的（层层向下、过路由器、再层层向上），"水平直连"只是给应用层看的假象；网络层制造"主机直连"的假象，传输层在其上再制造"进程直连"的假象。
- **传输层比网络层多做四件事**：复用与分用、对**整个报文**做差错检测（IP 首部检验和只管首部）、可选的可靠传输、可选的流量与拥塞控制。前两件必做（UDP 也做），后两件可选（只有 TCP 做）——这就是 TCP 与 UDP 分道扬镳的位置。
- **端口取代进程标识符有三条理由**：进程标识符格式随操作系统而异（要一种与操作系统无关的统一标志）、进程动态创建撤销（对方无从知道编号）、我们要找的是"功能"而非"某个进程"。端口是应用层与传输层界面上的抽象终点，是**软件端口**，与设备上的硬件端口毫无关系。
- **端口号 16 位，只有本地意义**，不同计算机上相同的端口号没有关联。三段划分：**熟知端口 0~1023**（IANA 指派、人尽皆知）、**登记端口 1024~49151**（须登记，防重复）、**短暂端口 49152~65535**（客户端动态选取，用完由系统收回）。共 65536 个，铺满 16 位空间。
- **复用 = 多个进程共用一个传输层协议发送；分用 = 接收方剥去首部后交付正确的进程。** TCP 与 UDP 的分用依据不同：**UDP 按目的二元组**（IP + 端口），**TCP 按四元组**（源 IP、源端口、目的 IP、目的端口）。差别的根源是"接收方有没有为对端保存状态"，不是另外规定的一条。
- **TCP 连接的端点是套接字**：套接字 = (IP 地址 : 端口号)，连接 = 套接字对 {(IP1:port1),(IP2:port2)}。**不是主机、不是 IP、不是进程、不是端口。** 由此推出同一 IP 可有多条连接、同一端口可出现在多条连接中——"一个 80 端口同时服务上万客户"正是四元组分用的结果。
- **面向连接的本质是"两端各存一份对端状态"，不是"有一条专用线路"，也不等于"可靠"。** 有了状态才能编序号、能重传、能开窗口、能区分对端；也正因为状态是成对的，连接必然是点对点的、必须先建立后释放。连接建立要解决三件事：确知对方存在、协商参数、分配传输实体资源。
- **面向字节流 vs 面向报文，是"有没有序号"的推论。** TCP 每个字节都编号，怎么切都能拼回，所以它可以自由合并 / 拆分应用数据块——但**接收方收到的字节流必须与发送方发出的完全一样**，变的只是分块方式，消息边界要由应用层自己维护。UDP 没有序号，拆了拼不回，所以只能不拆。
- **选协议的三条判据**：重传是否还有意义 / 建连接开销是否超过数据本身 / 是否需要广播多播。任一成立即倾向 UDP。DNS 是两边都用的典型：短查询走 UDP，响应超 512 字节或区域传送时切 TCP。
