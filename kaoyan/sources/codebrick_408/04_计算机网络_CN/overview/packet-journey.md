# 数据包的网络之旅：协议栈封装与解封装

## 知识框架

本节回答 5 个问题：

- 每一层到底加了什么、为什么非加不可？
- 主机 A 明明要发给主机 B，为什么第一跳的目的 MAC 填的是路由器的？
- 为什么 MAC 地址逐跳都在变，IP 地址却全程不变？把这两条反过来会坏在哪里？
- 路由器除了换帧头，还偷偷改了哪些字段？为什么它必须重新算两个校验值？
- 数据到了主机 B，凭什么知道要交给 IP、再交给 TCP、再交给浏览器？

**封装是穿衣服，解封装是脱衣服，中间设备只解到自己能看懂的那一层。** 这句话是整篇的骨架，但它只是结论；下面要做的是把"为什么只解到那一层""解开之后又重新包成什么样"补齐。

## 场景设定

全程用同一个例子，参数一次给全：

| 设备 | IP 地址 | MAC 地址 |
| --- | --- | --- |
| 主机 A | 192.168.1.10 | `AA:AA:AA:00:00:01` |
| 路由器 R 接口 1（接 A 侧） | 192.168.1.1 | `CC:CC:CC:00:00:01` |
| 路由器 R 接口 2（接 B 侧） | 192.168.2.1 | `CC:CC:CC:00:00:02` |
| 主机 B | 192.168.2.20 | `BB:BB:BB:00:00:01` |

拓扑：**主机 A → 交换机 S1 → 路由器 R → 交换机 S2 → 主机 B**。A 的默认网关配置为 192.168.1.1，两侧都是以太网。A 上的浏览器（源端口 1234）向 B 上的 Web 服务器（目的端口 80）发送应用数据。

## 发送方的封装：每层加了什么、为什么

| 层次 | 数据块变化 | 本层加了什么 | 为了解决什么问题 |
| --- | --- | --- | --- |
| 应用层 | `[数据]` | 无 | 产生要传的内容，PDU 叫**报文** |
| 运输层 | `[TCP头][数据]` | 源端口 1234、目的端口 80、序号、确认号、校验和 | **交给哪个进程**、如何做可靠传输 |
| 网络层 | `[IP头][TCP头][数据]` | 源 IP、目的 IP、TTL、协议字段、首部校验和 | **送到哪台主机**、如何逐跳选路 |
| 数据链路层 | `[帧头][IP头][TCP头][数据][FCS]` | 源 MAC、目的 MAC、类型字段、FCS | **交给同一链路上的哪个节点**、这一跳传坏没有 |
| 物理层 | `01101000…` 比特流 | 无（不加控制信息） | 把比特变成信号送上介质 |

三条不能跳过的规律：

**1）每层只加自己的头部，上层的整体一律当作本层的"载荷"**

本层不去解释上层内容是什么，这就是分层的实质。链路层不看 IP 头里写了什么，它只负责把这一整块字节送到链路对端。

**2）数据链路层是唯一既加首部又加尾部的**

帧头装 MAC 地址与类型字段，帧尾装帧检验序列 FCS。FCS 必须放在数据之后——接收端要先把整帧收完才有可能算出校验值来比对，放在前面就得先缓存整帧再回头填，没有意义。

**3）第一跳的目的 MAC 不是主机 B 的**

这一条最反直觉，但推导只有三步：

- A 用自己的 IP 和子网掩码算出目的 IP `192.168.2.20` **不在本网段**
- 不在本网段 → 必须交给默认网关 `192.168.1.1`
- 帧要发出去必须填一个目的 MAC，而 MAC 只在本链路内有意义 → A 用 [[04_计算机网络_CN/network/arp.md|ARP]] 问出 `192.168.1.1` 的 MAC，填 `CC:CC:CC:00:00:01`

所以第一个帧的地址组合是：

```
目的 MAC = CC:CC:CC:00:00:01   （路由器 R 接口 1）
源   MAC = AA:AA:AA:00:00:01   （主机 A）
目的 IP  = 192.168.2.20        （主机 B）
源   IP  = 192.168.1.10        （主机 A）
```

**MAC 写的是"下一跳交给谁"，IP 写的是"最终要送到谁"**——这就是链路层与网络层职责分工在字段上的直接体现。

图源：谢希仁《计算机网络》（第 7 版）图 1-17「数据在各层之间的传递过程」，印刷版 **p33**。注意图中间那一段：**路由器只画到第 3 层**，且左右两侧的 H₂/T₂ 是**两组不同的**链路层首尾部——这正是本篇要展开的"帧头被替换"。

## 逐跳：三类设备各处理到第几层

| 设备 | 处理到第几层 | 依据什么转发 | 帧头帧尾 | IP 首部 |
| --- | --- | --- | --- | --- |
| 集线器 | 1 | 不做判断，向所有其他端口放大转发 | 原样 | 原样 |
| 交换机 S1 / S2 | 2 | 目的 MAC，查 MAC 地址表选端口 | **原样** | 原样 |
| 路由器 R | 3 | 目的 IP，查路由表选出接口与下一跳 | **整个替换** | **改 TTL 与首部校验和** |

**为什么每种设备只解到那一层？** 判据只有一条：**它的转发决策要读哪一层的字段，就必须解封装到哪一层，再往上就没有必要**。集线器的动作不依赖任何字段（收到信号就往其他端口放大转发），所以停在第 1 层；交换机要读目的 MAC 才能选端口，而 MAC 在帧首部里，所以必须解到第 2 层；路由器要读目的 IP 才能查路由表，IP 在网络层首部里，所以必须再往上解一层。

这条判据可以继续往上推：一台设备若要按运输层端口做决策，它就得解到第 4 层——下面提到的 NAT 正是如此，它的转换表项同时含 IP 与端口，所以它被迫读到并改写了比路由器更上面的东西。**"工作在第几层"从来不是设备本身的属性，而是它转发依据的属性。**

**交换机为什么不改帧头？** 因为它没有换链路。S1 的两个端口在同一个广播域、同一个 IP 网段里，帧的"下一跳"没有变——目的 MAC 仍然是路由器 R 的。交换机做的只是**选一个端口把这一帧原样送出去**。

**路由器为什么必须换帧头？** 因为它换了链路。出接口所在的是另一个网段、另一个广播域，原来那个目的 MAC（`CC:CC:CC:00:00:01`）在新链路上根本不存在。所以 R 必须：

- 把旧帧头帧尾**整个丢弃**（它已经完成使命：把数据送到了这条链路的对端）
- 用**出接口的 MAC** 做新的源 MAC：`CC:CC:CC:00:00:02`
- 用**下一跳的 MAC** 做新的目的 MAC。这里下一跳就是主机 B（目的网络直连），所以是 `BB:BB:BB:00:00:01`；若还要经过下一台路由器，填的就是那台路由器入接口的 MAC

## IP 全程不变，MAC 逐跳改变

这是整条路径上最重要的一条规律，值得把两个方向都推一遍。

### 为什么 MAC 必须变

MAC 地址是**链路层地址**，它的作用域就是**一条链路（一个广播域）**。理由很实在：

- 交换机的 MAC 地址表只记录"哪个 MAC 挂在我哪个端口上"，它对别的网段一无所知
- 跨过路由器之后是另一个广播域，那里的设备根本收不到、也不认识原来那个 MAC

所以每跨一条链路，"这一跳发给谁"这个问题就要重新回答一次，MAC 也就必须重填一次。

### 为什么 IP 必须不变

IP 地址是**网络层地址**，它承载的是**端到端的语义**："这份数据是谁发的、要送到谁"。如果路由器把源 IP 改成自己的：

- 主机 B 收到后会以为数据来自路由器，回复也会发给路由器，**端到端的会话建立不起来**
- 中途的路由器再也无法根据"最终目的地"选路——它只知道上一跳是谁，等于回退成了逐跳的接力，路由表也就失去了意义
- 运输层的 TCP/UDP 校验和覆盖了伪首部（含源 IP、目的 IP），IP 一改，**校验和必然失败**

反过来说，IP 不变正是"网络层提供**主机到主机**服务"这句话的具体含义。它和"IP 的转发动作是逐跳的"并不矛盾：**动作逐跳，语义端到端**。

唯一的例外是[[04_计算机网络_CN/network/nat.md|网络地址转换 NAT]]：NAT 设备会改写 IP 与端口。但那恰恰说明了改 IP 的代价——NAT 必须额外维护一张转换表，把回来的报文映射回去，还得同步修改运输层校验和。**它不是反例，它是"改 IP 要付出什么"的证据。**

### 路由器还改了什么

只说"换帧头、IP 不变"是不完整的，路由器还动了两处：

- **TTL 减 1**。每经过一台路由器减 1，减到 0 就丢弃并回送 [[04_计算机网络_CN/network/icmp.md|ICMP]] 超时报文。这是防止分组在路由环路里无限打转的兜底机制
- **IP 首部校验和必须重算**。因为 TTL 变了，而首部校验和只覆盖 IP 首部——首部一变，校验和就必须跟着变

另外，**FCS 也必然是新算的**，因为整个帧都换了首尾部。这一点常被忽略：路由器不是"改了几个字节"，而是**重新做了一次链路层封装**。

值得对照的是：**运输层的 TCP/UDP 校验和路由器不碰**。它覆盖的是运输层首部、数据和伪首部，路由器既不改这些内容，也没有权限修改端到端的校验结果——这正是端到端原则在字段级别的体现。

## 例题：逐跳的地址与帧长演变

**题**：在上面的拓扑中，主机 A 向主机 B 发送一个 TCP 报文段，应用层数据 500 B，TCP 首部 20 B，IP 首部 20 B。以太网帧首部 14 B、帧尾 FCS 4 B。求：

- A → R 与 R → B 两段链路上帧的源 / 目的 MAC 与源 / 目的 IP
- 两段链路上的帧总长
- 若 R → B 一段改用 PPP 链路（首部 4 个字段共 5 B、尾部 2 个字段共 3 B），该段的帧总长

**解**：

**（1）地址演变**

先确定 IP：源 IP 与目的 IP 由端到端语义决定，**全程不变**，恒为 `192.168.1.10 → 192.168.2.20`。

再逐段确定 MAC，判据是"**这一跳的发送方是谁、接收方是谁**"：

| 链路段 | 源 MAC | 目的 MAC | 源 IP | 目的 IP |
| --- | --- | --- | --- | --- |
| A → S1 → R | `AA:AA:AA:00:00:01`（A） | `CC:CC:CC:00:00:01`（R 接口 1） | 192.168.1.10 | 192.168.2.20 |
| R → S2 → B | `CC:CC:CC:00:00:02`（R 接口 2） | `BB:BB:BB:00:00:01`（B） | 192.168.1.10 | 192.168.2.20 |

这一步为什么这么做：交换机 S1、S2 不改帧，所以它们不产生新的地址组合——**链路段数由路由器个数决定，不由交换机个数决定**。有 1 台路由器就有 2 段，有 n 台路由器就有 n+1 段。

**（2）帧总长**

IP 数据报总长是各层首部逐层叠加：LIP=500+20+20=540 B

以太网帧再加链路层的首尾部：L以太帧=540+(14+4)=558 B

两段都是以太网，所以**两段都是 558 B**。

这一步为什么这么做：路由器换的是链路层封装，**网络层 PDU 一个字节都没动**（TTL 与首部校验和是改值不改长度）。所以 540 B 这个数在全程都成立，变的只是外面那层壳。

**（3）改用 PPP 之后**LPPP帧=540+(5+3)=548 B

比以太网段少 10 B。

这一步为什么这么做：**IP 数据报是链路无关的，链路层帧是链路相关的**。同一个 540 B 的 IP 数据报，走以太网就穿一件 18 B 的外套，走 PPP 就穿一件 8 B 的外套。这也是 IP 能"over everything"的原因——它不对下层的封装格式做任何假设。

**边界**：如果某段链路的 MTU 小于 540 B（例如 MTU = 512 B），IP 数据报就必须[[04_计算机网络_CN/network/ip-fragment.md|分片]]，此时一个网络层 SDU 会变成多个 IP 分组，上面"网络层 PDU 全程不变"的说法就不再成立。所以准确的表述是：**在不发生分片的前提下，IP 数据报内容除 TTL 与首部校验和外全程不变**。

## 接收方的解封装：靠三级分用链

主机 B 收到比特流后从下往上逐层剥壳：

| 步骤 | 层次 | 动作 | 交给上层的依据 |
| --- | --- | --- | --- |
| 1 | 物理层 | 把信号还原成比特流、组成帧 | — |
| 2 | 数据链路层 | 校验 FCS；比对目的 MAC 是不是自己；剥去帧首尾部 | **类型字段** `0x0800` → 交给 IP |
| 3 | 网络层 | 校验首部校验和；确认目的 IP 是自己；剥去 IP 首部 | **协议字段** `6` → 交给 TCP（`17` → UDP） |
| 4 | 运输层 | 校验 TCP 校验和；按序号重组；剥去 TCP 首部 | **目的端口** `80` → 交给 Web 服务器进程 |
| 5 | 应用层 | 拿到原始数据 | — |

这张表里最值得单独记的是最后一列：**每一层的首部里都有一个字段专门用来回答"我该把载荷交给上面的谁"**。类型字段→协议字段→目的端口

这就是**分用（demultiplexing）** 的完整链条。没有这三个字段，接收方拿到一串字节根本不知道该按什么格式解释——分层不只是"往上交"，还必须"说清楚交给谁"。它与发送方的**复用**正好对称：多个进程的数据向下汇聚成一条 IP 流，到了对端再按这三级字段散开。

另外两个动作也有明确分工：

- **每一层都有自己的检错**，且只覆盖自己关心的范围：FCS 覆盖整帧、IP 首部校验和只覆盖 IP 首部、TCP 校验和覆盖运输层首部与数据（含伪首部）。三者不重复也不互相替代——链路层检错保证"这一跳没传坏"，运输层检错保证"端到端没坏"，中间路由器内存出错这类问题只有后者能发现
- **每一层都要确认"这是给我的吗"**：链路层比对目的 MAC，网络层比对目的 IP，运输层比对目的端口。任何一层对不上就丢弃

## 易混淆知识点

**1. 目的 MAC 什么时候是"最终目的主机"的？**

判据是**目的主机是否与发送方在同一网段**。同网段：目的 MAC 就是目的主机的；跨网段：目的 MAC 是**下一跳路由器接口**的。所以"目的 MAC 是谁"这个问题必须先问"这一跳的接收方是谁"，而不是"最终收件人是谁"。

**2. 交换机改不改帧？路由器改不改 IP？**

交换机**不改帧**（它没换链路），路由器**不改 IP 地址**（那是端到端语义），但路由器**改 TTL 与 IP 首部校验和**，并**完全重建帧首尾部与 FCS**。"路由器不改 IP"这句话要补一句"**地址不改，TTL 和首部校验和要改**"才准确。

**3. 经过 n 台路由器，MAC 地址变几次？**

变 n+1 段——即产生 n+1 组不同的（源 MAC，目的 MAC）。**交换机不计入**，因为它不产生新的链路段。这是判断这类题时唯一要数的东西：数路由器，不数交换机。

**4. IP 首部校验和和 TCP 校验和，路由器各处理哪一个？**

**只重算 IP 首部校验和**（因为它改了 TTL），**绝不碰 TCP/UDP 校验和**。后者是端到端的凭据，中间设备无权改动——NAT 是唯一被迫破例的场合，代价是它必须自己把运输层校验和也修好。

**5. 帧长在全程是不变的吗？**

不是。**IP 数据报长度不变**（不分片时），**帧长随链路技术变化**：以太网加 18 B、PPP 加 8 B。把"帧长"和"分组长"混为一谈，是这类计算最常见的错法。

**6. 主机 B 凭什么知道该交给 TCP 而不是 UDP？**

靠 **IP 首部的协议字段**（TCP = 6，UDP = 17），不是靠端口号。端口号只在运输层剥完自己的首部之后才起作用，用来选进程。三级分用链的顺序不能颠倒：类型字段 → 协议字段 → 端口号。

**7. "封装"和"分片"是一回事吗？**

不是。封装是**加首部**，每层各加一次，不改变数据本身；分片是**把一个数据单元拆成几个**，发生在网络层且只在 MTU 不够时才发生。封装总会发生，分片是例外情况。

## 本节小结

- **封装是穿衣服、解封装是脱衣服，中间设备只解到自己能看懂的那一层**——但要补三层理解：为什么只解到那一层、解开后重新包成什么样、哪些字段被迫跟着变。
- **设备解到第几层，由它的转发依据在第几层决定**：集线器不看任何字段（第 1 层）、交换机看目的 MAC（第 2 层）、路由器看目的 IP（第 3 层）、按端口做决策的设备（如 NAT）必须解到第 4 层。"工作在第几层"是转发依据的属性，不是设备本身的属性。
- **封装只发生在上四层**，物理层不加控制信息；**只有数据链路层既加首部又加尾部**，FCS 必须在数据之后（接收端要收完整帧才能比对）。
- **第一跳的目的 MAC 是默认网关的，不是目的主机的**。推导三步：算出目的 IP 不在本网段 → 必须交给默认网关 → 用 ARP 问出网关 MAC。**MAC 写"下一跳交给谁"，IP 写"最终送到谁"**。
- **交换机不改帧**（它没换链路，两个端口在同一广播域），**路由器整个替换帧首尾部**（换了链路，旧 MAC 在新链路上不存在）：新源 MAC = 出接口 MAC，新目的 MAC = 下一跳 MAC。
- **MAC 必须变**，因为它的作用域只有一条链路；**IP 必须不变**，因为它承载端到端语义。改源 IP 会同时打断三件事：对端回不来、中途路由器无从选路、运输层伪首部校验和失败。**动作逐跳、语义端到端**。
- **路由器还改了两处**：TTL 减 1（防路由环路），IP 首部校验和重算（因为 TTL 变了）；**FCS 也是新算的**（整帧重封装）。**TCP/UDP 校验和路由器绝不碰**——那是端到端的凭据。NAT 是唯一破例者，代价是自己维护转换表并修补运输层校验和。
- **链路段数由路由器个数决定，不由交换机个数决定**：n 台路由器 → n+1 组（源 MAC，目的 MAC）。
- **IP 数据报是链路无关的，帧是链路相关的**：540 B 的 IP 数据报走以太网是 558 B 帧（+18 B），走 PPP 是 548 B 帧（+8 B）。分组长与帧长不能混为一谈。
- **准确表述**：不发生分片时，IP 数据报内容除 TTL 与首部校验和外全程不变；一旦某段链路 MTU 不足就要分片，此时一个网络层 SDU 会变成多个 IP 分组。
- **三级分用链：类型字段（`0x0800` → IP）→ 协议字段（`6` → TCP、`17` → UDP）→ 目的端口（`80` → 进程）**。每层首部里都有一个字段专门回答"载荷该交给上面的谁"，顺序不可颠倒。它与发送方的复用正好对称。
- **每层各有自己的检错，覆盖范围互不重叠也不互相替代**：FCS 覆盖整帧（保证这一跳没传坏），IP 首部校验和只覆盖 IP 首部，TCP 校验和覆盖运输层首部与数据（保证端到端没坏）。路由器内存出错这类问题只有端到端校验能发现。
- **每层还要各自确认"这是给我的吗"**：链路层比目的 MAC、网络层比目的 IP、运输层比目的端口，任何一层对不上就丢弃。

## 教材出处

- 谢希仁《计算机网络》（第 7 版）印刷版 **p33**（图 1-17 及其正文）给出逐层封装的完整描述：第 5 层加上必要的控制信息"就变成了下一层的数据单元"，依此类推，"不过到了第 2 层（数据链路层）后，控制信息被分成两部分，分别加到本层数据单元的**首部（H₂）和尾部（T₂）**；而第 1 层（物理层）由于是比特流的传送，所以**不再加上控制信息**"。
- 同书印刷版 **p34** 描述路由器的处理层次与重新封装：比特流到达路由器后"就从路由器的第 1 层依次上升到第 3 层。每一层都根据控制信息进行必要的操作，然后将控制信息剥去……**当分组上升到了第 3 层网络层时，就根据首部中的目的地址查找路由器中的转发表，找出转发分组的接口，然后往下传送到第 2 层，加上新的首部和尾部**，再到最下面的第 1 层，然后在物理传输媒体上把每一个比特发送出去"。"加上**新的**首部和尾部"这半句就是本篇"帧头被整个替换"的直接依据。
- 同书同页给出信封比喻：数据"每经过一层就包上一个新的信封，写上必要的地址信息。包有多个信封的信件传送到目的站后，从第 1 层起，每层拆开一个信封后就把信封中的信交给它的上一层"。
- 同书印刷版 **p80**（3.2.2 PPP 协议的帧格式）给出本篇例题第 3 问的依据："**PPP 帧的首部和尾部分别为四个字段和两个字段**"，首部第一个字段与尾部第二个字段都是标志字段 F，规定为 0x7E。[[04_计算机网络_CN/overview/architecture.md|上一篇体系结构与参考模型]][[04_计算机网络_CN/overview/performance-metrics.md|下一篇性能指标]]
