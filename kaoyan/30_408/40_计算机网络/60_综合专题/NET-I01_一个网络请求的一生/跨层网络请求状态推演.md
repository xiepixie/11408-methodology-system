# 跨层网络请求状态推演

> 训练定位：解决“给出 URL 与一组本地/网络缓存状态后，怎样判断实际会经过哪些模块、按什么顺序创建或复用状态，并定位第一次失败”的综合题。  
> 模型归属：[NET-I01 一个网络请求的一生](NET-I01_一个网络请求的一生_综合手册.tex)。模块组合顺序、四条并行轨迹与失败边界由 Canonical Integration 拥有；DNS、ARP/LPM、TCP、拥塞和 HTTP 的局部机制继续由各 Topic/Bridge Owner 拥有。

## 母题表示：输入不是一个 URL，而是 `URL + 当前状态`

同一个 URL 在第一次访问和第二次访问时，事件轨迹可能完全不同。草稿先把初始状态写成六格：

```text
IP configuration / DHCP lease: valid or missing?
DNS cache: hit / miss / expired?
FIB + next-hop decision: available?
ARP/ND neighbor cache: hit / miss?
Transport connection: existing / absent / reset?
HTTP cache / reusable application state: hit / miss?
```

只有缺失状态才需要创建；已有且仍有效的状态直接复用。

### 局部规则：先找第一个未满足的前置条件

**触发信号**：题目同时出现 URL、DNS、ARP、TCP、HTTP、网关、缓存或“第一次/第二次访问”。

**第一动作**：从“能否形成合法 source IP 配置”开始，沿依赖顺序寻找第一个未满足条件：

```text
Configuration
-> Name resolution
-> Forwarding / current next hop
-> Link identity
-> Transport state
-> Application semantics
```

**检查与退出**：不要从最熟悉的协议名开始。例如没有 IP 配置时，不能先 DNS；DNS 已命中时，也不应机械再画 root/TLD/authority 查询。

## 四条轨迹必须同时保持类型正确

### Name / Identity

```text
URL/domain
-> destination IP
-> current next-hop IP
-> current-link MAC/identity
-> transport port/endpoint
```

这些不是同一种“地址”。DNS 不输出 next-hop MAC，ARP 不解析远端 HTTP resource，port 也不参与 LPM。

### Encapsulation

```text
HTTP message bytes
inside transport segment/datagram
inside IP packet
inside current-link frame
```

跨 router 时旧 frame 被删除并重建；在无 NAT/隧道等改写时，destination IP 仍保持端到端语义。

### State Owner

| 状态 | Owner |
|---|---|
| DHCP lease / host prefix / gateway | host configuration / NET04 |
| DNS RR + TTL | resolver/cache / NET08 |
| selected route / installed FIB | NET05/NET04 |
| IP→MAC neighbor state | current host/router interface / NET04-B01 |
| TCP SEQ/ACK/rwnd/cwnd | transport endpoints / NET06/07 |
| HTTP resource/cache/session semantics | application / NET08 |

### Cost / Dependency

只有真正串行依赖才相加：DNS cache miss、TCP 建连、HTTP main object、解析后发现的 subresources 等必须先画 DAG，再计算 RTT/传输时间。

## 问题一：第一次访问与第二次访问为什么不能共用一条固定流程

设第一次访问时：

```text
lease missing
DNS cache miss
neighbor cache miss
TCP connection absent
HTTP cache miss
```

则必须逐步创建配置、DNS 结果、当前一跳身份和 TCP state，再交换 HTTP request/response。

若第二次立即访问同一 origin：

- lease 可能仍有效；
- DNS RR 可能仍在 TTL 内；
- neighbor cache 可能仍命中；
- persistent TCP connection 可能可复用；
- HTTP cache 还可能直接满足请求。

因此：

$$
\text{same logical request}\not\Rightarrow\text{same event trace}.
$$

### 检查与退出

“访问过一次”不代表所有缓存都必然有效。每个状态有自己的 key、scope 和 lifetime；任何一个失效都只重建对应阶段。

## 问题二：跨层故障题怎样找 First Divergence

不要从最终症状倒推一个喜欢的协议。按前置条件链逐项问：

1. 主机是否有合法 source IP / prefix / gateway / DNS 配置？
2. domain 是否已解析成可用 destination IP？
3. FIB 是否给出可执行 next hop/egress？
4. 当前链路是否已经知道 next-hop identity？
5. transport endpoint 是否建立/可用？
6. application response 是否满足目标语义？

第一个“不成立”的位置就是首个候选 Owner。后面的失败现象可能只是连锁结果。

### 局部规则：错误归属必须停在第一处证据断裂

**触发信号**：浏览器打不开、连接超时、DNS 成功但网页不返回等综合症状。

**第一动作**：只使用当前可观察证据，找到第一条无法继续满足的接口，不越级猜后续层。

**检查与退出**：若 DNS 已返回 IP，却把“ARP cache miss”写成 DNS 错误，或 TCP 尚未建立就分析 HTTP status code，说明 Owner 越级。

## 题库证据：目前只验证了局部接口，还没有真正打穿 Integration

现有 305 题提供了可以拼接的局部证据：

| 证据题 | 验证的接口 |
|---|---|
| 968 | 无 IP 配置时 DHCP 是 DNS/TCP 之前的前置条件 |
| 987 | 域名 cache miss 时 DNS 必须先于 Web TCP 建连 |
| 860、862、865–867 | destination IP -> next-hop IP -> current-link MAC 的 B01 交接 |
| 847、909 | installed FIB + LPM 决定 packet-time action |
| 934–936 | TCP connection state 必须先完成序号同步，应用才有稳定 byte stream |
| 993–996 | HTTP 主对象/子资源依赖、persistent/pipeline 决定后续 RTT |
| 997 | 同一次成功 Web 访问中 DNS/HTTP/TCP/ARP 是否出现取决于状态与前置条件 |
| 1000 | NAT mapping 是额外的 stateful forwarding 分支，不能只靠地址表面判断 |

这些题说明各接口方向是正确的，但**没有任何一道题单独要求把完整状态链从 URL 推到 HTTP representation，并在中间插入 cache hit/miss 与失败分支**。所以 NET-I01 当前应视为“Canonical 组合模型成立，但训练证据仍不足”。

## 变式轴

1. **配置状态**：lease 有/无、是否过期；
2. **名字状态**：DNS RR hit/miss/expired；
3. **Scope**：同网段目标 / 远端目标；
4. **链路状态**：neighbor cache hit/miss、Ethernet/其他链路；
5. **控制状态**：route selected 但 FIB 尚未安装、next hop 无法解析；
6. **transport 状态**：新建 / persistent reuse / reset / zero window / congestion-limited；
7. **HTTP 状态**：cache hit、main object 后发现 subresources、pipeline/multiplex；
8. **第二次请求**：只重建已经失效的状态，而不是重跑全部协议。

## 题目攻击：用现有题只改一个状态，检查事件图是否真的重算

把现有题库看成一组接口靶点，而不是协议清单：

| 基准题 | 只改一个条件 | 正确的模型变化 |
|---|---|---|
| 968 | `DHCP lease = valid` | DHCP 前置阶段消失，直接进入名字/转发依赖 |
| 967 | `.com delegation cached` | DNS 不再从 root 开始，查询链缩短 |
| 866 | gateway ARP cache hit | 当前第一跳不再发 ARP Request；不能仍按“路由器数”计次 |
| 890 | 某 router FIB 仍是旧版本 | 不能再使用最终收敛路径，进入 NET-B02 mixed-state 推演 |
| 934–936 | TCP connection already reusable | 三次握手阶段消失，但 HTTP authority/请求语义仍存在 |
| 995 | 禁止 pipeline | 3 个图片请求不再共享同一 RTT 批次，总依赖时间改变 |
| 997 | DNS 与 neighbor cache 都 hit | DNS/ARP 事件都可能消失，只保留仍缺失的 transport/application 阶段 |

### 局部规则：单变量攻击后，只有依赖于该状态的子图可以变化

**触发信号**：同一道综合题只修改一个 cache、FIB、connection 或 pipeline 条件。

**第一动作**：在原依赖 DAG 上标出这个状态的直接 consumers，只重算从它向后的受影响分支。

**检查与退出**：例如把 DNS cache 从 miss 改成 hit，不应让 ARP/TCP/HTTP 的语义自动消失；把 ARP cache 改成 hit，也不应改变 destination IP。若无关分支一起变化，说明层次依赖被串成了错误的裸线性链。

## 代表母题：状态向量驱动实际事件轨迹

给定：

```text
URL = http://www.example.test/index.html
DHCP lease = valid
DNS cache = miss
FIB = installed
ARP cache for gateway = hit
TCP connection = absent
HTTP cache = miss
```

正确轨迹不是 DORA 全流程，而是：

```text
reuse host configuration
-> DNS resolution
-> consume installed FIB
-> reuse gateway neighbor entry
-> build current-hop frame
-> route across network
-> TCP handshake
-> HTTP request/response
```

若把 DNS cache 改成 hit，则 DNS authority 查询消失；若再把 TCP 改成可复用 persistent connection，则 handshake 也消失。题目的本质是**状态复用改变事件图**，而不是背协议名顺序。

## 陌生综合题固定落笔协议

```text
1. 把 URL 和初始状态分开写。
2. 先找第一个缺失前置条件，不机械重跑全部协议。
3. Name track 保持 domain / dst IP / next-hop IP / MAC / port 类型正确。
4. 每过 router 只替换当前 frame；无改写时 dst IP 保持。
5. 把 control-plane state 与 packet-time state 分开。
6. TCP 建立/复用后才进入 HTTP message semantics。
7. 性能题先画依赖 DAG，再数 RTT 与数据传输。
8. 第二次请求只重建 expired/missing state。
9. 失败时停在第一处接口断裂，并回到唯一 Owner。
```

## 最短压缩

> **综合题不是背 `DHCP→DNS→ARP→TCP→HTTP`：先盘点已有状态，再沿前置条件找缺口；同一个请求因为 cache/connection 状态不同，可以拥有完全不同的事件轨迹。**
