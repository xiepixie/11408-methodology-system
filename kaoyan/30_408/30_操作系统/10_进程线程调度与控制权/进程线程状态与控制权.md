# 进程线程状态与控制权

> 训练定位：面对进程/线程共享与私有状态、ULT/KLT、M:N、阻塞传播、系统调用/中断、PCB/TCB 与 IPC 进程侧语义时，训练先确定当前实体、调度域和控制权，再追踪事件引起的状态变化。  
> 模型归属：[OS-01/02 进程线程调度与控制权方法论手册](OS-01_OS-02_进程线程调度与控制权_方法论手册.tex)。进程/线程对象、状态机、调度域、trap、block/wakeup 与 IPC 机制由 Canonical 正文拥有；本文件只负责状态推演与检查。

## 线程题：先分资源世界与执行实体

1. 当前对象是进程资源上下文、用户执行上下文、内核可调度实体还是物理 CPU？
2. 哪些状态属于整个进程，哪些属于每条执行流？
3. 题目说“私有/共享”时问的是 Ownership、Addressability 还是 Concurrency Safety？
4. 谁能看见并调度当前执行流？
5. U 到 K 的映射是 M:1、1:1 还是 M:N？
6. 当前 Ready/Blocked 属于用户运行时还是内核调度域？
7. 这个 syscall/fault 是否真的需要等待？
8. 事件作用域是单线程还是整个进程/线程组？
9. 若发生切换，改变的是 privilege、execution、memory 还是 mapping？

### 局部规则：Ready 必须带主语

**触发信号**：M:N、协程/虚拟线程、两级调度或 carrier 阻塞题。

**第一动作**：明确是 `User-Ready` 还是 `Kernel-Runnable`，并标出当前可用 carrier 数量。

**检查与退出**：如果只写一个“Ready”却说不清属于哪个 scheduler，就不能继续判断物理并行度或阻塞传播。

## 进程状态题：事件必须能解释箭头

1. 当前实体是 New / Ready / Running / Blocked / Exit 中哪一类？
2. 题设是否额外引入 Suspend？
3. 它当前缺的是 CPU、外部事件还是重新激活/换入资格？
4. 哪个事件刚刚发生？
5. 这次事件只改 task state，还是也创造了调度机会？
6. 若等待完成，先到 Ready 还是能直接 Running？
7. 当前属于高级、中级还是低级调度问题？
8. 是否把“原进程在内核态执行”误写成“已经切换成另一个进程”？

### 局部规则：wakeup 只先承诺 Ready

**触发信号**：I/O 完成、信号量 V、条件变量 signal、等待事件发生。

**第一动作**：先把 waiter 从 Blocked 移到 Ready；再由调度条件决定它何时获得 CPU。

**检查与退出**：除非题设明确立即抢占且调度发生，否则不要把完成事件直接连到 Running。

### 局部规则：Blocked 和 Suspended 必须分开

**触发信号**：题目同时出现“阻塞、挂起、换出、I/O 等待、重新激活”等词，或者选项把“等待事件”与“被换出内存”混成同一状态。

**第一动作**：分别写当前实体缺什么：

```text
Blocked   -> 缺等待事件/资源条件；事件完成后可回 Ready
Suspended -> 缺重新激活/换入资格；即使原等待条件满足，也未必立刻进入内存中的 Ready
```

**检查与退出**：一个进程发出阻塞式 I/O 时，默认先发生 `Running -> Blocked`；除非题设另外触发中级调度/换出，否则不能自动写成 Suspended。反过来，Suspended 也不等于“正在等 I/O”。

### 局部规则：内核不可见 ULT 的系统时间片属于承载它们的内核可调度实体

**触发信号**：一个进程内有几十/上百个用户级线程，题目问 CPU 时间片、物理并行度或某个 ULT 阻塞后的影响。

**第一动作**：先数内核真正能看见并调度的实体，再看用户态运行时怎样在进程内部二次分配执行机会。经典 M:1 ULT 中，100 个 ULT 并不会让内核看到 100 个独立 CPU 调度对象。

**检查与退出**：不要把“用户态有多少线程”直接等价成“内核就分多少份时间片”；只有映射成多个内核可调度实体时，才可能同时占用多个 CPU。 

## 系统调用 / 中断 / 异常

做控制权题时依次确认：

- 入口是 syscall、exception 还是 interrupt；
- 事件同步还是异步；
- 哪些现场由硬件入口保证，哪些由软件保存；
- 是否发生 privilege transition；
- 当前是否仍在原执行实体上下文；
- 服务能否立即完成；
- 若不能，进入哪个等待状态；
- 是否已经到允许 context switch 的安全点；
- 最终是 return same task，还是 scheduler 选择 another task。

### 局部规则：进入内核不等于切换进程

**触发信号**：syscall/interrupt/trap 后题目问“当前进程是否改变”。

**第一动作**：把 privilege/mode switch 与 execution-context switch 分成两条判断。

**检查与退出**：只有 scheduler/dispatcher 真正交接执行上下文，才算换成另一个可调度实体。

## PCB / TCB 与资源引用

先问题目中的字段属于：身份、CPU 保存现场、调度状态、进程级资源上下文还是某个外部对象的引用。`fork()`、`exec()`、线程创建与 fd 继承题尤其要分“新建身份/执行现场”和“继承或共享资源引用”。如果题目继续追到 OFD/inode/offset 内部语义，立即转到 OS-06/07。

## IPC：先判断传递的是哪一种东西

- 共享状态 → shared memory；随后若问并发正确性，切 OS-03；
- 数据流/消息 → pipe / queue / mailbox 等通信对象；
- 事件通知 → signal/event 等控制状态；
- 生命周期等待 → join/wait，不要混成普通数据通信。

## 题库母题：把抽象规则落到具体问题

### [Q518｜“进程被唤醒，究竟意味着什么？”](../../../archives/408/题库/操作系统/02_进程线程状态与调度_选择题.md#518)

题目最容易诱导成“唤醒 = 立刻运行”。真正的第一步应该问：**这个进程原来为什么 Blocked？现在只是哪个等待条件消失了？** 等待事件发生后，它只是重新具备了运行条件，因此先进入 Ready；是否真的变成 Running，还要再经过 scheduler 分配 CPU。

这题适合作为状态题母题，因为它能强迫我们把“事件完成”和“CPU 所有权”分开。

### [Q521–525｜“用户级线程到底是谁在调度？”](../../../archives/408/题库/操作系统/02_进程线程状态与调度_选择题.md#521)

这一组题表面上分别问 ULT/KLT 的切换、时间片、多核并行和阻塞，实际上都先回答同一个问题：**内核现在到底能看见几个可调度实体？**

- M:1：多个 ULT 只映射到一个内核可见实体；一个阻塞系统调用可能拖住整个承载实体，也不能让多个 ULT 同时跑在多个 CPU 上。
- 1:1 / M:N：内核可见实体数量变化以后，阻塞传播和并行能力也随之变化。

所以做线程题不要先背“ULT 快、KLT 慢”，先画映射关系。

### [Q528 / Q536｜“运行进程在时间片中途发出阻塞式 I/O，会发生什么？”](../../../archives/408/题库/操作系统/02_进程线程状态与调度_选择题.md#528)

题目故意把 RR/FCFS 等调度算法和 I/O 阻塞混在一起。第一步不是看剩余时间片，而是看当前执行流**还能不能继续运行**。阻塞式 I/O 需要等待设备事件，于是立即 `Running → Blocked`；I/O 完成后只是 `Blocked → Ready`，再由调度器决定何时 Running。

这里还要特别分清：Blocked 是“在等事件”，Suspended 是“失去激活/驻留资格”，两者不是同义词。

### [Q529｜“上下文切换到底保存什么？”](../../../archives/408/题库/操作系统/02_进程线程状态与调度_选择题.md#529)

这题用“是否要把代码和数据写回磁盘”攻击一个常见误解。Context switch 只需要保存以后恢复执行所必需的 CPU/调度上下文，例如 PC、寄存器、状态等；它不等于把整个进程映像换出内存。

**这一组题的共同方法：先问谁在等什么、谁能调度它、哪个事件刚刚发生，再画状态箭头。状态名必须由事件解释，不能反过来靠背箭头猜事件。**

## 最短压缩

进程线程题先问三句话：**现在是谁在运行？谁能调度它？什么事件让哪一级状态发生变化？** 这三句没有主语时，不开始画状态箭头。
