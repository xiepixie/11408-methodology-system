# 死锁判断与 Banker

> 训练定位：面对“是否安全、请求能否批准、是否已经死锁、怎样预防或恢复”等题面时，训练先判问题语义，再选择 Safety、Resource-Request、Detection 或 Recovery；不把几个长得相似的算法混成一套模板。  
> 模型归属：[OS-03 并发锁与 PV 方法论手册](OS-03_并发锁与PV_方法论手册.tex)。死锁条件、安全状态、Banker、检测与恢复的定义和机制由 Canonical 正文拥有；本文件只负责题面识别、执行顺序、检查与代表题。

## 先判题面究竟在问什么

| 题面问法 | 真正问题 | 首先调用 |
|---|---|---|
| “死锁形成需要哪些条件” | 哪些结构条件共同允许死锁出现 | Coffman 四条件 |
| “当前状态是否安全” | 是否存在让所有进程最终完成的安全序列 | Safety Algorithm，使用 `Need` |
| “这个请求能否立即批准” | 当前请求合法且试分配后是否仍安全 | Resource-Request 三关 + Safety |
| “系统现在是否已经死锁” | 当前实际等待是否已形成不可消去集合 | Detection，使用当前 `Request` |
| “资源分配图里有环是否死锁” | 环在当前资源实例语义下是否构成充分条件 | 先判断每类资源实例数 |
| “怎样保证不发生死锁” | 设计时阻断必要条件，或运行时保持安全状态 | Prevention / Avoidance |
| “已经死锁怎么办” | 怎样破坏当前死锁并控制恢复代价 | Detection + Recovery |

题目表面都在谈“资源不够”，但输入状态、算法目标和失败含义并不相同。

## 局部规则：先分清 `Need` 和 `Request`

**触发信号**：题面同时出现 Max、Allocation、Need、Request、Available，或者你准备套“找一个能完成的进程然后释放资源”的消去过程。

**第一动作**：先在草稿上写一句当前问题：是“未来还能不能全部完成”，还是“现在卡住的人能不能被消去”。前者使用 `Need = Max - Allocation`；后者使用当前实际等待的 `Request`。

**检查与退出**：如果你无法解释某一行矩阵表示“未来最多还需要多少”还是“此刻正在等多少”，停止运算，回到 Canonical 的 Avoidance / Detection 边界。不要因为两个算法都维护 `Work` 就把输入矩阵互换。

## Safety Algorithm：只维护一份可释放资源账本

做安全性判断时：

1. 先核对 `Available = Total - ΣAllocation`；
2. 令 `Work = Available`；
3. 找尚未完成且 `Need_i <= Work` 的进程；
4. 假设它获得剩余需求并完成，只把它原先占有的 `Allocation_i` 归还到 `Work`；
5. 重复直到全部完成，或再也找不到可推进者。

### 局部规则：`Work` 为什么只增不减

**触发信号**：你在 Safety Algorithm 中准备执行 `Work -= Need_i`，或者算到后面 `Work` 比初始 Available 更小。

**第一动作**：把当前一步解释成“存在一种安排可以让这个进程完成；完成后它把原有占用归还”。因此模拟完成后的净结果是 `Work += Allocation_i`。

**检查与退出**：若最终所有进程完成，`Work` 应回到总资源向量；若没有，优先检查 Available、Allocation 求和、Need 减法和向量逐分量比较。

## Resource-Request：三关不能跳

请求 `Request_i` 到来时依次检查：

1. `Request_i <= Need_i`：没有超过自己声明的最大剩余需求；
2. `Request_i <= Available`：当前物理资源足以试分配；
3. 做一次 tentative allocation，再运行 Safety Algorithm：试分配后的状态仍安全。

### 局部规则：能分配不等于应该批准

**触发信号**：题目给出的 Request 小于 Available，你准备直接回答“可以分配”。

**第一动作**：先做试分配，更新 `Available / Allocation_i / Need_i`，再跑安全性检查。

**检查与退出**：如果请求本身合法且当前资源足够，但试分配后不存在安全序列，应拒绝或推迟请求；不要把“当前有资源”偷换成“未来不会进入 Unsafe”。

## Detection：只问当前等待能否被消去

Detection 不使用未来最大需求。核心动作是：

1. `Work = Available`；
2. 寻找尚未消去且 `Request_i <= Work` 的进程；
3. 若找到，假设其当前等待被满足并完成，执行 `Work += Allocation_i`；
4. 最终仍无法消去的进程集合才是当前死锁候选集合。

> **易错边界：**“系统利用率低”“很多进程阻塞”“资源紧张”都不能直接证明已经死锁。最终仍要回到等待关系或 Detection 的当前状态语义。

## 资源分配图：先看实例数

### 局部规则：看到环先问每类资源有几份

**触发信号**：资源分配图出现环，选项直接写“因此发生死锁”。

**第一动作**：先判断环中每类资源是否都是单实例。单实例模型下，等待环可直接刻画死锁；多实例模型下，有环通常只说明存在风险，不能把它当一般充要条件。

**检查与退出**：只要存在多实例资源，就停止用“有环即死锁”的单实例结论，切回矩阵/消去语义或题目给出的更具体条件。

## Recovery：恢复不是“随便杀一个进程”

恢复至少要同时考虑：

- 终止哪些进程能释放关键资源；
- 已完成工作会损失多少；
- 是否支持回滚与检查点；
- 被抢占资源是否可安全恢复；
- 是否总让同一个低优先级进程当牺牲者而形成恢复饥饿。

### 局部规则：逐个恢复后必须重新检测

**触发信号**：题目采用“逐个终止进程/逐个抢占资源”的恢复策略。

**第一动作**：每执行一次恢复动作，就把释放后的资源重新放回当前状态并重新检测。

**检查与退出**：不能沿用恢复前的死锁集合机械继续删除；一次释放可能已经打破多个等待环。

## 最短压缩

拿到死锁题只先回答四件事：

```text
1. 这是 Prevention / Avoidance / Detection / Recovery 中哪一个问题？
2. 当前矩阵语义是 Need 还是 Request？
3. 我在证明“未来仍安全”，还是识别“现在已经死锁”？
4. 每一步资源账本变化能否解释成真实的占有、等待或释放？
```

四件事没有分清之前，不开始跑矩阵。
