# 管程与条件变量状态推演

> 训练定位：解决“给 Monitor / mutex / condition variable / wait / signal 代码或并发场景，判断谁阻塞、谁持锁、是否丢失唤醒、该用 `if` 还是 `while`”的题目族。  
> 模型归属：[OS-03｜并发锁与 PV](OS-03_并发锁与PV_方法论手册.tex)。管程、条件变量、Hoare/Mesa 语义和同步不变量由 Canonical 正文拥有；本文件只训练等待关系和事件顺序。PV 题继续使用 [PV同步题](PV同步题.md)。

## 母题表示：条件变量题先分三种对象

```text
mutex        保护共享状态
predicate    真正决定“能不能继续”的布尔条件
condition    保存“等待这个条件可能变化”的等待关系
```

最关键的一句：

> **Condition Variable 不是条件本身。**

所以 `signal(cv)` 不等于“把条件设为 true”，也不等于“被唤醒者立即执行”。

## 问题一：标准等待模板为什么一定是 `while`

```text
lock(m)
while (!predicate)
    wait(cv, m)
use_state()
unlock(m)
```

`wait(cv,m)` 的语义必须包含：

$$
\boxed{\text{原子地释放 mutex + 进入等待}}
$$

返回前又必须：

$$
\boxed{\text{重新获得 mutex}}
$$

### 为什么 `if` 不稳健

Mesa 风格下：

```text
T1 被 signal
-> T1 只变成可运行候选
-> T2/T3 可能先获得 mutex 并再次改变共享状态
-> T1 真正获得 mutex 时 predicate 可能又是假
```

因此醒来后必须重新检查。

## 问题二：为什么“先 unlock 再 sleep”会丢失唤醒

错误过程：

```text
T1: check predicate == false
T1: unlock
        context switch
T2: change predicate -> true
T2: signal
T1: sleep
```

signal 发生时 T1 还没进入等待队列，通知没有保存；随后 T1 才睡下，就可能永久等待。

### 局部规则

**触发信号**：题目把“释放锁”和“进入睡眠”写成两个普通独立操作。

**第一动作**：在二者之间插入一次最坏 context switch；如果能出现 signal 早于真正 sleep 的窗口，就是 lost wakeup 反例。

**检查与退出**：正确的 wait 必须把“释放 mutex + 加入 condition 等待队列/睡眠”做成不可丢通知的原子状态转换；如果这两个动作仍能被普通调度点分开，协议尚未闭合。

## 问题三：`signal` 与 `V(semaphore)` 为什么不能互换

| 操作 | 状态存在哪里 | 当前无人等待时 |
|---|---|---|
| `V(S)` | semaphore 许可计数 | 许可通常被保存，后续 `P(S)` 可消费 |
| `signal(cv)` | 真正条件在共享 predicate；cv 只管等待者 | 通知通常不积累成未来许可 |

因此：

```text
先 signal 再 wait
```

对条件变量通常不会像 semaphore 那样“存一张票”等待未来 waiter。

### 检查

如果题目需要“事件发生过一次，未来线程仍应消费这个事实”，要问这份状态是否已经被写入共享变量/计数，而不能只依赖一次 condition signal。

## 问题四：修改方必须先改共享状态，再通知

标准事件：

```text
lock(m)
change_state()
signal/broadcast(cv)
unlock(m)
```

### 局部规则

**触发信号**：代码先 `signal`，后修改 predicate 所依赖的共享状态。

**第一动作**：问被唤醒者若现在检查 predicate 会看到什么。

**检查与退出**：通知的意义是“你等待的状态可能变了”；若状态尚未修改，通知与事实脱节。

## 问题五：Hoare 与 Mesa 的差别要放在“signal 后谁拿管程”

### Hoare 经典语义

```text
signal caller
-> 唤醒 condition waiter
-> caller 去 urgent/next queue
-> waiter 立即获得 monitor
```

被唤醒者得到直接交权，因此刚成立的条件不容易被第三方抢先破坏。

### Mesa 常见语义

```text
signal caller 继续运行
waiter 只变为未来可竞争 mutex 的候选
```

所以 waiter 返回前需要重新取得 mutex，并用 `while` 重检 predicate。

### 稳定结论

题面没明确 Hoare/Mesa 时，至少保留：

- notify ≠ 条件永久成立；
- wakeup ≠ 立即 Running；
- condition variable ≠ semaphore count。

## 问题六：经典 Hoare 管程有三类等待关系

1. **Entry Queue**：等进入管程；
2. **Condition Queue**：已进入过管程，但 predicate 不成立，执行 wait；
3. **Urgent/Next Queue**：signal caller 暂时让权给被唤醒者，等取回管程。

这三类等待的“在等什么”不同，不能统称一个“阻塞队列”后就不区分。

## 问题七：管程的互斥是封装语义，不代表没有等待

管程可压成：

$$
\boxed{Shared\ State+Operations+Implicit\ Mutual\ Exclusion+Condition\ Variables}
$$

同一时刻只有一个执行流在管程过程内活动，不等于所有调用者都立即进入：

- 外部调用者可能在 entry queue；
- 当前线程也可能主动 `wait` 释放管程；
- 被唤醒者还要按具体语义重新获得/接管管程。

## 代表母题：有界缓冲区的 Monitor 读法

```text
put(x):
  lock(m)
  while (count == N):
      wait(notFull, m)
  insert(x); count++
  signal(notEmpty)
  unlock(m)

get():
  lock(m)
  while (count == 0):
      wait(notEmpty, m)
  x = remove(); count--
  signal(notFull)
  unlock(m)
```

做题不要背名字，直接写 predicate：

- producer 继续条件：`count < N`；
- consumer 继续条件：`count > 0`。

`notEmpty/notFull` 只是等待队列的名字，真正条件仍由 `count` 决定。

## 陌生 Monitor 题固定落笔协议

```text
1. 写共享状态和 mutex Owner。
2. 把“能继续的条件”写成显式 predicate。
3. wait 必须原子 release+sleep，返回前 reacquire。
4. 醒来后 while 重检 predicate。
5. 修改方先 change_state，再 signal/broadcast。
6. 区分 semaphore permit 与 condition notification。
7. 若考 Hoare/Mesa，画 signal 后控制权流向。
8. 最后攻击 lost wakeup：在 check / sleep 之间插入最坏调度。
```

## 最短压缩

> **Monitor 题不背 `wait/signal`：mutex 保护状态，predicate 决定能否继续，condition 只保存等待关系；`wait` 必须原子释放并睡眠，Mesa 醒来必须 `while` 重检。**
