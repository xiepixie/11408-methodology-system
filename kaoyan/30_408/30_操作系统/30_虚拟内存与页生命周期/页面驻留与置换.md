# 页面驻留与置换

> 训练定位：面对缺页次数、FIFO/LRU/CLOCK、脏页写回、局部/全局置换、工作集与抖动题时，训练逐次维护 frame 状态，并把“选择 victim”与“页面是否允许被替换、替换代价多大”分开。  
> 模型归属：[OS-04 虚拟内存与地址翻译方法论手册](OS-04_虚拟内存与地址翻译_方法论手册.tex)。驻留、置换、访问位/脏位、工作集与 PFF 的机制由 Canonical 正文拥有；本文件只负责状态模拟、决策与检查。

## 母题表示：维护一个会随每次访问变化的 Resident Set

每次 reference 只做四件事：

1. 当前页是否 resident；
2. 若命中，算法状态怎样更新；
3. 若缺页，有无 free frame；
4. 若必须淘汰，谁是 victim，淘汰是否需要额外 write-back。

不要先背“某算法怎么排队”，先把每一步状态写出来。

## 局部规则：每次访问后立即更新策略状态

**触发信号**：题目给页面访问串并要求计算 fault 数或 victim 序列。

**第一动作**：建立按访问时刻展开的 frame 表；每处理一个 reference，就在同一列完成 hit/fault、frame 内容和策略元数据更新。

**检查与退出**：如果你打算先把所有页装入结果写完、最后再补 LRU 时间戳或 CLOCK reference bit，停止。置换策略依赖历史状态，漏一次更新会让后续全部偏离。

## FIFO / LRU / CLOCK 分别在维护什么

| 策略 | 需要维护的最小状态 | victim 判据 |
|---|---|---|
| FIFO | 页进入当前驻留集合的先后顺序 | 最早进入者 |
| LRU | 最近一次访问顺序/时间 | 最久未被访问者 |
| CLOCK | 环形指针 + reference bit | 从指针开始扫描，给 `R=1` 第二次机会，选择首个可淘汰的 `R=0` |

### 局部规则：算法名不能替代状态变量

**触发信号**：你知道题目是 LRU/CLOCK，却没有在草稿里记录“最近使用”或指针/访问位。

**第一动作**：先写算法真正依赖的状态变量，再开始模拟。

**检查与退出**：每个 victim 都必须能从“当前这一刻”的状态直接解释出来；解释不了就回退到上一次状态更新。

## Dirty bit：victim 相同，代价也可能不同

### 局部规则：置换结束前再看一次脏位

**触发信号**：题面给读/写访问、dirty bit 或 page-out 时间。

**第一动作**：选出 victim 后检查它是否 dirty；clean page 通常可直接丢弃映射副本，dirty page 需要在可复用 frame 前或相应策略下安排写回。

**检查与退出**：不要把“发生 page fault”与“必有一次写盘”绑定。写回由 victim 的修改状态和 backing policy 决定。

## Local / Global：先锁 victim 候选域

**触发信号**：多进程共享物理内存，题目同时给 fixed/variable allocation、local/global replacement。

**第一动作**：在运行算法前先写 victim 候选集合属于“当前进程自己的 frames”还是“全局可回收 frames”。

**检查与退出**：若候选域没有锁定，FIFO/LRU/CLOCK 本身即使算得正确，也可能是在错误集合上运行。

## Belady 异常：不要误推广

FIFO 在某些访问串上可能出现 frame 数增加而 fault 数反而增加。它用于说明 FIFO 不具备 stack property，不应推成“frame 越多通常越差”。

### 局部规则：比较 frame 数时必须重新完整模拟

**触发信号**：题目问增加页框后 fault 数怎样变化，尤其点名 FIFO/Belady。

**第一动作**：对不同 frame 数分别维护完整状态；不能在原表上“多塞一个 frame”后凭直觉修补。

**检查与退出**：若算法具有 stack property，可使用相应包含关系判断；否则不要把单次示例推广成一般单调性。

## Working Set / PFF：先问“分配是否跟得上局部性变化”

工作集和缺页率控制不是另一种 victim 排序技巧。它们观察的是进程当前真正活跃的页面集合与 frame 配额是否匹配。

### 局部规则：看到抖动先区分“算法差”还是“驻留预算不足”

**触发信号**：CPU 利用率下降、page fault 频繁、进程不断 page-in/page-out，题目提到 thrashing、working set 或 PFF。

**第一动作**：先判断活跃工作集总需求是否超过可用 frames，或当前分配是否长期低于进程局部性需要。

**检查与退出**：不要只靠“换成更聪明的 LRU”解释抖动；当驻留预算根本不足时，replacement policy 只能改变受害者，不能凭空创造内存容量。

## 一次 page 生命周期的训练阶梯

不要把“训练阶梯”留在 Canonical；真正训练时按能力逐级检验：

1. 能逐访问维护 resident set；
2. 能解释每次 hit/fault 的原因；
3. 能从算法状态推出 victim；
4. 能把 dirty/writeback 加入成本；
5. 能锁定 local/global victim scope；
6. 能解释 frame allocation、working set/PFF 与 thrashing 的关系；
7. 能把 page-in I/O、Blocked→Ready 与重试接回地址翻译/缺页训练。

## 最短压缩

```text
Reference
→ Resident?
→ 更新策略状态
→ Fault 时先找 free frame
→ 没有则在正确候选域选 victim
→ 检查 dirty / write-back
→ 装入并更新 frame/PTE/策略状态
```

任何一步没有写出“当前状态是什么”，都不要跳到最终 fault count。
