# 连续分配、重定位与分段

> 训练定位：面对单一/固定/动态分区、首次/最佳/最坏/邻近适应、回收合并、静态/动态重定位、分段与段页式等题目时，训练先确定“地址何时绑定、物理空间怎样切、碎片属于哪一种、运行时谁做地址检查”，再进行表格模拟与访存计数。  
> 模型归属：[OS-04 虚拟内存与地址翻译方法论手册](OS-04_虚拟内存与地址翻译_方法论手册.tex)。重定位、连续分配、分段/分页/段页式的机制定义由 Canonical 正文拥有；本文件只负责题面识别、状态模拟、计算顺序与检查。

## 先判四个维度，不要见“内存管理”就直接套分页

| 维度 | 先问什么 | 典型答案对象 |
|---|---|---|
| 地址绑定时机 | 逻辑地址什么时候解释成物理地址？ | 静态重定位 / 动态重定位 |
| 物理放置粒度 | 进程是否必须占连续物理空间？ | 连续分区 / page frame |
| 逻辑组织粒度 | 用户地址是否显式按逻辑模块分段？ | segmentation / segmented paging |
| 碎片位置 | 浪费发生在已分配块内部还是空闲块之间？ | internal / external fragmentation |

这四个维度经常被题目放在同一组选项中。先拆维度，再判断真假。

## 局部规则：静态/动态重定位先问“什么时候做地址加法”

**触发信号**：题面出现装入、重定位寄存器、基址、地址变换机构、程序移动。

**第一动作**：写出绑定时机：

```text
静态重定位：load time 一次性修补地址
动态重定位：run time 每次访问由硬件状态解释
```

最简单的动态基址模型：

$$
PA = Base + LA,
$$

同时必须做界限/权限检查。

**检查与退出**：不要把“每个进程有自己的重定位值”误读成“机器必须为每个进程永久配置一只物理寄存器”。经典单处理器模型只需一组当前运行进程使用的硬件寄存器，context switch 时换值。

## 局部规则：内存保护必须落到不可绕过的硬件检查

**触发信号**：选项声称“只靠 OS 软件约定即可阻止用户程序越界访问”。

**第一动作**：问用户态代码能否绕过检查直接发出 load/store/jump。若能，保护就不成立；因此必须有特权级、Base/Limit、MMU/PTE 权限等不可被普通用户代码绕过的硬件边界。

**检查与退出**：Protection policy 可以由 OS 决定，但 enforcement 不能只靠用户程序自觉。

## 动态分区：把内存画成有序区间，不只记空闲块大小

题目给 First Fit / Next Fit / Best Fit / Worst Fit 时，统一维护：

```text
[start address, size, free/allocated]
```

### 局部规则：每次申请都完成“选块 → 切割 → 更新顺序”

**触发信号**：多个进程依次申请/释放动态分区。

**第一动作**：按当前算法选择一个真实区间，再根据题设说明从低地址端或高地址端切割；把剩余空闲区放回正确地址位置。

**检查与退出**：只写“430KB 还剩 214KB”而不记录它位于哪里，会在后续回收合并和 Next Fit 中失去必要状态。

## 四种适应算法真正比较的是“候选顺序”

- First Fit：按地址顺序，从头找到第一个足够大的块；
- Next Fit：从上次搜索停止位置继续；
- Best Fit：在所有可容纳候选中选最小者；
- Worst Fit：在所有可容纳候选中选最大者。

### 局部规则：时间复杂度不能脱离数据结构宣称完全相同

**触发信号**：选项说“四种算法时间复杂度完全一致”。

**第一动作**：先问空闲区如何组织。无序链、按地址链、按大小平衡树/桶等会改变搜索与维护成本。

**检查与退出**：算法策略与数据结构实现是两个维度；不能只看“都要找空闲块”就断言复杂度相同。

## 回收合并：只看地址邻接，不看采用哪一种 fit

回收区可能有四种情况：

1. 上下都不空闲 → 新增一个 free block；
2. 只邻上 → 扩大上邻空闲块；
3. 只邻下 → 把下邻空闲块首址前移并扩大；
4. 上下都空闲 → 三块合一，空闲表项净减少 1。

### 局部规则：问“空闲区数变化”时做净变化

**触发信号**：题目问回收后空闲区数增加/不变/减少。

**第一动作**：先数回收前有几个相邻 free block，再数合并后变成几个。

**检查与退出**：不要把“发生合并”直接等价成“空闲区数一定减少”；只与一侧合并时，原有一块变大，数量可以不变。

## 碎片：先问浪费落在已分配区内部还是区间之间

```text
Fixed Partition / Paging  -> 典型内部碎片
Dynamic Partition / Segmentation -> 典型外部碎片
Segmented Paging -> 段内分页，物理分配以页框为单位，主要留下页内内部碎片
```

外部碎片的判据不是总空闲量不足，而是：

$$
\sum_i Free_i \ge Request,
\qquad
\max_i Free_i < Request.
$$

### 局部规则：Compaction 只能在可动态重定位时成立

**触发信号**：题目提出“紧凑/拼接空闲区”。

**第一动作**：先问运行中的进程能否搬到新物理地址而保持逻辑地址语义不变。

**检查与退出**：若只有静态重定位，运行后随意搬移会让已有地址失效；不能把 compaction 当无条件操作。

## 分页 / 分段 / 段页式：先看“用户地址结构”和“物理分配结构”

| 机制 | 用户看到的逻辑结构 | 物理分配 | 典型碎片 | 典型表结构 |
|---|---|---|---|---|
| Paging | 一维线性地址，page 对用户通常透明 | 固定 frame | 内部 | page table |
| Segmentation | `segment + offset`，逻辑模块显式 | 可变连续段 | 外部 | segment table: base/limit/rights |
| Segmented Paging | 先分段，段内分页 | 固定 frame | 页内内部 | 每进程段表 + 每段页表 |

### 局部规则：访存次数先数“索引层”，最后再加目标数据

**触发信号**：题目问无 TLB 时分段/段页式访问一次数据需几次主存访问。

**第一动作**：把链写出来：

```text
Segmentation: segment table -> data          = 2
Segmented paging: segment table -> page table -> data = 3
```

前提是这些表项本身位于内存且未被 TLB/专用 cache 命中。

**检查与退出**：不要只数“查了几张表”而漏掉最后一次真实数据访问。

## 段共享：共享的是对象，不要求共享同一逻辑段号

**触发信号**：题目问“共享段表/共享代码段”。

**第一动作**：先画多个进程的 segment entry 是否可以引用同一只读/共享物理对象。

**检查与退出**：多个进程可以用不同 segment number / logical address 映射同一共享代码或数据；“共享对象”不等于“所有逻辑地址字段必须相同”。

## 题库母题：经典内存管理怎样从题面落到状态表

### [Q581｜“内存保护能不能只靠操作系统软件？”](../../../archives/408/题库/操作系统/05_内存管理与虚拟内存_选择题.md#581)

第一步不是背“需要硬件支持”，而是反问：**如果用户程序故意不执行那段软件检查，它还能不能直接访问别人的地址？** 如果能，保护就没有强制性。因此真正的保护必须落到用户代码无法绕过的硬件检查，例如特权级、Base/Limit、MMU/PTE 权限。

### [Q582 / Q587–589｜“静态重定位、动态重定位到底差在哪？”](../../../archives/408/题库/操作系统/05_内存管理与虚拟内存_选择题.md#582)

先只问一个问题：**逻辑地址什么时候才被解释成物理地址？**

- 静态重定位：装入时一次性修正；运行时直接使用结果。
- 动态重定位：运行时每次访问都由当前 Base/Relocation 状态参与解释。

随后再问“寄存器属于谁”。每个进程当然要保存自己的重定位值，但经典单 CPU 并不需要为每个进程永久配一只物理寄存器；CPU 只保存当前运行进程的值，context switch 时换入即可。

### [Q583–595｜“First/Best/Worst/Next Fit 为什么不能只记空闲块大小？”](../../../archives/408/题库/操作系统/05_内存管理与虚拟内存_选择题.md#583)

因为后续还会释放和合并。做这类题统一维护真实区间：

```text
[start address, size, free/allocated]
```

每次申请都执行“选块 → 按题设从高/低地址端切割 → 把余块放回正确位置”；每次释放再检查上下地址是否相邻。只记“还剩 214KB”会在 Next Fit、回收合并和外部碎片判断时丢失关键状态。

### [Q596｜“多个进程共享一个段，必须使用相同段号吗？”](../../../archives/408/题库/操作系统/05_内存管理与虚拟内存_选择题.md#596)

不需要。共享的核心是**不同进程的段表项最终指向同一个底层代码/数据对象**。逻辑段号只是各自地址空间中的名字，可以不同。这题用来提醒：共享对象和逻辑地址标识不是一回事。

### [Q597–605｜“分页、分段、段页式为什么总容易混？”](../../../archives/408/题库/操作系统/05_内存管理与虚拟内存_选择题.md#597)

因为题目同时混了四个维度：

1. 用户看到的逻辑组织是不是按段；
2. 物理内存是不是按固定 frame 分配；
3. 地址翻译要查几层表；
4. 浪费发生在已分配块内部还是块与块之间。

例如段页式是“逻辑上分段、段内分页、物理按 frame”，所以无 TLB 访问链是 `段表 → 页表 → 数据`，碎片主要是页内内部碎片。

Q606 以后进入《地址翻译与缺页》和《页面驻留与置换》，不再继续用连续分区状态表。

## 最短压缩

拿到经典内存管理题先写四句话：

```text
1. 地址在 load time 还是 run time 绑定？
2. 物理空间必须连续还是按 frame 离散？
3. 当前浪费是 internal 还是 external fragmentation？
4. 需要模拟分区表、segment table 还是 page table？
```

四句话一旦确定，后面的 fit、回收、访存次数和共享题都会落到正确模型。
