### 4.2 Lesson 02 的当前 xv6 实现事实

基于当前 `mit-pdos/xv6-riscv`：

- `user/usys.pl` 生成 stub：`a7 ← SYS_xxx; ecall; ret`；
- RISC-V trap 到 `uservec` 后已经在 S-mode，但仍使用 **user page table**；
- `kernel/trampoline.S:uservec` 软件保存用户通用寄存器到 per-process trapframe，并软件加载 `kernel_sp`、切 `satp`、再进入 `usertrap()`；
- `kernel/trap.c:usertrap()` 对 U-mode ecall 判断 `scause == 8`；当前 `sepc` 指向 `ecall` 本身，因此 xv6 把保存的 `epc` 加 4；
- `kernel/syscall.c:syscall()` 从 `trapframe->a7` 取调用号，通过 `syscalls[]` 分发，并把返回值写回 `trapframe->a0`；
- 当前源码返回准备函数名为 `prepare_return()`，随后由 `trampoline.S:userret` 切回用户页表、恢复寄存器并执行 `sret`。

这组实现事实用于约束 HTML 和 Canonical Bridge：**“硬件自动切内核栈 / 自动切页表 / 自动保存完整 Trap Frame”不是 RISC-V/xv6 的事实，也不应提升为跨架构定义。**

### 4.4 Lesson 03 的当前 xv6 trap 实现事实

基于当前 `mit-pdos/xv6-riscv`：

- `kernel/trap.c:usertrap()` 明确处理来自 user space 的 system call、device/timer interrupt 与 page fault/exception；
- 进入 `usertrap()` 后先把 `stvec` 改到 `kernelvec`，因为之后已处于 kernel environment；返回 user 前 `prepare_return()` 又把 `stvec` 指向 trampoline `uservec`；
- 当前 lazy-allocation fault 路径对 load/store page fault 调用 `vmfault()`；修复成功继续返回，失败则 kill process；
- `devintr()` 当前识别 supervisor external interrupt 与 supervisor timer interrupt：外部 IRQ 经 PLIC claim/complete，timer 进入 `clockintr()`；
- `usertrap()` / `kerneltrap()` 在 timer event 后调用 `yield()`，这是一项 xv6 scheduling policy，不应泛化为“每次 timer interrupt 都必然切进程”；
- `kernel/kernelvec.S` 在已经处于 supervisor mode 时使用当前 kernel stack 保存 caller-saved registers，再调用 `kerneltrap()`；这与 user→kernel 的 trampoline 路径职责不同；
- `kerneltrap()` 进入时先保存 `sepc/sstatus/scause`，因为后续 `yield()` 可能使别的 trap 使用这些 per-hart CSR；返回前恢复原 `sepc/sstatus`。

这组事实用于 Lesson 03 的核心区分：**共享的是 trap 入口骨架；system call、fault 与 interrupt 的 event source、恢复语义和是否产生调度机会不能机械合并。**

### 4.6 Lesson 04 的当前 xv6 Page Table 实现事实

基于当前 `mit-pdos/xv6-riscv` main branch 与 2026 lab spec：

- RISC-V Sv39 的架构 VA 采用 39-bit canonical address（高位按 bit 38 符号扩展）；xv6 为避免处理高半区 sign-extension，当前 `MAXVA` 只使用低于 `2^38` 的范围。`kernel/vm.c:walk()` 将其中 VPN 按 `9 + 9 + 9` 分级、offset 为 12 bit；
- 4 KiB page 与 8-byte PTE 导出每张 page-table page 有 512 个表项，因此每级 index 是 9 bit；
- Sv39 架构允许任一级 PTE 成为 leaf：L0=4 KiB、L1=2 MiB、L2=1 GiB，并要求相应对齐；当前 base xv6 的普通 `walk()` 主要按 L2/L1 非叶、L0 4 KiB leaf 使用，2026 superpage lab 正是在扩展 L1 2 MiB leaf；
- `mappages()` 建立 leaf mapping，`uvmunmap()` 删除 mapping，`uvmalloc()` 体现“allocate physical frame + install PTE”的两步责任；
- 当前 kernel page table 显式把 trampoline 映射到固定高地址；user page tables 也需要对应映射，从而允许 trap trampoline 在切换 `satp` 前后连续执行；
- TLB 属于硬件翻译缓存；`walk()` 是 xv6 软件操作/检查页表的函数，不应误画成“每次用户 load/store 都调用 C 函数 walk()”；正常用户访存由 MMU 根据 `satp`/PTE 自动完成 page walk；
- `USYSCALL` 与 superpage 是 2026 `pgtbl` lab branch 的教学扩展，不默认假定 current main branch 已包含相同宏与实现。

这组事实用于 Lesson 04 强化 X-B02 的稳定接口：**OS 建 Mapping/PTE State；MMU/TLB 消费；TLB miss、Page Fault 与 Cache miss 的缺失对象和处理者必须分开。**

### 4.7 Page Fault / COW（2026 当前版）精简路由

2026 schedule 在 LEC 8 安排 Page Fault，并在同日分配 COW lab；当前 lecture 链接实际落地文件标题仍是 `6.1810 2025 Lecture 8: Page faults`，所以其角色是 **inherited lecture material**。课程结构与 lab 要求按 2026 页面；实现事实则继续区分 current main 与 cow lab branch。

#### 当前 main 的 Page Fault 基线

- `kernel/trap.c:usertrap()` 已把 RISC-V load/store page fault（`scause` 13/15）路由给 `vmfault()`，用于 lazy allocation；
- `kernel/vm.c:vmfault()` 当前只负责合法 `p->sz` 范围内、尚未映射的 lazy page：`kalloc -> memset(0) -> mappages(R|W|U)`；
- 当前 `uvmcopy()` 仍为 child 分配新 frame 并逐页复制，是 **eager fork**；
- 当前 `copyout()` 不依赖“用户态 store 触发 fault”：它显式 walk user page table，目标未映射时主动调用 `vmfault()`。这解释了为何 COW lab 也必须覆盖 kernel-to-user write path。

#### 2026 COW Lab 的稳定任务语义

- fork 后，child 与 parent 先共享原物理页；只对**原本可写**的用户页，两边 PTE 都撤销写权限；
- write page fault 必须区分“COW 临时只读”与“本来就只读”的 text 等页面；只有前者可 repair；
- repair 为 faulting address space 建立独立可写 view，核心状态变化是 allocate/copy/remap；
- 共享 physical frame 必须做生命周期计数：最后一个 PTE reference 消失前不能 `kfree()`；
- `copyout()` 必须维护同一 COW 语义，不能成为绕过只读共享的写入口；
- 完整性门禁是 `cowtest` 与 `usertests -q`；optional challenge 才进入“统计少复制了多少页/字节”等性能扩展。

#### RISC-V 架构边界

- page-fault exception code：instruction=12、load=13、store/AMO=15；`stval` 可提供 faulting VA；
- PTE 的 `RSW` 字段保留给 supervisor software，硬件忽略，因而适合保存 COW 一类软件语义；
- `PTE_W=0` 本身绝不能等价成 COW：原本只读页也同样没有写权限；
- Page Fault 只是同步 trap 入口，**不自动推出 Blocked / Schedule**。COW 与 demand-zero 可以纯内存修复后直接 retry；需要 page-in/swap/writeback 等外部 I/O 时才典型进入等待链。

### 4.8 Process / Scheduler / Context Switch 路由

2026 schedule 的 Thread Switching 位于 LEC 13；当前链接落地文件标题为 `6.1810 2025 Lecture 13: Thread switching`，继续按 inherited lecture material 使用。它在 MIT 原课中位于 Locking 之后，但本 HTML 为服务 408 把 Process/Scheduler 提前到 Locking 之前：这是 **408 dependency reorder**，不是声称 MIT 课程顺序如此。

当前 `mit-pdos/xv6-riscv` 提供的稳定实现事实：

- `proc.h` 分离 user trapframe、kernel `struct context`、per-CPU scheduler context 与 `enum procstate`；
- `scheduler()` 是 per-CPU 无限循环：寻找 `RUNNABLE` process，设为 `RUNNING`，再 `swtch(&c->context, &p->context)`；
- `sched()` 从 process kernel context 切回该 CPU 的 scheduler context；process 之间不是直接 `P1 -> P2` 的单条 `swtch()`；
- `yield()` 把当前 process 从 `RUNNING` 改回 `RUNNABLE` 后进入 `sched()`；当前 xv6 timer path 会调用它，但这是 xv6 policy，不是“每次 timer interrupt 必然换进程”的通用定理；
- `swtch.S` 保存/恢复 `ra`、`sp`、`s0..s11`，这是 kernel calling-convention 边界的 context；完整 user registers 由 trapframe Owner 负责；
- xv6 在跨进程宏观过程里，execution-context switch 与 user page-table switch 并不发生在同一条指令：kernel threads 运行在共同 kernel page table，真正返回 P2 user 时才切回 P2 user `satp`。

408 轨道因此分成两部分：

1. **xv6**：学习 state/context/scheduler/swtch 的真实 mechanism；
2. **自建 Scheduler Simulator**：学习 FCFS/SJF/SRTF/Priority/RR 的 policy、decision point、tie rule 与 turnaround/wait/response 指标。

不得把 current xv6 的 process-table scan + timer yield 简化实现直接称为 408 教材定义的“标准 RR”。

### 4.9 Locking（2026 当前版）精简路由

2026 schedule 的 Locking 页面当前落地标题为 `6.1810 2025 Lecture 12: Locking`，按 inherited lecture material 使用；Fall 2026 `lock` lab 则是当年正式实验要求。

稳定教学主线：

```text
shared state
→ multi-step update
→ invalid intermediate state can be observed
→ invariant violation
→ critical section / lock contract
→ atomic entry + memory ordering
→ contention / granularity trade-off
```

当前 main 与课程任务要显式分层：

- current `kernel/spinlock.c` 使用 `__atomic_exchange_n(...,__ATOMIC_ACQUIRE)` 与 `__atomic_store_n(...,__ATOMIC_RELEASE)`；
- 2026 reading homework 页面仍以 `__sync_lock_test_and_set` 的替换实验说明“普通 check + set 为什么会 race”。因此这个作业用于机制观察，不把其具体 C API 写成 current main 事实；
- `push_off()/pop_off()` 管的是当前 CPU 的本地中断嵌套与 per-CPU state 稳定性；它不阻止其他 CPU，跨核互斥仍由 shared-memory atomic lock 提供；
- Fall 2026 lock lab 的 allocator 部分要求从单一 freelist/lock 重构到 per-CPU freelists + stealing，教学重点是 **reduce sharing / contention by redesigning data ownership**；
- Fall 2026 lab 还要求实现 read-write spinlock，并显式处理 writer starvation / writer priority；这与 408 readers-writers 的 Safety vs Liveness 分层高度一致。

408 轨道取舍：atomic-RMW failure experiment 与 RW-lock model 优先；per-CPU allocator 是高价值系统扩展，但在 408 时间紧张时做到 invariant + contention trace + redesign rationale 即可停止，不以完成全部工程量作为掌握标准。

### 4.10 Coordination / Sleep-Wakeup 路由

2026 schedule 的 Coordination 页面当前落地标题为 `6.1810 2025 Lecture 14: Coordination (sleep&wakeup)`，因此按 inherited lecture material 使用；实现事实以 current xv6 main 校验。

稳定机制链：

```text
condition predicate false
→ atomically register wait + give up CPU
→ event/state change
→ wake eligible waiter
→ RUNNABLE
→ scheduler
→ reacquire protection + recheck predicate
```

当前 xv6 实现事实：

- `sleep(chan, lk)` 先取得当前 process 的 `p->lock`，再释放 caller 持有的 condition lock `lk`；随后设置 `p->chan`、`p->state=SLEEPING` 并进入 `sched()`；恢复后清 chan、释放 `p->lock`、重新取得原 `lk`；
- `wakeup(chan)` 扫描 processes，并在每个目标 `p->lock` 下把匹配的 `SLEEPING` waiter 改成 `RUNNABLE`；caller 应持有保护 predicate 的 condition lock；
- 这个 lock handoff 消除“检查 condition false → 释放锁 → 尚未睡着”之间的 lost-wakeup window：sleep 过程中始终持有 condition lock、`p->lock` 或二者之一，而 waker 需要 condition lock + target `p->lock` 才能完成状态观察；
- wait channel 只是 rendezvous key，**不是 condition 本身**；真正 predicate 由共享状态 Owner 定义；
- wait loop 必须在恢复后重检：多个 waiter 可能竞争同一资源，而且 `kill()` 也能把 sleeping process 变为 RUNNABLE，即使原 predicate 仍然为假；
- `pipe.c` 是最小双条件实例：reader 在 empty 时睡在 `&nread`，writer 在 full 时睡在 `&nwrite`，两边都由同一个 `pi->lock` 保护对应 predicate；
- console/UART 路径展示 I/O interrupt 改变共享状态并 wake sleeper；这只得到 `RUNNABLE`，何时 `RUNNING` 仍属于 scheduler；
- `wait_lock` 保护“parent 是否已经存在 ZOMBIE child”这一 condition 的 check→sleep window；`ZOMBIE` 还承担“退出者不能在仍使用自己的 kernel stack 时完全回收自己”的生命周期边界；
- `sleeplock.c` 展示在内部 spinlock 保护的 predicate 上继续构造 blocking lock。

408 轨道重点不是背 xv6 API，而是形成 OS-B01 的接口不变量：**predicate Owner、condition lock、wait relation、Blocked/Ready 状态和 scheduler 是不同职责；Wakeup ≠ condition true ≠ immediate running。**

### 4.11 Interrupt / Driver / DMA / I/O 路由

Fall 2026 `net` lab 当前正式页面要求完成 E1000 transmit/receive driver，并明确使用 descriptor rings、MMIO、DMA 与 interrupt。OS 轨道只取 Part One 的设备/驱动机制；UDP/IP/ARP、port queue、bind/recv 等协议语义转交后续 CS144 / 408 Network。

Current xv6 可核对的最小实例：

- `uart.c`：低速字符设备的 interrupt-driven wait，不应因为“有 interrupt”就误判为 DMA；
- `virtio_disk.c`：descriptor submit、设备直接访问 memory、调用线程 sleep、used-ring completion、ISR 验证并 wake waiter；
- `trap.c/plic.c`：外部 IRQ 的 claim/dispatch/complete；PLIC priority/routing 与 process scheduling priority 是不同 Owner；
- E1000 RX ring：driver 预置 buffer → NIC DMA 填充 → DD/completion → driver 把 packet 交上层 → 给 descriptor 补 fresh buffer。

本轮 Source Diff 已把 X-B03 的 DMA 接口从“raw PA + interrupt + CPU 完全不介入”收窄为：

```text
prepare/map
→ submit DMA-visible descriptor
→ device transfer
→ completion evidence
→ interrupt OR poll
→ driver verify/sync
→ wake / completion queue / callback
→ unmap/reuse
```

经典 408 题若明确采用“DMA address = 主存物理地址”的简化模型，按题设推演；通用工程模型不再把 DMA address 与 CPU PA 永久画等号。

### 4.12 File System 路由

2026 schedule 已确认 FS Lab、LEC17 File Systems 与 Homework17。当前 LEC17 链接实际标题仍为 `6.1810 2025 Lecture 17`；2026 FS lab 页面本轮抓取超时，所以实验具体 task 不把不可见页面伪装成已逐字核验，Stable task 边界与官方相邻版本/课程路线交叉核对。

408/HTML 主线固定为四层对象：

```text
pathname / directory entry
→ inode / persistent object
← open file object / OFD
← process fd binding
```

重点：

- pathname 与 fd 是两条不同入口；已有 fd 不重新做 pathname lookup；
- unlink 删除 name→inode link，不自动删除仍有 open-reference 的 object；
- `dup/fork` 可让不同 fd binding 继续引用同一 open file state，因此 offset sharing 取决于 OFD/open object，而不是整数 fd 是否相同；
- Large File 路线训练 LBN→direct/single/double-indirect；典型 11 + 256 + 256² = 65,803 blocks；
- symbolic link 用于训练 name resolution ≠ object identity；
- buffer cache one-copy invariant 属于并发正确性，不只是性能。

### 4.13 Logging / Crash Recovery 路由

Fall 2026 schedule 明确安排 LEC18 Crash Recovery，并指定阅读 `kernel/log.c`；Logging Homework 当前可访问。Crash lecture 页面本轮抓取 cache miss，因此具体实现事实以 current source 为最终基线。

Current xv6 physical redo log 的稳定顺序：

```text
buffer modifications
→ write_log()          # log block images
→ write_head()         # commit point
→ install_trans()      # redo to home locations
→ clear log header
```

Recovery 看到非空 committed header 时重放全部 log blocks，再清 header。HTML 必须让学生攻击不同 crash point，理解：commit 前可忽略，commit 后必须 redo；redo 重放应保持幂等。`begin_op/end_op` 与 log-space reservation 同时维护“不能提交半个 syscall”和“不能执行到中途才发现 journal 空间不足”的 Safety。

### 4.14 mmap 路由

2026 schedule 明确分配 mmap Lab，但 `/2026/labs/mmap.html` 本轮持续 timeout。因此当前只把“2026 有 mmap lab”作为 2026 事实；具体 lab task 使用 MIT 官方 Fall 2025 mmap lab 作 fallback，并显式标记版本。

稳定机制：

```text
mmap()
→ VMA / region contract + file reference
→ no PTE yet
→ first touch page fault
→ derive file offset
→ allocate/fill frame
→ install PTE
→ retry
```

- VMA ≠ PTE ≠ Frame；
- VMA 必须持有独立 file reference，不能依赖整数 fd 永久存在；
- MAP_SHARED / MAP_PRIVATE 是可观察语义，是否立即共享同一 physical page 是实现层；
- munmap/exit 负责 writeback（shared dirty）、unmap、VMA teardown、file-ref drop；
- fork 继承 VMA metadata 与 backing-file reference；物理页共享优化不是基础语义的前置条件。

### 4.15 两个 Integration 的 Source Boundary

Lesson 14 / 15 不再创建新机制：

- **Blocking read** 只组合 syscall、fd/OFD、file range、cache/residency、I/O request、sleep/wakeup、scheduler 与 return；先分 cache hit / miss，禁止 `read(file) ⇒ disk I/O`；
