Sleep / Wakeup：
怎样等待而不烧 CPU，也不把事件弄丢？

“条件不满足就睡眠，条件满足就唤醒”听起来很简单，真正难的是那一瞬间：线程已经判断条件为假，但还没来得及让自己变成可被唤醒的等待者。如果事件恰好在这个窗口发生，就可能产生 Lost Wakeup。xv6 的 sleep(chan, lock) 本质上是在实现一个原子交接契约：从“我确认条件仍为假”安全过渡到“未来的 waker 一定能找到我”。

1 · Mother Question

如果我在“检查条件”和“真正睡着”之间放开锁，怎样保证改变条件的那个事件不会刚好从缝里溜过去？

OS-B01 的稳定接口：Condition false → safe wait registration + block → event → wake eligibility → scheduler → reacquire + recheck。

2 · 先分三个对象：Predicate ≠ Wait Channel ≠ Process State

Condition Predicate

真正决定“能不能继续”的共享事实，例如 pipe 的 nread != nwrite、UART 的发送槽空闲、某 child 变 ZOMBIE。

Wait Channel

xv6 用一个方便双方约定的地址/标识把 sleeper 与 waker 对上。它只是 rendezvous key，不知道“为什么等待”。

Task State

SLEEPING 表示暂时没有 CPU 调度资格；RUNNABLE 只是恢复资格，不等于立即运行。

最常见误读：wakeup(chan) 不是“把 condition 设置成 true”。改变 predicate 的动作由真正拥有共享状态的代码完成；wakeup 只是通知一批可能值得重新检查的 waiter。

3 · 为什么 Busy Wait 不够？

Busy wait
while (!condition) { // repeatedly poll }

执行流仍是 runnable/running，持续消耗 CPU。若 condition 只能由另一个执行流或慢设备推进，它甚至可能妨碍真正的进度。

Blocking wait
while (!condition) sleep(chan, &condition_lock);

登记等待关系并放弃 CPU，让能制造条件的执行流继续工作；代价是 sleep/wakeup/schedule/resume 的固定开销。

所以 spin vs sleep 还是成本问题：极短、可预期的等待可能适合自旋；外设、pipe、child exit 等事件等待通常更适合 block。

4 · Interactive Lost Wakeup：事件是怎样“丢”的？

    5 · 修复核心不是“先 sleep 再 unlock”，而是连续持有一把能挡住 waker 的锁

    xv6 的 sleep(chan, lk) 要求 caller 已持有保护 predicate 的 condition lock。内部顺序是：

    acquire(&p->lock); // 先取得“我的睡眠状态”保护 release(lk); // 现在才允许别人改 condition p->chan = chan; p->state = SLEEPING; sched(); // 持 p->lock 交给 scheduler ... release(&p->lock); acquire(lk); // sleep 返回前重新拿回 condition lock

    关键不是死背 6 行，而是下面这个覆盖不变量：

    从“我在 condition lock 下看到条件为假”直到“我已经是可被 wakeup 发现的 SLEEPING waiter”，整个交接窗口里 sleeper 始终持有 condition lock、p->lock 或两者之一。而 waker 要先持 condition lock，再在扫描时取得目标 p->lock。因此它无法刚好穿过那个窗口。

    6 · Interactive Correct Handoff：两把锁怎样把窗口缝起来？

      7 · 为什么一定写 while，而不是 if？

      原因 1 · 多等待者竞争

      一次 wakeup 可以让多个 waiter 变 RUNNABLE。最先真正得到 CPU + lock 的线程可能先把资源消费掉，后来的线程不能凭“我被叫醒过”继续。

      原因 2 · 其他唤醒原因

      xv6 的 kill() 会把 SLEEPING process 改成 RUNNABLE，即使它原来等待的 predicate 根本没成立。

      acquire(&lock); while (!predicate) { sleep(chan, &lock); // return with lock re-acquired } // only now consume/update protected state

      Wakeup 的语义应压缩成：“现在值得你重新竞争 CPU/锁并检查一次”，而不是“资源已经永久归你”。

      角色Predicate等待 channel谁改变条件并 wake？

      Writernwrite != nread + PIPESIZE，或者 reader 已关闭&nwritereader 消费后 wakeup(&nwrite)

      当前 xv6 piperead() 真的写成 while (empty && writeopen) sleep(&nread,&pi->lock)；pipewrite() 在 full 时睡在 &nwrite，reader 消费后叫醒 writer。

      这页不要把 channel 名字背成语义：&nread 只是“读者等数据”这类 sleeper 的 rendezvous key。真正决定是否有数据的 predicate 仍是计数关系。

      这正是 OS-B01 与 I/O 的桥：设备完成事件可以改变 predicate 并恢复任务调度资格，但 interrupt handler 不需要、也通常不会“直接把 CPU 交给那个进程”。

      再次阻断：Device Interrupt ≠ process instantly running。ISR 使等待条件成立、执行 wakeup；真正何时 Running 仍由 scheduler 决定。

      10 · wait/exit：Lost Wakeup 不只发生在设备和 pipe

      parent 的 wait() 本质上在等 predicate：

      exists child with state == ZOMBIE

      但 parent 事先不知道“到底哪个 child 会先退出”，所以不能拿某一个 child 的 p->lock 当 condition lock。xv6 使用全局 wait_lock：

      Parent wait()

      持 wait_lock 扫描 children；若没有 ZOMBIE，则 sleep(parent,&wait_lock)。

      Child exit()

      持 wait_lock 完成 parent/child 关系与 ZOMBIE/wakeup 交接，避免 parent 在“扫描完”和“睡下去”之间错过 child exit。

      生成性理解：condition lock 应保护“决定我是否应该睡”的那份 predicate。锁不是按函数名选，也不是一定等于目标对象自己的锁。

      11 · 为什么退出要经过 ZOMBIE，而不能自己把自己完全 free 掉？

      Child runningstill using kstack/proc
      →
      kexit()partial cleanup
      →
      ZOMBIEnot runnable, still reclaimable
      →
      parent wait()freeproc()
      →
      UNUSEDslot reusable

      正在执行的线程不能把当前正在使用的 kernel stack 和自身 struct proc 直接从脚下抽掉。于是“逻辑退出”和“最终物理回收”被拆成两个 owner/time point。

      这和 COW refcount 是同一类生命周期思维：资源能否 free，取决于是否仍有活跃执行/引用关系需要它，而不是“逻辑上已经不想要了”。

      12 · kill：为什么“终止另一个进程”也只能先请求，不能立刻摧毁？

      目标进程可能：

      • 正运行在另一个 CPU；
      • 正持有锁；
      • 正处在文件系统/内核数据结构更新中；
      • 正睡眠等待某个必须完成的 I/O。

      所以当前 xv6 的 kkill() 设置 killed；如果目标是 SLEEPING，则把它改成 RUNNABLE。目标之后在安全边界检查 killed 并自行退出。

      这正是“wakeup ≠ predicate true”的第二证据：被 kill 叫醒的 pipe reader，数据可能仍为空；因此 wait loop 必须重检 condition 和 competing exit condition。

      13 · Sleep Lock：Spinlock 上面还能继续构造“让权等待”的锁

      当前 xv6 sleeplock.c 的结构很干净：

      acquire(internal_spinlock); while (locked) sleep(lock_object, &internal_spinlock); locked = 1; release(internal_spinlock); ... release: acquire(internal_spinlock); locked = 0; wakeup(lock_object); release(internal_spinlock);

      内部 spinlock 保护 sleeping-lock 自己的 predicate；真正等待锁的线程则通过 sleep 放弃 CPU。

      层级很重要：硬件原子 → spinlock → sleep/wakeup coordination → sleeping lock / condition-style primitives。高级同步原语最终仍需要更低层原子性来保证 wait registration 不丢失。

      15 · 从 xv6 底层原语封装 408 Counting Semaphore：P/V 到底落在哪里？

      408 的 P/V 不要求某个内核必须真的提供一个叫 P() 的函数。它要求的是一个更稳定的契约：P 原子地消费 permit，没 permit 就进入可被未来 V 找到的等待关系；V 原子地产生 permit，并让等待者重新有机会消费。

      struct semaphore { struct spinlock lock; // 保护 permit count + wait protocol int value; // 非负：当前可立即消费的 permits }; sem_wait(S): acquire(&S.lock) while (S.value == 0) sleep(&S, &S.lock) // 原子释放 S.lock + block；返回前重新拿锁 S.value-- // 真正消费一份 permit release(&S.lock) sem_post(S): acquire(&S.lock) S.value++ // 先改变同步事实 wakeup(&S) // 再通知可能能消费的人 release(&S.lock)

      这就是 07 + 08 如何生成高层原语：atomic RMW / spinlock 保证 semaphore 自身状态不被并发破坏；sleep/wakeup 把“permit=0 时等待”从 busy-wait 变成 blocking wait。

      表示法边界：有些 408 教材把 semaphore value 允许记成负数，并用绝对值表达等待者数量；上面的真实实现选择“value 永不为负 + waiters 另存在进程等待关系”。编码可以不同，语义必须相同。xv6 wakeup 还可能唤醒多个 waiter，因此必须用 while 重新竞争 permit；它不天然提供 FIFO 公平。

      16 · 生产者—消费者：先从两个不变量推导 empty/full/mutex

      容量不变量

      0 ≤ count ≤ N；不能从空缓冲取，也不能向满缓冲塞。

      许可守恒

      empty + full = N（经典模型）。生产一次把一个 empty 转成 full；消费反过来。

      结构互斥

      真正修改 buffer / in / out / count 的多步事务不能被另一个执行流交错破坏。

      Producer
      produce_item() // 私有工作，别占 mutex P(empty) // 先确认有空位 P(mutex) buffer[in] = item in = (in + 1) % N V(mutex) V(full) // 发布“多了一件可消费对象”
      Consumer
      P(full) // 先确认有产品 P(mutex) item = buffer[out] out = (out + 1) % N V(mutex) V(empty) // 发布“多了一个空位” consume_item() // 私有工作

      为什么通常先 P(empty/full)，再 P(mutex)？如果 producer 先拿 mutex 再因 empty=0 睡眠，consumer 想制造 empty 又必须拿同一个 mutex，就可能形成“持锁等待只能由竞争者制造的条件”。把资源条件等待放在进入共享结构临界区之前，正是在破坏这条依赖。

      落到 xv6：empty/full 是两个 counting semaphore；mutex 可以是 binary semaphore / sleeping mutex；它们最终都可由“低层原子保护 + wait relation + wake”实现。于是 PV 题不再是神秘符号排列，而是对 predicate、permit 和临界区的组合。

      17 · 读者—写者：同一个共享对象，差别只是“准入谓词”怎么定义

      读者优先：第一位 reader 锁住资源，最后一位 reader 释放

      semaphore rw = 1; // writer 与 reader-group 互斥 semaphore rmutex = 1; // 只保护 readcount int readcount = 0; reader: P(rmutex) readcount++ if (readcount == 1) P(rw) // first reader closes writer gate V(rmutex) read() P(rmutex) readcount-- if (readcount == 0) V(rw) // last reader opens writer gate V(rmutex) writer: P(rw) write() V(rw)

      Safety 很清楚：多个 reader 可并发；writer 与 reader-group 互斥；writer 之间也互斥。但持续新 reader 可能让 readcount 长期不归零，于是 writer starvation。

      写者优先：一旦有 writer 等待，就先关闭“新 reader 入口”

      semaphore resource = 1; // 真正保护共享数据 semaphore readTry = 1; // writer 用它关闭新 reader 入口 semaphore rmutex = 1, wmutex = 1; int readcount = 0, writecount = 0; reader: P(readTry) P(rmutex); readcount++; if (readcount == 1) P(resource) V(rmutex) V(readTry) read() P(rmutex); readcount--; if (readcount == 0) V(resource) V(rmutex) writer: P(wmutex); writecount++; if (writecount == 1) P(readTry) // first waiting writer closes reader gate V(wmutex) P(resource); write(); V(resource) P(wmutex); writecount--; if (writecount == 0) V(readTry) V(wmutex)

      生成性理解：读优先和写优先不是两份无关模板。真正变化的是 admission policy：读优先只维护“当前 reader-group 是否存在”；写优先再增加 writecount/readTry，把“已有 writer 等待”也纳入新 reader 的准入谓词。

      公平性边界：“写优先”避免 writer 被源源不断的新 reader 插队，但也可能让 reader 等得很久。若题目要求严格无饥饿，还需要公平 service queue/turnstile 等更强协议，不能从这段伪代码无条件推出。

      20 · Quick Attack

      Q1 · wakeup(chan) 后，等待者是不是已经获得它等待的资源？
      不是。wakeup 只恢复调度资格；真正运行时还要重新获取保护并检查 predicate。资源可能已被另一个 waiter 消费，也可能这次 wake 来自 kill 等其他原因。
      Q2 · 为什么不能先 release(condition_lock)，再调用普通 sleep(chan)？
      这会打开 lost-wakeup window：waker 可以在 waiter 尚未登记为 SLEEPING 时改变 predicate 并调用 wakeup；之后 waiter 再睡下，可能永远等不到下一次事件。
      Q3 · wait channel 为什么不等于 condition？
      channel 只是让 wakeup 找到一组 sleeper 的 rendezvous key。真正“能否继续”的事实存放在受 condition lock 保护的共享状态里。
      Q4 · child exit 后把 parent 叫醒，parent 为什么还要重新扫描 ZOMBIE child？
      wakeup 只表示“某个相关状态可能变化”。parent 等的是“存在一个自己的 ZOMBIE child”这个 predicate；真正运行后仍要在 wait_lock 保护下重新确认并选择可回收对象。
      Q5 · signal(cv) 和 V(S) 都能唤醒等待者，它们是否等价？
      不等价。condition variable 的通知不拥有 predicate/permit；共享变量才是条件事实。信号量 V 会改变 semaphore 自身的许可计数，并可为未来 P 保存许可。
      Q6 · 用 xv6 sleep/wakeup 封装 semaphore 时，为什么 sem_wait 仍要写 while(value==0)？
      因为 xv6 wakeup 可能把多个 waiter 都变 RUNNABLE，而真正 permit 可能只有一个；第一个重新拿锁者消费后，其余线程必须再次检查并继续睡。Wakeup 不是 permit ownership。
      Q7 · 生产者若先 P(mutex) 再 P(empty)，为什么危险？
      缓冲区满时 producer 会持 mutex 等 empty；但 consumer 要拿同一 mutex 才能消费并 V(empty)，于是制造条件的人被锁在门外，形成 hold-and-wait 依赖。
      Q8 · 读者优先为何可能饿死 writer？
      只要新 reader 能在最后一个旧 reader 离开前不断加入，readcount 就可能长期不降到 0，writer 持续等不到 rw/resource。系统整体仍推进，所以这是 starvation，不是 deadlock。

      21 · Retrieval Check

      1. 不用函数名讲清 Lost Wakeup 的最小 5 步反例。
      2. 解释安全 sleep 为什么要求从 condition lock 到 process/wait-state lock 的原子交接。
      3. 用 pipe 说清 predicate、condition lock、wait channel、sleeping process 四者分别是什么。
      4. 解释 wakeup 为什么只得到 RUNNABLE，不能直接推出 RUNNING。
      5. 用 kill 反例解释为什么 condition wait 必须 while 重检。
      6. 解释 wait/exit 的 wait_lock 为什么保护的是“是否存在 ZOMBIE child”的检查-睡眠窗口。
      7. 不用背模板，从“permit count + atomic wait registration”重新推导一个 counting semaphore 的 wait/post。
      8. 从 0≤count≤N 与 empty+full=N 推导生产者—消费者的 empty/full/mutex，并解释 P 的先后顺序。
      9. 解释读优先为何只需 reader-group gate，而写优先为何必须再增加“waiting writer closes reader gate”的状态。

      通过标准：看到任何“等待某事件”的题，你先问“predicate 由谁拥有？什么锁保护它？如何原子注册等待？谁改变 predicate？wake 后为什么还要重检？”而不是只背 Blocked→Ready 箭头。
