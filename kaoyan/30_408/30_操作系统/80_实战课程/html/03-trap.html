Trap：
系统调用、异常与中断的共同骨架

Lesson 02 已经追过 system call。这一页不再重复 ecall 路径，而是建立更上位的事件模型：为什么 system call、page fault、timer/device interrupt 都能把控制交给内核，却不能按同一套“返回 PC / 是否重试 / 是否调度”规则处理。最后用 MIT 2026 的 sigalarm 实验，把“保存现场 → 暂时改写用户控制流 → 恢复现场”真正跑一遍。

CPU 正在顺序执行程序时，什么事件有资格“打断正常控制流”，内核又怎样知道处理完以后该继续、重试、终止，还是调度别人？

统一骨架：三者共享的是“保存足够恢复状态 → 进入可信 handler → 识别原因 → 处理 → 决定出口”。它们不共享同一个触发源，也不共享同一个恢复语义。

2 · 先把术语钉住：Trap 是机制伞，不是第四种事件

System Call

同步当前程序主动执行 ecall，请求内核服务。对 xv6 来说，它以一个特定的 synchronous trap cause 进入。

Exception / Fault

同步当前指令执行遇到特殊条件，例如 page fault、illegal instruction。能否修复决定是 retry 还是 terminate。

Interrupt

异步外部设备或 timer 相对当前指令流独立到来。它首先代表“外部状态改变了”。

术语边界：不同教材会把 “trap/exception/interrupt” 分组得略有不同。这里采用 xv6/RISC-V 的实用视角：trap 是进入特权处理程序的共同控制转移机制；再用 event source 区分 syscall、同步 exception/fault 与异步 interrupt。做 408 时若题目明确采用自己的“内中断/外中断/异常”术语，以题设分类为准，但推演骨架不变。

3 · Interactive Classifier：先问“谁触发”，再问“怎么回”

4 · xv6 的一个入口，实际上有两条低级路径

User → Kernel

stvec → TRAMPOLINE:uservec save user registers → trapframe establish kernel stack / page table → usertrap()

来自 U-mode，需要先完成地址空间/栈环境交接。usertrap() 随即把 stvec 改为 kernelvec，避免已经在 kernel 中时又走 user trampoline。

Kernel → Kernel

stvec → kernelvec current stack already kernel stack push caller-saved registers → kerneltrap() restore registers → sret

来自 S-mode 时已经在 kernel stack / kernel environment，低级入口职责不同。当前 kernelvec.S 就直接在当前 kernel stack 保存寄存器。

为什么 stvec 会动态改？同一个 CPU 在“准备返回 user”时把下一次 trap destination 指向 uservec；进入 usertrap() 后又把它切回 kernelvec。入口本身就是状态，必须与当前运行环境匹配。

5 · 三个关键 CSR：不是背寄存器，而是回答三个问题

CSR它回答的问题xv6 怎么用
scause为什么进来了？usertrap() 用它区分 U-mode ecall、page fault，devintr() 用 interrupt cause 识别 timer / external device。
sepc处理完从哪里继续？系统调用主动推进到下一条；page fault 修复时保留 faulting continuation；kernel trap 还要防止 yield() 等过程破坏它。
stval事件还携带什么上下文？page fault 时可给出故障虚拟地址；unexpected trap 的诊断也会打印它。

压缩成三问：Cause? → Resume Where? → Extra Value?。这比背 CSR 编号更能迁移到 x86 的 vector/error code/CR2 等其他体系结构。

6 · Page Fault：为什么“失败”可以成为正常机制？

当前 xv6 usertrap() 会把 load/store page fault 交给 vmfault() 尝试处理 lazy allocation。若修复成功，就不是“程序一定出错”，而是一次慢路径。

load/storetranslation cannot proceed
→
page faultscause + stval
→
vmfault()repair mapping?
→
returnretry / kill
可修复

例如 lazy allocation、后面的 COW。内核补足映射后，用户执行应获得重新完成那次内存访问的机会。

不可修复

例如非法地址且没有合法 VMA/策略支撑。内核记录错误并终止进程，而不是“随便跳过出错指令”。

7 · Timer Interrupt：获得控制权 ≠ 一定换进程

当前 xv6 的 devintr() 把 supervisor timer interrupt 识别为 timer event，clockintr() 更新 ticks 并安排下一次 timer；回到 usertrap()/kerneltrap() 后，xv6 对 timer 调用 yield()。

408 三道闸门：Interrupt happens → kernel gets control → scheduler may run → scheduler may choose another task。每个箭头都有条件，不能把“时钟中断”直接画等号成“进程切换”。xv6 的具体策略是 timer 后主动 yield()，但这属于 OS policy/implementation，不是所有 OS 每次 timer interrupt 的跨系统定律。

8 · Device Interrupt：完成事件通常只改变“可运行资格”

当前 xv6 external interrupt 通过 PLIC 取得 IRQ，分给 UART 或 virtio disk handler，最后 complete IRQ。设备 handler 可能使某个等待条件成立并触发 wakeup。

Completion ≠ Running：设备完成的核心含义是“等待条件可能已经满足”。被唤醒任务通常只是获得进入 ready/runnable 集合的资格，何时真正占 CPU 是另一层调度决策。

9 · 一个很深的实现细节：为什么 kerneltrap() 要先备份 sepc/sstatus？

当前 xv6 kerneltrap() 入口先把 sepc、sstatus、scause 读到局部变量。若这是 timer interrupt，后面可能调用 yield()；切换出去再切回来期间，别的 trap 可能已经使用过这些 per-hart CSR。因此返回前 xv6 再写回原来的 sepc/sstatus。

kernel trap A save sepc / sstatus locally → timer → yield() → other execution / other traps may occur ← eventually resume A kernel path restore A's sepc / sstatus → kernelvec.S → sret

心智模型：“现场”不只是寄存器集合，而是谁拥有哪一份可恢复状态。只要控制流可能离开当前处理路径，那些稍后仍要使用、但中途可能被覆盖的状态就必须获得独立 owner。

11 · Interactive Alarm：内核怎样“插入”一次用户函数又不破坏原程序？

12 · Alarm 真正保护的不变量

Transparent Resume

handler 结束后，原程序的 PC 与寄存器必须像“这次插入没有破坏它”一样继续。

No Re-entrancy

handler 尚未 sigreturn 时，下一次 timer 不能再次把同一 handler 套进去，除非系统显式设计支持嵌套。

a0 Is State Too

sigreturn 自身也是 syscall，会涉及 a0；恢复时不能漏掉原来用户 a0，否则“返回值寄存器”会悄悄破坏原执行。

这就是 trapframe 的生成性定义：为了让未来某一时刻能够恢复“同一个逻辑执行”，必须保存所有会影响后续可观察行为、且中途可能被覆盖的状态。

14 · Quick Attack

Q1 · system call、page fault、timer interrupt 都进入 usertrap()，所以它们返回 PC 的处理可以一样吗？
不可以。共同入口只表示共享 trap 骨架。system call 需要继续到调用后的指令；可修复 page fault 要让故障访问重新获得执行机会；interrupt 则恢复被异步打断的 continuation。具体 saved PC 语义还要尊重 ISA。
Q2 · timer interrupt 发生，能不能立刻写“Running A → Running B”？
不能。至少还要经过进入 kernel、handler/记账、是否产生调度机会、scheduler 选择结果。xv6 timer 后会 yield，但其他 OS 策略并不要求每个 timer tick 都换人。
Q3 · I/O interrupt 唤醒进程 A，A 的状态一定立刻变成 Running 吗？
通常不是。完成事件让等待条件成立，A 从 Blocked/Sleeping 变为 Ready/Runnable；是否马上获得 CPU 取决于 scheduler 和抢占策略。
Q4 · alarm handler 为什么不能只保存 PC，不保存寄存器？
handler 自己会使用并覆盖通用寄存器。若不恢复原值，虽然能跳回原 PC，原程序的数据状态已经被污染，不能称为透明恢复。
