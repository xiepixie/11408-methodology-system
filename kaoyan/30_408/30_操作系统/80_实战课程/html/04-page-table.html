Page Table：
地址空间是怎样被“制造”出来的？

页表不是“把虚拟地址换算成物理地址的一张表”这么简单。它是 OS 写给 MMU 的可执行映射契约：这个虚拟页指向哪里、允许 R/W/X 哪一种访问、当前映射是否有效。硬件在每次访存时消费这份契约；只有契约不足以完成访问时，fault 才把控制权交回 OS。

1 · Mother Question

责任链：OS Mapping Decision → PTE State → MMU/TLB Consumption → PA or Fault。OS 不参与每一次正常地址翻译；它预先把策略编码成页表，让硬件快速执行。

2 · 先分三层：Address Space ≠ Mapping ≠ Physical Page

Virtual Region

回答“哪些 VA 在逻辑上属于进程、用途/权限是什么”。现代系统常用 VMA 等高层结构描述；xv6 更简化。

Page-table Mapping

回答“某个 VPN 当前怎样翻译、权限如何”。这是硬件可消费的页级状态。

Physical Frame

真正的 RAM 页面。多个 VA 可以映射同一 frame；一个合法 VA 也可能暂时还没有 frame。

以后处理 COW / mmap / demand paging 都靠这个区分：“这个地址属于进程”不等于“已经有物理页”，而“两个进程有不同页表”也不等于“所有物理页都不共享”。

3 · Paging Math：为什么地址一定要拆 VPN | Offset？

页面内部的字节相对位置不会因为映射改变，所以页表只需要翻译页号：

VAVPN | Offset
→
Page TableVPN → PPN
→
PAPPN | same Offset

若页面大小为 2^p bytes，则 offset 固定占 p 位。剩余高位才是 VPN。408 所有地址位数题，第一动作都应该是：先从 page size 定 offset。

4 · Interactive Sv39 Address Split

RISC-V Sv39 的架构地址是 39-bit canonical VA（高位按 bit 38 符号扩展）；xv6 为了简化地址判断，只使用低半区并定义 MAXVA = 1<<38。这里按 xv6 的实际范围校验。

VPN[2]9 bits · Level 2 index
VPN[1]9 bits · Level 1 index
VPN[0]9 bits · Level 0 index
Offset12 bits · 4 KiB page

为什么恰好 9 bits/level？一个页表页大小 4096 B，每个 PTE 8 B，因此一页容纳 4096/8=512=2^9 个 PTE。不是“39 位平均除三份”，而是由页表页容量反推每级索引位数。

5 · 多级页表不是为了“翻译更复杂”，而是为了稀疏

单级页表需要为整个 VPN 空间准备表项，即使进程只用了很少地址。多级页表把页表本身变成一棵按需展开的树：只有某段 VA 真被使用，才分配它沿途需要的低层 page-table pages。

Root / L2
普通 xv6 路径：V=1, R/W/X=0 → 下一层；Sv39 架构也允许这里直接成为 1 GiB leaf
PX(2, VA)
Level 1
普通 xv6 路径：V=1, R/W/X=0 → 下一层；2026 superpage lab 要你支持这里成为 2 MiB leaf
PX(1, VA)
Level 0
4 KiB Leaf PTE: PPN + R/W/X/U + V
PX(0, VA)
Physical Page
PPN | Offset
最终 byte

当前 xv6 main 的 walk() 从 level 2 往 level 0 走，并把 L2/L1 当作普通非叶路径；若中间 PTE 不存在且 alloc!=0，就分配新的 page-table page。注意：这是 base xv6 的实现范围，不是 Sv39 的架构上限；2026 superpage lab 正是在扩展这个边界。

7 · TLB：缓存的是“翻译”，不是数据

VA / VPNCPU load/store
→

Miss / Fault缺的是什么一定进入 OS？
TLB miss近期翻译缓存副本不一定；硬件 page walk 可以找到合法 PTE 并 refill
Page / permission fault当前映射、驻留或访问权限不足以完成操作需要 trap 到 OS 决定 repair / reject
Cache miss目标物理数据块不在硬件 Cache通常不进入 OS；由存储层次继续取数据

三者绝不能互推：TLB miss ≠ Page Fault ≠ Cache miss。同一次 load 甚至可能 TLB miss → page walk success → Cache miss → memory hit，而 OS 全程不知道。

8 · satp：页表根不是“进程地址空间本身”

RISC-V 的 satp 给硬件当前地址翻译上下文的根信息；xv6 在 user/kernel trap 交接时会切换它。Lesson 02 已经看到：同一个进程进入内核时，可以临时切到 kernel page table，但这不等于进程换了地址空间 owner，更不等于 context switch。

Logical ownership

进程仍拥有自己的 user address space 与 p->pagetable。这是 OS 对该进程的资源关系。

Active translation root

CPU 此刻由哪个 page-table root 驱动地址翻译，是执行环境状态。xv6 trap path 会在 user/kernel 两套 page table 间切换。

9 · 为什么 trampoline 能跨页表切换？

当前 xv6 kernel page table 把 trampoline 映射到最高虚拟地址；每个 user page table 也把同一 trampoline 物理页映射到相同虚拟地址。于是：

User PTVA T → trampoline PA
→
execute Tuservec/userret
→
switch satptranslation context changes
→
Kernel PTsame VA T → same PA

不变量：执行 satp 切换前后，下一条仍要执行的 trampoline 指令必须在两套映射下具有连续、合法的身份。这个例子比“页表就是地址转换”更深地展示了 mapping 也是控制流可达性的一部分。

11 · USYSCALL：一页只读映射为什么能省掉一次系统调用？

如果 getpid() 只是读取一个内核已经知道、用户可以知道的值，为什么每次都必须 ecall？

2026 lab 让每个进程在一个固定 user VA 映射只读页面，并把 PID 放进去。用户直接读取，不需要每次跨 privilege boundary。

13 · Quick Attack

Q1 · TLB miss 后，CPU 一定触发 page fault 吗？
不一定。TLB 只是翻译缓存。若 page table 中存在合法 PTE，硬件 page walk 可以成功并 refill TLB，完全不需要 OS 介入。
Q2 · 一个 VA 已经属于进程，是不是一定已经分配物理 frame？
不是。合法虚拟区域可以采用 lazy allocation / demand paging；真正首次访问时才通过 page fault 分配或装入物理页。
Q3 · 两个进程能不能把不同 VA 映射到同一个 physical frame？
可以。共享库、共享内存、COW 等都会使用这种关系。页表隔离的是“每个地址空间如何解释 VA”，不是禁止共享物理页。
Q4 · 多级页表为什么省空间？
因为它只为实际使用的虚拟地址子树分配低级页表页；大块未使用 VA 区域可以在高层以 invalid entry 直接停止，不需要为每个 VPN 预留 leaf PTE。

15 · Retrieval Check

  1. 解释为什么 page table 是“OS 写、MMU 读”的接口，而不是 OS 每次帮 CPU 翻译。
  2. 从 4KiB page + 8B PTE 推出 Sv39 每级 9-bit index，不看答案。
  3. 给一个 PTE，先判断它是 non-leaf 还是 leaf，再判断 V/R/W/X/U；不要只提取 PPN。
  4. 完整区分 TLB miss、page fault、Cache miss 的缺失对象与处理者。
  5. 解释同一个进程为什么进入 xv6 kernel 时可以切 satp，却仍不是 context switch。
  6. 解释 USYSCALL 为什么必须 read-only，以及它为何能省一次 system call。

通过标准：看到任何地址翻译题，你能先画 VA → TLB/page walk → PTE permission → PA or fault，再计算，而不是先找一个 EAT 公式硬套。
