Process / Scheduler：
“能运行”为什么不等于“正在运行”？

这一页把两件经常混在一起的事拆开：Mechanism 负责保存/恢复执行现场，使 CPU 可以换执行流；Policy 负责在合法候选者中决定下一个是谁。xv6 给我们真实的 context-switch mechanism，408 的 FCFS/SJF/SRTF/RR/Priority 则用来训练 policy 与时间轴。

1 · Mother Question

一个进程已经 Ready / RUNNABLE，为什么它仍然可能很久都没有执行一条用户指令？
Runnable Set有资格竞争
→
Scheduler Policy选谁
→
Dispatcher / Switch让选择生效
→
Running真正占有 CPU

压缩：RUNNABLE = eligibility，RUNNING = ownership of a CPU now。wakeup 只让任务重新有资格竞争；获得 CPU 还需要一次调度选择与必要的现场切换。

2 · Process state 是 scheduler 的输入，不是装饰标签

xv6 state核心含义可否被 scheduler 直接选中？
RUNNING此刻已经在某个 CPU 上执行（用户态或内核态都可能）已经拥有 CPU
RUNNABLE没有等待外部条件，希望运行，但当前没占 CPU可以
SLEEPING等待某个 channel/event；即使给 CPU 也不能按当前逻辑继续不可以，先 wakeup
ZOMBIE执行已结束，保留退出状态等待 parent 回收不可以

不要把 OS 状态轴和 CPU mode 轴混在一起：同一个 RUNNING process 可以先在 user mode 执行，trap 后继续以同一 process 身份在 kernel mode 执行。

3 · Thread 到底是什么？从“暂停后怎样恢复”反推

MIT 当前 schedule 的 Thread Switching notes 用了一个很生成性的定义：如果一条串行执行路径现在暂停，过一会还要从原处继续，那么系统至少必须保存足以恢复它的状态。

User saved state

用户寄存器保存在 trapframe，支撑 kernel → user 的恢复。

Kernel saved context

kernel thread 在 swtch() 处暂停时，需要独立 context + kernel stack。

Scheduling state

p->state、等待原因、锁等决定它是否有资格被恢复。

最深的共同点：执行流的身份不是“CPU 里那套寄存器”。CPU 寄存器只是它当前运行时的临时载体；暂停后，身份由一份可定位、可恢复的保存状态继续存在。

4 · xv6 一次真正的 switch 为什么不是 P1 → P2 直接跳？

P1 kernel threadp1 context + kstack
→
swtchsave p1 context
→
CPU scheduler threadper-CPU context/stack
→
scheduler()find RUNNABLE
→
swtchrestore p2 context
→
P2 kernel threadresume saved point

当前 xv6 每个 CPU 有自己的 scheduler context。一个进程进入 sched() 后先切回该 CPU 的 scheduler thread；scheduler 之后才选择一个 RUNNABLE process，再切入它的 kernel context。

为什么需要 scheduler 自己的 stack/context？如果 P1 正在退出或睡眠，就不能继续依赖“马上不该运行的 P1 栈”去完成长期调度循环。Scheduler 需要一个独立、安全的执行落脚点。

5 · swtch.S 没有保存“所有寄存器”，为什么仍然正确？

当前 RISC-V xv6 的 swtch(old,new) 保存 ra、sp 与 s0..s11，然后加载另一份 context 并 ret。它不是 user trap 的完整寄存器快照。

Trapframe

解决 user ↔ kernel 边界：用户寄存器必须足以恢复完整用户执行现场。

Context

解决 kernel thread 在规范函数调用点的暂停/恢复：利用 RISC-V calling convention，只需保存跨调用必须保留的 callee-saved 状态、SP 和返回路径。

所以：trapframe ≠ context ≠ PCB 的全部字段。它们分别服务不同恢复边界。

6 · 跨进程切换不等于 swtch() 那一刻就切 user page table

xv6 是一个特别好的反例：从 P1 用户态进入内核时，trampoline 已经先把 active translation root 切到共同的 kernel page table；随后 P1 kernel thread 才通过 swtch() 去 scheduler，再进入 P2 kernel thread。直到 P2 准备返回用户态，trampoline 才切到 P2 的 user page table。

P1 userP1 user PT
→
P1 kernelkernel PT
→
swtch → schedulerkernel PT
→
P2 kernelkernel PT
→
P2 userP2 user PT

所以要继续坚持四维切换模型：execution-context switch 与 memory-context switch 是两个维度，可能发生在同一宏观“换进程”过程的不同位置。不要把“swtch() = 改页表寄存器”写成定义。

7 · Timer interrupt → yield：这是“获得一次重新选择机会”，不是宇宙定律

当前 xv6 的 timer path 会调用 yield()；yield() 把当前 process 改回 RUNNABLE 后进入 sched()。但“每次时钟中断都必须换成另一个进程”不是 OS 通用定义。xv6 的实现只是一个具体 policy。

408 里的“抢占原因”真实控制流里最早在哪里被看见？Current xv6 的边界
RR 时间片到timer interrupt → trap.c → timer event → yield()；这里获得强制进入内核并重新选择 CPU owner 的机会xv6 直接 yield，是简单教学 policy；408 RR 还要求显式 quantum 记账与 FIFO ready queue
更高优先级任务因 I/O 完成而 Readydevice interrupt → driver completion → wakeup() 先制造新的 RUNNABLE candidate；之后抢占式 policy 才比较优先级current xv6 没有 408 priority scheduler，不能声称 wakeup 后会按“更高优先级”立即抢占
更高优先级任务新到达创建/唤醒路径把它加入 runnable set；真正 switch 必须发生在内核允许调度的安全点“priority arrival”是 policy 条件，不是某条 RISC-V trap 的硬件定义

把“抢占点”理解成两件事：事件先让系统知道“候选集/预算变了”，policy 再决定是否需要换人；只有决定换人后才进入 context-switch mechanism。时钟中断只是最经典的强制 decision opportunity。

8 · Mechanism vs Policy：为什么 xv6 不能替你学完 408 调度算法？

层问题这一页的来源
Mechanism怎样保存现场、把 CPU 交出去、以后从原处恢复？xv6 swtch / sched / scheduler
Eligibility谁此刻合法进入候选集？RUNNABLE state / ready queue abstraction

Metric用什么评价？周转、等待、响应、公平、切换成本？408 题目目标

不要给 xv6 强行贴“标准 RR”标签：current xv6 scheduler 是 per-CPU 扫描 process table 的简单教学实现，并配合 timer yield。408 的 RR 则有明确 ready-queue order 与 quantum 模型。我们用 xv6 学 mechanism，用自建 simulator 学 policy。

9 · Interactive 408 Scheduler Simulator

统一 tie-break：先 arrival，再输入顺序。RR 在“新任务到达”和“旧任务时间片恰好结束”同一个 tick 时，模拟器约定先把新到达者入队，再把时间片用尽者放回队尾。时间取整数 tick，切换成本暂按 0。真实考题若另有约定，以题设为准。

10 · 四个时间指标必须从生命周期定义推出来

指标定义不要混成
Turnaroundcompletion - arrival不是“CPU 真正执行了多久”
Waitingturnaround - CPU service（本页单 CPU-burst 模型）不是所有现实 I/O 生命周期的万能公式
Responsefirst_run - arrival不是 completion；交互系统尤其关注第一次响应
Weighted turnaroundturnaround / service是任务完成后的评价指标；不是 HRRN 在选择时刻计算的 key
HRRN response ratioR=(waiting+service)/service=1+waiting/service只在 CPU 需要重新选择的决策点，对已到达候选者重算；选中后非抢占运行

11 · 不要分别背算法：统一成 Candidate → Key → Decision Point

算法候选集Ordering Key / Decision
FCFS已到达、未完成arrival 最早；非抢占，只在 CPU 空闲时选
SJF已到达、未完成burst 最短；非抢占
SRTF已到达、未完成remaining 最短；新任务到达等决策点可抢占
HRRN已到达、未完成R=1+W/S 最大；非抢占，只在 CPU 空闲时重算
Priority已到达、未完成priority；必须先看题设“数值大/小谁更高”及是否抢占
RRready queue队头；运行最多 q，再把未完成者按题设入队规则放回队尾

做题起手：先写 Candidate Set → Key → Decision Point → Tie Rule → Preemption?，再画 Gantt。绝大多数调度计算错误，其实是在某个决策点把“不该进入候选集的人”或错误 tie-rule 偷进来了。

12 · HRRN：为什么“响应比”不是完成后的带权周转时间

HRRN 在某个调度决策时刻 t 对每个已经到达、尚未完成的候选任务计算：

waiting W = t - arrival service S = burst R = (W + S) / S = 1 + W / S choose max R

它和“带权周转时间 T/S”长得很像，是因为如果这个候选现在立刻被选中且无额外等待，它完成时的带权周转恰好就是当前响应比；但一个是调度时的动态 key，一个是完成后的结果指标，不能把所有任务最终的 weighted turnaround 拿回来当 HRRN 的历史选择依据。

手算动作：HRRN 不需要每个 tick 都重算。只在 CPU 真正空闲、需要选下一个任务时，对当时的 Candidate Set 计算 R；选中后由于非抢占，运行到本次服务结束。

13 · MLFQ / MFQ：它不是一条固定公式，而是一组“反馈规则参数”

Classification

新任务通常从高层进入；队列 membership 可以根据历史 CPU 使用变化，这正是“反馈”。

Inter-queue

高层是否绝对优先？低层运行时高层到达是否抢占？这些必须读题设。

Intra-queue

每层可用 RR/FCFS，不同层 quantum 常逐级变大。

一套常见教学规则状态变化考试不能偷省的参数
新任务进入最高层 Q0先给短/交互任务快速响应机会初始层级
用满本层时间预算仍未完成Q0 → Q1 → Q2… 降级每层 quantum / allotment
高层出现 runnable task可抢占正在运行的低层任务被抢占任务剩余时间片是否保留
周期性 boost / aging低层任务重新上移boost 周期与提升范围

MLQ ≠ MLFQ：多级队列只说明“有多条队列”；MLFQ 的关键是 queue membership 会因执行反馈而变化。因此没有题设给 queue rule，就不存在唯一的 MLFQ 甘特图。

14 · 408 算法定量对比：先看目标，再看代价

算法抢占常见定量关注主要风险/代价
FCFS否arrival 顺序；周转/等待Convoy effect
SJF否已知 burst 下平均等待/周转通常优秀未来 burst 难准确知道；长任务饥饿
SRTF是每个 arrival 决策点比较 remaining；响应通常更快抢占/切换更多；长任务可被持续推迟
HRRN否决策点计算 1+W/S；兼顾等待与短任务偏好需估计 service；只在选择点重算
RR是q、response、context-switch taxq 太小开销高；太大趋近 FCFS
MLFQ通常支持queue level、quantum、降级/boost 轨迹规则参数多；饥饿与 gaming

Simulator 输出现在同时给 Turnaround / Waiting / Response / Weighted Turnaround。同一 workload 切换算法后，不要只找“谁最小”，还要解释这个指标对应的系统目标是什么。

15 · RR 的 q 是权衡旋钮，不是越小越好

q ↓

通常首次响应更快、轮转更细，但 context-switch / scheduler 的固定成本占比升高。

q ↑

切换税降低，但交互响应可能变差；若 q 大到不再触发时间片抢占，固定 workload 下会趋向 FCFS 顺序。

Simulator 默认没有切换成本。如果题目给 context-switch cost δ，Gantt 必须显式插入成本区间，并重新计算 arrival 在切换期间发生时的候选状态；不要只在最后总时间加一个常数。

16 · Scheduling ≠ Context Switch

Event

时间片到、block、exit、wake higher-priority task……让系统获得/需要重新考虑 CPU ownership。

Schedule

Policy 对候选集做选择。这个动作可能仍然选中当前实体。

Context Switch

只有最终要把 CPU 的 execution context 换给不同执行流时，才需要真正 save/restore。

三连不等于：interrupt ≠ schedule ≠ switch-to-another-process。这条边界是 408 高频选择题的稳定检查器。

19 · Quick Attack

Q1 · 一个进程从 SLEEPING 被 wakeup 后，是否立刻变 RUNNING？
不是。xv6 wakeup 把匹配进程改成 RUNNABLE；它重新拥有“可被选择”的资格。何时真正 RUNNING 仍由 scheduler 与 CPU availability 决定。
Q2 · 系统调用进入 kernel mode 是不是已经发生 context switch？
不是。它可以仍然是同一进程/执行流，只是 privilege/environment 改变。只有保存当前执行流现场并恢复另一执行流时才是 execution context switch。
Q3 · xv6 的 swtch() 为什么只保存一部分寄存器？
它发生在 kernel 的正常调用约定边界，使用 struct context 保存跨调用必须保留的 callee-saved 寄存器、SP 和 RA。完整 user register state 属于 trapframe 的责任。
Q4 · RR 时间片变小，平均周转时间一定变好吗？
不一定。q 小主要改善轮转粒度/响应，但会增加切换开销；平均周转还取决于 workload。不能把“响应更快”偷换成“所有指标都更好”。
Q5 · HRRN 的响应比是否就是这个进程最终的带权周转时间？
不是同一概念。HRRN 的 R 是某个调度决策点的动态排序 key；最终带权周转是完成后 T/S 的评价指标。只有在“此刻立刻选中并无额外等待”的假设下，两者在这个候选的假想完成结果上数值对应。
Q6 · 高优先级任务被 I/O 中断 wakeup，是否说明 CPU 已经在 ISR 里完成了进程切换？
不说明。ISR/wakeup 先改变 candidate eligibility；抢占式 priority policy 再决定是否需要 reschedule，真正 context switch 发生在合法调度点。current xv6 本身也没有 408 那套 priority scheduler。

20 · Retrieval Check

  1. 不用图解释 RUNNABLE 与 RUNNING 的资格/占有区别。
  2. 复原 xv6 的 P1 kernel → scheduler context → P2 kernel switch 主链，并解释为什么需要 scheduler 独立 context。
  3. 解释 trapframe 与 struct context 分别在什么边界恢复谁。
  4. 看到一道调度题，先写 Candidate / Key / Decision Point / Tie / Preemption，而不是立刻画甘特图。
