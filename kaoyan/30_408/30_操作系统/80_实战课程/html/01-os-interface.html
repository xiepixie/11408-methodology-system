操作系统接口：
从用户程序到内核

这一页先不钻进内核实现。我们只建立一个必须牢固的入口模型：应用程序看到的是稳定的 OS 接口，而不是裸 CPU、裸内存和裸设备。随后用 xv6 的 shell、fork、exec、wait 和文件描述符，把“进程 / 文件 / 系统调用”从名词变成一次可运行的状态变化。

Source: xv6 Book Ch.1MIT 2026 Lab util408 Anchor: OS-00 / OS-01/02预计 60–90 min

1 · Mother Question

为什么普通程序可以像在“直接使用机器”，却又不能随便执行特权操作、改别人的内存或控制设备？

真正要建立的不是“OS 有四大功能”这张表，而是下面这层关系：

Physical MachineCPU / RAM / device
→
Kernel保护 + 管理 + 复用
→
OS Interfaceprocess / fd / file / syscall
→
User Program看到稳定逻辑对象

核心压缩：程序真正使用的不是“硬件本身”，而是 OS 暴露的逻辑机器。抽象回答“我能通过什么对象做事”，保护回答“哪些状态我不能直接改”，虚拟化回答“有限资源怎样看起来像多个独立实例”。

2 · Minimum Model：先只记 5 个对象

Process

一个受 OS 管理的执行实体。不是“程序文件”本身，而是带运行状态与资源引用的动态对象。

Address Space

进程看到的虚拟地址空间。此处只知道它存在，页表机制留到 Lesson 04。

File Descriptor

进程内部的小整数句柄。它不是“磁盘文件本体”，只是通往内核文件对象的入口。

Kernel

拥有关键受保护状态，代表进程执行受控操作，并管理资源共享。

System Call

用户程序请求内核服务的受控接口。它不是普通函数调用的同义词。

Event

如 fork、exec、wait、read。每个事件都让 Objects / Relations / Queues 发生确定变化。

3 · 第一个关键区分：Program ≠ Process

Program

磁盘上的静态代码和数据，像一份“可执行蓝图”。同一个程序文件可以被运行多次。

/bin/echo /bin/sh user/_ls

Process

程序一次运行产生的动态执行实例。它有自己的 PID、执行上下文、地址空间、打开文件等状态。

Process A → running / runnable / sleeping Process B → 也可以来自同一 program

408 常见混淆：“程序进入内存”并不自动等于“获得 CPU”；“创建进程”也不是简单复制一份程序文本。后续调度页会把 runnable 与 running 明确分开。

4 · 用 xv6 shell 看一条真实主链

假设你在 xv6 shell 输入：

$ echo hello

shell 自己也是一个用户进程。它不会“变成 echo 后永远消失”，而是典型地通过 fork → exec → wait 组织一次命令执行。

shell已有进程
→
fork()创建 child
→
child exec()替换程序映像
→
echo runs写 stdout
→
exit / waitparent 回收

5 · Interactive Trace：一步一步看 fork / exec / wait

    6 · 为什么 fork 和 exec 要分开？

    这其实是 Unix 接口设计最值得记住的一点之一：创建执行实体和选择它接下来运行哪个程序是两个不同动作。

    动作它改变什么它不等于什么
    fork()产生新的进程关系与执行实例；父子从 fork 返回点继续不是“加载另一个程序”
    exec()把当前进程的用户态程序映像替换成新程序通常不是“再创建一个新进程”
    wait()父进程等待子进程状态满足条件，并完成回收语义不是“父进程一直占着 CPU 空转”

    生成性理解：如果 shell 想在运行子命令前调整文件描述符、重定向输入输出，那么“先 fork 出 child，再让 child 改自己的 fd，再 exec”就非常自然。接口可组合性来自这几个原语职责分开。

    7 · File Descriptor：为什么 stdin/stdout 可以被重定向？

    在用户程序眼里，0 / 1 / 2 只是小整数。真正的文件对象和偏移等状态在内核里。于是程序可以把“1 号入口”重新连接到别的内核对象，而程序内部仍然只管往 fd 1 写。

    write(1,...)用户代码只拿 fd
    →
    fd table进程级映射
    →
    kernel file object状态由内核拥有
    →
    console / pipe / file实际终点可变化

    边界：fd ≠ 文件名；fd ≠ inode；fd 甚至不必指向普通文件。后面 File System 单元会继续拆成 pathname → inode 与 fd → kernel file object 两条入口。

    8 · xv6 Code Path：这页只读这些

    用户侧

    • user/sh.c：shell 怎样组合 fork / exec / wait / fd。
    • user/user.h：用户可见系统调用声明。
    • user/usys.S（生成结果）：系统调用 stub 的入口感。

    内核侧

    • kernel/sysproc.c：进程相关 syscall wrapper。
    • kernel/proc.c：fork / wait / exit 的真实内核状态操作。
    • kernel/file.c：文件引用的内核对象感。

    本页先看“接口和对象关系”，不要现在追 ecall → trapframe → trampoline。那是 Lesson 02–03 的 Owner。提前钻进去会把“为什么有这个接口”和“这个接口怎么跨特权级实现”混成一团。

    10 · 408 Bridge：把教材词汇翻译成真实对象

    408 抽象xv6 / Unix 里看到什么做题时第一动作
    程序 vs 进程program file vs process object先问题目描述的是静态蓝图还是动态执行实例
    系统调用fork/read/write/exec/wait 等用户可见接口先分 library API / syscall / kernel internal function
    进程资源address space、fd table、执行上下文、父子关系列 Objects / Relations，不把“进程”看成只有 PCB 名词
    阻塞wait() 等可能使进程等待条件blocked ≠ running；等待期间不应理解为一直占 CPU
    文件接口fd 作为进程到内核对象的引用入口看到 fd 先走 fd→内核对象，不先做 pathname 解析

    11 · Boundary / Anti-Pattern

    错误 1：系统调用就是普通函数调用

    不对。用户层可以用 C 函数形式调用它，但其语义包含进入内核服务边界；真正的特权级切换留到后面展开。

    错误 2：fork = 运行另一个程序

    不对。fork 解决“创建进程”，exec 才负责把当前进程的程序映像换掉。

    错误 3：wait = 父进程忙等

    不对。OS 可以让等待进程睡眠/阻塞，把 CPU 给其他 runnable 进程。

    错误 4：fd = 文件

    不对。fd 是进程局部句柄；它可以连普通文件、pipe、console 等不同内核对象。
