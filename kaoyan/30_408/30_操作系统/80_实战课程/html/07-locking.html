Locking：
锁真正保护的不是“一行代码”，而是不变量

并发最危险的不是“两个线程同时运行”这件事本身，而是它们能够看到共享状态更新的非法中间态。锁的职责是把一段必须整体成立的状态事务变成对其他执行流不可交错的原子区域；它换来 Safety，却也会制造等待、争用与并行度损失。

并发控制的起手不是“加什么锁”，而是：共享对象是什么？一次逻辑操作要维护什么不变量？哪些中间状态绝不能让另一个执行流观察？

2 · MIT 的 free-list 反例：每一行都“像对的”，组合却会丢页

把 free page 插到单链表头，逻辑操作至少包含两个相关状态变化：

r->next = freelist; freelist = r;

如果 Core A 与 Core B 在这两步之间交错，二者都可能读取旧 head，并各自发布新 head；最后一个写入会覆盖另一个，某个刚释放的 page 从 free list 消失，甚至后续产生重复分配等更严重坏状态。

关键：即使你给这两条单独的 memory access 各包一把锁，再在中间释放，也仍然错误。真正需要 atomic 的是“把新节点完整接到链表头”这个多步状态事务。

    4 · Lock Contract：Entry / Critical / Exit 不是格式，而是协议

    Entry

    原子获得准入资格；若失败，按 spin/block 协议等待。不能让两个竞争者同时“都认为自己拿到了”。

    Critical Section

    允许内部暂时破坏局部不变量，但对外不可见；释放前必须恢复所有承诺。

    Exit

    把此前的状态更新按内存序要求发布，再归还准入资格，让后来者看到一致状态。

    锁与数据并没有自动绑定。程序员必须建立“这把锁保护哪个不变量/哪些字段”的 ownership contract；拿错锁与没拿锁一样危险。

    5 · 为什么普通 if(lock==0) lock=1 不够？

    普通读 + 普通写

    两个核心都可能先读到 0，再都写 1，于是两者同时进入 critical section。问题发生在“检查 + 占有”被拆开。

    Atomic RMW

    硬件把“读取旧值 + 写入新值”作为不可分割的状态变化，只允许一个竞争者看到旧值 0。

    当前 xv6 main 的 acquire() 使用 C atomic exchange，RISC-V 上可落到 atomic swap 一类硬件操作；这建立的是准入原子性。

    版本边界：2026 Lock reading homework 页面仍展示旧式 __sync_lock_test_and_set 的替换实验，而当前 xv6 main 已使用 __atomic_exchange_n(...,__ATOMIC_ACQUIRE)。课程任务与 current main 的具体 API 不能混写；我们只抽取共同机制。

    6 · Atomicity 还不够：Memory Ordering 为什么也属于 Lock Contract？

    就算“抢锁变量”本身原子，如果编译器或 CPU 可以把 critical section 内的普通 load/store 移到 acquire 前或 release 后，另一个 CPU 仍可能看到逻辑上不允许的顺序。

    Acquireatomic ownership
    →
    Critical loads/storesmust stay inside ordering boundary
    →
    Releasepublish before unlock

    当前 xv6 main 对 acquire/release 使用 acquire/release memory-order 语义，目的就是让锁不仅解决“谁能进”，还建立跨核可观察的顺序。

    408 层面：你不需要背 C11 memory-order API，但要知道“硬件原子指令”解决准入竞争，“内存序/屏障”解决 critical data 的可见顺序；两者是不同问题。

    7 · 为什么 xv6 spinlock 还要关本地中断？

    push_off() 不是为了让其他 CPU 停止访问共享内存。其他核完全可以继续并行，所以真正跨核互斥仍靠 atomic lock。

    Local interrupt control

    避免当前 CPU 在持锁/依赖 per-CPU 状态时被中断路径重入或发生不合适的 involuntary switch，防止同核死锁与 CPU identity 竞态。

    Atomic lock

    阻止其他 CPU 同时进入同一个 critical section。这才是 SMP 共享内存互斥。

    Anti-Bridge：disable interrupts ≠ multiprocessor mutex。关掉 Core 0 的中断，不会冻结 Core 1。

    8 · Spin 还是 Block？先比较“预计等待”与“让权成本”

    等待方式优点代价 / 适用边界
    Spinlock不发生 sleep/wakeup/context-switch；短临界区多核下可能很便宜等待时烧 CPU；单核上若持锁者无法运行尤其糟；不能持有太久
    Blocking lock长等待时释放 CPU 给别人做有效工作入队、调度、唤醒、局部性重热有固定成本；某些中断/原子上下文不能 sleep

    生成性判据：不是“自旋锁高级/互斥锁高级”，而是比较预计剩余持锁时间与 block+schedule+resume 的总成本，并检查当前上下文是否允许睡眠。

    9 · Lock Granularity：最好的优化常常不是“更快的锁”，而是减少共享

    1 global free list1 lock · easy invariants
    →
    contention measuredmany failed TAS
    →
    per-CPU listsdifferent cores touch different data
    →
    rare stealingcross-list coordination only when needed

    Fall 2026 Lock Lab 的 memory allocator 部分就是这个设计训练：从一把 kmem.lock + 单一 free list，重构为 per-CPU freelists；本地 alloc/free 可以并行，只有本地空时才去别的 CPU steal。

    代价：细粒度不是免费午餐。锁越多，lock ordering、跨分区平衡、steal protocol、调试与证明成本越高。先用粗锁得到正确性，再用 measurement 找真正 contention hotspot。

    10 · Readers/Writers：互斥不是只有“所有人都串行”一种合法答案

    组合是否可并发原因
    Reader + Reader通常可以都不改变受保护状态，不互相破坏 read-only observation
    Reader + Writer不可以reader 可能看到 writer 的中间状态
    Writer + Writer不可以两个修改事务可能互相覆盖/破坏不变量

    2026 Lock Lab 新增了 read-write spinlock：允许多个 reader 并发，但最多一个 writer，且 writer 在场时不能有 reader。Lab 还要求考虑 writer starvation：一旦 writer pending，新 reader 不应无限插队。

    这和 408 读者-写者模型直接对接：Safety 只规定哪些组合非法；Fairness / writer priority 是另一层 Liveness policy，不能混成同一个问题。

    14 · Quick Attack

    Q1 · 两个线程只要访问同一变量，就一定必须互斥吗？
    不一定。多个纯读者通常可并发；关键是是否存在至少一个写者、是否有会被交错破坏的共享不变量，以及当前协议是否提供其他同步关系。
    Q2 · 把链表更新的两条语句分别各自加锁，是否足够？
    通常不够。锁要覆盖整个必须原子呈现的逻辑事务；如果中间释放，另一个执行流仍可能观察/修改非法中间态。
    Q3 · 单 CPU 上关中断能帮助临界区，为什么多 CPU 仍需要原子锁？
    关本地中断只阻止当前 CPU 的异步抢占/重入，其他 CPU 仍在执行并访问共享内存。跨核互斥必须有共享内存层面的硬件原子协议。
    Q4 · RW lock 允许 reader 并行，是否自动保证 writer 不饥饿？
    不保证。Safety 只规定 reader/writer 的合法并发组合；若新 reader 可以无限插队，writer 可能长期得不到机会。需要额外公平/优先策略。

    15 · Retrieval Check

    1. 从 free-list lost update 复原：共享对象 → 多步事务 → 非法中间态 → 不变量 → critical section。
    2. 解释 atomic RMW 与 memory ordering 分别解决什么，不把两者混成“原子指令很强”。
    3. 解释 push_off() 为什么不等于多核互斥。
    4. 给出 spin vs block 的成本判据，而不是背使用场景列表。
    5. 解释 per-CPU freelist 为什么本质上是“减少共享”而非“锁实现更快”。
    6. 把 read/write lock 的 Safety 与 writer starvation 的 Liveness 分开。

    通过标准：面对陌生并发代码，你先寻找共享状态和不变量，再决定原子区域与等待协议；不再从“这里好像要加 mutex”开始猜。
