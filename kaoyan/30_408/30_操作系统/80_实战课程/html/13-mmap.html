MIT 6.1810 mmap × OS-B04

mmap：
“文件在内存里”不是复制，而是一条长期映射契约

mmap() 最适合把虚拟内存与文件系统真正焊在一起：系统先只记录一段 VMA——“这个虚拟范围属于哪个 file、什么权限、什么共享语义”；第一次访问才 Page Fault，把对应 file offset 的内容装进物理页并建立 PTE。于是 VMA、PTE、Frame、File Reference 四层生命周期第一次同时出现。

1 · Mother Question

为什么 mmap() 成功返回，并不意味着文件内容已经读进 RAM？
mmap()record VMA
→
No PTE yetlazy promise
→
First touchpage fault
→
file offsetread backing data
→
Frame + PTEresident mapping

核心：VMA 说“这段地址应该代表什么”；PTE 说“这一页现在怎样翻译”；Frame 说“数据此刻住哪里”。三层不能压成“mmap 就分配内存”。

2 · VMA 是 Region Contract，不是 Page Table

Region

start / length：哪些 VA 属于这份映射。

Access Semantics

PROT_READ/WRITE；本次 load/store 是否在逻辑上允许。

Backing Object

file reference + file offset；fault 时从哪里取得内容，unmap 时怎样处理共享修改。

VMA exists ≠ page resident。一个 1 GB mapping 可以只实际触碰几页；lazy fault 正是为了不为未使用范围支付 RAM 和 I/O。

3 · Interactive First-Touch Trace

    4 · File Reference 为什么必须独立于 fd 生命周期？

    用户可以：

    fd = open("x", ...); p = mmap(..., fd, ...); close(fd); use p; // mapping still must know its backing file

    因此 VMA 不能只记整数 fd；它要持有对内核 file object 的独立引用。Lab 提示使用 filedup()，完整 unmap/exit 时再归还引用。

    这和 Lesson11 的 fd → open file → inode 生命周期完全一致：fd 是入口，VMA 是另一个长期引用者。

    5 · Page Fault 怎样把 VA 翻译成 file offset？

    page_va = PGROUNDDOWN(fault_va) relative = page_va - vma.start file_offset = vma.file_offset + relative allocate frame read file[file_offset ...] map page_va → frame with VMA permissions retry instruction

    这是 OS-B04 的接口：VM 输出 faulting VA + region offset，File 层接收 file object + logical byte offset，I/O 完成后 VM 再把 Frame 变成 PTE mapping。

    6 · MAP_SHARED vs MAP_PRIVATE：别只背“写不写回”

    MAP_SHARED

    映射修改属于共享 file-backed state；lab 要求 dirty modification 在 munmap/exit 时写回文件。完整系统还要解决多个 mapping 与 read/write 的一致性。

    MAP_PRIVATE

    写入不能修改 backing file。真实系统常通过 COW 建立私有视图；教学 lab 只要求达到可观察语义，不必把所有共享物理页优化做完。

    物理页是否共享 ≠ MAP_SHARED 语义是否成立。旧 lab 明确允许两个 MAP_SHARED mapping 暂时不共享同一 physical page；语义层仍要求共享修改最终回到 file。实现优化与 API 语义是两层。

    8 · fork / exit 又把生命周期接回来

    事件必须复制/继承什么不能忘什么
    forkchild 获得相同 VMA metadata 和 backing file references增加 file refs；物理页是否立即共享是另一层实现选择
    exit像 munmap 一样 teardown 每个 VMAMAP_SHARED 写回、PTE/frame 清理、file ref 归还

    这说明 Process、VM、File 三个 Owner 真正在生命周期事件上发生交接，而不是靠“mmap 属于内存管理”一句话就能解释完。

    9 · Double Caching：为什么同一文件数据可能在 Buffer Cache 和 mmap Frame 各有一份？

    教学实现通常 fault 时新分配 page，再通过 readi() 从文件读取；底层文件读取本身又经过 buffer cache，于是同一数据可能同时存在 FS buffer 和 user-mapped frame。

    旧 mmap lab 把“统一 buffer/page cache、让 read/write 与 mmap 自动共享同一物理页”列为 Optional Challenge。这是很好的工程方向，但不应偷偷假设基础 lab 已拥有现代统一页缓存。

    11 · Quick Attack

    Q1 · mmap 返回后 PTE 一定已经存在吗？
    不一定。该 lab 的核心就是先建立 VMA，第一次访问再通过 page fault lazy 建 PTE。
    Q2 · close(fd) 后 mmap 是否必须立刻失效？
    不应。VMA 持有自己的 backing file reference；fd 只是创建 mapping 时的入口。
    Q3 · 两个 MAP_SHARED mapping 若使用两个不同物理页，语义一定错误吗？
    在教学 lab 的简化测试范围内不一定；共享语义主要通过 writeback 体现。完整统一一致性模型会更复杂，这正是 optional unified cache 的价值。
