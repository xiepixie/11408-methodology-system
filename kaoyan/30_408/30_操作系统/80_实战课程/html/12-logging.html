Logging：
一次操作跨多个磁盘块，崩溃时怎样不剩“半个世界”？

文件创建、写入、unlink 都可能同时修改 bitmap、inode、directory/data block。若电源在中间消失，磁盘可能留下彼此矛盾的持久状态。xv6 的 redo log 用一个非常干净的原则解决它：先把所有新版本写到 log；只有 commit record/header 落盘后，这组修改才被允许在重启时重放。

1 · Mother Question

如果 create() 要改 3 个持久块，而机器在第 2 个 home write 后掉电，重启时怎样知道“这个操作到底算成功还是没发生”？

真正的坏状态不是“少写一个字节”，而是多个持久结构之间的不变量被撕裂：directory 已指向 inode，但 inode 未初始化；bitmap 说块已占用，但没有对象引用它；或反过来两个对象认为自己拥有同一块。

2 · Crash Consistency：先定义合法持久状态

Atomicity

一组必须一起生效的更新，重启后不能只剩任意子集。

Consistency

inode、bitmap、directory、data mapping 等关系满足文件系统不变量。

Durability

一旦跨过系统承诺的持久边界，崩溃恢复后仍必须存在。它与“write() 返回”不是天然同义词。

当前 log.c 自己把 write_head() 注释为“true point at which the current transaction commits”。这句话的含义是：在它之前，重启可以忽略未提交 log；在它之后，即使 home blocks 只安装了一部分，recovery 也有足够信息把全部 committed blocks 重放到一致的新状态。

5 · 为什么 redo 可以在“安装一半后又崩一次”仍安全？

recovery 看到非空 commit header 时，会把 log 中的 committed block image 再复制到各自 home location。把同一个最终 block image 写两次，结果仍是同一个 image，因此这种 replay 是幂等的：

home[A] ← log[A] home[B] ← log[B] ... crash ... reboot → replay A,B,C again → same committed state

这就是为什么 commit point 必须在“所有 log data 已经可重放”之后，而 clear log 必须在 home install 完成之后。

6 · log_write() 不等于立刻写 home block

当前 xv6 FS 修改一个 cached block 后调用 log_write(b)，它主要做两件事：

  1. 把 home block number 记入内存 log header（同一 transaction 中重复写同一 block 会吸收/去重）；
  2. pin buffer，防止 transaction commit 前 cache 把它复用掉。

真正的 on-disk log 写发生在 commit() → write_log()。

因此：log_write() 这个名字不能理解成“现在已经 durable”。函数名不是持久性边界。

7 · begin_op / end_op 为什么也是正确性机制？

xv6 允许多个 FS system calls 并发参与一批 log transaction，但只在 outstanding == 0 时 commit。这避免 commit 把某个仍在执行、只完成了一半的 system call 的 block updates 当成已提交事务。

begin_op()

若正在 commit 或预留空间可能耗尽 log，则 sleep；否则增加 outstanding。

end_op()

减少 outstanding；最后一个结束者触发 commit。其他 begin_op waiter 在空间/commit 状态变化后被 wake。

这把 Logging 和 Lesson08 的 Wait/Wakeup 又接起来了：log capacity 也是一个 predicate，begin_op 会因“现在安全空间不够”进入等待。

8 · 为什么 log 有容量上限？

每个 transaction 需要保存“所有可能被本轮 FS operations 修改的 block images”。若系统允许无限 outstanding operations，log 可能装不下。于是 xv6 用 MAXOPBLOCKS 做保守 reservation：

if (log.lh.n + (outstanding + 1) * MAXOPBLOCKS > LOGBLOCKS) sleep(...)

这不是性能小技巧，而是 Safety：必须保证已允许进入 transaction 的 operations 在最坏情况下也能把所有修改写入 log，不能执行到一半才发现 journal 没空间。

9 · 2026 Logging Homework：为什么 echo hi > f 会 log 多个块？

Homework 要求在 writei() 的 log_write 前打印 block 信息，然后观察一个看似简单的 shell 命令触发多次 log write。课程要你发现：高层“写一个文件”并不是只改 file data；目录、inode、长度、block mapping 等持久元数据也可能一起变化。

学习动作：不要背官方输出里的 block number。给每次 log write 标上“它属于 data / inode / directory / bitmap 中哪一种不变量”，再解释为什么它必须与其他块原子地提交。

10 · Logging ≠ fsck ≠ write return ≠ fsync

概念解决什么
Journal / WAL / redo log正常运行时维护事务信息，让 crash recovery 能恢复到合法 committed state
fsck-style scan重启后扫描全盘结构、发现并修复不一致；通常恢复成本高
write() returnAPI 操作已按该系统调用语义完成；不自动等于数据已越过所有持久缓存层
fsync() / flush boundary更强的持久性承诺；具体保证依系统/设备协议

11 · Quick Attack

Q1 · log blocks 都写完了，但 commit header 还没写，崩溃后是否应该 replay？
不应该把它当 committed transaction。commit record/header 尚未建立，重启应把这批未提交 log 当作无效；旧 home state 仍是合法基线。
Q2 · commit header 已写，home blocks 只安装一半后崩溃怎么办？
recovery 再 replay 全部 committed log blocks。已安装的块被再写一次没有问题，未安装的块得到补齐。
Q3 · 为什么不能在还有一个 FS syscall outstanding 时随便 commit？
那个 syscall 的多块更新可能只记录了一部分；commit 会把“半个逻辑操作”升级成可恢复持久状态，破坏 syscall-level atomicity。
