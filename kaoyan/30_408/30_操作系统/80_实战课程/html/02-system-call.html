System Call：
一次受控的控制权转移

这一页只追一件事：用户态的 write() 怎样安全地进入内核、找到 sys_write()，再回到原用户程序。关键不是背函数名，而是把 ISA 硬件最小动作 与 xv6 软件补全动作 分开。你会看到一个非常反直觉、也非常重要的事实：在 RISC-V/xv6 里，ecall 发生后 CPU 已经进入 S-mode，但此刻仍在使用用户页表和用户寄存器；内核栈与内核页表都是随后由 trampoline 软件切换的。

1 · Mother Question

如果用户程序不能执行特权操作，它怎样请求内核替自己做事，又怎样保证用户不能趁机在 S-mode 任意执行？

保护边界同时要求两件看似矛盾的事：用户必须能够主动“敲门”，但不能决定门后从哪里开始执行。

User requestwrite(fd, buf, n)
→
Trusted entryecall + stvec
→
Save / switchtrapframe + stack + satp
→
Dispatcha7 → syscalls[]
→
Returna0 + sret

母模型：Request → Trusted Entry → Preserve User State → Establish Kernel Environment → Dispatch Service → Prepare Resume → Return。其中“Trusted Entry”的最小硬件动作与“建立完整内核运行环境”的软件动作必须分层。

3 · ABI：系统调用号和参数到底放哪？

xv6 的 RISC-V 用户 stub 由 user/usys.pl 生成。核心只做三件事：把服务号放入 a7，执行 ecall，返回。

write(fd, buf, n) RISC-V calling convention / xv6 syscall ABI: a0 = fd a1 = buf a2 = n a7 = SYS_write user stub: li a7, SYS_write ecall ret
a0arg0 / return
a1arg1
a2arg2
a7syscall number

为什么 service number 不是“内核函数地址”？因为用户若能任意指定内核入口地址，就可能绕开统一校验。受限编号 + 内核分发表把“允许请求哪些服务”变成可控接口。

4 · Interactive Trace：从 write() 到 sret

    5 · 为什么 trampoline 必须存在？

    刚执行完 ecall 时，CPU 已在 S-mode，但仍然挂着用户页表。那它怎样执行切换页表之前的第一小段内核代码？

    问题

    此时普通 kernel text 并不在用户页表中。如果硬件只是把 PC 跳到一个仅在 kernel page table 可见的地址，第一条指令就无法取到。

    xv6 的答案

    把 trampoline 那一页以相同虚拟地址映射进用户页表和内核页表。于是 uservec 可以在旧页表下开始执行，随后切 satp，PC 仍然落在同一虚拟地址的 trampoline 代码上。

    U page tableTRAMPOLINE 可见
    →
    uservecsave regs
    →
    csrw satp切 kernel PT
    →
    same VA仍是 trampoline
    →
    usertrap()进入 C kernel

    这也是一个 Bridge：“特权级已经切换”与“地址翻译环境已经切换”是两条独立状态轴。不要把 user/kernel mode 与 page-table root 绑成一件事。

    6 · trapframe：为什么不是“把所有寄存器自动压到内核栈”？

    进入时

    • uservec 必须保住用户通用寄存器，否则 kernel C 会覆盖它们。
    • 每个进程有自己的 trapframe 内存区，但映射到相同的 TRAPFRAME 虚拟地址。
    • sscratch 提供一个 supervisor-only 的临时落脚点，让入口代码能先腾出 a0。

    返回时

    • 内核先准备好返回所需的 sstatus、sepc 与下次 trap 所需元数据。
    • userret 切回用户页表并恢复寄存器。
    • 最后 sret 依据已准备好的状态回到 U-mode 与用户 PC。

    更稳的定义：Trap Frame 是“为了恢复被打断执行而保存的体系结构/软件状态记录”。它可以位于内核栈，也可以像 xv6 一样使用专门的每进程内存页；位置是实现选择，不是定义本身。

    7 · usertrap()：同一个入口为什么能处理三类事件？

    所有来自 user space 的 trap 先进入同一条低级入口，但到了 usertrap() 后必须看 scause 分流。统一的是入口骨架，不统一的是事件来源与恢复语义。

    事件来源xv6 入口后的关键分支恢复语义
    System call用户主动执行 ecall，同步scause == 8 → EPC + 4 → syscall()服务完成后继续 ecall 后一条用户指令
    Device / timer interrupt外部/时钟，异步devintr()；timer 可能进一步 yield()恢复被打断执行；是否调度是额外决策
    Page fault / exception当前指令触发，同步尝试 vmfault()，失败则标记进程终止可修复 fault 通常要让原指令获得再次执行机会

    注意 RISC-V 细节：ecall 的 sepc 指向 ecall 本身；xv6 在软件里把保存的 EPC 加 4，才得到“系统调用返回后继续下一条指令”的语义。不要把“逻辑返回到下一条”误写成“所有硬件都会自动保存 PC+4”。

    8 · syscall()：受限编号怎样变成内核函数？

    trapframe->a7service number
    →
    bounds / exists合法编号？
    →
    syscalls[num]函数表
    →
    sys_write()具体服务
    →
    trapframe->a0return value

    当前 xv6 kernel/syscall.c 从 p->trapframe->a7 读取系统调用号；参数获取函数从保存的 a0...a5 读取，返回值写回 trapframe 的 a0。这解释了一个常见疑问：进入 C 内核代码后，为什么不能“直接读此刻 CPU 的 a7”？因为通用寄存器已经被入口代码拿来做自己的工作，用户原值应该从保存现场读取。

    参数地址再过一层：如果参数是用户指针，拿到一个数值地址不等于内核可以直接无条件解引用。xv6 的 copyin/copyout/copyinstr 路径承担跨地址空间与合法性边界的一部分。

    9 · Mode Switch ≠ Context Switch

    System call fast path

    同一个进程：U-mode → S-mode → 执行内核服务 → U-mode。可能切换栈和当前页表，但没有因此换成另一个进程。

    真正的 context switch

    只有当前执行实体阻塞、被抢占或调度器选择了别的实体时，才需要保存当前调度上下文并恢复另一个实体。跨进程时通常还伴随地址空间切换；同进程线程切换则未必。

    最稳判据：不要用“有没有换内核栈 / 页表”判断 context switch；要看CPU 之后代表哪个调度实体继续执行。xv6 的系统调用入口本身就证明了：页表可以切到 kernel page table，而进程身份完全没换。

    12 · 408 Bridge：把考试语言落到真实状态

    408 词在 xv6 里看什么第一动作
    系统调用a7 + ecall + trusted trap path + syscalls[]先分“用户请求”与“内核实际执行”，再追受控入口
    用户态 / 内核态RISC-V U/S privilege state只把它当 CPU 权限轴，不和 Ready/Running/Blocked 混

    模式切换U↔S；xv6 软件还会切 stack/satp不要由 stack/page-table 是否变化反推是否 context switch
    进程切换scheduler/swtch 恢复不同调度实体看下一段 CPU 时间到底代表谁执行

    13 · Quick Attack：你能不能挡住这些错觉？

    Q1 · 执行 ecall 后，xv6 是否已经在使用 kernel page table？
    没有。CPU 已经进入 S-mode 并跳到 stvec，但 satp 仍是用户页表；uservec 稍后才在软件中切换页表。
    Q2 · 系统调用一定发生进程上下文切换吗？
    不一定。快速系统调用可以始终代表同一进程执行，只经历 user↔kernel privilege transition。只有阻塞、抢占或其他调度原因让 CPU 改为代表另一个实体执行时，才发生相应 context switch。
    Q3 · RISC-V ecall 会不会自动把所有通用寄存器压到内核栈？
    不会。xv6 的 uservec 软件把用户寄存器保存到 trapframe，并在随后建立 kernel stack / kernel page table 环境。
    Q4 · 为什么 xv6 system call 返回时能继续 ecall 后一条指令？
    RISC-V 的 sepc 在该异常上指向 ecall 本身；xv6 在 usertrap() 里把保存的 epc 加 4，返回前再写回 sepc。

    3. 为什么 trampoline 必须同时映射在 user/kernel page table 的相同虚拟地址？
    4. 为什么 trapframe 是“恢复协议对象”，而不是“内核栈上的固定结构”这个定义？
