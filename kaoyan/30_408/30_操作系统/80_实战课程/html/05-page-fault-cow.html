Page Fault → COW：
把“失败路径”变成可编程机制

Page Fault 最值得学的地方，不是“缺页就去磁盘”。真正强大的思想是：先让硬件阻止当前访问，再让内核根据 fault 原因修改映射，最后重新执行那条指令。这让 lazy allocation、Copy-on-Write、demand paging、mmap 都可以建立在同一条慢路径上。

2 · Minimum Model：只追 6 个状态

Faulting VA

哪一个虚拟地址导致访问失败。RISC-V page fault 时通常由 stval 提供。

Access Type

取指、读还是写。它决定应该检查 X/R/W 哪一种权限以及 fault 分类。

Saved PC

哪条指令需要恢复。可修复 fault 的关键是不丢失明确 retry point。

PTE State

映射是否存在、权限是什么、是否带 COW 等软件语义。

Physical Frame

真正存放数据的物理页。COW 的核心变化发生在“谁指向哪个 frame”。

Reference / Owner

这个 frame 还有哪些有效映射要求它继续存活；最后一个引用消失前不能回收。

4 · 最关键边界：Page Fault ≠ 一定阻塞

Fast Repair · 纯内存内修复

fault → validate → kalloc / copy / zero → edit PTE → return → retry same instruction

典型：lazy demand-zero、COW split。若内存可立即取得，当前 task 可以一直在自己的 kernel path 中完成，不要求调度别人。

Slow Repair · 需要外部完成

fault → validate → submit disk/file I/O → Blocked → scheduler → interrupt/completion → Ready → Running → finish mapping → retry

典型：swap-in、真正需要磁盘 page-in、dirty victim write-back。此时才出现等待和调度链。

408 的“缺页中断后进程阻塞”通常来自经典请求分页题设：题目默认所需页需要从外存调入。在完整系统模型中，必须先问“这次 repair 是否需要等待外部事件”。

6 · Lazy Allocation：当前 xv6 main 已经在用 Page Fault 做“延迟付款”

当前 xv6 main 已经包含一个很适合作为 COW 前置模型的 vmfault()：进程可以先扩大逻辑地址空间，而不立即为每一页分配物理内存；第一次真正访问时，fault path 再分配、清零、建立 PTE。

Lazy 的本质：不是“免费”，而是把 allocate + initialize + map 从申请时搬到第一次真正使用时。若一部分申请最终从未访问，这些成本就永远不必支付。

7 · 一个容易漏掉的入口：copyout() 为什么也要理解虚拟内存？

如果页还没映射，而 kernel 正准备把系统调用结果写进 user buffer，会发生 user page fault 吗？

不一定。当前 xv6 的 copyout() 是 kernel helper：它显式拿 user page table 做 walkaddr()，再通过 kernel 对物理内存的映射完成复制。若目标 user VA 尚未映射，当前 main 会主动调用 vmfault() 创建 lazy page。

因此 COW lab 有一个关键完整性要求：不能只处理“用户执行 store → hardware fault”这一条路径；kernel 代表用户写 user memory 的 helper 也必须维护同一个 COW 不变量。否则系统调用可以绕过你建立的只读共享边界。

8 · 为什么 eager fork 很浪费？

当前 xv6 main 的 uvmcopy() 会遍历 parent user pages：为 child 分配新 frame，复制整页内容，再建立 child mapping。语义很直观，但它把“child 可能永远不会写这些页”当成“child 现在就必须拥有独立副本”。

Eager Copy

fork() 时支付全部复制成本；如果 child 很快 exec()，刚复制的旧地址空间会被丢弃。

Copy-on-Write

fork() 先共享物理页；只有某一方第一次写、真正要让内容分叉时才复制。

策略变换：copy now → protect + share now, copy on first write。Page Fault 在这里不只是“错误处理”，而是 deferred work 的触发器。

9 · COW 的三个不变量

Private-Semantics Invariant

父子可以暂时共享同一个 frame，但任一方完成写入后，另一方不能观察到本应私有的修改。

Permission Invariant

只有“原本可写、因 COW 临时去掉写权限”的页可以在 write fault 后恢复写。原本只读代码页仍必须拒绝写。

Lifetime Invariant

一个 frame 只要仍有有效 owner/reference 需要它，就不能回 free list；最后一个引用消失后才可释放。

这三个不变量比记函数名更重要。MIT lab 的所有代码改动——uvmcopy、fault handler、refcount、copyout——本质上都在共同维护它们。

    14 · 不给你 Lab 答案，给你调试控制器

    1. 先列页状态：fork 前/后父子 PTE 的 PA、W、COW marker、refcount 分别是什么？
    2. 先测原本只读页：代码页 write 是否仍然被拒绝？如果被“修复”为可写，COW 分类错了。
    3. 再测单次 split：child 写后，parent/child 是否指向不同 frame，内容是否只在 child 变化，旧页 ref 是否恰好减一？
    4. 再测 exit / unmap：一个共享者退出时，另一个仍能读原页吗？如果 crash，通常是 premature free。
    5. 再测重复 fork：一个 frame 被 3 个以上 page table 共享时，refcount 是否仍保持真实生命周期？
    6. 最后测 kernel write：系统调用通过 copyout() 写 COW user page 时是否也能安全 split？

    调试原则：不要从“哪行代码错了”开始。先找哪一个不变量第一次被破坏，再回到负责这个状态变化的入口。

    15 · 408 Bridge：经典请求分页与 COW 用的是同一个骨架，不是同一个原因

    408 / OS 概念真实系统状态第一动作
    缺页异常当前 access 不能按现有 page-table state 完成先找 fault reason；不要直接写“调页”
    请求分页合法页 nonresident，需要 backing store/page-in若题设要求磁盘 I/O，再推 Blocked → Ready
    COW映射存在，但 write permission 被有意撤销以维持共享验证 COW marker → split mapping → retry
    页面置换无空闲 frame 时才需要选择 victim 的 policyfault 不自动推出 replacement；先判断是否真的缺 frame
    引用计数共享 frame 的存活责任任何 unmap / split / exit 都检查 ref 生命周期

    压缩：translation → fault → classification → repair/reject → retry/terminate 是机制；FIFO/LRU 是只有“需要 victim”时才进入的 policy。

    17 · 408 Page Replacement Lab：OPT / FIFO / LRU / CLOCK 真正按状态跑一遍

    Simulator 只训练 408 的 frame-state / fault-count / victim reason。它不假装模拟完整 OS 的 page-in latency、dirty write-back 与多进程配额。

    CLOCK、NRU、改进 CLOCK：三个名字不要糊成一个

    策略主要状态选择思想
    Basic CLOCK / Second Chance访问位 A/R + 环形指针指针遇 A=1 就清 0 并跳过；遇 A=0 才淘汰。它近似“最近是否被用过”。
    NRU (Not Recently Used)通常看 (A/R, D/M) 四类周期性清 A/R 后，从较低类别优先选，例如 (0,0) 优于 (0,1)，体现“近期未访问 + clean 更便宜”。
    Enhanced / Improved CLOCKA/R + D/M + 环形扫描把 CLOCK 的圆环扫描与 dirty 成本结合；不同教材的扫描轮次细节可能不同，考试必须按题设版本执行。

    硬件支持怎样接上？408 常把 PTE 的访问位 A/R 视为“最近是否使用”的证据，把脏位 D/M 视为“淘汰是否需要写回”的证据。RISC-V Sv39 PTE 也定义 A/D 语义，但当前 xv6 main 并没有据此实现完整 swap replacement，所以这里属于 408 Policy Bridge，不是 xv6 已有功能。

    OPT 为什么也放进 simulator？OPT 需要知道未来，因此不能作为在线 OS 实现，但它给出同一引用串/页框数下的理论 fault 下界，最适合当比较基线。另一个高频边界：FIFO 可能出现 Belady anomaly（frame 更多反而 fault 更多）；理想 LRU/OPT 属于 stack-style 策略，不会出现这种容量反常。CLOCK 是近似 LRU，不要直接把 LRU 的所有数学性质无条件搬给 CLOCK。

    18 · Working Set / PFF / Thrashing：置换算法之外还有一个“系统是否装得下”的问题

    Working Set = 集合预测

    W(t,Δ) 是最近窗口内出现过的不同页面。它在问“当前局部性阶段大约需要保留哪些页”。

    PFF = 结果反馈

    缺页率过高 → 说明配额可能不足，应尝试增加 frames 或降低并发；缺页率很低 → 可能回收部分 frames。

    Thrashing = 容量失配

    活跃工作集长期超过可用 frames，系统不断 fault → evict → I/O → retry，CPU 时间被换页吞掉。

    一个很容易写错的因果链：CPU 利用率低并不自动意味着“应该再调入更多进程”。若低利用率来自大量 page fault I/O，继续提高多道程序度会扩大工作集竞争，形成颠簸正反馈。

    控制器视角：Working Set 提供“需要哪些页”的对象级估计；PFF 提供“当前 frame 配额是否够”的结果反馈。它们解决的不是同一个问题，也不能被某个更聪明的 replacement policy 完全替代。

    19 · Quick Attack

    Q1 · Page Fault 发生后，当前进程一定从 Running 变 Blocked 吗？
    不一定。COW、demand-zero 等可以完全在内存内修复，然后直接返回当前 task 并 retry；只有修复需要等待磁盘、文件 I/O 等外部完成事件时才必须阻塞。
    Q2 · fork 后发现某页 PTE_W=0，写 fault 时能不能直接认定它是 COW？
    不能。代码页可能本来就只读。COW 必须保留“原本可写、因为共享而临时只读”的软件语义；否则会把真正的 protection fault 错误修复成可写。
    Q3 · child 第一次写 COW 页以后，为什么 parent 仍能看到 fork 时的旧内容？
    fault handler 给 child 建立了独立可写 frame 并复制旧内容，parent PTE 仍指向旧 frame。共享物理实现只持续到第一次需要内容分叉。
    Q4 · 为什么只改 usertrap 的 store-fault 分支仍可能让 COW 实现不完整？
    因为 kernel 也会代表用户向 user buffer 写数据，例如 copyout。它可能显式 walk 用户页表并通过物理映射复制，不会执行那条用户 store，自然不会触发同一 user page fault；kernel helper 必须显式维护 COW 不变量。
    Q5 · COW 与共享内存 IPC 的关键语义差别是什么？
    COW 虽暂时共享物理 frame，却继续承诺每个进程的私有内存语义；一旦写入会分裂。共享内存 IPC 的目标反而是让多个进程有意观察同一共享状态。
    Q6 · Basic CLOCK 为什么只靠访问位也能近似 LRU？
    它不维护完整“最近访问时间全序”，只周期性区分“自上次检查后用过/没用过”。A=1 的页先清零并获得 second chance；只有再次绕到仍为 0 的页才优先淘汰，因此保留近期活跃页的概率更高。
    Q7 · Working Set 总和一度大于 frames，就能断言系统已经 Thrashing 吗？
    不能只凭一个瞬时快照下结论。Thrashing 强调持续的工作集容量失配与高频 fault/换入换出。工作集总需求超过可用内存是强风险信号，还要结合持续时间、PFF 和实际 I/O 行为。
    Q8 · 页框数增加后，缺页数是否一定不会增加？
    不是对所有算法都成立。FIFO 可能出现 Belady anomaly；理想 LRU/OPT 的驻留集合具有 stack property，容量增加时缺页数不会增加。不要把这个结论无条件套给任意近似算法。

    21 · Retrieval Check

    1. 关闭页面后完整复原：store → page fault → classify COW → split → update PTE/refcount → retry。
    2. 解释为什么 Page Fault 不等于磁盘 I/O，也不等于 context switch。
    3. 解释为什么 PTE_W=0 不能单独作为 COW 判据。
    4. 从“共享 frame 的生命周期”推导为什么必须 refcount，而不是背“COW 要计数”。
    5. 解释 copyout() 为什么可能绕过 user store-fault path，以及因此必须维护什么不变量。
    6. 给出经典请求分页与 COW 的共同骨架，以及它们在 repair reason 上的差异。
    7. 对任意引用串手算 OPT/FIFO/LRU/CLOCK：每一步先写 frame state，再写 hit/fault，再说明 victim 为什么被选；能用 OPT 作为理论下界比较。
    8. 解释 Belady anomaly 为什么能出现在 FIFO，却不能据此推翻“更多内存通常更有利”的一般直觉；准确说出 stack algorithm 的边界。
    9. 明确区分 Basic CLOCK、NRU 与改进 CLOCK；看到 A/R、D/M 位时先确认题设到底定义哪一种扫描规则。
    10. 用 W(t,Δ) 算一个工作集，并解释 PFF 为什么是“反馈配额”而不是“预测页面集合”。

    通过标准：你既能从三个 COW 不变量重新推导“共享映射、写保护、fault split、refcount、copyout 完整性”，也能把 408 请求分页题拆成 fault → free frame? → replacement? → dirty? → page-in → map → retry，不会被 xv6 没有 swap 的实现边界带偏。
