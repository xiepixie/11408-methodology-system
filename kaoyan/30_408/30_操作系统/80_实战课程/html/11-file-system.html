File System：
一个“文件”其实横跨四层身份

文件系统真正难的不是背 inode 字段，而是知道题目此刻追踪的到底是：名字、打开实例、持久对象，还是数据块。只要把这四层拆开，hard link、unlink-while-open、fork 后共享 offset、inode 索引和 pathname lookup 就会从一堆规则变成同一个对象图。

1 · Mother Question

为什么 unlink("x") 之后，一个早就 open("x") 得到的 fd 仍然可以继续读写？
Namedirectory entry
→
inodepersistent object identity
←
Open Fileoffset + mode + ref
←
fdprocess-local handle

核心：unlink 删除的是一条 name→object 边；fd 已经沿另一条运行时引用链到达 inode，所以名字消失不等于对象立即消失。

2 · 四层对象不要再混

Namespace / Directory Entry

名字属于目录。经典 xv6 dirent 保存 name → inode number。

Persistent Object / inode

身份、size、type、nlink、数据定位；inode 不是文件名。

Open File Object

一次打开实例，保存 offset、readable/writable、引用计数，并指向 inode/pipe/device。

fd

某个进程 fd table 中的小整数入口，本身不是 inode、也不是磁盘位置。

3 · Pathname 与 fd 是两条不同入口

名字入口

/a/b/c → root/cwd → lookup "a" → directory inode → lookup "b" → ... → target inode

每一级可能涉及目录 inode 和目录数据块；磁盘 I/O 次数必须根据 cache 假设逐项数。

打开引用入口

fd=3 → p->ofile[3] → struct file → offset + inode → read/write

已有 fd 时不需要重新 pathname lookup。408 题先判断入口是哪一条。

4 · 独立 open、dup、fork：offset 到底共享吗？

来源fd 表项Open File / OFDoffset
两次独立 open()两个句柄通常两个打开对象独立
dup()新增 fd同一打开对象共享
fork()父子各有 fd table entryxv6 用 filedup() 增加同一 file object 引用共享同一 file object 的 offset

fd 数字相同/不同都不能直接推出 offset 是否共享。真正的问题是：这些 fd 是否指向同一个打开实例。

5 · unlink-while-open 生命周期

name "x"nlink=1
→
inode Xdata still exists
←
file objectopen ref
←
fd=3

unlink("x") 后，name 边消失、nlink 递减；但打开引用仍使对象存活。只有“无持久名字 + 无活引用”时，inode/data blocks 才具备最终回收资格。

这和 COW refcount、ZOMBIE lifecycle 是同一类思维：逻辑上“不要了”与物理上“可以 free”之间必须有明确引用/执行生命周期。

Fall 2026 FS Lab 的 symbolic-link 任务非常适合训练“名字解释层”和“对象身份层”分开；O_NOFOLLOW 则显式控制是否继续解析最后一层 symlink。

7 · 408 Mixed Index Calculator：最大文件大小不是背公式，是逐层扩地址空间

K = floor(B / a) // 一个间接块能放多少块地址 Nmax = d + s·K + q·K² + t·K³ // 最大可寻址数据块数 Size_max = Nmax · B // 最大可寻址文件数据大小

公式有前提：这里只算“索引结构能寻址多少数据块”。题目若另外给 inode 的 file-size 字段位宽、磁盘总容量或其他限制，最终最大文件还要取这些上界中的最小值。

8 · I/O 次数：层数告诉你“可能多读几个索引块”，缓存条件决定最终答案

数据块落点inode 已在内存、索引块/数据块均未缓存时为什么
Direct1 次inode 已给出 data block number，只读数据块
Single indirect2 次1 个索引块 + 1 个数据块
Double indirect3 次2 层索引块 + 数据块
Triple indirect4 次3 层索引块 + 数据块

不要见“二级间接”就条件反射答 3 次。先写假设：inode 是否已在内存？相关索引块是否 cache hit？目标数据块是否已在 page/buffer cache？题目若从 pathname 开始，还要另算目录查找。

9 · xv6 Large File Lab 是 408 通用公式的一个特例

Fall 2026 Large File Lab 使用的是很具体的 inode 布局：把 base xv6 的一个 direct slot 改成 double-indirect，得到 11 direct + 1 single + 1 double。若 BSIZE=1024、块地址 4B，则 K=256：

11 direct + 1 × 256 single-indirect + 1 × 256² double-indirect = 65,803 data blocks

桥接动作：xv6 帮你看真实 bmap() 怎样逐级取得 block number；408 再把布局参数抽象成 d/s/q/t/B/a。不要反过来把 xv6 的 11+1+1 当成所有 UNIX inode 的固定格式。

10 · Buffer Cache：为什么“一块磁盘块在内存中只能有一个 canonical buffer”很重要？

xv6 bio.c 维持一个关键不变量：同一 (dev, blockno) 同时只由一个 cache buffer 代表。否则两个线程可能各自修改同一个磁盘块的不同副本，最后谁写回都可能覆盖另一份更新。

bcache.lock

保护“缓存里有哪些 block→buffer 绑定”和 refcount/replacement metadata。

b->lock

保护具体一个 buffer 的内容，让调用者得到锁住的 canonical block image。

MIT 2026 FS homework 的“让 a 的内容被 b 覆盖”反例，本质上就是在攻击 allocation/cache/object-identity 不变量；做这种题不要猜代码行，先问是哪种唯一性被破坏。

12 · Quick Attack

Q1 · unlink 后 nlink=0，是否一定立刻释放 data blocks？
不一定。仍有打开引用时对象必须继续存活；最终回收要等持久名字和活引用都消失。
Q2 · fork 后父子 fd=3 是否共享 offset？
在 xv6/Unix 的 fork 语义中，对应 fd 引用同一打开 file object，因此共享其 offset；关键不是数字 3，而是 underlying open object。
Q3 · 二级间接访问一定要 3 次磁盘 I/O 吗？
只有在 inode 已在内存且两级索引块都未缓存、数据块也未缓存的特定口径下才是 3 次。题设缓存条件会改变次数。
Q4 · 块大小 4KiB、块地址 4B 时，一个间接块能放多少地址？
K=4096/4=1024 个地址项。二级间接的一根 inode 指针因此可覆盖 1024² 个数据块，三级可覆盖 1024³ 个数据块。
Q5 · 已知索引结构能寻址 8GiB，就能断言最大文件一定是 8GiB 吗？
不能。还要检查题目是否给了更小的 file-size 字段位宽、文件系统/磁盘容量等独立上界；最终限制取最先撞到的那个。

13 · Retrieval Check

  1. 从 pathname 和 fd 两个入口分别走到 inode。
  2. 解释 inode 为什么不能存“唯一文件名”。
  3. 用 unlink-while-open 复原 name lifetime + open-ref lifetime。
  4. 从 fork/dup/independent open 判断 offset 是否共享。
  5. 从 B/a 推出每个间接块地址数 K，再从 d+sK+qK²+tK³ 推出最大文件大小。
  6. 给一个 LBN，先减 direct 区、再减 single 区，逐层用整除/取余定位 double/triple 的每级 index。
  7. 在“inode 已在内存、索引/数据均未缓存”的口径下说出 direct/single/double/triple 的 1/2/3/4 次 I/O，并能根据 cache 条件删掉命中的访问。
  8. 解释 buffer cache one-copy invariant 为什么是并发正确性，而不只是性能。
