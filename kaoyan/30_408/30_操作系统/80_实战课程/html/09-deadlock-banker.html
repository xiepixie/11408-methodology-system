Deadlock / Banker：
“安全”不是“此刻没死锁”

MIT 6.1810 没有把 Banker 做成独立 xv6 lab，这里不硬凑。我们用 408 自建模拟器训练一个更重要的判断层次：当前请求是否能满足？分配后是否仍有安全序列？系统是否已经死锁？这三个问题分别对应不同状态和算法，不能混成“资源不够就是死锁”。

2 · Deadlock ≠ Long Wait ≠ Livelock ≠ Starvation

Deadlock

等待依赖无法自行消解，相关执行流全部失去推进可能。

Long Wait

暂时很久，但未来某个持有者仍可运行并释放资源。

Livelock

大家都在动、都在重试/退让，但整体状态没有有效推进。

Starvation

系统整体在推进，却有特定执行流长期被越过、拿不到资源。

3 · Coffman 四条件：不要背名字，要看“环为什么能闭合”

Mutual Exclusion

某些资源不能同时共享占有。

Hold and Wait

持有已有资源的同时继续等新资源。

No Preemption

系统不能安全强制夺回并恢复资源。

Circular Wait

等待依赖形成闭环。

Prevention 的生成法：任何能稳定破坏至少一个必要条件的设计都可阻断经典死锁，但通常要付利用率、并发度、回滚或模块耦合代价。

4 · “图里有环”为什么有时是充分条件、有时不是？

每类资源只有 1 个实例

Wait-for / Resource-allocation graph 出现依赖环时，没有“同类的另一个实例”从环外进入打破依赖，因此经典模型下：

Cycle ⇔ Deadlock

资源类有多个实例

图中有环只能说明存在风险。环内某个请求可能由环外释放的同类实例满足，从而让一个进程完成并继续释放资源。

Cycle ≠ universal deadlock test

5 · Safe / Unsafe / Deadlocked：三个集合必须分层

Safe存在一条保证全部完成的安全序列
⊂
All States所有合法资源分配状态

更准确的关系是：

Deadlocked ⊂ Unsafe ⊂ All allocation states

Unsafe ≠ Deadlocked。Unsafe 的含义是“基于声明的最大需求，系统已经失去保证一定能让所有进程完成的证书”。未来如果实际请求比 Max 少，它仍可能碰巧顺利结束；Banker 拒绝的是风险，而不是在宣判“现在已经死锁”。

6 · Banker 三关：Legality → Availability → Safety

关检查失败意味着什么
1 · 合法性Request_i ≤ Need_i进程请求超过自己事先声明的 Max；请求本身非法
2 · 当前充沛性Request_i ≤ AvailableInsufficient Now：现在资源不够，只能等；这不是 Unsafe 的同义词
3 · 试探后安全性临时扣 Available、加 Allocation、减 Need，再跑 Safety Test若无安全序列：Rollback 这次试探；状态被判 Unsafe

事务视角：Tentative Transition → Safety Check → Commit / Rollback。Banker 不是“算一遍矩阵”，而是在每次关键资源状态改变前做风险准入控制。

8 · Safety Algorithm：为什么 Work 只加 Allocation？

找到某个 Need_i ≤ Work 的进程时，我们“假想”它拿到剩余 Need、运行结束，再归还全部持有资源。因为借出的 Need 在模拟结束时又还回来，净增加只来自它原来已经占住的 Allocation：

Work' = (Work - Need_i) + (Need_i + Allocation_i) = Work + Allocation_i

这也是手算最强自检：Work 只会单调增加；若全部进程都完成，末态 Work 应回到系统 Total。若不对，优先检查 Available、Need 或矩阵抄错。

9 · “选哪个可推进者”会影响是否找到安全序列吗？

在标准 Safety Algorithm 中，只要当前 Need_i ≤ Work，选择它完成后 Work 会变成 Work + Allocation_i ≥ Work。资源只增不减，因此其他原本可推进者不会因为你先选了 i 而失去资格。

因此：标准模型里只要存在当前可完成者，任选一个合法者推进不会把“原本存在的安全序列”选没。这正是贪心消去可行的单调性来源。

10 · Avoidance vs Detection：Need 与 Request 是两个世界

Banker / AvoidanceDeadlock Detection
什么时候批准分配之前允许状态发展后，事后/定期检测

关键输入Need = Max - Allocation当前 Request 矩阵

最常见错题源：看见矩阵就套 Banker。先读题：它给的是“最大还会要多少”，还是“此刻正在等多少”。

11 · 单类资源公式：先过假设门，再用

只有一类同质、不可剥夺、可重用资源，进程拿齐最大需求后能完成并一次释放，若 Pi 最大需求是 mi，保证不会形成“每人都差 1”的死局所需最小总量：

R_min = 1 + Σ(m_i - 1) = Σm_i - n + 1

因为最坏可以让每个进程先占 m_i-1，再多 1 份至少能让某一个完成并释放，随后形成连锁。

Stop：出现多资源向量、Allocation/Need 矩阵、给定状态安全性时立刻回 Banker；不要拿这个标量公式绕过状态建模。

12 · Lock Ordering：真实系统为什么更常见“预防一个依赖环”而不是全局 Banker？

上一页已经看到多把锁会形成 Hold-and-Wait。工程里最常见的办法之一是给资源建立全局/局部一致的申请顺序：

Rule: acquire A before B before C → wait edges can only point “forward” → circular wait cannot close

代价：锁序必须跨模块维护，会降低 API 灵活性；因此它是 Prevention 的工程权衡，不是“死锁问题从此不存在”。

14 · Quick Attack

Q1 · Banker 判 Unsafe，是否说明现在已经 Deadlocked？
不是。Unsafe 表示基于声明的 Max 已不存在“保证全部完成”的安全序列；实际未来请求可能更少，因此系统仍可能碰巧完成。Deadlocked 是 Unsafe 的真子集。
Q2 · Request 不超过 Available，是否可以立即批准？
Banker 还必须验证 Request≤Need，并在试探分配后跑 Safety Test。当前有资源只回答“现在能给”，不回答“给完以后是否仍有安全保证”。
Q3 · 多实例资源分配图出现 cycle，是否必然死锁？
不必然。环外可能有同类实例释放后满足环内请求。单实例模型下 cycle 才是经典充要条件。
Q4 · 安全算法里为什么不是 Work += Max_i？
Need 是从 Work 临时借给进程再被归还的中间量；真正使系统可用资源净增加的是进程原先已经占住的 Allocation，所以完成后 Work'=Work+Allocation_i。
