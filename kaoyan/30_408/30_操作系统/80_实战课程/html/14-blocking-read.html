OS-I01 · Full Lifecycle

一次 blocking read() 的一生：
四条状态线终于合流

前 13 页学的是局部机制。这一页禁止再“按章节思考”。同一个 read(fd, buf, n) 会同时穿过 task/control、file reference、data residency、device/completion 四条轨迹；cache hit 和 cache miss 甚至会让同一句 syscall 走完全不同的生命史。

Canonical Owner: OS-I01Uses: syscall · fd/OFD · FS · cache · I/O · sleep/wakeup · schedulerCurrent xv6 source paths as mechanism instances预计 120–170 min

1 · Mother Question

“磁盘读完了”为什么仍然不等于 read() 已经返回用户程序？

成功条件不是某个中间模块“完成”，而是：本次 read 的接口语义已经得到合法结果，原 task 以后真正获得 CPU，从旧 syscall 内核路径继续，把 bytes/EOF/error 交付给用户态。

2 · 四条并行轨迹

Task / Control

user/kernel、Running/Blocked/Ready、scheduler。

File Reference

fd → open file → inode，current offset 与 file range。

Data / Residency

内容在 cache、device、kernel buffer 还是 user buffer。

Device / Completion

request、descriptor、DMA/PIO、completion evidence、interrupt/poll。

3 · Fast Path vs Slow Path：先切换条件

    4 · syscall entry 只是进入内核，不是换进程

    A userread(fd,...)
    →
    A kernelsame task identity
    →
    validatefd / buffer / mode

    system call → kernel mode 不自动推出 context switch。只有 A 真正因为某条件不能推进、进入 Blocked，scheduler 才必须寻找别人。

    5 · fd 决定“这次读文件的哪一段”

    fd → process fd table → open file object / OFD → inode/file object → current offset → requested file range

    如果是普通顺序 read，成功消费的实际 bytes 会推进共享 open-file offset；如果 parent/child 或 dup fd 指向同一 open object，这个状态是共享的。若是 pread，显式位置语义不同。

    6 · read(file) ≠ disk I/O

    Hit

    所需 block/page 已在可用内存 cache 中，直接进入数据交付和 offset 更新；不需要因为“文件属于磁盘”就阻塞。

    Miss

    文件层先算 LBN/block mapping，I/O 层建立 request；只有 blocking 调用且结果尚不可返回时，当前 task 才建立 wait relation。

    cache miss 也不自动等于 page replacement。是否需要 victim 还取决于 frame/buffer 可用性与具体缓存层。

    7 · 真正慢路径：request 与 task wait 是两条线

    File range → block mapping → I/O request → driver/device │ └─ A: condition unavailable → register wait → SLEEPING/BLOCKED → scheduler → B runs device completes → driver validates completion → data/cache state updated → wake A → RUNNABLE → scheduler later picks A → resume after sleep → copy/deliver bytes → offset/result update → syscall return

    submit I/O ≠ block。异步接口可以提交后先返回；blocking read 也可能 hit/EOF/error 而不睡。

    8 · Completion → Ready ≠ Running

    设备完成只是让“等待的数据条件”成立。driver 消费 completion evidence 后 wake A，使它重新 RUNNABLE；如果 CPU 此刻在跑 B，A 是否立即抢占由 scheduler/policy 决定。

    IRQ → wakeup → A user continues 中间缺了最重要的一层：调度资格恢复与实际 CPU ownership。

    9 · 返回 n 字节也不是必然

    情况read 可能结果
    普通文件到 EOF0 或此前已读取 partial bytes
    pipe/terminal可按对象语义在有部分数据时返回
    error / interrupted condition错误或 partial result，依接口约定
    cache hit不经设备慢路径直接返回数据

    请求长度 n 是上限/请求，不是“系统必须读满 n 才允许返回”的普遍承诺。

    10 · 五个容易偷换的“完成”

    完成实际含义
    device transfer complete硬件搬运结束
    driver completion processed软件确认 request outcome
    data cache ready目标内容可从内存状态交付
    task wakeA 重新 RUNNABLE
    syscall returnA 真正 Running 后完成内核路径并恢复 user

    11 · Quick Attack

    Q1 · 普通文件 read 是否一定引发设备中断？
    不一定。缓存命中时可完全绕开设备；即使有 I/O，完成发现也可以是 interrupt/polling 等不同机制。
    Q2 · wakeup(A) 后 A 是否已经“从 read 返回”？
    没有。A 只恢复 RUNNABLE；仍要等待 scheduler 选中，恢复旧 kernel context，继续完成 read，再 syscall return。
    Q3 · fork 后 parent read 100 bytes 会影响 child 吗？
    若继承 fd 指向同一 open file object/OFD，则 parent 的成功 read 会推进共享 offset，child 后续普通 read 从新位置继续。

    12 · Retrieval Check

    1. 画出四条轨迹，并说明每条的 Owner。
    2. 分别复原 cache hit 与 miss 生命周期。
    3. 指出真正发生 execution context switch 的位置，而不是把 syscall/IRQ 都算 switch。
    4. 解释 device completion、wakeup、Running、return 四个时间点。
    5. 解释 offset 在什么对象上，按什么事件推进。

    通过标准：给你任意一句“进程阻塞读取文件”，你都能先问 cache/EOF/error，再决定是否展开设备慢路径，而不是机械背“系统调用→磁盘→中断→返回”。
