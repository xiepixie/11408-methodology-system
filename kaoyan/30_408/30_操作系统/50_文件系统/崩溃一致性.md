# 崩溃一致性

> 训练定位：面对 create/write/unlink 等高层操作被拆成多次持久写、题目要求分析 crash point、fsck、journaling、commit 或 `fsync()` 时，训练逐写枚举可见状态并判断文件系统不变量是否仍成立。  
> 模型归属：[OS-06/07 文件系统与持久化方法论手册](OS-06_OS-07_文件系统与持久化_方法论手册.tex)。crash consistency、fsck、journaling/WAL 与持久边界机制由 Canonical 正文拥有；本文件只负责状态枚举、恢复路径与检查。

## 母题表示：一个高层操作会展开成多结构更新

文件系统操作往往同时修改：

- inode / object metadata；
- block / inode bitmap；
- directory entry；
- file data；
- journal / transaction metadata。

真正的问题不是“哪一块先写”，而是：**如果机器在任意两个持久写之间断电，磁盘上剩下的组合状态还能否解释成一个合法文件系统？**

## 局部规则：先列持久写集合，再谈顺序

**触发信号**：题目给 create、append、unlink、rename 等操作，并问某个 crash point 后会出现什么。

**第一动作**：先把高层操作拆成需要持久化的独立对象，例如 `inode allocation / bitmap / directory entry / data / size`；再根据题设协议排列可能写序。

**检查与退出**：如果连“这次操作到底涉及哪些独立持久结构”都没列完，就不要直接判断“崩溃后文件丢失/损坏”。

## 局部规则：每个 crash point 都重新检查不变量

**触发信号**：题目给多步磁盘写或 journal transaction。

**第一动作**：在每两个持久写之间插入一个 crash point，逐点问：目录是否引用不存在对象？bitmap 是否与实际占用矛盾？inode 是否指向未分配块？link count 是否一致？

**检查与退出**：不要只检查最终状态。Crash consistency 的难点正是中间前缀状态。

## fsck：允许先不一致，重启后全局检查修复

### 局部规则：fsck 题先找“磁盘事实之间的矛盾”

**触发信号**：题目明确采用 fsck / scan-and-repair 思路。

**第一动作**：把 inode、bitmap、directory、reference count 等持久事实互相对账，找出不可能同时成立的组合。

**检查与退出**：fsck 的目标首先是恢复结构一致性，不保证恢复到用户最期待的最近语义状态；不要把“consistent”自动等价成“最新写入都保留”。

## Journaling：先判断事务有没有达到提交边界

### 局部规则：先找 commit，再决定 replay

**触发信号**：题目给 write-ahead log / journal record / commit record / checkpoint。

**第一动作**：先判断该事务是否具有有效 commit。已提交但 home location 尚未完整更新的事务可以按协议 replay；未提交事务不能因为“日志里有一部分记录”就当成已经生效。

**检查与退出**：如果题目区分 metadata journaling、data journaling 或 ordered mode，必须按题设确认 data 与 metadata 的先后承诺，不能用一套通用顺序覆盖所有模式。

## `write()`、writeback、commit、`fsync()`：四个时点别合并

### 局部规则：问“完成”时先给完成加主语

**触发信号**：题目问“写入是否完成/是否已落盘/是否能抗崩溃”。

**第一动作**：明确它问的是：用户数据被内核接受、脏页开始/完成 writeback、journal transaction commit，还是应用要求的持久边界已经完成。

**检查与退出**：`write()` 返回通常只证明当前接口已经接受数据，不自动证明非易失介质已经持久化。

## 综合训练：create/write 中突然 crash

草稿固定按下面格式跑：

```text
高层目标：要让哪个新状态最终成立？
涉及结构：directory / inode / bitmap / data / journal ...
合法不变量：哪些引用与分配关系必须一致？
持久写序：题设允许哪些先后？
逐 crash point：当前磁盘事实是什么？
恢复协议：ignore / redo / undo / repair？
最终边界：结构一致 ≠ 最近数据一定持久
```

## 易错边界

> **Consistency ≠ Durability/Freshness。** 结构可以一致，但最近尚未跨过持久边界的数据仍可能丢失。

> **Journal commit ≠ 所有 home locations 已写完。** commit 给恢复协议提供“这笔事务应当生效”的判据，checkpoint/home write 可以随后完成。

> **`write()` return ≠ `fsync()` completion。** 两者承诺的时间边界不同。

## 最短压缩

文件系统崩溃题只记一句：**把一次操作拆成多个持久事实，然后攻击每一个前缀状态。** 恢复机制的价值，就是让这些前缀状态要么仍合法，要么能够被确定地恢复到合法状态。
