# 计组做题规则与性能工具箱

状态：工作稿。当前只保留**跨多个计组专题仍然需要统一维护的做题控制**；Booth、浮点、指令格式、流水线、Cache、TLB、DMA 等专有规则已经下沉到各自 Topic Practice，不再把 Subject Rules 写成第二本题型大全。

## 本文件负责什么

计组 Subject Rules 只回答：

> 当题目同时涉及不同表示、不同硬件层次、不同成本口径，或者还没确定该进入哪个 Topic 时，第一轮应该怎样稳定地表示和检查？

它不负责：

- 重新讲 CO-01～CO-08 的机制；
- 保存某个 Topic 的全部局部技巧；
- 维护题库录入质量门；
- 规定真题题解格式。

这些职责分别由 Canonical Handbook、同目录 Topic Practice、项目级 [`题目与心智模型双向验证协议`](../../../00_system/problem_model_validation.md) 和真题题解 QA 拥有。

一个简单的作用域判断是：**如果规则的触发信号本身就是 Booth、TLB、Cache set、DMA、PC-relative 等专有对象，它默认不属于这里。**

## 待验证

### 先锁对象、解释、单位和统计分母

**触发信号**：题目同时出现多种位宽、地址粒度、访问次数、频率、时间、命中率或吞吐率，或者一句“访问一次/执行一次”可能有多种解释。

**第一动作**：在计算前先写清四件事：当前对象是什么、按什么语义解释、单位是什么、最终比率或计数的分母是什么。

**检查与退出**：如果推导中途把“一个数组元素”换成“一次 Cache reference”，把“地址空间”换成“实际装机容量”，或把“总线时钟”换成“有效传输率”，立即退回重新统一口径。进入具体机制后，转对应 Topic Practice。

### 题设没有给出的实现条件，不自动脑补

**触发信号**：答案依赖具体 ISA、ABI、寄存器读写时序、forwarding 端点、Cache policy、DRAM geometry、总线协议或编译器行为。

**第一动作**：把会改变答案的实现条件列出来，只使用题面明确给出的条件和当前 Canonical 已声明的稳定定义。

**检查与退出**：如果唯一答案只能靠“经典五级默认……”“一般机器通常……”才能得到，先判断题面是否缺条件。不要为了让旧答案成立而把实现习惯写成普遍规律。

### 先表示状态、位置和路径，再开始算

**触发信号**：题目出现寄存器、主存、Cache、TLB、流水级、总线、DMA 等多个状态位置，或者要求追踪一个值/请求如何移动。

**第一动作**：先写 `对象当前在哪里 → 要去哪里 → 中间经过哪些状态/资源 → 什么事件使它前进`，再进入数值计算。

**检查与退出**：如果连“值现在在哪”“谁拥有这一步状态”都说不清，就不要直接套公式。定位到明确 Topic 后，使用该 Topic 的局部状态表或时间线。

### 先数事件，再给事件定价

**触发信号**：题目同时出现 miss、stall、fault、burst、write-back、DMA request、访存次数或 CPI 增量，并要求时间、带宽或平均成本。

**第一动作**：先单独得到事件数量，再分别给每类事件标成本；最后确认哪些成本互斥、哪些已被上一级成本包含、哪些可以重叠。

**检查与退出**：如果同一等待时间既算进 miss penalty 又算进流水线 stall，或一次 burst 的地址开销被按每个 beat 重复计价，说明发生重复计数。具体事件怎样产生由对应 Topic Practice 负责。

### 跨层异常或缺失，写清“谁发现、谁处理、从哪重试”

**触发信号**：题目出现 miss、fault、exception、interrupt、retry、page walk、DMA completion 等跨模块事件。

**第一动作**：写三列：`检测者 | 处理者 | 完成后从哪里继续/重试`。必要时再补“哪些状态已经提交、哪些还没有”。

**检查与退出**：如果把 TLB miss 直接写成 Page Fault，把 DREQ 直接写成 CPU interrupt，或把 forwarding ready 写成 architectural commit，说明 Owner/阶段混在一起，应回到对应 Bridge 或 Topic。

### Verification 从起手就开始，不只放在最后

**触发信号**：任何容易出现位宽、范围、符号、单位、状态合法性或数量级错误的数值/状态题。

**第一动作**：正式推导前先找一个最便宜的预期约束，例如结果范围、符号、位数、单位、守恒关系、最大/最小数量级；用它排除明显不可能的路径。

**检查与退出**：求解后再用尽量独立的方法核对，例如反算、边界样例、商余关系、地址范围、状态不变量。若“校验”只是把原计算再抄一遍，它没有提供新的错误检测信息。

### 性能比较只认完整工作量和完整时间

**触发信号**：题目比较两台机器、两种实现、不同流水深度、Cache 参数、总线方案或 I/O 方式的“快慢”。

**第一动作**：先确定工作量是否相同，再列会改变总时间的量：事件数、每个事件成本、可重叠部分和最终完成/提交点。CPU 题优先回到

$$
T_{CPU}=IC\times CPI\times T_{clk}.
$$

**检查与退出**：GHz 更高、CPI 更低、命中率更高或峰值带宽更大，都只能作为局部证据，不能单独推出完整任务更快。进入具体性能题后使用本目录的性能工具或对应 Topic Practice。

## 已否定

### “一个局部指标更好，就能直接说明整机更快”

CPI、GHz、IPC、MIPS、命中率、峰值带宽、单次 latency 都只描述部分成本。比较性能必须回到相同工作量下的完整事件链和完整时间。

### “经典教材模型可以自动补齐题面没有写的条件”

教材模型可以帮助解释，但只要不同合理实现会改变答案，相关条件就必须进入题面或明确声明采用哪一个模型。解析不能偷偷替题面做选择。

## 最短压缩

计组跨专题题先做六件事：

```text
对象与口径
-> 状态与位置
-> 路径与 Owner
-> 事件数量
-> 事件成本
-> 独立校验
```

一旦问题已经落到某个具体 Topic，就停止扩张本文件，转对应 Practice。题目是否自洽、模型是否真的被打穿、模型修改后怎样回测，统一转项目级 [`problem_model_validation.md`](../../../00_system/problem_model_validation.md)。
