# 一条指令全过程推演

> 训练定位：面对“分析一条 LOAD / STORE / ALU / BRANCH 指令从取指到完成”的综合题时，训练把局部机制放到同一条合法时间线上，并明确值何时产生、何时可用、异常发生后哪些效果还能提交。
> 模型归属：[CO-I01｜一条指令的一生](CO-I01_一条指令的一生_综合手册.tex)。完整单指令协作轨迹由 Integration 正文拥有；各局部机制仍回 CO-01～08、CO-B01 / CO-B02。本文件只训练如何组织一次完整推演。

## 母题表示：全过程题必须同时追三条线

只画 IF / ID / EX / MEM / WB 阶段不够，因为阶段名不能直接回答“值是否已经能用”或“异常后哪些副作用还合法”。更稳的表示是同时追三条线：

1. **值依赖线**：每个结果由谁产生，下一步谁需要它；
2. **时间线**：producer 何时 produced / ready，consumer 何时 need；
3. **异常与提交线**：哪一步可能失败，失败时哪些较年轻效果必须作废，最终何时允许改变软件可见状态。

这三条线共同决定一条指令是否真的走到了合法完成点。

## 局部规则：全过程题先画三条线，再填阶段名

**触发信号**：题目要求分析一条指令的完整执行过程，或同时出现 ISA 语义、数据通路、流水线、地址翻译、Cache / Memory、异常和提交中的多个模块。

**第一动作**：先写三行：

```text
Value：谁产生什么值 → 谁消费
Timing：produced → ready → need
Commit：可能失败的位置 → 已提交/未提交状态 → retry / next PC
```

再把 IF / ID / EX / MEM / WB、TLB、Cache、主存等阶段挂到这三行上，而不是反过来用阶段名代替推理。

**检查与退出**：如果某一步只能说“现在到了 MEM，所以数据已经有了”或“已经 forwarding，所以指令完成了”，说明把阶段名、ready 和 commit 混在一起。回到三条线重新标时刻。

## 第一步：先从 ISA 状态差开始

对当前指令先写最少的软件可见合同：

```text
Read Set
Derived Values
Write Set
Next PC
Memory Effect
Possible Exception
```

例如 LOAD 至少要区分：

- base register 与 displacement 生成 EA；
- EA 只是地址，不是 load value；
- translation / permission 成功后才有合法 PA；
- Cache / memory 返回后才有 data ready；
- 无异常且达到提交点后，目标寄存器才真正改变。

## 第二步：每个跨层节点写清输入和输出

一次典型 LOAD 可以按下面的交接检查：

| 节点 | 输入 | 输出 | 仍不能直接推出 |
|---|---|---|---|
| Decode / Operand Read | instruction fields、架构寄存器 | opcode、base、disp 等 | EA 已形成 |
| EA generation | base + interpreted displacement | virtual EA | 数据已经返回 |
| Translation | VA、权限/翻译状态 | 合法 PA 或 fault | Cache 一定命中 |
| Cache / Memory | PA、访问宽度、Cache state | load value ready 或 miss path | 指令已经提交 |
| Commit | 正确结果 + 无阻止提交的异常 | 架构状态更新 | — |

局部机制的内部计算不要在这里重写；需要时跳回相应 Topic。

## 局部规则：每个慢路径都写“谁发现、谁处理、从哪继续”

**触发信号**：TLB miss、Cache miss、Page Fault、exception、interrupt、memory wait 等慢路径出现在同一道全过程题中。

**第一动作**：对每个事件写：

```text
发现者：谁检测到当前条件？
处理者：谁负责把状态修好或完成服务？
继续点：完成后从哪里 retry / resume？
提交边界：哪些副作用此时仍不能出现？
```

**检查与退出**：TLB miss、Page Fault 和 Cache miss 必须分别处理；如果三者都被写成“去主存取一下再继续”，说明跨层责任已经混淆，应分别回 CO-07、X-B02 / OS-04、CO-06。

## 第三步：ready 与 commit 分开

数据已经在某条内部路径上可用，只说明消费者可能取得它，不说明软件可见状态已经更新。

例如：

```text
ALU result produced
→ forwarding path ready
→ younger instruction may consume
```

并不等于：

```text
producer architectural state committed
```

因此全过程题至少要能回答两个不同问题：

- **谁现在能拿到这个值？**
- **这个值什么时候才允许写入架构状态？**

## 四种最有价值的扰动

### LOAD → ADD

去掉数据地址翻译和数据 Cache / Memory 路径，但仍保留取指、译码、ALU 结果和提交。若模型仍机械保留 data TLB / Cache，说明没有按指令语义裁剪轨迹。

### LOAD → STORE

不再写目标通用寄存器，而要追踪内存副作用何时允许对架构可见。写策略属于 CO-06 / memory system，不由“STORE”名称自动决定。

### LOAD → BRANCH

核心输出变成 Next PC。要追踪条件何时确定、错误路径如何 flush，以及正确 PC 何时成为后续取指依据。

### Fast path → miss / fault

只改变一个节点的状态，观察 slow path 从哪里分叉、由谁修复、修复后从哪里重新进入。这样可以检验是否真的掌握 Owner 边界，而不是背一条固定流水线。

## 独立校验

全过程题结束后，用下面四问检查，不把原推导再抄一遍：

1. **Write Set**：最终真正改变的软件可见状态是否都被 ISA 允许？有没有多余写入？
2. **时间**：任何 consumer 是否早于可达的 ready 时刻使用了值？
3. **异常**：发生 fault / exception 时，较年轻副作用是否仍被错误保留？
4. **成本**：同一个 miss / wait 是否既包含在下一级服务时间，又被重复加进 stall？

## 代表题怎样保留

本问题族的回归题不需要很多，优先保留：

- 一道正常 LOAD fast path；
- 一道 load-use 或其他 ready / need 边界题；
- 一道 TLB / Cache 慢路径题；
- 一道 fault 后要求判断 retry / commit 的题。

若后续 Canonical Integration 修改，先重跑这些有区分力的代表题；出现异常再扩大检查范围。

## 压缩

全过程题先画：

```text
值依赖线
+ ready / need 时间线
+ exception / commit 线
```

再把各阶段和 Owner 挂上去。

> **阶段名只是位置标签；真正决定正确性的，是值依赖、时间合法性和提交边界。**
