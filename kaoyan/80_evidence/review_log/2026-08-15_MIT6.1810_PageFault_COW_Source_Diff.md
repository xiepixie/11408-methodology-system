## 2. 外部 Source 暴露的 Canonical 问题

### 2.1 “Page Fault = 阻塞链”过度泛化

OS-04 旧文把缺页处理整体描述为阻塞、I/O、wakeup、retry 链。这个模型适用于经典 request paging / swap 等需要外部 I/O 的慢路径，但不能覆盖：

- demand-zero；
- COW split；
- 其他可以纯内存修复的 fault。

这些路径可以在当前 task 的 kernel path 内完成修复后直接 retry，不要求 Blocked，也不要求 context switch。

**Canonical Update**：把统一模型改成：

```text
Page Fault
→ classify
→ in-memory repair / I/O repair / reject
→ retry / block+resume / terminate
```

并明确 `Page Fault != disk I/O`、`Page Fault != necessarily Blocked`。

### 2.2 `PTE_W=0` 不能作为 COW 判据

Fall 2026 COW lab 明确要求：只对 fork 前原本可写的页面建立 COW；原本只读的 text 页面保持只读，write 必须被拒绝。

因此 COW handler 必须保存/恢复“为什么只读”的软件语义，而不能使用：

```text
W=0 → COW → make writable
```

作为判断。

**Canonical Update**：OS-04 COW 段增加 `RO != COW` 与 software COW marker 边界。

### 2.3 Frame 生命周期需要被解释成 owner/reference，不是“进程数”

COW 后一个 physical frame 可以被多个 PTE 共享；最后一个 reference 消失前不可回 free list。

**Canonical Update**：强调 refcount 表达 frame 的存活责任，不机械等于进程数量；unmap / split / exit 都是可能改变引用的事件。

### 2.4 COW 完整性不仅是 user store fault

当前 xv6 `copyout()` 在 kernel 中显式 walk user page table 并通过物理映射复制数据。Fall 2026 COW lab 因而要求 `copyout()` 同样维护 COW。

结论：一个安全/共享不变量必须覆盖所有写入入口，不能只修“最显眼的硬件 fault path”。

此结论用于 Derived HTML 的 Lab 调试模型；Canonical OS-04 当前只补 COW 生命周期与 fault 分类，不把 xv6-specific `copyout()` 提升为通用 OS 定义。

## 3. Page Table Lesson 回归发现

复审 Lesson 04 时同时修正两项架构边界：

1. Sv39 架构地址是 39-bit canonical VA，高位需要按 bit 38 符号扩展；当前 xv6 自己把 `MAXVA` 限制在低于 `2^38`，不是“Sv39 最大地址就是 `2^39-1`”。
2. Sv39 任一级 PTE 都可以是 leaf；L0/L1/L2 分别可表示 4 KiB / 2 MiB / 1 GiB 页面。base xv6 普通 `walk()` 的 4 KiB 路径不能被提升成 ISA 限制；2026 superpage lab 正是在扩展 L1 leaf。

这些属于 HTML 具体教学页的 Architecture Boundary 修正；稳定 X-B02 已经保留“具体 ISA page-walk 细节回 ISA Owner”的边界，因此本轮对 X-B02 **No Update**。
