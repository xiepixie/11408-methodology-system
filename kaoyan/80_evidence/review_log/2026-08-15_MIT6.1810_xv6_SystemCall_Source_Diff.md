## 1. 为什么触发 Canonical Update

在制作 `30_操作系统/80_实战课程/html/02-system-call.html` 时，用当前 xv6-RISC-V 入口代码逐步核对已有系统调用/特权边界模型，发现 Canonical X-B01 与 OS-01/02 中有若干把某类传统 x86 入口行为泛化成“所有 trap/mode switch 都如此”的表述。

这不是新增知识偏好，而是会直接导致错误推理的事实边界，因此满足稳定 Handbook 的更新条件。

### 2.2 当前 xv6-RISC-V system call entry

当前 `kernel/trampoline.S:uservec` 源码明确表明：

1. trap 从 user space 进入时已经处于 supervisor mode，**但仍使用 user page table**；
2. `uservec` 软件把用户通用寄存器保存到 per-process trapframe；
3. `uservec` 从 trapframe 取 `kernel_sp`、`kernel_satp`、`usertrap` 地址；
4. **软件**写 `satp` 切 kernel page table，再进入 `usertrap()`。

当前 `kernel/trap.c:usertrap()` 明确表明：

- U-mode ecall 的 `scause == 8`；
- `sepc` 指向 `ecall` 指令本身；
- xv6 软件执行 `p->trapframe->epc += 4`，把逻辑返回点推进到下一条用户指令。

当前 `kernel/syscall.c` 明确表明：

- syscall number 从 `p->trapframe->a7` 读取；
- 参数由保存的 `a0...a5` 取得；
- `syscalls[num]` 完成受限分发；
- 返回值写回 `p->trapframe->a0`。

## 3. 原 Canonical 中需要纠正的地方

### X-B01

原文曾把以下动作写成通用“硬件责任”：

- trap 自动切到内核栈；
- PC/PSW 自动压入内核栈；
- Trap Frame 定义为“保存在内核栈上的完整寄存器快照”；
- system call 的硬件保存 PC 固定为 `PC+4`。

这些说法对某些架构/入口机制可作为例子，但不是跨架构定义；RISC-V/xv6 是直接反例。

### OS-01/02

原文把 Mode Switch 压缩为“仅换特权级与内核栈，不换页表”，并把 Process Context Switch 压缩为“通用寄存器 + CR3”。这会把四条不同状态轴绑死：

```text
Privilege State
Kernel/User Stack Choice
Active Page-Table Root
Scheduled Execution Entity
```

xv6 system call entry 证明前三者并不具有固定联动关系；context switch 是否更换地址空间也取决于新旧实体是否属于不同 address space。

## 4. 已回写的唯一 Owner

- `30_408/50_桥梁专题/X-B01_PrivilegeExceptionSystemCall与OSControl/X-B01_PrivilegeExceptionSystemCall与OSControl_桥梁手册.tex`
  - 改为“硬件最小可信入口 + 软件补全环境”的架构无关模型；
  - Trap Frame 改为恢复协议对象，不绑定固定存放位置；
  - 新增 RISC-V/xv6 反例边界；
  - 系统调用/异常/中断的 saved-PC 语义改为 ISA-dependent；
  - `read()` 轨迹改成当前 xv6-RISC-V 可追踪路径。

- `30_408/30_操作系统/10_进程线程调度与控制权/OS-01_OS-02_进程线程调度与控制权_方法论手册.tex`
  - Mode Switch 不再定义为“必然换内核栈且不换页表”；
  - Context Switch 不再定义为“必然换 CR3”；
  - 将“当前页表是否临时切换”与“用户地址空间归属是否改变”分开；
  - 典型辨析改用“CPU 后续代表哪个调度实体执行”判断是否发生 execution context switch。
