# X-B04 Process / Socket × Transport Endpoint 覆盖核对

> 日期：2026-08-12
>
> 性质：Evidence 层 Bridge Promotion Gate 记录，不是知识 Owner。
>
> 结论：**Candidate Core / No Canonical Update**。

## 1. 问题与边界

本记录只回答：`Process Action -> Socket Object -> Transport Endpoint -> Buffer Availability -> Wake/Return` 是否已经有足够的 408 覆盖证据，值得建立独立 Cross-Subject Core Bridge。

它不重新拥有 OS 的进程/阻塞机制，也不重新拥有 NET06 的端口、连接和传输语义。NIC、DMA、driver ring、NAPI 和 zero-copy 仍属于 X-B03 / Extension。

## 2. 事实证据

| 证据 | 可支持的事实 | 限定 |
|---|---|---|
| [RFC 9293 TCP](https://www.rfc-editor.org/rfc/rfc9293.html) | TCP 端点由状态机维护；OPEN、SEND、RECEIVE、CLOSE 等用户动作会触发状态处理；被动 OPEN 接受进入连接 | 证明协议接口真实，不证明 408 独立考查频率 |
| [POSIX `recv()`](https://pubs.opengroup.org/onlinepubs/9799919799/functions/recv.html) | `recv()` 面向 socket fd 接收数据；阻塞 socket 在无可用数据时等待；`SOCK_STREAM` 不保留消息边界 | 证明进程可见的系统调用接口，不替代 OS/NET Topic Owner |
| NET06 | 已拥有 port、多路复用、UDP/TCP endpoint、connection/sequence state | 覆盖网络侧状态 |
| OS01/OS05 与 OS-B01 | 已拥有 process、system-call、file-like object、buffer、block/wakeup 的通用机制 | 覆盖操作系统侧状态 |
| NET-I01 | 请求 Integration 在 TCP endpoint / HTTP 之后停止，不承诺内核接收唤醒 | 防止 Integration 越界 |

## 3. 仓库覆盖核对

| 检查项 | 结果 | 解释 |
|---|---|---|
| 接口是否真实可复用 | Pass | RFC/POSIX 与现有 NET06/OS Owner 形成稳定交接 |
| 是否已有明确 Owner | Pass | OS 负责本地对象与等待；NET06 负责 endpoint/transport |
| 是否存在重复稳定正文 | Pass | 当前没有 X-B04 `.tex`；旧总图中的 `recv/read` 片段仍作为 Source，不是第二 Owner |
| 是否有两道独立 408 题目证据 | Not proven | 当前仓库没有按题号登记的独立题目，不能把旧总图重复叙述计为独立证据 |
| 是否产生不可替代的新推理 | Partial | 阻塞接收的事件序列有教学价值，但尚未证明为 408 高频独立接口 |

## 4. Promotion Gate 判定

第一道 **Bridge Validity** 已通过：输出、翻译、输入、不变量和失败/恢复均可明确描述。

第二道 **Standalone Promotion** 尚未通过。当前只能保留 Candidate，理由是：

1. 真实工程接口不等于考试范围内的独立核心；
2. 内部文档中的重复出现主要来自同一批旧 Source，不能作为 independent scenes；
3. NET-I01 已主动停止在内核接收唤醒之前，避免 Integration 抢占 X-B04 的潜在 Owner。

## 5. 下一步最小证据

收集两道独立 408 真题或明确考纲覆盖，且每道都要求同时推理：

- 进程在 `recv/read` 上等待、事件到达后何时可返回；
- socket receive buffer 与 port/connection demultiplexing 如何共同决定可见结果。

在此之前保持 `Candidate Core`，不建立 Canonical `.tex`，不把 X-B04 改写为已采用。
