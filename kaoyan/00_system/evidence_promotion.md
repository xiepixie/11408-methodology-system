# Inbox 与规则验证协议

本协议不要求建立错题数据库。它只规定：一段真实体验怎样经过 AI 辅助和新题检验，最后决定是否修改 Rules 或 Handbooks。

## 1. Inbox 首先要低摩擦

Inbox 可以只写：

```markdown
今天做一道页表题，一看到 TLB 就开始算访问次数，
但题目其实先发生了 page fault。
我可能把“地址翻译”和“页面是否驻留”混在了一起。
```

这已经足够开始讨论。

Inbox 不要求：

- ID；
- YAML；
- 固定标签；
- 完整题目分类；
- 每道题都建立记录；
- 当天就得出结论。

题目、原始过程、答案、用时或当时想法能保留多少就保留多少。缺失的信息保持缺失，不让 AI 补造。

## 2. 什么值得进入 Inbox

值得记录的通常是：

- 对模型产生了疑问；
- 正确但路径不稳或耗时异常；
- 错误似乎重复出现；
- 出现了可能可复用的有效动作；
- 现有 Rule 没有发挥作用；
- 考试中的取舍影响了后续表现。

偶发的小计算错误可以不记。Inbox 不是学习流水账，也不承担“证明今天学过”的功能。

## 3. AI 诊断顺序

把题目、原始过程和答案交给 AI 后，默认使用以下顺序：

1. **不要先重做整题**；
2. 复原使用者实际识别了什么、计划了什么；
3. 找到思维第一次偏离有效路径的位置；
4. 判断属于五类问题中的哪一类；
5. 把主观感觉翻译成可观察行为；
6. 提出一个主要假设和至少一个竞争解释；
7. 说明什么反例或新题能区分这些解释。

最终错误位置不等于 First Divergence。AI 的价值是找到系统最早在哪里开始失控，而不是更快给出标准答案。

## 4. 五类诊断与去向

五类问题的统一词义见 [`terminology.md`](terminology.md) §6。下表只负责给出典型表现和后续路由，不重新定义分类。

| 诊断 | 典型表现 | 可能修改位置 |
|---|---|---|
| 模型问题 | 把 TLB miss 等同于 page fault | Topic / Bridge / Integration Handbook |
| 识别问题 | 会 OFD，但把题目识别成 inode 链接问题 | 单一问题族进 Topic Practice；跨多个训练专题才进 Subject Rules |
| 路径问题 | 应先画状态，却直接开始计算 | 单一问题族进 Topic Practice；跨多个训练专题才进 Subject Rules |
| 执行/检查/表达问题 | 推演中漏更新状态，或没有形成得分链 | 单一问题族进 Topic Practice；跨多个训练专题才进 Subject Rules |
| 考试决策问题 | 低价值题卡住太久，没有按策略退出 | Exam Control |

诊断类型只说明“哪里出了问题”，不直接决定物理 Owner。Control Plane 还必须再做一次**作用域判断**：只服务一个问题族的动作与检查留在对应 Topic / Bridge / Integration 的训练 Markdown；只有同一控制跨多个训练专题反复出现，才进入 Subject Rules。

分类只是为了决定下一步，不需要继续拆成几十种错误标签。

## 5. 从感觉到候选规则

AI 应帮助完成这样的显化：

```text
感觉会但写不出来
-> 能识别换元，但没有明确换元后的目标表示
-> 假设：缺少的不是公式，而是转换前的目标表征
-> 候选规则：换元前先说清希望把复杂结构变成什么
```

一条候选规则至少应当能够回答：

- 什么情况下触发；
- 下一道题具体做什么；
- 怎样知道它有帮助；
- 什么情况下可能不适用。

如果只能得到“认真一点”“注意检查”“多练习”，不建立规则。

## 6. 候选规则放在哪里

先看作用域，不先看它听起来有多“通用”。位置和成熟度是两个不同问题。

先做一个简单检查：**触发信号里是否出现某个 Topic 的专有对象？** 如果一条规则只有看到 Booth、TLB、Cache set、某类积分结构、某个具体分布时才有意义，它默认就是局部 Practice 规则。

- **单一问题族**：进入最相关 Topic / Bridge / Integration 同目录训练 Markdown，按“触发信号—第一动作—检查与退出”维护；例如“分部积分前预测复杂度”只服务积分拆法选择时，应留在 Topic05 的对应训练入口。
- **跨多个训练专题**：只有当同一动作在多个独立训练文件中都能直接使用，删掉具体 Topic 名以后仍然清楚，而且统一维护确实能减少重复时，才进入学科 Subject Rules 的“待验证”。
- **跨学科、跨考试仍然成立**：优先检查是否已经属于 `01_control/problem_solving_kernel.md`，不要在各科重复维护。
- **作用域尚不清楚**：继续留在 Inbox，不为了尽快归档而提前选择 Owner。

局部规则即使后来被稳定采用，只要仍能由一个问题族完整拥有，也继续留在对应 Practice；它不会因为“验证通过”自动上移 Subject Rules。

## 7. AI 必须主动攻击规则

候选规则听起来聪明，不等于正确。AI 应当追问：

- 什么时候不成立？
- 最小反例是什么？
- 去掉一个条件还成立吗？
- 它是机制结论、考试技巧，还是只适合一个题型？
- 它减少了什么错误，又增加了多少时间和注意力？
- 是否已有更简单的规则完成同一目标？

反例不是为了否定一切，而是为了找到真实作用范围。

## 8. 怎样决定保留、修改或放弃

不设置固定题数门槛。复盘时同时看**收益、边界和认知成本**：

- 是否在陌生题而非记忆题中发挥作用；
- 是否跨越了不止一种表面形式；
- 是否出现反例，失效条件是否说得清；
- 是否真的减少错误、搜索分支或决策时间；
- 为了执行它，需要新增多少记忆、书写步骤和注意力；
- 是否已有更短、更清楚的动作达到同样效果；
- 使用者是否能够自然调用，而不是每次都靠提醒才想起；
- 使用者是否愿意把它作为当前行动规则。

可以把判断直观理解成：**规则带来的稳定收益，必须大于它新增的执行负担。** 不需要计算分数，但要警惕“为了防一个小错，给每道题增加一长串固定检查”的做法。

然后只有几种结果：

- **已采用**：若是跨专题控制，移入 Subject Rules 的稳定区域；若仍是单一问题族局部规则，继续由对应 Topic Practice 唯一拥有，并补充代表题/反例证据，不因采用而上移；
- **修改后继续验证**：收窄条件或换一个动作，并保持在当前正确作用域；
- **局部技巧**：只留在对应专题训练文档附近；
- **模型更新**：如果暴露的是世界模型错误，先调用 [`problem_model_validation.md`](problem_model_validation.md) 区分题面、Practice、Bridge 与 Canonical，再修改唯一 Handbook Owner；
- **已否定**：保留一句拒绝理由或直接清理；
- **No Update**：不足以改变系统。

AI 可以综合证据和提出建议，最终决定由使用者做出。

## 9. 快循环与慢循环

### 每天：快循环

```text
学习/做题
-> 暴露问题
-> AI 定位和显化
-> 候选规则或 No Update
```

### 每周或专题结束：慢循环

```text
查看 Inbox 和待验证规则
-> 找重复模式
-> AI 生成反例并综合表现
-> 人决定保留、修改、否定
-> 必要时更新 Canonical Owner
```

日常可以频繁使用 AI，但不频繁重构 Handbooks。

## 10. 什么时候才需要单独 Case

默认不建 Case 文件。只有以下情况值得额外整理：

- 同一问题反复出现，却无法解释；
- 多个候选原因难以区分；
- 一道题揭示了重要模型冲突；
- 这个案例以后适合用来训练或检验 AI；
- 需要长期保留原始过程和反例链。

即使单独整理，也按问题需要写，不使用强制 schema。

## 11. 删除是正常维护

Inbox 可以删除：

- 已确认只是一次性事件；
- 已被稳定 Rule 吸收；
- 已无法复原上下文；
- 重复且没有新增信息；
- 继续保留不会改变任何未来行动。

已否定但很容易再次提出的“聪明规则”，可以保留最小反例和拒绝理由，避免以后重复踩坑。

## 12. 防止 AI 制造“会了”的错觉

默认交互顺序是：

```text
我先判断
-> 我先解释
-> AI 攻击
-> 我修正
-> AI 给反例或新题
-> 我重新解释或执行
```

而不是：

```text
AI 完整解释 -> 我看懂 -> 假设自己会了
```

AI 的目标不是增加答案数量，而是提高：

$$
\frac{\text{有效认知反馈}}{\text{学习时间}}
$$

## 13. 隐私

公开仓库中的 Inbox 或案例必须去除姓名、账号、联系方式、准考证号和未公开试卷等敏感信息。无法安全脱敏的材料留在仓库外，只在这里保留必要摘要。
