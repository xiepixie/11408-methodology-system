# 题目与心智模型双向验证协议

> **身份：Control / Validation Owner。**
>
> 本文件只负责一件事：当我们用题目检验心智模型，或修改模型后再用题目回测时，怎样判断问题究竟出在题目、训练控制、跨模块接口还是 Canonical Handbook。
>
> 它不拥有题面转译、具体解题步骤、规则晋升标准或 Handbook 机制正文：题面忠实恢复仍归 Exam Source / 题库 Source 规则；单题求解归 `01_control/problem_solving_kernel.md`；规则成熟度归 `evidence_promotion.md`；机制正文归唯一 Handbook Owner。

## 1. 为什么需要单独的验证协议

一道题“做不通”，至少可能有五种完全不同的原因：

1. 题面缺条件、口径不清或选项本身有问题；
2. 心智模型是对的，但题目信号没有触发正确训练动作；
3. 两个 Owner 的交接没有说清；
4. Canonical Handbook 的事实、机制或边界真的有缺口；
5. 题目和模型都没问题，只是本次执行失误。

如果不先分层，很容易出现两种错误维护：

- 为了救一道人为条件不足的题，去修改正确的 Handbook；
- 为了保护现有 Handbook，把真正的模型错误解释成“题目特殊”。

因此验证必须双向进行：

```text
题目 -> 模型：现有模型能否独立生成正确结论？
模型 -> 新题：条件变化以后，模型能否知道哪里应变、哪里不变？
```

## 2. 各文件分别负责什么

| 文件 / 资产 | 只负责什么 | 不负责什么 |
|---|---|---|
| Canonical Question / 正式题库题面 | 保存题目事实与必要条件 | 不替解析补模型，不保存审校推理 |
| Canonical Handbook | 定义对象、机制、不变量、边界和成本 | 不维护完整题型树和考场步骤 |
| Topic / Bridge / Integration Practice | 一个问题族的识别、第一动作、变式、局部检查和代表题 | 不复制第二套机制正文 |
| Subject Rules | 多个训练专题都反复需要的跨专题控制 | 不收集所有局部技巧 |
| `problem_solving_kernel.md` | 面对一题时怎样表示、选择、执行和检查 | 不决定稳定资产该改哪里 |
| 本协议 | 判断题目与模型谁被打穿，并规定修改后的回测方法 | 不直接拥有具体学科知识 |
| `evidence_promotion.md` | 候选规则是否值得保留、收窄、晋升或否定 | 不判断题面是否自洽 |
| Exam Solution / 正式解析 | 展示一次模型运行 | 不成为新的理论 Owner |

后续如果发现同一原则在多个文件出现，优先保留上表中的唯一 Owner，其他位置只留一句调用说明。

## 3. 正式题目先过“题目质量门”

可编辑练习题进入长期题库、代表题或模型回归题组前，先检查下面六件事。真题也执行同样检查，但检查出的歧义只能记录在题解 / review 中，不能为了得到唯一答案而改写 Canonical Exam Source。

### 3.1 题目真正属于谁

先判断主要机制 Owner。来源章节、教材目录和题目标签都不能替代 Ownership。

跨多个 Owner 的题要明确谁提供什么输入、谁接收什么输出；如果只是一个 Topic 使用另一个 Topic 的结论，不为了“综合感”强行建立 Bridge。

### 3.2 目标和统计对象是否明确

先问题目到底要求什么，以及答案的分母或计数对象是什么。

例如：

- instruction 还是 cycle；
- source-level array reference 还是实际 Cache reference；
- Cache line、set、page 还是 byte；
- CPU time、wall-clock time、latency 还是 throughput。

如果解析过程中必须偷偷更换统计对象，题面还没有准备好。

### 3.3 唯一答案依赖的条件是否已经写进题面

凡是会改变答案的条件，都不能只藏在解析里，例如：

- alignment；
- row count / DRAM geometry；
- Bank busy window 与请求到达节拍；
- PC 基准与位移单位；
- ISA / ABI / 编址单位；
- Cache write / allocation / replacement policy；
- 编译器是否复用中间结果。

**如果解析必须先写“这里默认……”才能得到唯一答案，优先回修题面。**

### 3.4 从题面出发能否得到可复现的状态轨迹

同一组条件交给两个独立求解者，应该能沿同一个合法模型得到一致结论。

如果 way 编号、实现自由度、未定义语言行为或未说明的硬件时序会改变答案，应消除这种自由度，或者改问不受它影响的语义不变量。

### 3.5 输出是否确定

- 单选题必须只有一个正确选项；
- 多选题必须有明确选取标准；
- 计算题必须明确单位、精度与口径；
- 综合题允许多种实现时，应明确“任一满足哪些条件的方案均可”。

“答案不唯一”本身不是问题；**评分目标不清楚**才是问题。

### 3.6 解析能否由模型正向生成

正式解析应当从

```text
对象 / 状态 / 约束
-> 机制或不变量
-> 推导或状态演化
-> 结果
-> 独立校验
```

自然得到答案。

如果解析只能先知道标准答案，再补一套理由，说明题目或模型仍需继续检查。

## 4. 第一方向：用题目攻击模型

新题先独立求解，不先看旧答案。随后只问一个核心问题：

> **现有 Canonical 是否足以生成正确结论？**

结果只落到以下位置之一：

```text
能生成，但题面缺条件
-> 只修题面（仅限可编辑练习题；真题保持原文，在 review / solution 中记录问题）

能生成，但识别或第一动作不稳定
-> 当前问题族 Practice；只有跨多个训练专题才考虑 Subject Rules

能生成，但两个 Owner 的交接反复说不清
-> 补 Bridge 或路由说明

不能生成，并且缺的是稳定定义、机制、不变量或边界
-> 更新唯一 Canonical Handbook

题目和模型都没有稳定新增
-> No Update
```

判断 Canonical 缺口时，不能只依据“旧解析写得不一样”。先排除题面错误、legacy 答案错误和适用边界差异，再进入稳定写入。

## 5. 第二方向：用模型反过来攻击题目

一个模型在原题上能工作，还不能证明它已经成熟。更有价值的检查是只改变一个关键条件，看模型是否知道结论为什么变化。

重要模型修改后，优先从下面三类变化中选择最小回测集合；不要求为了凑数量机械出题。

### 5.1 同机制换表面

对象和机制不变，只改变数字、语言、代码写法或图的表示方式。

目的：检查我们学到的是模型，还是原题外观。

### 5.2 改一个边界条件

例如改变：

- signed / unsigned；
- aligned / unaligned；
- forwarding endpoint；
- burst / non-burst；
- Cache policy；
- 参数是否达到临界值。

目的：检查模型能否指出“哪条前提失效，因此哪一步必须改变”。

### 5.3 改表示或跨层接口

同一个对象改用另一种表示，或让问题从一个 Owner 交给另一个 Owner。

目的：检查模型是否分得清对象与表示、局部状态与跨层责任。这里所谓跨层接口，就是一个 Owner 的输出如何成为另一个 Owner 的合法输入，不额外引入新的机制。

如果只有原题能够复现，而一做这些最小变化就只能重新背答案，这次更新还没有形成稳定模型。

## 6. 修改模型后建立“小回归题组”

Canonical Handbook 发生事实、机制或边界修改后，不需要盲目重做所有旧题。先在最相关的 Practice / Evidence 中保留少量有区分力的代表题：

- **基线题**：正常条件下能跑通主机制；
- **边界题**：专门检查适用条件；
- **扰动题**：只改变一个关键条件；
- **接口题**：若该 Topic 经常与其他 Owner 交接，再保留一题检查 handoff。

不是每个 Topic 都必须固定四道。只保留那些能在未来模型修改后迅速发现回归的题。

回归时先运行这组；只有出现异常，才扩大到更多历史题解。这样既能防止旧错误复发，也不会让每次小修都变成全库重算。

## 7. 怎样判断一个模型真的成熟

比“能解释标准答案”更重要的是下面五件事：

1. **能识别**：从题面知道应该调用哪个模型；
2. **能生成**：不知道答案时也能推出第一动作和主路径；
3. **能扰动**：改一个条件时知道哪一步应变、哪一步不变；
4. **能拒绝**：条件不足时能明确指出缺什么，而不是自动脑补；
5. **能被推翻**：知道什么反例或边界会让当前结论失效。

其中任何一项长期失败，都说明模型或训练接口还有缺口。

## 8. Verification 不只放在最后

验证有两种位置：

- **事前约束**：先预测范围、符号、单位、位宽、状态不变量或数量级，用它限制候选路径；
- **事后校验**：算完后用独立信息检查结果，例如反算、守恒、边界样例、商余关系、地址范围或状态合法性。

好的验证不是把原推导再算一遍，而是尽量使用另一条信息来源。

## 9. 和规则验证怎样衔接

题目已经证明某个“第一动作”有帮助，不代表它自动成为 Subject Rule。

后续仍由 `evidence_promotion.md` 判断：

- 它只服务一个问题族，还是跨多个训练专题；
- 它是否在陌生题中反复有效；
- 它减少了多少错误或搜索分支；
- 它新增了多少记忆、书写和注意力成本；
- 是否存在更短、更清楚的动作完成同一目标。

先决定**放哪里**，再决定**是否成熟**。位置和成熟度是两个不同问题。

## 10. 最短闭环

以后遇到“这题把模型打穿了吗”，固定问：

```text
题目条件够不够？
-> 现有模型能否正向生成答案？
-> 若不能，缺口在 Question / Practice / Bridge / Canonical 哪一层？
-> 修改以后，用一个换皮题 + 一个边界扰动重新跑。
```

目标不是让每道题都产生新规则，而是让题目不断筛掉含糊条件、脆弱口诀和错误边界，最后留下更少、更稳定、能迁移的模型与控制动作。
