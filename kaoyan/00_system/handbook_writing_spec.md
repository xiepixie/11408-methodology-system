# 学科心智模型手册与专题手册通用写作规范

> **系统总目标**：本系列手册的目标不是"覆盖尽可能多的知识"，而是帮助学习者建立：
>
> $$\boxed{\text{理解} + \text{生成} + \text{区分} + \text{推理} + \text{调用}}$$
>
> 最终达到：面对熟悉问题，不依赖死记公式；面对陌生问题，也能从对象、关系、约束、机制、不变量和目标重新推出可行路径。

因此，一本合格的手册必须回答的不只是"这个知识点是什么？"，还必须回答：

- **为什么会需要它？**
- **它解决了哪个更基本的问题？**
- **它和哪些相邻概念不同？**
- **题目什么时候在考它？**
- **做题时应该在哪个节点调用它？**
- **忘掉具体公式以后，能不能重新推出主要结论？**

本规范拥有所有心智模型手册与专题手册的认知结构、写作原则与验收标准。`AGENTS.md` 只负责把任务路由到正确契约；协作写入见 [`collaboration_workflow.md`](collaboration_workflow.md)，Ownership 见 [`ownership_matrix.md`](ownership_matrix.md)，Handbook 物理交付见 [`handbook_contract.md`](handbook_contract.md)，仓库发布一致性见 [`repository_integrity.md`](repository_integrity.md)。

## 1. 首先区分四种文档身份

不同类型的手册不能争夺同一知识。

### 1.1 心智模型总册：Map

负责回答：

> 这门学科究竟研究什么？有哪些根本对象？有哪些反复出现的母问题和母模型？各章节在整个学科中的位置是什么？

总册负责建立 $\boxed{\text{Coordinate System}}$，而不是讲透所有机制。

总册应该做到：

- 学完任何新章节，都知道它应该挂在哪里；
- 遇到陌生问题，知道先从哪个模型观察；
- 不需要把教材每个公式重新讲一遍。

### 1.2 专题手册：Depth

负责回答：

> 某一个核心问题究竟怎样从根本矛盾一步一步生成具体机制？

例如不是"TCP 有哪些机制？"，而是"不可靠信道怎样构造可靠传输？"。不是"矩阵特征值怎么算？"，而是"怎样找到一个线性算子自身最自然的方向和坐标？"。

专题册负责机制深度。

### 1.3 桥梁手册：Interface

负责回答：

> 两个专题之间为什么真的能够连接？

例如：Hessian ↔ 二次型；Jacobian ↔ 行列式；Socket ↔ OS I/O；Cache ↔ 虚拟内存；概率积分 ↔ 多重积分。

桥梁册不重新教授两边全部内容，只解释 $\boxed{\text{Interface Contract}}$：左边输出什么，经过什么翻译，右边接收什么，中间保持什么不变量。

建立 Bridge 前必须做“去题目测试”：删掉具体例子后，如果仍剩一条稳定、普遍、可复用的 A ↔ B 共享机制，才值得成为 Bridge；如果只剩多个模块共同完成一个问题，则应进入 Integration。

### 1.4 综合手册：Integration

负责回答：

> 当多个专题同时参与一个完整过程时，它们怎样接起来？

例如：一个网络请求的一生；一次 `read()` 的完整路径；一个参数统计推断从总体到检验的全过程；一条 LOAD 指令从 ISA 到 Cache Miss 的执行路径。

综合册不拥有具体机制。它负责 $\boxed{\text{Composition}}$。

### 1.5 Extension 与 Anti-Bridge：关系边界，不新增 Handbook 类型

- **Extension**：真连接，但超出当前核心范围；只保留足够指向未来的最小解释。
- **Anti-Bridge**：假连接或禁推关系；明确为什么容易混淆、真正判据和停止类比的位置。

它们用于控制知识网络，而不是扩张目录。默认写在相关 Atlas / Topic / Bridge 的边界或扩展段落。

### 1.6 跨科母模型补充：Atlas 的可展开关系层，不是第五种 Handbook

如果同一种问题形状跨多个独立 Topic/Subject 反复出现，而它又**不是**一条稳定的 `A output -> translation -> B input` 接口，可以由上层 Atlas 建立独立 Markdown 补充文档，把这条关系连续讲清。它负责：

- 共同母问题与生成逻辑；
- 可迁移的不变量、状态维度和权衡；
- 相似机制之间的 A≠B 边界；
- 从统一模型路由回各自唯一 Owner；
- 明确“停止类比”的位置。

它必须同时满足：跨至少两个独立 Owner、能产生新的判别/迁移能力、不会复制局部完整机制。它**不改变稳定 Handbook 类型仍为 Atlas / Topic / Bridge / Integration**，也不因为篇幅很长就获得新的机制 Ownership；可以理解为 Atlas 把一条高价值跨模块关系从 README 中展开到单独的 Canonical Supplement，以避免 Atlas 本体膨胀。

## 2. 第一原则：先寻找学科真正的"对象"，不要先列章节

写任何学科之前，第一步都不是复制教材目录。先问：

> **这门学科究竟在操作什么对象？**

例如可能是：函数、空间、映射、随机变量、状态、数据结构、资源、信号、文本、市场主体、化学反应体系。

然后进一步问：

- 这些对象有什么状态？
- 对象之间有什么关系？
- 什么操作会改变它？
- 什么性质必须保持？
- 我们真正关心什么结果？

因此最通用的观察镜头可以写成：

$$\boxed{Object \rightarrow Representation/State \rightarrow Operation/Event \rightarrow Invariant/Boundary \rightarrow Goal/Cost}$$

注意：这不是要求所有学科都强行套同一个模型。它只是一套**观察问题的共同语言**。不同学科必须继续形成自己的 Adapter。

## 3. 第二原则：找到能够"生成知识"的母问题

好的母模型不是"本章包含 A、B、C、D"，而应该是一个问题。例如：

- 一个有限信道为什么需要窗口？
- 一个空间到底需要多少独立方向？
- 怎样从局部变化恢复整体函数？
- 得到新证据以后为什么应该修改原概率？
- CPU 怎样在保持程序语义的前提下重叠执行指令？

一个好的母问题应该满足：

1. **能生成多个知识点**：如果一个模型只能解释一个公式，它不够"母"。
2. **能解释"为什么"**：它应该说明机制为什么出现，而不只是给机制名称。
3. **能导向题目**：看到题面信号以后，学习者应该能够调用这个模型。
4. **能容纳反例和边界**：模型不能只在标准例题里成立。

---

## 4. 第三原则：必须区分"对象"和"表示"

这是很多学科最容易产生深层混乱的地方。一般形式是 $\boxed{Object \neq Representation}$。

例如：

- 向量 ≠ 坐标；
- 线性映射 ≠ 矩阵；
- 随机现象 ≠ 随机变量；
- 文件对象 ≠ 文件名；
- 数据结构的逻辑关系 ≠ 内存布局；
- 函数 ≠ 一个具体解析式。

必须进一步问：**换一种表示以后，什么发生变化？什么保持不变？什么信息丢失了？**

这会自然引出五层结构：

$$\boxed{Object \rightarrow Representation \rightarrow AllowedTransform \rightarrow Invariant \rightarrow InformationLoss}$$

第五层 **InformationLoss**（信息丢失）在实际辨析中至关重要——很多概念混淆恰恰来自"以为变换是无损的"。例如：

- 从联合分布到边缘分布，丢失的是变量间的依赖结构；
- 从矩阵到特征值，丢失的是特征向量方向；
- 从文件内容到 inode，丢失的是名称与路径。

## 5. 第四原则：任何抽象模型都必须"落地"

严禁只画一串没有关系类型的 $A\to B\to C$ 然后默认读者理解。任何第一次出现的英文术语、箭头、符号、流程、母模型，都必须完成下面五步：

### Step 1：Plain-language Meaning

用自然语言解释：它究竟在问什么？

### Step 2：Why this order?

先判断 $A$ 与 $B$ 的关系类型。若是逻辑推导，写 $A\Rightarrow B$；若是状态变化，写 $S\xrightarrow{e}S'$；若是映射，写 $x\mapsto f(x)$；若只是阅读或检查顺序，直接用编号列表。不能让一个裸箭头同时承担这些语义。

### Step 3：Chapter Mapping

明确告诉学习者：后面的哪些章节实际上是在展开这个模型的哪一个位置。

### Step 4：Worked Example

至少用一个足够简单的具体例子，把整个模型完整运行一次。不是只举名词，而是逐项展示对象、关系类型、条件和结果。

### Step 5：Problem-solving Call

说明做题时什么时候应该调用这条模型？题目给什么信号时，它成为你的第一观察方式？

这里的“调用”只要求给出**最小接口**：让学习者知道当前问题应该回到哪个模型观察。不要因此在 Handbook 里继续展开整套题型树、所有变式、速算技巧和长控制流程。若这些内容对训练有价值，应进入同目录按内容命名的训练 Markdown，由 README 导航；训练文档再把母题、局部规则、技巧与代表题放在一起。

因此任何抽象模型都必须同时具备五项信息：`Abstract Model / Meaning / Chapter Mapping / Worked Example / Problem Action`。这是**覆盖契约**，不是逻辑蕴含链。

**缺任何一环，都不能算真正完成。**

### 5.1 结论必须有证据等级，不能只放公式

手册提出结论时，必须让读者知道“它为什么成立、依赖什么、何时不能用”。这里的“证明”不等于每个定理都展开成教材级形式证明，而是根据结论的性质提供足够的可复原证据：

| 结论类型 | 最低证据要求 | 不能省略的边界 |
|---|---|---|
| 定义、恒等式、基本运算 | 从定义或公理写出关键等式变形；至少展示首步和收尾 | 定义域、存在条件、符号方向 |
| 本册主干定理/公式 | 写清前提，并用等式变形、`$\Rightarrow$` / `$\Leftrightarrow$` 或明确调用的定理得到结论；省略技术细节时必须给出证明骨架 | 假设、参数范围、适用对象、失败反例 |
| 调用外部定理的结论 | 说清定理名称/版本、当前对象如何逐项满足前提，以及它输出什么 | 哪个前提一旦缺失就不能套用 |
| 经验性策略或近似 | 给出机制解释、误差/代价来源和一个反例或失效区间 | 不能把经验规律伪装成必然定理 |

每个核心结论尽量按以下四句落地：

1. **前提**：当前已知的对象、条件和参数范围；
2. **证据**：定义展开、代数计算、几何/概率机制或定理映射；
3. **结论**：得到的公式或判断，以及它解决的目标；
4. **边界**：不能直接推出什么，换条件后要改用哪条路径。

因此，“结论证据”可以是完整证明、压缩推导或可检查的证明骨架，但不能只有“记住公式”。证明与心智模型承担不同职责：证明保证结论可靠，模型保证学生知道何时生成和调用它。

### 5.2 正式定义与推理先行；直觉负责解释“为什么”

心智模型既要可理解，也必须先把对象、条件和逻辑资格钉死。**定义、定理和主干推理不得由比喻代替，也不得先用比喻偷偷加入正式定义没有的性质。**

对于需要进入稳定 Handbook 的核心概念，默认顺序是：

1. **正式对象 / 定义**：使用本学科的专业术语、量词、集合、函数、状态或等式明确“它是什么”；
2. **成立条件**：写清定义域、参数范围、前提、合法变换或事件资格；
3. **推理 / 定理**：用等式、逻辑蕴含、等价关系或明确标注的状态迁移说明“由什么推出什么”；
4. **结论与边界**：明确可以推出什么，以及不能反推什么；
5. **直觉解释**：在正式关系已经成立以后，再用几何图像、最小数值例子、物理意义或类比解释“为什么这样定义、为什么这个结论合理”；
6. **微扰校准**：只改变一个条件，检查结论怎样变化，用最小反例阻断过度直觉。

对数学正文，可压成：

$$
\text{Definition/Assumption}
\Longrightarrow
\text{Derivation/Theorem}
\Longrightarrow
\text{Consequence},
$$

随后再给 Intuition / Why。这里的 $\Longrightarrow$ 只表示逻辑推导，不表示阅读顺序。

直觉仍然重要，但它的职责是**解释和预测**，不是定义和证明。进入例题或探索场景时，可以在正式对象已经明确后先做方向、符号、数量级或候选位置的直觉预判，再用正式推导验证；若预判失败，以定义和推理链为准。

> **禁止三种退化：**只有术语却没有严格定义；只有严谨推导却无法解释“为什么”；只有形象类比却说不清对象、条件、量词和可推出的结论。

## 6. 第五原则：机制必须从问题中长出来

专题手册最忌讳按“定义、性质、公式、例题”机械堆叠。更好的机制生成叙事应依次回答四件事：**Problem、Naive Solution、Failure、Mechanism**。这里是解释顺序，不自动构成数学蕴含；只有能够由前提严格推出的步骤才使用 `$\Rightarrow$`。

例如解释为什么需要滑动窗口时，应分别说明：目标是可靠传输；Stop-and-Wait 在可靠性上可行；当 RTT 相对发送时间很大时，它使链路长期空闲；若希望提高链路利用率，就需要允许多个 packet 同时在途；窗口机制为“允许多少数据在途”提供状态约束。这里每一步的因果或设计关系都应在文字中说清，而不是用一串裸箭头代替论证。

这种写法让机制从已确认的问题和约束中长出来，而不是看起来像教材规定。

## 7. 第六原则：必须写完整生命周期或状态轨迹

凡是研究"会变化的对象"，都不能只给静态定义。必须回答：

- 它怎么产生？初始状态是什么？
- 什么事件改变它？有哪些分支？
- 失败后怎样处理？最后怎样结束？

$$S_0 \xrightarrow{E_1} S_1 \xrightarrow{E_2} S_2 \xrightarrow{E_3} \cdots$$

需要明确：Object、State、Event、Transition、Branch、End condition。

我们通常称之为 **"X 的一生"**。这在 OS、网络、算法、概率抽样、ODE、工程系统中都非常有效。

---

## 8. 第七原则：概念边界不能只是写"A ≠ B"

这是前期手册最重要的教训之一。只写 $A \neq B$ 几乎没有教学价值。

完整的概念边界必须同时回答五件事：$A\neq B$、Why Confused、True Criterion、Question Signal、Failure If Confused。它们是诊断字段，不是一条逻辑蕴含链。

排版标准为 **5 列表格**（`≠` 符号独占居中列）：

| 概念 A | ≠ | 概念 B | 真正区别与题目信号 | 混淆后果 |
|---|:---:|---|---|---|
| Routing | ≠ | Forwarding | Routing：表怎样生成（Dijkstra/RIP/OSPF）；Forwarding：已有表时当前 packet 去哪里（LPM）。若题目给现成转发表并要求做 LPM，应判断为 Forwarding | 混淆后会把控制平面和数据平面混为一谈 |

概念边界最终必须改变做题行为，否则就是术语表。

---

## 9. 第八原则：每个专题都要寻找不变量

很多知识真正的核心并不是"发生了什么变化"，而是：

> **变化过程中什么绝不能被破坏？**

形式：$\boxed{Invariant(State) = True}$

可能是不变量，也可能是合法性条件、守恒量或结构约束。例如：

- 排序过程必须保持元素集合不变；
- 线性变换换基后某些结构保持；
- OS 不能破坏权限；
- 并发不能破坏共享状态不变量；
- 概率密度总质量必须为 1；
- 数值方法要保持误差边界；
- 几何变换可能保持长度、角度或方向。

不变量是从"记步骤"升级到"理解为什么步骤合法"的关键。

---

## 10. 第九原则：必须解释代价与权衡

不能只回答"为什么正确？"，还必须回答"为什么不用另一个方案？"

因此任何机制至少问：$\boxed{Correctness + Cost + Tradeoff}$

Cost 不仅是时间复杂度，还可能是：空间、I/O、通信、延迟、精度、稳定性、并行性、可解释性、实现复杂度。

高质量理解必须包含：**这个机制用什么代价换来了什么能力。**

---

## 11. 第十原则：正文只承担本册的 Ownership 责任

Ownership 角色的统一词义见 [`terminology.md`](terminology.md) §7，具体 Owner 台账见 [`ownership_matrix.md`](ownership_matrix.md)。本规范不再维护第二份角色定义。

写正文前只做一个检查：**这段话在本册属于哪种责任？**

- `Own`：可以展开完整定义、机制、边界和反例；
- `Use`：只写当前推理必需的最小摘要，并链接 Owner；
- `Bridge`：只写两侧怎样交接，不重讲两侧 Topic；
- `Integrate`：只追踪多个 Owner 怎样按顺序协作；
- `Extension / Anti-Bridge`：只保留扩展指针或禁推边界，不扩成平行主干。

例如 Page Cache 可以同时出现在 I/O、文件系统、VM 和一次 `read()` 的完整过程里，但只有一个位置负责修改它的定义；其他位置按各自责任引用。**同一个名词出现多次不等于重复定义，多个文件都声称能修改同一定义才是重复 Owner。**

---

## 12. 第十一原则：总图与专题必须保持不同解释粒度

总图不要变成浓缩教材，专题也不要只是总图扩写。

| 文档类型 | 回答 |
|---|---|
| **总图 Map** | Why + Where + Relationship |
| **专题 Depth** | How + State + Mechanism + Boundary + Cost |
| **桥梁 Interface** | Interface Contract |
| **综合 Integration** | Composition |

---

## 13. 第十二原则：考纲覆盖和认知结构必须分离

考试大纲的目录适合 $\boxed{\text{Coverage Check}}$，但不一定适合 $\boxed{\text{Mental Structure}}$。

因此：

- **正文**：按照认知逻辑组织。
- **附录**：按照考试大纲逐项查漏。

$$\boxed{MainText = Understanding} \qquad \boxed{Appendix = Coverage}$$

这样既不会为了追求"心智模型"漏考点，也不会让考纲目录绑架认知结构。

---

## 14. 第十三原则：每本手册都必须有贯穿母例

好的母例应该能在多章反复回来。它的作用不是"多做一道例题"，而是帮助学习者看到：同一个对象在不同章节分别被怎样观察。

母例最好满足：

1. 足够简单；
2. 结构足够丰富；
3. 能覆盖多个章节；
4. 后面可以不断升级；
5. **能暴露至少一个可验证的失败路径或边界**——好的母例应允许学习者在具体场景中看见“某个看似合理的路径为什么失效、哪条条件阻止它”。只有已有题目、错题或教学证据支持时，才称该路径为“常见错误”或“典型错误”；没有证据时只写反例或候选失败路径。

如果母例只能展示"正确做法"，它就退化成了普通例题。

---

## 15. 第十四原则：每个重要模型都必须提供最小调用接口

知识不能停在理解层，但 **Canonical Handbook 的调用责任只到“把学习者送进正确模型”**，不能继续扩成第二套训练控制系统。每一个重要模型至少应让读者知道：

### 题目信号

看到哪些对象、结构、条件或事件时，应想到本模型？

### 第一观察层

进入本模型后，第一眼应该确认什么对象、状态、关系或合法性条件？例如“先确定 support”“先找 state owner”“先判断当前对象属于哪个空间”。这里给的是观察入口，不是完整做题步骤。

### 退出 / 转交边界

出现什么信息后，应停止在本册继续展开并切换到另一个 Topic / Bridge / Integration？

完整的“触发信号—第一动作—检查与退出”局部规则、固定问答清单、题型路由、速算技巧、作答模板和训练阶梯，统一进入同目录训练 Markdown；真正跨多个训练专题的控制才进入 Subject Rules。

---

## 16. 第十五原则：专题模型必须能被训练层特化，而不是在 Canonical 中内置完整解题协议

通用解题控制底座可以使用 `Object / Goal / Structure / Representation / Route / Execute / Verify`，但它属于控制层。Canonical Handbook 只需要提供足够清晰的机制对象和最小调用接口，使训练层能够在不重写理论的前提下把底座特化成当前问题族的具体动作。

例如，积分训练可以把底座特化成 `Quantity / Region / Coordinates / Element / Bounds`，方程组训练可以特化成 `Goal / Rank / Consistency / Nullity / Solution Structure`；这些完整检查顺序应写在对应训练 Markdown，而 Canonical 正文只解释为什么这些对象和判据成立。

> **Handbook 负责让控制动作有机制根据；训练 Markdown 负责把机制压成可执行协议。**

---

## 17. 第十六原则：验证不是最后"检查计算"

Verification 必须成为推理的一部分。每个专题都应该告诉学生：算完以后用什么独立信息检查？

例如：

- 概率是否在 $[0,1]$；
- 密度积分是否为 1；
- 方差是否非负；
- rank 是否超出维数；
- 特征值之和是否等于 trace；
- 导数是否与单调性一致；
- 积分符号是否符合几何；
- 网络地址是否处于合法前缀；
- 算法复杂度是否与操作数量匹配。

好的验证应当尽量 $\boxed{\text{Independent from the original route}}$，而不是把原来的计算再抄一遍。

---

## 18. 第十七原则：解释深度不能靠抽象程度伪装

"深刻"不等于多说"本质、范式、状态空间、哲学、不变量、系统"。

抽象概念只有在能够：

1. 解释具体知识；
2. 推出具体结论；
3. 区分具体错误；
4. 改变具体做题行为；

时才有价值。

$$\boxed{Abstraction \;\text{without}\; OperationalConsequence = Decoration}$$

不能因为一句话很漂亮，就把它当成心智模型。

---

## 19. 第十八原则：不要过度统一

不同学科必须允许拥有不同世界模型。例如：

| 学科 | 代表性观察坐标（不是用 `+` 定义的新数学对象） |
|---|---|
| 高数 | Limit；Local Model；Accumulation；Local–Global；Infinite Construction；Dynamics |
| 线代 | Object；Representation；Allowed Transform；Invariant；Simplest Valid Form |
| 概率 | Random Object；Distribution；Information Operation；Sampling；Inference |
| 计算机网络 | Scope；State Owner；Event / Transition；Feedback；Cost |
| 操作系统 | Objects / Relations；Resource Metadata；Queues；Event / Transition；Safety / Liveness |

这比制造一个覆盖所有学科的"万能公式"更重要。我们的目标是：

$$\boxed{\textbf{统一写作方法，不统一学科本体。}}$$

---

## 20. 第十九原则：语言必须稳定、具体、可执行

术语应该：

- 前后统一；
- 一个概念尽量只有一个正式名称；
- 英文术语首次出现时解释；
- 不随意使用近义词制造假区别；
- 箭头、符号、框架含义固定。

### 20.1 形式语言与箭头语义契约

稳定正文中的符号必须先有唯一语义，再承担压缩作用。默认约定如下：

| 记号 | 唯一职责 | 例子 |
|---|---|---|
| `$:=$` | 定义一个新记号或本册明确约定的表示 | `$S:=\{x:f(x)=0\}$` |
| `$=$` | 数学相等、恒等或已经建立的同一数值/对象关系 | `$\dim V=n$` |
| `$\Rightarrow$` / `$\Longrightarrow$` | 在当前前提下的逻辑蕴含或可复原推导 | `$A\text{ 可逆}\Rightarrow\ker A=\{0\}$` |
| `$\Leftrightarrow$` | 充要关系 | `$A\text{ 可逆}\Leftrightarrow\det A\neq0$` |
| `$f:A\to B$` | 函数的定义域与陪域 | `$T:V\to W$` |
| `$x\mapsto f(x)$` | 元素在映射下的像 | `$x\mapsto Ax$` |
| `$S\xrightarrow{e}S'$` | 事件 `$e$` 触发的状态迁移 | `$Blocked\xrightarrow{wake}Ready$` |
| `$A\xrightarrow{\text{label}}B$` | 明确标注的信息流、接口交接或物理传输 | `$SDU\xrightarrow{\text{encapsulation}}PDU$` |
| `$\approx,\sim,\propto$` | 近似、渐近/分布关系、比例等各自标准数学语义 | 按学科定义使用 |

硬规则：

1. **不要用裸 `$A\to B$` 表示“所以”“然后”“建议先看”。** 如果关系是逻辑推理，用 `$\Rightarrow$`；如果只是检查顺序，改成编号列表或明确写“检查顺序”；如果是状态变化，必须标事件。
2. **不要用 `$=$` 表示“本册把它理解成”“大致相当于”“可以看作”。** 这类工作模型用自然语言说明，数学定义用 `$:=$`，近似用相应近似符号。
3. **同一张图中的箭头必须同义。** 如果必须混用因果、信息流、状态迁移和调用顺序，使用不同线型或显式标签，并给出图例。
4. **推理链必须可逐步复原。** 对数学与逻辑结论，优先写等式、等价变形和 `$\Rightarrow$` / `$\Leftrightarrow$`；不能把教学叙事顺序画成“证明”。
5. **直觉解释不得反向修改正式语义。** 比喻只能在定义、条件或定理之后解释“为什么”，不能成为新前提。

避免："关注结构""理解本质""灵活转换""建立联系"——这种无法直接执行的句子。

替换成：

- "先判断当前对象属于哪个空间。"
- "把题目给出的条件改写成 $Ax=b$。"
- "固定 $x$，沿 $y$ 方向画截线确定积分区间。"
- "收到 ACK 后只更新发送端窗口状态。"

语言风格应该像：**一个优秀教练站在学习者旁边，在每个十字路口明确告诉他：现在看什么、为什么看、接下来做什么。**

## 21. 第二十原则：手册必须支持局部修改

手册不是一次性交付物。正文结构必须让后续修改能够回答三件事：**改哪一段、哪些相邻结论受影响、哪些引用方不需要复制修改。**

因此：

- 一个机制的完整解释集中在唯一 Owner；
- Use / Bridge / Integration 通过最小摘要和链接调用，不复制整段定义；
- 章节标题和内部结构要足够稳定，让新反例或边界能够插入明确位置，而不是每次重写整册。

**什么时候允许更新 Handbook、Owner 变化后同步哪些文件，不由本写作规范决定。** 稳定写入动作见 [`collaboration_workflow.md`](collaboration_workflow.md)，证据是否足以推动更新见 [`evidence_promotion.md`](evidence_promotion.md)。

## 22. 推荐的专题手册标准结构

每一本专题可以采用：

### §0 本册定位

- 本册负责什么、不负责什么；
- Own / Use / Bridge 声明；
- 前置知识。

### §1 根本问题

为什么这个专题会出现？

### §2 母模型

一句话 + 一张图 + 中文解释。

### §3 对象与状态空间

问题里真正有哪些对象？

### §4 机制生成

按 Problem、Naive Solution、Failure、Mechanism 的解释顺序组织，并逐项说明它们之间究竟是因果、设计约束还是逻辑推导。

### §5 生命周期 / 动态轨迹

完整跑一次。

### §6 不变量 / 合法性

为什么这样做仍然正确？

### §7 代价与权衡

为什么不用另一个方案？

### §8 概念边界

用 5 列标准表格（§8 原则）。

### §9 与其他专题的接口

明确 Bridge。

### §10 章节 / 考纲映射

这个模型覆盖哪些传统知识点？

### §11 最小调用接口

说明题面出现什么对象/结构/事件时应回到本模型，第一眼观察什么，以及何时停止并转交相邻 Owner。不要在这里展开完整题型树、固定问答清单、作答模板或速算流程。

### §12 贯穿母例

完整跑一遍，且暴露至少一个可验证的失败路径或边界。

### §13 认知边界与失败路径

说明哪些混淆来自对象、表示、状态、前提或因果链错误；若需要把这些失败压成反复执行的纠偏动作，迁入对应训练 Markdown。

### §14 一页压缩

留下：一句话 + 一张母图 + 若干重建问题，以及最小调用入口。

## 23. 一本手册完成后的九项验收测试

| # | 测试 | 问题 |
|---|---|---|
| 1 | **压缩** | 能不能压成一句话和一张图？ |
| 2 | **生成** | 忘掉某些公式以后，能不能从模型重新推出？ |
| 3 | **映射** | 新知识进来以后，能不能知道应该挂在哪里？ |
| 4 | **边界** | 相邻概念能不能给出稳定判据？ |
| 5 | **生命周期** | 动态对象是否能完整推演？ |
| 6 | **应试调用** | 能不能从题面信号转化成第一步行动？ |
| 7 | **生长性** | 以后做题产生的新经验，能不能被吸收到系统中而不会破坏原结构？ |
| 8 | **直觉** | 不看最终公式时，能不能先预测符号、方向、尺度、趋势或候选位置，并解释这种预判来自什么对象？ |
| 9 | **细节** | 能不能主动指出最可能改变结论的符号、方向、端点、定义域、分支、量词或严格性细节，并用一个最小例子检查？ |

**如果其中任何一项失败，手册都还没有完成。**

## 24. 三类典型失败作品

### 失败一：教材摘要

- 症状：定义很多，公式很多，结构很整齐。
- 问题：学完仍然不知道为什么这些知识放在一起。

### 失败二：抽象哲学手册

- 症状：到处是"结构、系统、不变量、反馈、空间"。
- 问题：遇到具体题不知道第一步干什么。

### 失败三：题型技巧大全

- 症状："看到 A 用 B""看到 C 用 D"。
- 问题：题目稍微换皮就识别失败，而且无法解释技巧成立条件。

我们的目标处于三者之间：

$$\boxed{\text{Mechanistic Understanding} + \text{Operational Control}}$$

---

## 25. 最终质量标准

一本真正合格的心智模型/专题手册，读者学完以后应该发生下面的变化：

| 以前 | 以后 |
|---|---|
| "这个公式怎么背？" | "它解决什么问题？" |
| "这是哪个题型？" | "当前对象是什么？结构是什么？目标是什么？" |
| "粗心。" | "我第一次偏离正确推理发生在哪个节点？" |
| 复习靠重新看几十页 | 从 30 页压缩到 10 页、3 页、1 页后，仍然能从最后一页重新展开整套知识 |

因此，本系列手册最终追求的并不是把知识写得更多，而是：

$$\boxed{\textbf{用尽可能少而稳定的生成性结构，重新生成尽可能多而可靠的知识。}}$$

## 26. 从认知正文到物理交付

本规范只拥有“正文怎样写才合格”。Handbook 的物理 package、状态语义、编译发布和仓库检查分别服从：

- [`handbook_contract.md`](handbook_contract.md)：Handbook 物理职责与最低契约；
- [`latex_layout_spec.md`](latex_layout_spec.md)：LaTeX 视觉/几何参数与数学符号定界符排版契约（`\lvert ... \rvert`、`\lVert ... \rVert` 等通用标准）；
- [`terminology.md`](terminology.md)：Canonical、Landing Page、状态等术语；
- [`repository_integrity.md`](repository_integrity.md)：发布文件和仓库一致性检查。

两层关系只有：

$$\boxed{\text{认知结构不合格} \implies \text{不进入正式正文}} \qquad \boxed{\text{物理交付不合格} \implies \text{不标记为已发布}}$$

本规范仍拥有正文内部的写作/排版要求，例如 TikZ 图表可读性、概念边界表格和压缩页设计；数学公式符号（绝对值 `\lvert`、范数 `\lVert`、条件 `\mid` 等）无论在 `.tex` 源码还是日常 `.md` 笔记中均服从 `latex_layout_spec.md` §3.3；但本规范不再复制 README、`.tex`、PDF 的 Source-of-Truth 或编译命令。
